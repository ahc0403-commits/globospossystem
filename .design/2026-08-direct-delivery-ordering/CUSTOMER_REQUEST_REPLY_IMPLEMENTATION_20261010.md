## 고객과 캐셔의 흐름

주문 요청 사항과 메뉴별 요청 사항을 별도 요청으로 보관하고 채팅에 표시한다. 요청 상태는 `답변 필요 → 고객 확인 대기 → 확정`이다. 다른 요청의 답변이나 일반 인사·채팅은 해당 요청을 완료 처리하지 않는다.

캐셔는 요청의 **요청에 답변하기**를 열어 상황에 맞는 문장을 직접 입력하고 전송한다. `가능합니다 / 어렵습니다` 같은 선택형 답변은 사용하지 않는다. 전송 실패 시 작성한 내용을 유지하며 동일한 전송의 재시도는 같은 식별자를 사용한다.

**고객 확인 필요**가 기본으로 선택된다. 변경 조건이나 대안을 안내한 경우 고객이 **이 내용으로 확정**을 눌러야 확정된다. 고객은 **추가 요청 / 다시 문의**에서 문장을 직접 입력할 수도 있으며, 이때 그 요청만 다시 답변 필요 상태로 돌아간다. 캐셔가 원래 요청을 그대로 수락하여 고객의 추가 확인이 필요 없는 경우에는 체크를 해제하여 전송과 함께 확정할 수 있다.

미확정 요청이 남으면 견적 발송 버튼을 비활성화하며 서버 RPC에서도 발송을 거부한다. 기존 결제 기록과 조리 진행을 변경하지 않는다. 캐셔에게 별도의 조리 완료·기사 전달 상태 버튼을 추가하지 않았다.

주문 목록에 미답변 수와 고객 확인 대기 수를 일괄 표시한다. 답변 전송 결과는 이미 받은 상세 응답으로 즉시 반영한다. 고객 확정 역시 응답에 포함된 전체 상태로 갱신하므로 요청마다 추가 상세 조회를 하지 않는다.

## 확정 내용과 영수증

새 고객 영수증에는 확정된 요청과 합의 내용을 함께 넣는다. 확정 기록에는 원문, 캐셔 답변, 고객의 추가 문의, 연결 메시지, 버전과 확정 시간을 보관한다. 종이 전표와 디지털 영수증의 기존 베트남어 표시 규칙을 유지한다.

캐셔는 전표용 고객 요청과 합의 내용을 베트남어로 확인한다. 베트남어 화면에서 답변을 입력하면 전표용 답변도 채워지고, 고객 요청의 베트남어 번역이 있으면 해당 문구를 미리 채운다. 다른 언어로 답변할 때는 베트남어 전표 문구를 함께 입력·검토해야 한다. 출력에서 사라지는 한국어·지원하지 않는 문자와 제어 문자는 서버와 화면에서 거부한다. 고객에게 보여주는 답변은 입력한 원문을 보존하고 기존 자동 번역 경로를 이용한다.

출력 대상을 **주방·포장 / 기사·배송 / 모두**로 지정할 수 있다. 고객 영수증은 전체 확정 내용을, 주방·트레이 전표는 조리·포장 내용을, 기사 전표는 배송 내용을 받는다. KDS에도 확정된 준비 사항을 일괄 추가하고 전체 문구를 열어 볼 수 있게 했다.

이미 전표나 디지털 영수증이 발행된 뒤 요청이 확정되면 **추가 확정 요청 전표**를 별도로 생성한다. 원본 출력 payload와 디지털 영수증 snapshot은 보존한다. 추가 전표는 같은 주문의 기존 출력 목적지로 보내고, 금액·재결제 내용을 출력하지 않는다. 재출력도 원래 목적지를 유지한다. 디지털 영수증에는 추가 확정 기록을 별도로 표시한다. 이 작업은 기존 주문의 채팅·접근이 열려 있는 동안 처리된다.

## 서버 계약과 접근 제어

- 신규 마이그레이션: `20261010040000_direct_order_confirmed_requirements.sql`
- 고객 상세: `status_v5` / `direct_order_public_status_v5`
- 고객 결정: `decide_requirement` / `direct_order_public_decide_requirement`
- 캐셔 목록·상세: `direct_order_staff_list_v4` / `direct_order_staff_detail_v4`
- 캐셔 직접 답변: `direct_order_staff_reply_requirement`
- 이전 고객 상세 버전은 기존 응답 키를 유지한다.
- 요청 테이블에 클라이언트 직접 읽기·쓰기 권한을 주지 않는다. 기존 매장 권한과 고객 세션·주문 링크 범위 검증을 이용한다.
- 현재 버전과 답변 메시지 ID가 일치해야 고객이 확정할 수 있다. 오래된 답변, 다른 주문의 요청과 잘못된 재시도는 거부한다.
- 견적, 답변, 고객 확정, 메뉴 요청 변경은 주문 행 잠금으로 직렬화한다.
- 기존 개인정보 정리 시 새 요청 기록과 추가 기록도 지우며, 추가 출력 작업의 문구를 정리한다.
- `process_payment`의 기존 정의를 변경하지 않았고 로컬 SQL 실행 전후 해시가 동일하다.

## N+1 검증 범위

| 읽기 경로 | 데이터 수 | 측정 결과 |
|---|---|---|
| 캐셔 요청 상세 | 요청 1 / 10 / 50건 | 전체 요청 snapshot 집계 1회씩 |
| 고객 요청 상세 | 요청 1 / 10 / 50건 | 전체 요청 snapshot 집계 1회씩 |
| 캐셔 목록의 대기 수 | 같은 측정 요청을 포함한 페이지 | 요청별 상세 호출 0회 |
| 프린터·연결 정보 | 목적지 1 / 10 / 50개 | 실제 Supabase SDK를 통한 모의 HTTP 읽기 2회씩 |

요청·번역은 같은 상세 응답에 집합 집계로 포함한다. 목록의 상태 수와 KDS 확정 문구도 JOIN/GROUP BY로 처리한다. 요청 snapshot의 실제 SQL 본문을 `EXPLAIN ANALYZE`하여 상관 SubPlan이 없음을 확인했다. 프린터 설정과 연결 정보는 일괄 조회로 변경했으며 프린터마다 조회하지 않는다. 출력 완료 확인은 실제 출력 작업별 쓰기 동작이다.

이 결과는 수정한 경로에 대한 검증이며 POS 전체의 모든 경로에 N+1이 없다는 의미는 아니다. 기존 통합 SQL 검증의 고객 진행 상태, 캐셔·주방 목록과 조리 완료 알림 배치 검증도 함께 통과했다.
