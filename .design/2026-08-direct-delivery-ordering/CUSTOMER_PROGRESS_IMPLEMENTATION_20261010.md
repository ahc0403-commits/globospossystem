# 고객 주문·배송·일회용 식기 개선 구현 보고

소스 구현을 완료했다. 사용자 지시에 따라 운영 DB 마이그레이션 적용과 운영 배포는 하지 않았다.
기존 사용자 변경을 보존한 현재 작업 사본에서 구현하고 로컬 검증했다.

## 구현 결과

| 개선 항목 | 구현 동작 |
|---|---|
| 고객 상태 | 결제와 별도로 매장 확인, 결제 대기, 입금 확인, 음식 준비, 조리 완료·포장 중, 포장 완료·기사 대기, 기사 전달·배송 중, 배달 완료 표시 |
| 상태 근거 | 조리 완료는 취소되지 않은 KDS 메뉴·구성품의 필요 수량 완료와 확인 필요 여부로 판단. 기록이 없거나 일부만 완료되면 완료 표시하지 않음 |
| 기사 인계 근거 | 기존 배차 기록·기사 정보로 확인. 과거 KDS의 dispatched 상태만으로 배송 중을 표시하지 않음 |
| 방문 포장 | 픽업 준비와 수령 완료로 안내. 취소·거절·만료가 우선 |
| 모바일 | 같은 주문·채팅 화면에서 현재 상태를 먼저 표시. 상세 단계는 펼쳐서 확인하며 주문 상세도 기존 상태 응답을 재사용 |
| 배송 링크 | 카드와 기존 grab_link 및 일반 채팅의 HTTPS URL에 열기·복사 제공. 정확한 URL 선택 복사 가능. 열기 실패와 복사 권한 오류 안내 |
| 일회용 식기 | 인원수 1~100, 초기 1명. 인원수대로 받기 / 받지 않기 별도 저장. 음식 포장 용기는 제공 |
| 캐셔 업무 | 표시를 위한 추가 클릭 없음. 기존 주방 완료·포장 완료·기사 전달 기록을 사용 |
| 주문 종료 | 실제 고객 전달 확인 후 기존 캐셔 완료 처리를 유지. 완료 후 미환급 금액·환급 증빙 지원은 서버 접근 기준에 맞춰 유지 |
| 알림 | 조리·포장 완료 시스템 메시지와 KO/VI/EN 푸시 이벤트를 주문·종류별 중복 방지 |
| 식기 전달 경로 | 고객 → 캐셔 → 주방·KDS 트레이 → 고객/주방/트레이/기사 종이 전표 → 디지털 영수증·PDF. 인원 수정 시 거절 선택 유지 |
| 기존 자료 | 누락된 식기 필드는 기존 받기 동작으로 처리. 과거 인원 미입력은 확인 필요로 유지. 과거 인쇄 스냅샷과 결제 금액 변경 없음 |

## 조회 구조와 실측

고객 갱신에서 다른 주문별 상세 조회 루프를 없앴다. 목록에 견적 ID·버전과 증빙 요청 ID를 포함해 알림을 처리한다.
`orders_v3`와 기존 `orders_v2` 모두 선택 페이지를 기준으로 품목, 견적, 증빙 요청을 일괄 집계한다.
캐셔 목록의 최신 견적 LATERAL 조회와 주문별 픽업 환급 EXISTS도 집합 조회로 바꿨다.
KDS 식기 정보는 화면 카드별 호출 없이 전체 스냅샷 JOIN으로 전달한다.
조리·포장 알림 트리거는 문장 단위로 묶는다. 기존 주방 일괄 완료의 개별 수량 처리 중에는
고객 집계를 보류하고, 성공 후 변경된 주문을 한 번에 집계해 알림을 생성한다.

| 검증 규모 | 결과 |
|---|---|
| 고객 화면 1 / 10 / 50 주문, 다수 견적·증빙 변경 | 갱신당 목록 1 + 선택 상세 1, 다른 주문 상세 0 |
| 주문 전용 링크 | 로드·갱신당 상태 1, 목록 0 |
| 고객 SQL 1 / 10 / 50행 | EXPLAIN ANALYZE 반복 SubPlan 0; 조리 일괄 집계 함수 1; 상세·재무 컨텍스트 함수 0 |
| 캐셔·주방 SQL 1 / 50 / 200행 | 목록 내부 상세·재무 컨텍스트 함수 0 |
| 주방 일괄 완료 1 / 10 / 50개 할당 | 새 고객 조리 집계 함수 1, 주문별 완료 알림 1 |

실측은 합성 데이터의 임시 PostgreSQL 컨테이너에서 수행했다. 운영 데이터의 지연·실제 장치 인쇄 성능을 측정한 것은 아니다.
주방 일괄 완료 검사는 기존 개별 이벤트 삽입을 재현하는 축소 fixture로 새 집계 래퍼를 검증했다.
기존 KDS 배치의 전체 수량 처리 성능을 측정한 것은 아니다.
행 처리량은 주문 수에 따라 늘지만 원격 호출이나 주문별 집계 호출이 비례해 늘지 않는다.

## 검증 결과와 한계

- `dart analyze lib test --fatal-infos`: 통과.
- 고객 화면·링크·방문 포장·접근 링크·전표·디지털 영수증 관련 검사 151개: 통과.
- 임시 DB 통합 검사: 제출 재시도 시 식기 선택 유지, 인원 수정 유지, 기존 API 키 호환, 부분 조리·부분 구성품·취소·확인 필요, 시스템 알림 중복 방지, 전표 스냅샷, KDS 식기 전달, 완료 후 환급 접근, N+1 실측 통과.
- 결제 `process_payment` 함수 해시 불변 확인.
- Edge 포맷·lint·타입 검사와 API 24 / 푸시 6개 테스트 통과.
- Flutter 웹 릴리스 빌드 통과. 기존 wasm 호환성과 Cupertino 폰트 경고는 남아 있다.
- 전체 Flutter 실행: 1,848개 통과, 94개 건너뛰기, 이번 작업에서 수정하지 않은 계약 검사 2개 실패.
  - `direct_order_arrival_alert_test`: 생성 locale 파일의 기존 고정 해시와 현재 파일이 다름.
  - `route_operational_state_coverage_contract_test`: 기존 Admin 테스트명이 10개 탭을 기대하나 현재 파일은 9개 탭으로 되어 있음.
- `scripts/check_repo.sh` 전체 통과를 주장하지 않는다. 먼저 기존 감사용 `docs/audits/n_plus_one_20261005/*.dart`의 분석 경고에서 멈췄다. 나머지 공통 SQL 검사는 기본 PostgreSQL 소켓에 서버가 없어 시작되지 못했다. 관련 SQL 통합 검사는 별도 임시 DB에서 통과했다.
- 실제 기사 앱의 배달 완료 자동 연동이나 운영 배포를 완료한 것은 아니다.

## 배포 시 적용 순서

1. 추가 마이그레이션 `20261010030000_direct_order_customer_progress_and_utensils.sql` 적용.
2. `direct-order-public`의 `status_v4` / `orders_v3`와 푸시 이벤트 처리 변경 배포.
3. 새로운 Flutter 클라이언트 배포. 기존 `status_v3` / `orders_v2` 응답 키는 유지된다.
4. 프로젝트의 공식 배포 절차와 정확한 푸시 SHA의 GitHub Actions `POS release contract` 통과 후 운영에서 확인.
