# 설계 브리프: 비상 대응 KDS 고정 분할 보드

Date: 2026-08-11
Source: 사용자 제공 KDS 참고 이미지 2장과 현재 비상 대응 구현
Status: 계획 전용 — 구현·DB 적용·배포하지 않음

## 목표

키친, 트레이, 층별 비상 대응 화면을 같은 조작 방식으로 통일한다.

- 첫 화면은 주문 카드만 보이는 고정 분할 보드다.
- Phone `<600dp`는 한 페이지에 4개 슬롯, Tablet 이상은 8개 슬롯을 표시한다.
- 주문 카드를 누르면 해당 주문의 모든 메뉴명과 수량을 확인하는 상세 화면으로 들어간다.
- 상세 화면의 주 동작은 `완료`와 `취소(원복)` 두 가지로 제한한다.
- `완료`는 현재 스테이션의 처리 가능한 수량 전체를 다음 단계로 넘긴다.
- `취소(원복)`는 해당 스테이션의 직전 완료 동작만 되돌리며, 다음 스테이션이 이미 처리한 수량은 되돌리지 못한다.
- 주문이 4개 또는 8개를 넘으면 페이지 단위로 이동한다.

## 현재 구현에서 재사용할 부분

- `EmergencyFulfillmentScreen`의 배정 확인, 비상 모드 대기 화면, 헤더, 알람, 화면 점멸, 오프라인 배너
- `EmergencyFulfillmentNotifier`의 Snapshot, Realtime 구독, 10초 폴링, IndexedDB outbox
- `EmergencyFulfillmentOrder`와 `EmergencyFulfillmentItem`의 다국어 메뉴명과 단계별 수량
- 비상 세션, 주문 큐, 단계별 수량 체인, 이벤트 감사, 매장·층 권한 모델
- `/emergency` 전용 역할 라우팅과 `KitchenScreen`의 비상 화면 진입 게이트
- 현재 KO/VI/EN 및 Phone/Tablet 위젯 테스트 기반

## 수정할 부분

- 가로/세로 주문 목록과 선택 상세 분할 레이아웃을 고정 슬롯 페이지 보드로 교체
- 품목별 `+/-` 조작을 주문 단위 `완료`/`취소(원복)` 조작으로 교체
- 현재 모든 주문을 반환하는 Snapshot 결과를 스테이션별 작업 가능 카드와 최근 완료 카드로 분류
- 품목별 단일 변경 RPC를 보존하되, 화면에서는 주문 단위 원자적 완료/원복 RPC를 사용
- 오프라인 outbox payload를 품목 단위가 아닌 주문 동작 단위로 확장

## 화면 계약

### 1. 주문 보드

- Phone: 한 페이지 4슬롯
  - 세로는 2열 × 2행
  - 가로는 4열 × 1행
- Tablet 이상: 한 페이지 8슬롯
  - 가로는 4열 × 2행
  - 세로는 2열 × 4행
- 화면 크기 판정은 `shortestSide < 600`을 Phone 기준으로 사용한다.
- 주문이 적어도 빈 슬롯의 크기를 유지해 화면이 흔들리지 않게 한다.
- 카드에는 대기번호, 경과시간, 테이블, 층, 메뉴 종류 수, 추가 주문 표시, 현재 상태만 노출한다.
- 오래 들어온 작업부터 배치하고, 새 작업 도착 시 현재 사용자가 보고 있는 페이지를 강제로 바꾸지 않는다.
- 좌우 페이지 버튼, `현재 페이지/전체 페이지`, 현재 작업 수를 표시한다.
- 완료된 주문은 기본 작업 보드에서 빠지며 `최근 완료`에서 원복 가능 상태를 확인한다.

### 2. 주문 상세

- 카드 선택 시 같은 라우트 안에서 전체 화면 상세로 전환한다. 브라우저 뒤로가기와 화면 내 뒤로가기는 모두 주문 보드로 복귀한다.
- 모든 비취소 메뉴를 선택 언어 하나로 표시하고, `메뉴명 × 주문 수량`, 현재 단계 처리 수량, 이전/다음 단계 상태를 보여준다.
- 긴 메뉴명과 8개 이상 메뉴는 상세 내부 세로 스크롤로 처리한다.
- 하단 고정 동작 영역에 다음 두 버튼을 둔다.
  - `취소(원복)`: 직전 완료 action을 보상 트랜잭션으로 되돌림
  - `완료(다음 단계)`: 현재 처리 가능한 모든 메뉴 수량을 다음 단계로 전송
- 처리 중에는 두 버튼을 잠그고, 서버 확인 전에는 `동기화 대기`를 표시한다.
- 원복 불가 시 일반 오류 대신 `다음 단계에서 이미 처리하여 원복할 수 없음`을 명확히 표시한다.

### 3. 스테이션별 완료 의미

| 화면 | `완료` | `취소(원복)` 허용 조건 |
|---|---|---|
| 키친 | 모든 미완료 주문 수량을 `kitchen_done`으로 처리하고 트레이로 넘김 | 해당 완료분을 트레이가 아직 수령하지 않음 |
| 트레이 | 현재 `kitchen_done` 수량을 한 동작에서 수령·발송 처리하고 해당 층으로 넘김 | 해당 발송분을 층에서 아직 제공하지 않음 |
| 층별 | 현재 발송 수량을 `floor_served`로 처리하고 주문확인 완료 | 자신의 직전 제공 완료 action이 존재함 |

트레이는 사용자 요구의 “한 번 완료하여 다음으로 넘기기”에 맞춰 `tray_received`와 `tray_dispatched`를 한 원자적 action 안에서 함께 기록하는 안을 기본안으로 한다. 수령과 발송을 현장에서 별도 시점으로 반드시 기록해야 한다면 구현 전에 이 한 항목만 2단계 상세로 변경한다.

## 데이터·동시성 계약

- 새 additive RPC `emergency_complete_order_stage(queue_id, action_id)`와 `emergency_revert_order_action(action_id, revert_id)`를 둔다.
- 완료 RPC는 주문의 관련 품목 행을 `FOR UPDATE`로 잠그고 현재 처리 가능한 delta를 계산해 한 트랜잭션으로 반영한다.
- 여러 품목 이벤트에는 공통 `action_id`를 저장해 한 번의 사용자 동작과 원복 범위를 식별한다.
- 같은 `action_id` 재전송은 한 번만 반영한다.
- 원복은 원 이벤트를 삭제하지 않고 반대 delta의 새 감사 이벤트를 추가한다.
- 다음 단계 수량이 진행된 경우 DB에서 원복을 거절한다. UI 사전 판정만 신뢰하지 않는다.
- 추가 주문 또는 새 수량은 이미 완료된 원 주문이라도 다시 작업 카드로 나타나며, `완료`는 새로 처리 가능한 delta만 반영한다.
- 네트워크 단절 중 완료/원복은 action 단위로 outbox에 저장한다. 서버 확정 전 작업은 다음 장치에 노출되지 않는다.

## 범위 제외

- 정상 프린터 모드, 결제 RPC, 주문 생명주기 상태 변경
- 별도 키친/트레이/층별 앱 또는 네이티브 앱 배포
- 주문 카드에서 메뉴 전체를 미리 펼치는 고밀도 화면
- 다음 단계가 이미 처리한 이력을 Super Admin 승인 없이 강제 원복하는 기능

## 완료 판정

- 390×844 Phone에서 정확히 4개 슬롯, 768×1024 및 1024×768 Tablet에서 정확히 8개 슬롯이 첫 페이지에 배치된다.
- 5번째/9번째 주문부터 다음 페이지에 나타나고, 페이지 이동 중 신규 주문이 와도 사용자의 현재 상세/페이지가 보존된다.
- 키친 → 트레이 → 해당 층 완료가 주문 단위 버튼으로 이어지고 캐셔 미제공 수량이 0으로 해제된다.
- 원복은 다음 단계 미처리 시 성공하고, 다음 단계 처리 후에는 서버가 거절하며 수량 체인이 깨지지 않는다.
- 중복 탭, 재전송, 두 장치 동시 완료가 수량을 중복 반영하지 않는다.
- KO/VI/EN, 100%/130%/200% 글자 크기, 세로/가로 회전에서 overflow와 잘린 동작 버튼이 없다.
- 비상 모드 OFF의 출력·결제·기존 주문 흐름은 변경되지 않는다.
- 로컬 검증과 정확한 pushed head SHA의 필수 GitHub Actions가 모두 성공하기 전에는 release gate를 PASS로 보고하지 않는다.
