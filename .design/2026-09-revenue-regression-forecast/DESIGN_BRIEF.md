## 1. 확정 범위

사용자가 선택한 과거 매출 기간으로 회귀식을 계산하되, 미래 매출은 해당 매장이
실제로 소화할 수 있는 고객·주문량을 넘지 않게 한다. 수요 추세, 운영상 가용
매출 한도, 최종 예상 매출을 구분한다. 테이블이나 기기가 많다는 이유로 고객이
자동으로 늘어난다고 가정하지 않는다.

| 구분 | 레스토랑 | Photo |
| --- | --- | --- |
| 수요 추세 | 선택 기간의 채널별 매출 회귀 | 선택 기간의 유료 촬영 회수 회귀 |
| 용량 제한 | 테이블·좌석·주방·체커·층별 서빙·식사·영업시간 | 실제 가동 기기 수·기기별 가동시간 |
| 단가 | 선택 기간의 검증된 팀/주문당 순매출, 기본 고정 | **유료 촬영 1회 85,000 VND 고정** |
| 소요시간 | 매장별 측정/확인한 값 | **기기당 1회 입장부터 퇴장까지 8분 고정** |
| 개선 제안 | 병목별 단독·복합 개선과 추가 매출 비교 | **제공하지 않음** |

마지막 사용자 지시에 따라 Photo도 예측에 포함한다. 특정 매장, 빈탄점, 브랜드명,
UUID를 신규 계산기에 하드코딩하지 않는다. 매장별 예측 프로필의
restaurant / photo 전략으로 분리하며, 기존 소유/운영 형태인 store_type의
direct/external을 업종 판별값으로 오용하지 않는다.

현재 1차 소스 구현은 공통 화면, 일 단위 회귀·용량 제약, 프로필 버전 SQL,
세 언어, 모바일 배치와 예측 전용 파일까지 포함한다. 아래의 시간대 자원 스케줄,
실기기·운영 UAT와 배포 항목은 후속 검증 범위이며 완료로 표시하지 않는다.

계산 결과만 맞는 상태를 완료로 간주하지 않는다. 매장 선택부터 모바일 입력,
실행 중 언어 전환, 접근 가능한 결과·개선 비교, 파일 저장, 오류 복구, 권한 통제,
실기기 검증과 운영 인계까지 이어지는 전체 기능을 완성 대상으로 한다.

## 2. 핵심 원칙

1. **예측과 최대치 구분:** 회귀 추세는 매출 수요의 참고치이고, 용량은 제약이다.
   실제 관측 매출만으로 포화 시점의 미방문·대기 포기 고객을 알아낼 수 없다.
2. **시간대별 판단:** 일평균만으로 계산하지 않는다. 점심·저녁 피크와 비수기,
   요일, 층별 개방, 휴게시간, 마지막 주문·마감 제한을 반영한다.
3. **공유 자원 중복 금지:** 여러 층과 배달이 공유하는 주방·체커 용량을 각각
   별도 가산하지 않는다. 배달·포장은 테이블을 쓰지 않지만 해당 조리·포장 자원을 쓴다.
4. **시간 중복 금지:** 첫 음식 제공부터 결제까지의 기존 식사 지표에는 추가 주문
   대기도 섞인다. 전체 음식 제공시간과 이를 단순 합산하지 않는다.
5. **측정과 가정 구분:** 출처, 표본 수, 측정 기간, 확인자, 유효기간을 표시한다.
   없는 처리능력이나 영업시간을 임의 기본값으로 채우지 않는다.
6. **운영 의사결정 보조:** 추가 매출은 조건부 추정이며 이익·보장 매출이 아니다.
   인력 배치, 영업시간, 메뉴, 가격, 주방 정책을 자동 변경하지 않는다.

## 3. 사용자 흐름

1. 기존 매출 추이 분석에서 매장을 선택하고 학습 시작일·종료일을 적용한다.
   기본 종료일은 매장 시간대의 어제다. 날짜에는 연도를 명시한다.
2. 상단에서 적용된 기간, 매출 합계, 완료/누락 일수, 업종, 데이터 품질을 확인한다.
   기존 7·14일 버튼은 실제 분석에 유지하되 예측용 표본 부족을 안내한다.
3. **운영 조건**에서 실측 자료를 불러오고 부족한 항목을 확인·입력한다.
   프로필 저장은 권한이 있는 관리자만 수행한다. 가상 변경은 별도 시나리오다.
4. 전망기간 3·6·12·24개월 또는 종료일, 월 목표 10억·15억동 또는 사용자 금액을
   지정하고 계산한다. 28개 이상 유효 영업일은 최소 계산 조건이지 신뢰도 보장이 아니다.
5. 레스토랑은 예상 매출·용량·가동률·병목을 확인하고 개선 후보를 비교한다.
   Photo는 고정 8분·85,000동과 기기 용량을 확인하며 개선 영역은 아예 표시하지 않는다.
6. 필요하면 **예측 전용** 파일로 결과·회귀식·조건·품질·시나리오를 내려받는다.
   기존 실제 매출 Excel에는 예측값을 넣지 않는다.

Photo 운영 화면에서도 동일한 공유 예측 화면으로 진입할 수 있게 한다. 관리자
레스토랑 화면에만 기능을 넣어 Photo 사용자가 접근하지 못하는 설계를 피한다.
접근 권한은 화면 유형이 아니라 서버의 실제 매장별 조회 권한으로 확인한다.

## 4. 운영 조건 입력

### 레스토랑

| 영역 | 필요한 설정 | 자동 취득과 확인의 경계 |
| --- | --- | --- |
| 테이블 | 층별 테이블·좌석 수, 합석/연결 규칙, 사용 불가 일정 | 기존 tables를 불러오되 occupied를 사용 불가로 보지 않음 |
| 고객 | 평균 팀 인원·분포, 방문 단위 객단가, 추가 주문 | 주문/분할 결제를 방문 팀으로 중복 계산하지 않음 |
| 회전 | 착석→주문, 첫 음식→식사/결제, 퇴장→정리 | 실제 착석·퇴장 기록 부재 시 확인한 측정값 필요 |
| 주방 | 메뉴 구성별 작업량, 독립 조리 자원/병렬 처리, 지속 처리량 | 주문→조리 완료 경과시간만으로 처리량을 역산하지 않음 |
| 체커 | 조리 완료→접수 대기, 검수·합포장·출고 처리량 | 트레이 단계와 담당 인원/병렬 작업 범위 확인 |
| 층별 제공 | 출고→층 도착, 서빙 담당/왕복·묶음 운반 능력 | 층 수를 1F/2F로 고정하지 않고 실제 층을 사용 |
| 영업 | 요일·층별 운영 구간, 휴게/휴무, 주문 종료·퇴장 종료 | 기존 cutoff와 배달 접수시간을 전체 영업시간으로 오용하지 않음 |
| 채널 | 홀·포장·배달 매출/주문 비중과 공용 자원 | 메뉴의 floor_direct 등 실제 라우팅을 반영 |

### Photo

- 실제 설치·가동 가능한 기기 목록 또는 확인된 기기 수, 기기별 운영 구간,
  휴무·점검·고장 시간을 입력한다.
- 매출 기록에 등장한 기기 수는 설치 수가 아니라 **관측 가동 기기 수**로 표시한다.
- 8분과 85,000동은 읽기 전용 정책 상수다. 객단가 자동 학습이나 수정 입력을 제공하지 않는다.
- 무료 서비스 촬영이 있으면 유료 회수에서 제외하되 해당 기기 시간을 차감한다.
- 누락일은 0원일과 다르다. 수동 신고 완료와 명시적 무매출 확인을 구분한다.

## 5. 레스토랑 개선 제안

동일한 수요·가격·메뉴 구성을 고정한 상태에서 하나의 운영 조건만 바꿔 다시
계산한다. 따라서 용량 증가와 수요가 뒷받침하는 추가 매출이 분리된다.

| 개선 영역 | 비교할 변화 | 보호 조건 |
| --- | --- | --- |
| 테이블 회전 | 퇴장 후 정리 단축, 팀 크기에 맞는 배치, 확인된 테이블 추가 | 실제 공간·좌석·동선 및 승인된 사용 가능 수 준수 |
| 주방 | 피크 조리 자원 추가, 준비 작업/메뉴 동선 개선 | 조리 안전시간·품질을 임의 축소하지 않음 |
| 체커 | 접수 지연 감소, 검수·출고 분담/병렬화 | 체크 누락이나 검수 생략을 개선으로 권하지 않음 |
| 층별 제공 | 혼잡 층 담당 조정, 동선·운반 방식 개선 | 공유 인력을 다른 층에 중복 배정하지 않음 |
| 식사시간 | 결제 대기·추가 주문 지연 등 비식사 시간을 줄임 | 고객의 순수 식사시간 단축/퇴장 압박을 기본 제안하지 않음 |
| 영업시간 | 수요 근거가 있는 시간대·층의 운영 확대 | cutoff, 인력, 시설 제약 및 신규 시간대 수요 확인 필요 |

각 추천 카드는 다음을 함께 보여준다.

- 현재 병목 시간대·층·자원과 근거, 현재값 → 변경값.
- 하루/월 추가 처리 가능 팀·주문 수와 **수요 반영 추가 매출(VND, %)**.
- 변경 전후 가용 용량·가동률·목표 달성 예상 월·다음 병목.
- 실측/관리자 가정 여부, 입력 부족, 실행 전 확인사항과 서비스 품질 위험.
- 비용 미입력 시 “비용 미반영 추가 매출 — 수익성 판단 불가”.

단독 효과가 없더라도 두 병목을 함께 풀면 효과가 나는 복합 시나리오를 별도로
계산한다. 단독 증가분을 단순 합산하지 않는다. 시간 단축 10%가 매출 10% 증가라는
식의 고정 배율을 쓰지 않는다. 수요가 부족하면 “용량 여유 / 예상 매출 증가 없음”을
보여준다. 표본이 부족하면 확정적인 순위 대신 “추가 측정 필요”로 표시한다.

## 6. 결과 화면

기존 시각 언어와 반응형 구조를 유지한다. 실제 매출 영역은 그대로 두고 아래에
예측 요약/진입 패널을 추가한다. 공통 상세 화면에 조건·결과·개선·근거를 분리하고,
복잡한 운영 조건 편집은 모바일 전체 높이 화면 또는 넓은 화면의 시트에서 처리한다.
모바일 표는 목록/카드로 전환하며 큰 데스크톱 표를 축소해서 제공하지 않는다.

1. **입력·품질:** 매장, 학습 기간, 실제 합계, 완료 여부, 운영 프로필 버전.
2. **운영 조건:** 레스토랑 자원 또는 Photo 기기 정보와 근거 배지.
3. **핵심 결과:** 월 예상 매출, 운영상 가용 한도, 목표 상태. 레스토랑은 병목도 표시.
4. **차트:** 실제 실선, 예상 점선, 용량 한도선. 통계적 검증이 된 경우에만
   예측 범위를 표시한다. 단순 가정별 낮음/기준/높음은 “시나리오 범위”로 표기한다.
5. **월별 표:** 예상액, 해당 월의 운영조건 한도, 가동률, 부분 월, 근거 수준.
6. **개선 비교:** 레스토랑만 현재·단독·복합 조건을 나란히 비교한다.
7. **모델 설명:** 회귀식·계수·검증 오차·고정 단가·가정·제외 자료·장기 외삽 경고.

현재 달은 “누적 실적 + 남은 날짜 예상”을 보조 표시할 수 있지만 순수한 완전 월
예측과 구분한다. 기본 목표 판정은 예측 구간의 첫 완전한 달부터 한다.
“최초 도달”과 “3개월 연속 유지”를 구분하며 달성일을 보장하지 않는다.

목표 상태는 “예측상 도달”, “장기 시나리오상 도달”, “전망기간 내 수요 부족”,
“현 조건·전망기간 내 용량 초과”, “입력/근거 부족”으로 구분한다. 목표가 용량보다
높으면 단순 회귀식으로 미래 날짜를 만들어내지 않는다.

- PosColors, AppColors, AppFonts, 기존 fl_chart, Riverpod, KO/VI/EN 패턴.
- 새 문구는 AppLocalizations와 app_en/ko/vi.arb를 사용하며 private 언어 map을
  신규 예측 기능에 복제하지 않는다. 현재 LocaleController 저장/복원도 재사용한다.

### 수정/신규 구현 예정

- 기존 매출 화면과 Photo 화면에 공유 예측 진입점을 추가한다.
- 공통 입력·출력과 레스토랑/Photo 계산 전략은
  lib/features/report/revenue_forecast/로 분리한다. 네트워크와 순수 계산을 분리한다.
- 신규 RevenueForecastPanel, 운영 조건 편집, 품질 패널, 레스토랑 개선 비교,
  예측 전용 export. KPI는 기존 기본 위젯을 조합하며 존재하지 않는 컴포넌트를 가정하지 않는다.
- **예측 전용 프로필/버전과 완전성 확인 메타데이터를 저장하는 additive schema**, 그리고
  매장별 읽기 전용 집계 RPC를 추가한다. 기존 일별 매출만으로 자원 제약을 알 수 없으므로
  이전 계획의 “신규 DB 작업 없음”은 폐기한다.
- 테이블/주방/체커/층별 측정 자료가 없으면 설정 또는 측정 안내로 연결한다.
  새로운 현장 이벤트 수집은 향후 별도 작업이며 이번 1차 기능의 필수 선행조건은 아니다.
- 모바일/태블릿/데스크톱 화면, 전체 문구·semantics·파일 현지화, 탐색/재인증,
  offline/timeout/동시 저장 복구, 플랫폼별 계산·파일 adapter와 통합 검증을 포함한다.

### 변경하지 않음

- 기존 결제, MISA, 실제 매출 원장·Excel, KDS 상태 전이, 실제 인력/주문 정책.
- 물리 restaurants 및 id/name/address/is_active, Office 연동.
- 폐기된 Photo 자동 수집·집계 작업. 수동 신고를 자동 수집으로 바꾸지 않는다.
- 브랜드/전사 합산 예측, 자동 가격 조정, 자동 발주, 자동 배치, 자동 알림.
- 실제 운영조건으로의 시나리오 자동 적용. 프로필은 예측용이며 운영 제어권이 없다.

## 8. 완료 조건

1. 권한 내 모든 매장이 같은 인터페이스를 사용하고 매장·기간·프로필·모델 버전으로
   결과가 격리된다. 지연 응답이 다른 매장 결과로 표시되지 않는다.
2. 실제 매출 집계와 학습 원본 합계가 채널별로 일치하며 실패/누락을 0으로 숨기지 않는다.
3. 회귀 수요와 운영 용량이 분리되고, 동일한 단가·메뉴 구성에서 모든 미래 매출은
   검증된 자원 제약을 준수한다. 시뮬레이션 작업·금액 합계가 보존된다.
4. 레스토랑 6개 개선 영역을 평가하며 공유 병목·비식사 대기·복합 효과를 구분한다.
   미확인 자원이나 수요가 있으면 숫자의 조건과 보류 사유가 표시된다.
5. Photo는 모든 매장에서 8분·85,000동만 적용하고 무료 회수·고장·휴무를 처리한다.
   Photo의 API 결과·화면·export에는 개선 제안을 생성하지 않는다.
6. 10억·15억·사용자 목표는 완전 월 기준이며 용량 초과/수요 부족/근거 부족을 구별한다.
7. 순방향 과거 검증으로 단순 요일 기준과 비교한다. R²만으로 정확하다고 표시하지 않는다.
8. 운영 입력 변경은 현재 가상 결과만 바꾼다. 원본 거래, 실제 cutoff, 인력, 운영시간은 불변이다.
9. 320–1920 폭과 경계 크기, KO/VI/EN의 모든 전환, 200% 글자/400% 웹 확대,
   실기기 터치·키보드·화면낭독기로 핵심 여정을 완료하며 실제 보고서가 회귀하지 않는다.
10. 구현 시 관련 계산·SQL/RLS·widget·export 검증과 repository preflight를 완료한다.
    배포는 별도 승인 후 scripts/deploy_pos_production.sh 및 exact pushed head SHA의
    필수 GitHub Actions를 통과해야 한다. 소스 구현·DB 적용·배포·운영 검증을 각각 기록한다.
11. 제품 완료 계약의 상태/권한/파일/성능/접근성 행렬에 증거가 있고, 언어·모바일
    실패를 후속 정리로 넘기지 않는다. 미검증 환경은 완료가 아니라 NOT RUN/BLOCKED다.
12. 세 언어 도움말과 운영 담당자의 입력·오류 복구 안내가 준비되고, 승인된 공개 후
    레스토랑·Photo의 모바일/데스크톱 smoke 및 초기 운영 확인을 마친다.

## 9. 현장 입력 확보 및 검증

레스토랑은 매장별 테이블/좌석·층별 영업시간, 피크/비피크의 주방·체커·서빙
지속 처리량, 팀 크기·객단가, 착석부터 정리 완료까지의 관측 표본을 확보한다.
Photo는 실제 기기 수·가동시간과 수동 신고 완전성을 확인한다.

측정 기간은 기본 2주간 평일/주말·피크/비피크를 포함하도록 제안하되, 특정 표본 수만
채웠다고 정확성을 인증하지 않는다. 단계·층·시간대별 유효 표본과 오차를 확인하여
부족하면 더 측정한다. 측정 전에는 입력 가정 기반 시험 계산까지만 제공한다.

테이블 수나 주방 처리량이 없는 현재 상태에서 실제 매장의 최대 월매출 또는
10억·15억동 달성 월을 새로 확정하지 않는다. 이전 무제한 회귀 결과가 있더라도
이 설계의 용량 검증을 거치기 전에는 유효한 달성 전망으로 재사용하지 않는다.

구현은 TASKS의 순서로 진행하되 UI·언어·모바일을 처음부터 각 작업에 포함한다.
마지막에 한 번 점검하는 항목으로 미루지 않는다. 세부 상호작용/시험/성능 예산은
PRODUCT_DELIVERY_CONTRACT를 따른다. 기존 Android/iOS 앱의 기능 동작도 검증하되
새 앱 등록·스토어 출시는 별도 승인 범위다.

최종 완료 보고는 설계/소스 구현/품질 검증/DB 적용/웹 배포/네이티브 배포/운영 확인을
분리한다. 앱 전체가 무결하다는 보증 대신 정의한 범위와 각 검증의 실제 증거를 제시한다.
