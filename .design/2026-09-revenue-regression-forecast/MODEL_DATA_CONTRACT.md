# 매출 예측 계산·데이터·검증 계약

- 버전: 설계 v3 / 2026-09-16
- UI·모바일·언어·복구·출시: [PRODUCT_DELIVERY_CONTRACT.md](PRODUCT_DELIVERY_CONTRACT.md)
- 용도: 구현자가 수식, 데이터 의미, 보류 조건을 임의 해석하지 않도록 고정한다.
- 소스 확인만 수행했다. 아래 데이터가 운영 DB에 적용·축적되어 있다는 뜻은 아니다.
- 이 문서의 시간·수치 예제는 계산 검증용이며 특정 매장의 실적/처리능력이 아니다.

## 1. 입력과 기간

ForecastRequest는 storeId, trainingStart/End, forecastEnd, targetsVnd,
profileRevision, scenarioOverrides, modelVersion을 받는다. 실제 매장 접근 권한은
서버에서 별도로 확인한다. 업종은 승인된 매장 예측 프로필에서 가져온다.

- 매출 날짜는 Asia/Ho_Chi_Minh 기준. 조회는 현지 시작 00:00 이상,
  종료일 다음 날 00:00 미만을 UTC로 변환한다.
- 기본 trainingEnd는 어제. 오늘 실적은 진행 중이므로 자동 학습하지 않는다.
- 예측은 trainingEnd 다음 날부터 시작한다. 과거 종료일을 선택하면 그 시점 기준
  재현임을 표시하고, 종료일 이후 실제 매출을 학습/보정에 섞지 않는다.
- 현재 입력한 운영 조건으로 과거 기간 이후를 계산하는 경우 “현재 조건 가정”
  시나리오이며 진정한 과거시점 예측 검증으로 주장하지 않는다.
- 학습 범위 밖의 이동평균 보조 데이터나 다른 매장 데이터를 몰래 포함하지 않는다.
- 조회 지원 범위는 최초 366일, 전망 최대 24개월. 초과 입력은 명시적으로 안내하고
  자동으로 잘라내지 않는다. 더 긴 이력은 별도 성능 검증 후 확대한다.
- 기본 최소는 검증된 완료 영업일 28개와 영업 요일별 최소 4회 관측이다.
  이는 제품의 최소 계산 기준이며 통계적 신뢰 보증이 아니다.
- 고정 휴무 요일은 학습 더미에서 제외하고 해당 미래 날짜를 0으로 처리한다.
  임시 휴무도 확인된 일정에 따라 처리한다. 휴무 0과 영업 중 무매출 0을 구분한다.

### 2.1 매출 정의와 채널

- POS: payments.is_revenue=true, COALESCE(amount_portion, amount).
- 외부 판매: external_sales.is_revenue=true, order_status=completed, net_amount.
- Photo 과거 실제: gross_sales-service_amount. 음수/불일치는 품질 오류로 표시하고
  원본을 고치거나 0으로 은폐하지 않는다.
- 회계 날짜는 기존 보고서와 같은 결제/신고 기준이다. 도착 수요는 주문 시작 시각으로
  추정하므로 결제 시간대 매출을 입장 시간대라고 부르지 않는다.
- 홀/포장/POS배달/외부배달을 분리하고, 동일 주문이 POS와 외부 판매 양쪽에 있으면
  검증된 원천 ID 매핑으로 중복을 제거한다. 이름·유사 금액만으로 임의 병합하지 않는다.
- 총액=채널 합계의 대조가 실패하면 조용히 한 쪽 정의를 택하지 않고 계산을 보류한다.
  기존 보고서의 잠재적 버그 수정은 별도 승인 작업으로 분리한다.
- 통화/VAT/할인/무료 서비스 기준을 실제 보고서와 맞추고,
  “순매출”을 영업이익이나 플랫폼 수수료 차감 후 수익으로 바꾸어 부르지 않는다.
- 실적·예측·시나리오는 별도 필드/표/시트로 관리한다. 과거 실적은 85,000동으로
  재작성하지 않는다.

### 2.2 완전성

각 날짜·원천은 complete, confirmed_zero, closed, missing, partial, failed 중 하나다.
complete 판단은 수집 완료 정보와 원본 대조가 있어야 하며, 거래가 한 건 있다고
하루 전체가 완전하다고 간주하지 않는다.

Photo 수동 import는 양수 거래가 없는 지점에 집계 행이 없을 수 있다. 그러므로
전체 파일 import success만으로 모든 지점의 0원일을 확정하지 않는다. 무매출 확인
메타데이터에는 매장·날짜·원천·확인자·이유를 기록하고 실제 매출을 생성하지 않는다.
22:00 이후 수동 신고 원칙을 유지하며 폐기된 자동 수집 expected-slot 검사는 사용하지 않는다.

missing/partial/failed는 0 보충 금지. 사용자가 제외하여 계산하면 제외 날짜를 밝히고,
요일별 편향과 최소 표본을 다시 검사한다. 원본 재신고·수정 시 입력 fingerprint가
바뀌어 캐시와 사용자 확인을 다시 검증하도록 한다.

## 3. 레스토랑: 매출 회귀와 수요

1차 모델은 해석 가능한 채널별 회귀를 기준으로 한다.

~~~text
r_hat[d,c] = b0[c] + b1[c] * centered_day[d]
          + sum(b_weekday[c,w] * I(weekday[d] = w))
D[d,c] = max(0, r_hat[d,c]) / P[c]
~~~

r은 백만 VND 단위 학습값, P는 같은 통화 단위의 고정 팀/주문당 매출이다.
실제 반환은 VND. D는 “관측 매출 추세에 대응하는 서비스 수요”이지 숨겨진 잠재 고객의
관측값이 아니다. P는 일별 객단가의 단순 평균 대신 유효 총매출/유효 팀·주문 수로
계산한다. 방문 그룹화가 신뢰 가능할 때만 홀의 단위를 팀으로 명명한다.
그렇지 않으면 확인된 평균 팀 객단가와 팀 크기를 입력받고 가정으로 표시한다.

- 홀 팀 크기 분포, 메뉴 구성, 채널 비중, 평균 객단가는 학습 기준값으로 고정한다.
  회귀와 별도로 객단가가 무한 증가하여 용량 제한을 우회하지 못한다.
- 유효 방문/주문 회수가 충분하면 동일한 회귀의 종속변수를 회수로 바꾸는 후보를
  검증할 수 있다. 어떤 후보를 썼는지 결과에 명시한다.
- 사용 요일 평균/최근 동요일 기준을 비교 모델로 두고, 회귀보다 검증 오차가 작으면
  권장 예측에는 비교 모델을 사용한다. 사용자는 회귀식과 선택 이유를 모두 볼 수 있다.
- 수치 계산은 중심화·스케일링 및 QR/SVD 등 안정적인 해법을 사용한다.
  특이행렬을 임의 계수로 덮지 않는다. NaN, infinity, 단가<=0은 오류다.
- 미래 감소는 0 바닥에서 제한한다. 전부 0인 자료는 “관측 성장 근거 없음”이며
  양의 성장/목표일을 생성하지 않는다.
- 가격 변경, 판촉, 휴점, 구조 변경은 알려진 구간을 표시한다. 짧은 자료에서 날씨·월별
  계절성·행사 효과를 임의 학습하지 않는다. 구조 변경 전후 기간 선택을 안내한다.
- 포화 매장의 실제 매출은 용량에 막힌 관측이다. 외부 대기/거절/예약 수요 자료 없이
  용량 확대만으로 수요 증가를 추정하지 않는다. 그 경우 추정 추가 매출은 보수적이며
  별도 수요 가정이 있어야 낙관 시나리오를 계산한다.

## 4. 레스토랑: 자원·시간 계산

### 4.1 단위와 모형 수준

1차 버전은 고정 메뉴 구성의 “대표 팀/주문 묶음”과 자원별 작업량을 사용한다.
개별 요리의 모든 동작을 복제하는 디지털 트윈은 만들지 않는다. 대신 시간대
도착 분포와 연속 시간의 자원 예약 계산으로 테이블·조리·체커·서빙의 경합을 반영한다.
모든 계산은 재현 가능하며 입력값과 정책 버전이 같으면 동일한 결과를 반환한다.

- 시간대 입력/표시 기본은 30분. 자원 점유·서비스는 연속 시간으로 이어진다.
  경계마다 진행 중 작업, 테이블, 대기를 초기화하지 않는다.
- 시간대 도착 가중치는 해당 기간의 유효 주문 시작 자료로 만든다.
  자료가 없으면 사용자가 확인한 가정을 표시한다. 하루 총량을 균일 분산하지 않는다.
- 자원 용량은 메뉴/대표 묶음당 **실제 작업 분량 + 병렬 자원 수** 또는 확인된
  **포화 상태의 지속 처리량** 중 하나로 설정한다. 단위를 명시하며 두 입력을
  중복 곱하지 않는다. 한 직원이 두 층을 맡으면 동일 자원 ID를 공유한다.
- 비혼잡 시 완료 건 간격은 고객이 없던 시간을 포함하므로 처리능력으로 쓰지 않는다.
- elapsed_seconds에는 대기·운반·처리의 중첩이 있다. staff_count*60/elapsed_minutes로
  처리량을 자동 생성하지 않는다. 현재 KDS에는 모든 단계의 작업 시작 기록이 없다.
- 가동 가능시간(휴게/정비 제외), 지속 처리효율, 수요에 의한 이용률은 별도 개념이다.
  실측 처리량에 이미 포함된 휴게/효율을 다시 차감하지 않는다.

### 4.2 단계 의미

이벤트는 event_id 중복을 제거하고 시간순 delta/undo를 적용해 최종 유효 수량을
재구성한다. 취소/수량 수정 이후 무효가 된 완료 시각을 사용하지 않는다. 최초/최종
제공도 유효 수량 기준이며, source item/batch/route snapshot과 대조한다.
KDS session_id는 방문 팀 식별자가 아니다. 진행 중 자료는 완결 소요시간 표본과
분리하고, 단계 누락·음수 시간·취소·검토 필요 건수 및 전체 대비 coverage를 반환한다.
완료 건만의 짧은 평균을 전체 처리시간이라고 일반화하지 않는다.

| 구간 | 의미 | 계산상 주의 |
| --- | --- | --- |
| 착석→주문 | 사전 주문 대기 | 자료 부재 시 확인값 |
| 주문/추가 주문 접수→kitchen_done | 조리 대기+조리 경과 | 처리 자원 작업시간과 구별 |
| kitchen_done→tray_received | 체커 접수 대기 | 조리시간/체커 실작업에 중복 포함 금지 |
| tray_received→tray_dispatched | 체커 검수·조합·출고 경과 | 배치 대기 포함 가능, 능력은 별도 검증 |
| tray_dispatched→floor_served | 층별 전달 경과 | 왕복·운반 작업량과 고객 대기시간 구분 |
| 최초 제공→식사/결제 완료 | 식사+추가 주문/결제 대기 대용값 | 전 메뉴 최종 제공시간과 합산 금지 |
| 결제→퇴장→정리 완료 | 테이블 재사용 준비 | 기존 결제로 실제 퇴장을 확정하지 않음 |

개념상 테이블 사이클은 “착석부터 첫 음식까지 + 그 이후 퇴장까지 + 정리”다.
측정된 구간이 서로 겹치지 않게 분해해야 한다. 실제 좌석 사용시간을 측정한 자료가
있으면 우선 사용하고, 첫 제공→결제 대용값만 있으면 불확실성을 표시한다.

추가 주문은 주방/체커/층 작업량을 추가하지만 새 팀이나 새 테이블 사이클은 아니다.
최종 음식이 제공되기 전에 식사가 끝났다고 처리할 수 없다. 1차 묶음 모형은
추가 주문의 측정된 발생 지연과 최소 식사 여유를 포함해 퇴장 시각을 검증한다.
추가 주문 대기와 순수 식사를 분리할 수 없으면 식사시간 단축의 매출 효과를
확정 산출하지 않는다.

### 4.3 경로와 자원 예약

1. 예측 팀/주문을 시간대 도착 분포로 배치한다. 소수 기대 회수는 반복 샘플/가중치로
   합계 보존하고 화면 일별 반올림을 학습 입력으로 되먹이지 않는다.
2. 홀은 팀 크기에 맞는 테이블을 예약한다. 좌석이 남아도 합석 금지이면 다른 팀을
   같은 테이블에 자동 배치하지 않는다. 여러 테이블을 쓰는 팀은 모두 점유한다.
3. 메뉴 구성별 작업량을 실제 경로에 따라 주방→체커→층으로 예약한다.
   floor_direct 음료는 조리·체커를 우회하되 해당 담당의 작업량은 반영한다.
   combo 부모와 자식을 이중 계산하지 않는다.
4. 공유 주방·체커는 모든 층/채널의 작업을 한 번만 처리한다. 층별 제공능력은
   분기 자원으로 계산하며 가장 느린 한 층 때문에 다른 모든 층이 같은 속도로
   제한된다고 가정하지 않는다.
5. 배달·포장은 홀 테이블을 점유하지 않는다. 조리/체커/포장 등 실제 필요한 자원을
   공유하고 배달 채널의 별도 접수시간을 반영한다.
6. 고객이 기다릴 수 있는 시간, 주문 허용시간, 식사 종료/퇴장 마감까지 서비스
   가능한 작업만 인정한다. 미완료 작업을 다음 날 매출로 자동 이월하지 않는다.
7. 실제 매출과 대조할 때는 서비스 완료 시점과 결제 날짜의 시차를 함께 검증한다.
   자정 넘는 운영은 연속 자원을 유지하되 매출 날짜는 기존 회계 기준으로 귀속한다.

주문 우선순위/대기 정책은 기본 도착순+테이블 적합성으로 명시하고, 임의로
고가 주문만 골라 매출을 최대화하지 않는다. 취소/무료 제공도 자원을 소비했다면
용량에서 제외할 수 없다. 폐기·재조리율은 근거 있는 별도 작업량으로 반영한다.

### 4.4 용량과 최종 금액

~~~text
R_forecast[month] = sum(served_units[d,c] * fixed_net_price[c])
served_units = schedule(predicted_demand, tables, kitchen, checker,
                        floor_resources, dwell, opening_and_cutoff)
R_forecast >= 0
resource_work <= resource_available_work
table_occupancy <= available_matching_tables
~~~

“최소(테이블, 주방, 체커, 서빙)”은 단일 동질 경로에서만 쓰는 설명용 축약이다.
층/메뉴/채널마다 단위가 다른 수치를 그대로 비교하는 계산식으로 구현하지 않는다.

한도는 두 가지를 구분한다.

- **이론적 상한:** 같은 메뉴·단가·팀 구성에서 자원별 시간 예산으로 구한 상한.
  각 자원 r에 대해 sum(work_per_unit[r,c]*units[c])<=available[r]를 만족하고,
  테이블 시간/좌석 제약을 함께 사용한다. 대기와 도착 불일치를 완화한 상한이므로
  달성 가능액으로 광고하지 않는다. 구성비를 마음대로 고가 메뉴로 바꾸지 않는다.
- **운영상 가용 한도:** 충분한 수요를 넣어 동일한 운영 정책/일정으로 예약했을 때의
  계획 처리량. 실무 기준치이며 수학적 전역 최대라고 주장하지 않는다.
  서비스 모형·품질 조건이 없으면 이 수치도 계산 불가다.

최종 예측은 실현 가능한 일정만 합산하며 이론적 상한 이하임을 검사한다.
가용 한도 실험이 일반 예측보다 낮아지는 등 정책/혼잡의 불일치가 생기면 경고하고
상한/스케줄을 검증한다. 실제 관측이 계산 상한을 넘으면 설정·단가·채널·동시성 오류를
먼저 조사한다. 과거 실적을 상한에 맞춰 잘라내지 않는다.

월 한도는 해당 월의 실제 날짜·요일·휴무·기기/자원 변경일을 합산한다.
현재 조건에서 목표가 이론적 상한조차 넘으면 “현 조건·전망기간 내 용량 초과”,
운영 가용 한도만 넘으면 “운영 가정상 어려움 / 추가 확인”으로 구분한다.

## 5. 레스토랑 개선 시나리오

기본 수요·단가·메뉴·난수 경로를 같은 것으로 두고 baseline과 intervention을
쌍으로 비교한다. 이것은 가정 기반 모형 실험이지 관측 상관관계의 인과 증명이 아니다.

~~~text
extra_revenue = revenue(intervention, same_demand) - revenue(baseline, same_demand)
extra_capacity = capacity(intervention) - capacity(baseline)
~~~

- 회전/주방/체커/층별 제공/식사/영업시간 6영역의 입력 중 개선 가능한 값만 바꾼다.
- 10% 단축·1명 추가·30분 연장 등은 사용자 확인 전까지 시험 가정이다.
  서비스 최소시간, 이동거리, 병렬 작업 가능성, 공간/안전 범위를 검증한다.
- 주방의 작업 능력 증가와 첫 제공 대기 감소를 동일 사건의 효과로 연결한다.
  대기시간도 임의로 한 번 더 빼서 두 배 개선하지 않는다.
- 한 사람의 두 업무를 동시에 100% 배정하지 않는다. 층 인력을 옮기면 원래 층의
  감소까지 포함해 비교한다.
- 순수 식사시간 강제 단축은 기본 추천에서 제외한다. 식사 관련 개선은 근거가 있는
  비식사 대기 축소를 우선하고 고객 만족·재방문 효과는 자료 없으면 금액화하지 않는다.
- 영업시간 연장은 기존 운영시간에 이미 관측된 수요를 재배치하거나 확인된 추가 수요
  시나리오로만 계산한다. 새 시간대에 기존 평균 시간당 매출을 자동 복사하지 않는다.
- 조리 cutoff 21:30, grace 21:45, finalization 22:20 적용 매장은 이를 기준 조건에
  반영한다. 일반 cash close 23:00과 다르다. 정책 밖 연장은 “정책 변경 필요”이며
  예측 화면에서 실제 정책을 변경하지 않는다.
- 단독 자원 변화의 민감도, 대기/가동 지표, 인접 자원 관계로 후보를 정한다.
  p90 경과시간이 가장 길다는 이유만으로 병목이라고 확정하지 않는다.
- 단독 효과가 0인 공동 병목도 누락하지 않는다. 6영역의 검증 가능한 단독 후보와
  관련 2영역 조합을 비교한다. 여러 단축률을 무한 탐색하는 최적화는 1차 범위 밖이다.
- 복합 개선은 전체를 재계산한다. 단독 개선분의 합계를 복합 효과로 표시하지 않는다.
- 추가 매출이 0/음수인 결과도 그대로 보여준다. 늘어난 처리능력을 “추가 매출”로 바꾸지 않는다.

추천 출력: action, changedInputs, evidence, timeWindow/floors/resources,
extraServedUnits, extraRevenueVnd, extraCapacity, baseline/afterUtilization,
nextBottleneck, targetBefore/After, risks, prerequisites, confidenceClass.
기본 정렬은 실행조건이 확인된 후보 중 수요 반영 추가 매출 순이며 비용 미반영임을
명시한다. 미측정 후보는 확정 순위 대신 측정 안내로 분리한다.

## 6. Photo 전용 계약

### 6.1 고정 정책

~~~text
SESSION_MINUTES = 8
REVENUE_PER_PAID_SESSION_VND = 85000
machine_capacity = sum_over_contiguous_available_windows(floor(window_minutes / 8))
store_capacity = sum(machine_capacity)
forecast_revenue = expected_completed_paid_sessions * 85000
~~~

8분은 입장→촬영→퇴장 전체이므로 별도의 기본 교체시간을 중복 더하지 않는다.
기기별 실제 중단 구간은 제외한다. 30분 표시 구간마다 floor(30/8)를 합산하지 않고
기기 작업을 다음 구간으로 이어간다. 중단 전 완료되지 못한 촬영을 판매 완료로
인정하지 않으며, 기기 간 남은 4분씩을 합쳐 1회로 만들지 않는다.

- 1대가 중단 없이 12시간 가동: floor(720/8)=90회, 이론적 최대 7,650,000동/일.
- 2대×12시간×30일, 무료 서비스·중단 없음: 최대 459,000,000동/월.
- 이는 100% 유료 가동 가정의 상한 예제이지 예상 매출이 아니다.
- 단독 60분 운영구간은 7회 완료. 연속 120분은 15회 완료하므로 두 60분 표시 구간을
  각각 버림하여 14회로 줄이지 않는다.
- 월 목표 10억/15억동에 필요한 유료 회수는 각각 ceil(target/85,000)으로 계산한다.
  실제 기기·일정으로 충족하지 못하면 목표일을 생성하지 않는다.

### 6.2 실제 회수와 수요 회귀

현재 수동 신고 집계의 transaction_count에는 양수 서비스 거래가 포함될 수 있다.
동일 원천·날짜·기기 기준으로 다음 의미를 검증한 뒤 사용한다.

~~~text
paid_sessions = transaction_count - service_count
S_hat[d] = max(0, a0 + a1 * centered_day[d] + weekday_effect[d])
completed_paid = schedule_photo(S_hat, free_service_reserve, machine_windows, 8)
~~~

거래 행 1개=촬영 1회인지 원본 표본으로 확인한다. 1행이 여러 촬영/재출력/묶음 결제이면
transaction_count를 실제 회수로 확정하지 않는다. 부정합·음수 회수는 오류다.
무료 촬영은 매출 0이지만 같은 8분 자원을 사용한다. 미래 무료 서비스 예약은
과거 비중 또는 확인한 일정에 근거하고 수요와 함께 경쟁시킨다.

회수가 없고 실제 순매출만 있으면 순매출/85,000을 “환산 촬영 회수”로 사용할 수 있다.
이는 실제 고객 수가 아니며 낮은 근거 수준을 표시한다. 실제 거래 단가의 변동이
환산 회수 추세에 영향을 줄 수 있다는 경고를 표시한다.

Photo의 미래 매출은 반드시 유료 회수×85,000으로 계산한다. 과거 금액을 그대로
외삽한 뒤 한도만 씌우는 방식으로 고정 단가 요구를 우회하지 않는다.
예상 회수의 평균은 소수가 될 수 있지만 각 모의 경로의 완료 촬영은 정수다.

Photo 응답 타입에는 RestaurantRecommendation을 넣지 않는다. 병목 개선,
기기 증설 추천, 영업 연장 추천, 식사/주방 항목을 UI·export 어디에도 노출하지 않는다.
가동률과 목표 충족 여부는 예측 설명으로만 표시한다.

## 7. 정확도·불확실성·목표 판정

- 시간 순서를 지킨 rolling-origin 평가를 한다. 각 fold는 이전 날짜만 학습하며
  단가·메뉴 비중·시간대 분포도 fold 안에서 계산한다.
- 평가 가능한 7/28일 예측 오차를 요일 기준과 비교한다. 관측 자료가 짧아 평가 fold가
  없으면 “백테스트 자료 부족”이라고 표시한다. 미래 구간의 품질을 검증했다고 주장하지 않는다.
- MAE(VND), RMSE, 총액 WAPE(분모>0), 편향과 fold 수를 표시한다.
  전부 0인 분모에서 MAPE/WAPE를 무한대나 임의 0으로 만들지 않는다.
- R²는 학습 적합 설명에만 사용한다. 높은 R²만으로 미래 신뢰도를 높음으로 판정하지 않는다.
- 과거 자원 프로필이 없는 기간에는 수요 모델 검증만 가능하다. 현재 테이블/인력을 과거에도
  있었다고 가정해 운영제약 모형의 정확도를 검증했다고 보고하지 않는다.
- 장기 추세는 전망기간이 학습 길이 또는 검증 가능한 horizon을 넘는 구간에서
  “장기 외삽 시나리오”로 명시한다. 39일 자료로 24개월 목표월을 신뢰도 높은 예측으로 제시하지 않는다.
- 초기 기본 범위는 측정 오차·가정의 낮음/기준/높음 시나리오다. 이를 95% 구간이라 부르지 않는다.
- 충분한 검증 자료가 있을 때만 주간 잔차 블록/계수 변동 등을 반영한 예측 경로를
  자원 계산기에 통과시켜 조건부 예측 구간을 제공한다. 시간 자기상관과 모형 가정을 공개한다.
- 월별 구간은 각 경로의 월 합계를 낸 후 분위수를 계산한다.
  일별 하한/상한을 합산해서 월 95% 범위라고 표시하지 않는다.
- 범위도 0 이상이며 해당 경로의 운영 제약을 만족한다. 선택한 가격/인력/운영시간
  가정의 불확실성까지 모두 포함한 확률 보장으로 설명하지 않는다.

목표는 선택 전망기간 안의 첫 완전 월부터 판정한다.
첫 도달 월과 이후 3개 연속 월 유지 여부를 별도 계산하며, 마지막 달이 부분 월이면
보조 표에만 포함한다. 동(VND) 원 단위로 비교하고 표시 반올림 때문에 먼저 도달하지 않는다.
기간 내 도달하지 않으면 기간 밖 날짜를 회귀식 역산으로 덧붙이지 않는다.

## 8. 제안 스키마·서비스 경계

정확한 이름은 구현 시 convention에 맞출 수 있으나 권한/의미 계약은 유지한다.

### 저장

- revenue_forecast_profile_versions: restaurant_id FK, revision, model_type,
  effective_from/to, schema_version, typed settings JSONB, source/confirmed_by,
  confirmed_at, created_at. 같은 revision은 불변, 변경은 새 버전.
- settings에는 floor/table references, resources/shared resource IDs, schedules,
  party/menu/channel assumptions 또는 Photo machine windows를 넣는다.
  단위·범위·타입·중복·유효기간을 서버에서 검증한다.
- revenue_forecast_day_confirmations: restaurant_id, date, source,
  state(confirmed_zero/closed 등), evidence reference, source fingerprint,
  confirmed_by/at. 실제 거래나 신고 상태를 덮어쓰지 않는 예측용 메타데이터다.
- 현장 측정치는 프로필에 표본 기간/수/단위/집계값으로 보관하고 개인별 원본 행동
  로그나 고객 식별정보를 신규 보관하지 않는다.
- Photo 8분·85,000동은 모델 정책 상수다. JSON 설정으로 우회할 수 없도록 서버/클라이언트
  검증에 함께 고정한다.
- 미래 적용일의 프로필 변경은 해당 날짜 이후만 적용한다. 과거 버전을 덮어쓰지 않는다.

### 읽기·권한

- get_revenue_forecast_inputs(store, from, to): 매출/회수·시간대·층별/경로별
  단계 통계·분포 요약·프로필·완전성·대조 결과·source fingerprint 반환.
- 기존 report RPC의 의미를 몰래 바꾸지 않고 추가 aggregate endpoint로 구현한다.
  N+1 주문별 조회 대신 기간/매장 인덱스를 사용한다.
- 실제 접근 가능한 매장과 기존 매출 조회 capability를 서버에서 검사한다.
  restaurant/photo 화면 진입만으로 조회 권한을 부여하지 않는다.
- 프로필/완전성 확인 저장은 기존 매장 관리자 권한 또는 명시적으로 대응된 Photo
  관리자만 허용한다. 일반 조회자는 시나리오 임시 계산만 가능하다.
- 테이블에 RLS를 적용하고 일반 클라이언트에 service_role을 제공하지 않는다.
  definer RPC가 필요하면 고정 search_path, 명시적 권한 검사, execute grant 제한을 적용한다.
- 반환은 집계값에 한정한다. 고객 전화번호, 직원별 실적/이름 등 PII는 반환하지 않는다.
- 원천 수정 중 서로 다른 버전이 섞이지 않도록 DB snapshot 집계 또는 버전 확인을 한다.

### 클라이언트

순수 calculator와 입력 service를 분리한다. 공통 ForecastResult 아래
RestaurantForecastResult와 PhotoForecastResult를 별도 타입으로 둔다.
Photo에 빈 추천 목록을 억지로 렌더링하지 않는다.

캐시/비동기 세대 키는 storeId + applied period + profile revision + scenario hash +
source fingerprint + model version이다. 매장 전환 시 이전 결과를 폐기하고 늦게 도착한
응답을 무시한다. 프로필 편집 중 draft는 계산 완료 결과와 혼동되지 않게 표시한다.

계산기는 번역 문장 대신 enum/error code와 typed arguments를 반환한다. locale은 수학적
입력 hash에 포함하지 않으며 언어 변경만으로 금액·회귀·기준 날짜가 바뀌지 않는다.
표시/파일 cache에는 locale을 포함하고 파일 생성 시작 시 snapshot을 고정한다.

1차는 순수 Dart 계산기를 사용하되 실행 경로를 플랫폼별로 검증한다. 네이티브는
필요 시 isolate를 사용할 수 있다. Flutter Web의 compute는 메인 스레드에서 실행되므로
그 호출만으로 비차단을 주장하지 않는다. 웹은 짧은 계산 단위/yield/취소를 구현하고,
제품 완료 계약의 예산 미달이면 worker 또는 서버 계산 경로를 구현·검증한 후 공개한다.
원본 이벤트는 서버에서 집계하고 별도 ML 서버를 먼저 만들지 않는다.
기본 결과/후보 시나리오 수와 실행 취소를 제한하여 24개월 전망이 화면을 멈추지 않게 한다.
인증 만료·매장 전환 시 민감 cache를 폐기한다. 프로필 저장은 expected revision과
operation ID로 충돌·재시도 중복을 처리하며 offline 자동 저장 큐는 만들지 않는다.

### 품질 등급

- confirmed: 매출·회수/객단가·스케줄·자원이 검증되고 과거 대조도 통과.
- assumption_based: 관리자가 확인한 대용값으로 계산, 조건부 시나리오 표시.
- insufficient: 필수 단위/자원/완전성/식사 사이클 등이 없음. 지원되는 일부 분석만 노출.
- conflict: 원본 합계, 단계 순서, 관측 처리량과 상한 등 불일치. 결과 확정 금지.

등급은 임의의 “정확도 95%” 점수로 변환하지 않는다. 항목별 사유를 함께 보여준다.
주방 자료만 없다고 고객의 식사시간 등을 임의 30/60분으로 채우지 않는다.
