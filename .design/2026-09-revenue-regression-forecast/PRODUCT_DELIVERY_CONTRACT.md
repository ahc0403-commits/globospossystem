## 1. 완료의 정의와 지원 범위

계산기만 구현한 상태, 영어 화면만 동작하는 상태, 데스크톱에서만 쓸 수 있는 상태는
기능 완료가 아니다. 각 사용자 여정이 데이터→화면→언어→권한→실제 기기→파일 저장까지
연결되고 검증되어야 한다.

| 실행 환경 | 필수 범위 | 증거 |
| --- | --- | --- |
| 데스크톱 웹 | Chrome/Edge, Safari, Firefox의 주요 여정 | 출시 때의 버전·OS·테스트 결과 |
| 모바일 웹 | iPhone Safari, Android Chrome | 실기기 터치·키보드·회전·파일 저장 |
| 태블릿 웹 | iPad Safari, Android Chrome | 가로/세로·분할 화면·큰 글씨 |
| 기존 Android/iOS 앱 | 동일 권한의 공유 기능, 네이티브 뒤로가기/파일 저장 | 빌드와 기기/시뮬레이터별 실행 결과 구분 |
| 기존 데스크톱 앱 | 기존 지원 빌드에 신규 import/기능 회귀 없음 | 지원 대상 빌드 및 권한 경로 smoke |

모바일 웹과 네이티브 앱을 같은 것으로 기록하지 않는다. 기존 앱 안의 기능 검증까지
범위에 포함하되 새 앱 제작·App Store/Play Store 공개 출시는 별도 승인 없이는 하지 않는다.
서명/기기/특정 OS 시험이 불가능하면 해당 칸은 BLOCKED/NOT RUN이다. 전 플랫폼 완료로
발표하지 않는다. 기존 전역 역할/플랫폼 제한을 풀어 기능을 노출하지 않는다.

대상 브라우저의 최신 stable과 운영 중인 주요 이전 버전을 출시 시 확인하고 버전을
고정해 기록한다. 모든 과거 OS/브라우저 호환을 무제한 약속하지 않는다.
현재 저장소의 웹 배포 스크립트는 네이티브 앱 배포 증거가 아니다.

## 2. 정보 구조와 진입·이탈

### 2.1 화면 구성

~~~text
기존 매출 분석 / Photo 운영
└─ 매출 예측 (매장·적용 기간·권한이 보이는 공통 화면)
   ├─ 요약: 예상액 / 운영 한도 / 목표 상태 / 품질
   ├─ 조건: 학습·전망 기간 / 목표 / 운영 프로필
   ├─ 월별 결과: 차트 + 같은 값의 접근 가능한 표/목록
   ├─ 개선 비교: 레스토랑만, 단독·복합 시나리오
   ├─ 근거·설명: 회귀식 / 자료 품질 / 가정 / 측정 안내
   └─ 내보내기: 언어·범위 확인 → 예측 전용 파일
~~~

예측 기능을 기존 매출 보고서 아래의 거대한 단일 폼으로만 넣지 않는다.
기존 화면에는 요약/진입 패널을 두고, 복잡한 편집과 비교는 공통 상세 화면으로
분리한다. 탭·섹션 이름과 순서는 모든 기기에서 같고 표시 방법만 바뀐다.
Photo에는 개선 탭, 빈 개선 카드, 식사·주방 입력을 만들지 않는다.

### 2.2 탐색 계약

- 매출 조회 가능한 매장만 선택 가능하다. 기본은 호출한 화면의 매장·적용 기간.
- 주소/화면 인자에는 식별자·기간·선택 섹션만 넣고 매출/프로필 원문을 넣지 않는다.
- 새 경로를 도입하면 GoRouter의 인증·매장 capability 검사, 직접 URL, 새로고침,
  로그인 복귀를 함께 구현한다. 메모리 extra에만 의존하여 새로고침 시 깨지지 않게 한다.
- 상단 뒤로, 브라우저 Back/Forward, Android Back, iOS 뒤로 동작의 결과를 일치시킨다.
- 편집 미저장 상태의 앱 내 이탈은 “계속 편집 / 변경 버리기”를 선택하게 한다.
  실제 저장을 요청하지 않은 상태에서 언어 변경/탭 이동만으로 저장하지 않는다.
- 새로고침·OS 강제 종료에는 이탈 경고가 보장되지 않는다. 화면에 미저장 상태를
  명시하고 저장된 프로필만 복구한다. 예측 재무자료를 localStorage에 자동 영구 보관하지 않는다.
- 이동 전 실제 보고서의 기간/스크롤은 가능한 범위에서 복귀하고 기존 actual report
  provider를 예측 편집 때문에 변경하지 않는다.
- 주요 컨텍스트(매장·기간·실적/예측·가정)는 어떤 탭에서도 확인할 수 있어야 한다.

## 3. 디자인·컴포넌트 계약

현재 Flutter/Toast 디자인을 사용한다. 신규 디자인 시스템이나 React/Tailwind를 도입하지 않는다.

| 분류 | 현재 요소 | 조치 |
| --- | --- | --- |
| 공통 화면 | ToastWorkSurface, ToastResponsiveScrollBody, PosPageHeader | 재사용, 기존 다른 화면의 동작 변경 금지 |
| 데이터/조작 | PosDataPanel, PosStatCard, PosToolbar, PosPrimaryButton, PosSecondaryButton | 재사용하되 좁은 폭·큰 글씨를 확인 |
| 상태/확인 | ToastStatusBadge, PosEmptyState, PosExceptionAlert, ToastConfirmDialog | 재사용, 작업별 문구·다음 행동 명시 |
| 테이블 | ToastDenseDataTable, PosTableShell | 데스크톱 후보, 모바일 목록 대안 신규 |
| 토큰 | PosColors, ToastSpacingTokens, ToastRadiusTokens, AppFonts | 기존 값 우선; feature 한정 보정 근거 기록 |
| 기간/실적 | SalesRevenueAnalyticsScreen, SalesRevenueAnalysisDashboard | 요약/진입과 상태 연결만 변경 |
| Photo 진입 | PhotoOpsScreen, PhotoOpsService | 공통 예측 연결, 수동 신고 유지 |
| 언어 | LocaleController, AppLocalizations, app_*.arb, intl | 공통 원천 재사용 |
| 다운로드 | ReportExcelFileSaver, saveReportExcelFile | 재사용/래핑, 현재 void 성공값의 한계 처리 |
| 신규 | ForecastScreen, 운영 편집, 월별 목록, 비교 카드, 품질/도움말 | 새 공통 feature 컴포넌트 |

- 핵심 KPI를 먼저 제시하고 회귀식·상세 가정은 펼침 영역으로 제공한다.
- 버튼은 동사와 결과를 분명히 한다: “예측 계산”, “조건 저장”, “시나리오 계산”,
  “예측 파일 다운로드”. 프로필 저장과 실제 영업정책 적용을 혼동시키지 않는다.
- 매출·한도·예상 범위는 단위/기간을 항상 동반한다. 숫자를 과장하는 큰 장식 카드는 피한다.
- 실제/예측/한도는 색뿐 아니라 선 형태·라벨·범례로 구분한다.
- 현재 AppTheme는 light-first다. 기능만의 다크 테마를 별도로 만들지 않는다.
  OS 고대비·색 반전·큰 글씨에서는 내용과 조작이 유지되는지 검증한다.
- 프레임마다 반짝이는 로딩, 자동 차트 확대, 장식용 애니메이션을 추가하지 않는다.
  필요한 진행 표시만 사용하고 reduced motion을 존중한다.
- 신규 공용 위젯 수정이 필요하면 기존 소비 화면의 회귀 테스트를 함께 수행한다.

## 4. 모바일·태블릿·반응형 계약

### 4.1 레이아웃

화면 전체 폭이 아니라 실제 콘텐츠 제약 폭과 글자 크기를 기준으로 재배치한다.

| 사용 가능한 폭 | 배치 |
| --- | --- |
| 320–599 logical px | 한 열, KPI 세로/공간 허용 시 두 칸, 조건은 전체 높이 편집 화면 |
| 600–1023 | 입력과 결과의 두 열은 내용이 들어갈 때만; 큰 글씨면 한 열 |
| 1024 이상 | 조건·결과를 나눌 수 있으나 읽기 폭 제한, 비교표 사용 가능 |

- 시험 폭: 320/360/390/430/600/768/1024/1440/1920 및 경계 599/600, 1023/1024.
- 가로/세로, iPad 분할, 200% 텍스트, 400% 브라우저 확대에 따라 다시 배치한다.
  400% 확대에서는 실질 320 CSS px 수준의 reflow를 검사한다.
- 페이지 전체의 가로 스크롤, 잘린 KPI·목표액, 의도치 않은 nested scroll을 금지한다.
  본질적으로 2차원인 표/차트는 제한 영역 스크롤을 허용하되 동일 정보의 목록을 제공한다.
- 모바일 비교는 데스크톱 표를 축소하지 않고 현재→변경→효과→주의사항 카드로 바꾼다.
- 모바일 월별 결과는 월 단위 목록을 기본으로 하고 세부값을 펼칠 수 있게 한다.
- 차트 24개월을 좁은 화면에 모두 글자로 밀어 넣지 않는다. 읽을 구간을 선택하고
  전체 월 데이터는 목록에서 접근한다. 시각 샘플링으로 금액 합계를 바꾸지 않는다.

### 4.2 터치·입력·키보드

- 주요 조작의 터치 영역은 제품 기준 48×48 logical px 이상을 사용한다.
  아이콘만 있는 버튼도 이름·tooltip·Semantics를 갖는다.
- SafeArea, 노치, 홈 인디케이터, 브라우저 주소창 높이 변화, viewInsets를 처리한다.
- 키보드가 열린 상태에서도 현재 입력, 오류, 다음/완료, 취소/저장에 접근 가능해야 한다.
  공간 부족 시 하단 고정 버튼을 일반 문서 흐름으로 옮긴다.
- 숫자 키패드, 다음 입력 focus, paste, 텍스트 선택, IME 조합 입력을 지원한다.
  한글 조합/베트남어 성조 입력 중 formatter가 커서나 내용을 망가뜨리지 않는다.
- 날짜 입력은 picker와 명확한 직접 입력 경로를 제공하고 연도를 생략하지 않는다.
- hover에만 보이는 기능 금지. 차트는 tap, 키보드/월 목록으로 같은 값에 접근 가능하다.
- 가로 스와이프/핀치/드래그만으로 가능한 필수 동작을 만들지 않는다.
- 회전·화면 크기 변경 때문에 입력값, 탭, 비교 선택, 스크롤이 초기화되지 않게 한다.

## 5. 언어 전환과 현지화

### 5.1 단일 문자열 원천

- 한국어/베트남어/영어 모두 출시 필수다. 새 문구는 app_en/ko/vi.arb의
  revenueForecast 계열 키와 생성된 AppLocalizations로 관리한다.
- 기존 _SalesAnalysisCopy 등 private 언어 map을 신규 예측 기능에 복제하지 않는다.
  무관한 기존 화면의 전체 번역 구조를 이번 작업에서 일괄 재작성하지 않는다.
- 계산·서버 결과는 language-independent enum/error code + typed arguments로 반환한다.
  UI는 현재 locale로 번역한다. 서버 영문 오류/내부 enum/SQL 메시지를 그대로 노출하지 않는다.
- 언어별 키/placeholder 타입·이름 일치, 중복 키, ICU plural/select, 미번역/TODO를
  자동 검사하고 flutter gen-l10n 결과를 확인한다. 생성 Dart를 직접 수정하지 않는다.
- 도움말, 로딩, 빈 상태, 오류, 권한 거부, 확인 대화상자, tooltip, 차트 축/범례,
  추천 이유/위험/조건, 접근성 라벨, 파일 제목/시트/컬럼도 번역 범위다.
- 매장·메뉴·층 이름처럼 사용자 원본 데이터는 번역하거나 바꾸지 않는다.
  동적 개선 제안은 문장 조각의 조합 대신 placeholder가 있는 완전한 문장으로 만든다.
- 지원하지 않는 저장 locale은 기존 AppLanguage 정책(현재 Korean fallback)을 따른다.
  지원 세 언어 중 일부 키 누락은 조용한 fallback으로 감추지 않고 출시 오류로 취급한다.

### 5.2 실행 중 변경

KO→VI→EN→KO의 모든 방향을 실제 화면에서 검사한다.

- LocaleController의 현재 설정과 저장 동작을 사용한다. 예측 전용 언어 상태를 따로 만들지 않는다.
- 화면/열린 편집창/오류/선택 tooltip까지 새 언어로 갱신하되 매장·기간·목표·프로필
  draft·계산 결과·비교 선택을 잃지 않는다.
- locale 변경만으로 원본 재조회, 회귀 재학습, 프로필 저장을 하지 않는다.
  계산 입력 hash는 동일하고 presentation/export formatting만 갱신한다.
- locale 저장 실패는 사용 언어를 갑자기 되돌리거나 성공으로 표시하지 않는다.
  현재 선택과 “설정 저장 실패 / 다시 시도”를 표시하도록 공통 controller와의 경계를 검증한다.
  공통 controller 수정이 필요하면 범위를 좁히고 기존 언어 선택 회귀 테스트를 포함한다.
- 초기 저장 locale 복원 중 임시 한국어 결과가 확정 화면처럼 깜빡이지 않도록
  locale hydration 완료 전 언어 의존 UI를 안정적으로 표시한다.
- 편집 중 숫자 문자열은 입력 locale과 분리된 canonical 값을 유지한다.
  유효하지 않은 draft는 변환하지 않고 그대로 남기며 오류 설명만 새 언어로 바꾼다.

### 5.3 숫자·기간·파일

- 원본 VND는 숫자로 보관한다. 언어 변경은 통화 환전이 아니며 85,000동/목표액을 바꾸지 않는다.
- 전체 금액은 현재 locale 포맷과 VND 표기를 사용한다. 한국어의 “10억동”은
  영문 “1 billion VND”, 베트남어 “1 tỷ VND”와 같은 1,000,000,000을 가리킨다.
- 모바일 축약 단위는 명확히 쓰고 전체 숫자를 상세/접근성 라벨/파일에서 확인할 수 있게 한다.
- VND 금액 입력은 정수와 허용된 locale 그룹 구분자를 검사한다.
  “1.5”를 15나 1,500으로 임의 해석하지 않는다. 소수 가능한 분/비율 필드는
  locale 소수점 규칙과 허용 범위를 별도로 검증하고 ambiguity는 오류로 안내한다.
- UI 날짜 표시는 언어에 맞추되 매출 날짜 경계는 항상 Asia/Ho_Chi_Minh이다.
  단말 시간대나 언어 변경으로 조회 날짜가 하루 이동하지 않아야 한다.
- 다운로드는 시작 시점의 결과 snapshot과 export locale을 고정한다.
  진행 중 언어를 바꿔도 파일 한 개에 두 언어가 섞이지 않는다.
- 신규 번역은 세 언어 사용자 검토를 거친다. 기계 번역만 수행했다면 검수 완료로 기록하지 않는다.
  검수자는 “보장 매출 아님”, 용량/수요 부족, 무료 촬영, 객단가의 뜻을 특히 확인한다.

## 6. 입력·상태·오류 복구

| 상태 | 보여줄 내용 | 허용 행동 |
| --- | --- | --- |
| 최초 진입/권한 확인 | 구조를 유지한 로딩, 검증되지 않은 매장 정보 비노출 | 취소/뒤로 |
| 조건 미입력 | 부족한 항목·단위·예시 | 해당 입력으로 이동 |
| 자료 조회 중 | 조회 중인 매장·기간과 단계 | 취소, 기간 변경 |
| 계산 중 | 현재 조건으로 계산 중, 중복 요청 방지 | 취소, 입력 수정 후 재계산 |
| 성공 | 계산시각·적용값·근거·모델 버전 | 비교/조건 편집/다운로드 |
| 조건 변경됨 | 이전 결과는 이전 조건, 재계산 필요 | 계산; 이전 결과를 새 결과처럼 export 금지 |
| 유효한 무매출 | 실제 0과 성장 근거 부재 | 기간 변경/근거 확인 |
| 누락/부분/자료 불일치 | 누락 날짜·원천·보류 사유 | 재조회/확인/명시적 제외 |
| 기간 부족 | 필요한 유효 일수와 이유 | 기간 변경 |
| 용량 초과/수요 부족 | 다른 상태 문구와 근거 | 레스토랑 시나리오 또는 조건 확인 |
| 네트워크 끊김 | 최신 확인 불가, 수정값은 세션 메모리에 유지 | 연결 후 재조회 |
| timeout/서버 오류 | 작업명·번역된 원인·비식별 참조 코드 | 사용자 재시도 |
| 인증 만료/권한 회수 | 결과·민감 캐시 즉시 가림 | 재인증/권한 있는 매장으로 이동 |
| 프로필 저장 중 | 변경 요약, 이중 클릭 방지 | 불확실한 저장을 추가 중복 요청하지 않음 |
| 동시 편집 충돌 | 내 draft와 최신 revision 차이 | 새 버전 로드/명시적 재적용 |
| 다운로드 생성/전달 실패 | 생성과 기기 저장 상태를 구분 | 재시도/지원되는 저장 경로 안내 |

- 모든 필드는 라벨, 단위, 범위, 출처, 필수 여부를 갖는다. 오류는 필드 옆과
  요약으로 알리고 첫 오류에 focus를 옮긴다. 빨간 테두리나 사라지는 toast만 쓰지 않는다.
- 사용자 동작의 실패를 silent no-op으로 끝내지 않는다. 비활성 버튼에는 이유가 있다.
- 동일 버튼 연타/Enter 반복은 하나의 계산·저장·export 작업만 시작한다.
- 조회의 일시적 오류는 제한된 재시도와 backoff만 허용한다. 무한 재시도 금지.
- 저장에는 operation ID와 expected revision을 사용한다. timeout 후 성공 여부를
  먼저 조회하며 중복 프로필/확인 기록을 생성하지 않는다.
- 오프라인 자동 저장 큐나 신규 영구 매출 캐시는 1차에 만들지 않는다.
  이미 보이는 결과는 같은 인증 세션에서만 “오래된 결과”로 볼 수 있고 신규 계산/
  저장/export는 서버 권한·원천 재확인 후 수행한다.
- 앱 background→foreground 복귀 시 인증·프로필·원천 버전을 재확인한다.
  과거 응답을 최신으로 덮지 않고 알림 없이 전날까지의 기준을 바꾸지 않는다.
- 취소한 요청은 결과를 화면에 반영하지 않는다. 요청/계산 핸들과 구독을 dispose한다.

## 7. 차트·목표·비교의 사용성

- 첫 화면에서 “예상 매출”, “운영 한도”, “목표 상태”, “입력 근거 수준”을 구분한다.
  미계산/근거 부족은 0동이 아니라 상태 문구다.
- 목표는 항상 해당 월과 완전 월 여부를 표시하고, 미도달일 때 빈 날짜/NaN을 출력하지 않는다.
- 차트 tooltip에는 날짜, 금액, 실적/예측/한도, 부분 기간 여부와 단위를 표시한다.
  화면 밖으로 잘리지 않게 위치를 조절하고 tap/키보드로 닫을 수 있다.
- 같은 결과 snapshot에서 차트·카드·표·export를 만든다. 각 화면에서 별도 반올림 합산 금지.
- 시각 차트만으로 데이터 접근을 끝내지 않는다. 월별 표/목록은 숫자·상태·설명이 동일해야 한다.
- 레스토랑 비교는 현재 조건을 고정 기준으로 두며 변경 필드와 효과를 함께 표시한다.
  최고 증가액만 강조하여 비용·근거 부족·다음 병목 경고를 숨기지 않는다.
- 저장된 운영 프로필 변경과 시험 시나리오 변경은 다른 동작/배지를 사용한다.
  “적용”이 실제 직원 배치나 운영시간 변경으로 읽히지 않도록 “예측에 적용”이라고 쓴다.
- Photo는 현재 기기 조건·회수·한도·목표만 제공한다. 기기 증설 추천을 다른 이름으로 넣지 않는다.

## 8. 접근성 검증 계획

웹은 WCAG 2.2 A/AA 관련 성공기준을 목표로 평가하고, 네이티브는 동등 사용자 여정을
기기 접근성 기능으로 확인한다. 전체 앱의 WCAG 인증을 이 기능 검사만으로 주장하지 않는다.

| 관점 | 주요 기준 | 시험 |
| --- | --- | --- |
| 인지 가능 | 1.1.1, 1.3.1, 1.4.1/3/4/10/11 | 표/차트 대안, 구조, 색 외 구분, 대비, 글자/화면 확대 |
| 조작 가능 | 2.1.1/2, 2.4.3/7/11, 2.5.7/8 | 키보드, focus 순서·가시성, 가림 없음, 드래그 대안, 터치 |
| 이해 가능 | 3.1.1/2, 3.3.1/2/3 | 현재 언어, 라벨, 입력 오류·수정 방법 |
| 견고함 | 4.1.2/3 | 이름·역할·값, 저장/오류/완료 상태 알림 |

- 텍스트 대비는 일반 4.5:1, 큰 글씨 3:1, 의미 있는 비텍스트 UI 3:1을 검사한다.
  테마 토큰을 재사용했다는 이유만으로 통과 처리하지 않는다.
- 제품의 48px 터치 기준과 WCAG의 별도 최소 기준을 혼동하지 않는다.
- Tab/Shift+Tab/Enter/Space/Escape로 전체 여정을 수행한다. modal focus trap과
  닫은 후 원래 버튼 focus 복귀, 스크롤 밖 focus 자동 노출을 확인한다.
- VoiceOver(iOS/macOS), TalkBack(Android), NVDA(Windows 웹)로 매장 선택→기간→
  입력 오류 수정→결과→개선 비교→다운로드를 완료한다. 숫자의 VND/분/팀 단위를 읽는다.
- 언어 변경 후 semantics 언어와 상태 메시지도 갱신한다. 진행 상태를 매 프레임
  낭독하지 않고 필요한 변경만 알린다.
- 자동 Flutter accessibility guideline/Semantics tests, 웹의 노출된 semantics DOM에
  대한 접근성 검사를 병행한다. axe/Lighthouse가 canvas 내부를 검사하지 못한 것을
  “문제 없음”으로 해석하지 않는다.
- 200% 글자, 400% 브라우저 확대, OS 고대비/반전, reduced motion을 수동 확인한다.
- 음성 제어/스위치 제어로 핵심 조작을 확인하고 가능하면 접근성 사용자 테스트를
  실시한다. 참여자 협조는 별도 조율 사항이며 자동 검사로 대체했다고 보고하지 않는다.
- 결과는 기준 ID, 사용자 영향/심각도, 환경, 재현 절차, 수정 및 재검증 증거를 기록한다.
  미확인 장치/사용자 테스트는 미검증으로 남긴다.

## 10. 파일 출력·도움말·운영 인계

- 1차 파일은 예측 전용 XLSX. 기존 실제 매출 파일과 이름·시트·표지를 구분한다.
  PDF 보고서/외부 메시지 전송은 자동으로 추가하지 않는다.
- 파일에 매장, 학습/전망 기간, HCM 시간대, 생성 시각, locale, 프로필/모델 버전,
  단위, 근거 수준, 가정을 기록한다. 숫자 셀은 숫자로 보존한다.
- 긴 이름/시트명 제한/금지문자/중복을 안전하게 처리하고 한국어·베트남어가 깨지지 않게 한다.
  사용자 입력은 수식으로 실행되지 않는 텍스트 셀로 내보낸다.
- 모바일 Safari/Chrome, Android/iOS 앱에서 생성→다운로드/저장 선택→파일 열기를 검증한다.
  파일 생성 완료와 브라우저 전달 요청을 실제 디스크 저장 완료로 잘못 표시하지 않는다.
- 플랫폼별 저장 지원/취소/실패를 adapter로 구분한다. 네이티브 전용 API를 웹에서
  무조건 import하지 않고 기존 core PlatformInfo 경계를 따른다.
- 긴 작업 중 화면 이탈·언어 변경·매장 변경은 snapshot과 권한을 다시 검사한다.
  다운로드 취소/실패 후 메모리·Blob URL 등 임시 자원을 해제한다.
- 세 언어의 인앱 안내: 최초 설정, 데이터 부족 해결, 용량과 수요 차이, 개선액은
  이익이 아니라는 점, Photo 상수, 파일 확인 방법을 제공한다.
- 운영 인계 자료에는 입력 책임자 역할, 측정/확인 방법, 오류별 대응, profile 수정,
  사용자 문의용 비식별 참조 코드, 공개/비활성화/복구 절차를 넣는다.

## 11. 성능·품질 예산

아래는 확인된 성능 수치가 아니라 **구현 시 측정하여 충족할 수용 목표**다.
네트워크/장치/빌드/자료 크기를 고정한 release/profile 실행에서 최소 20회 측정하여
p50/p95를 기록한다. dev build 결과를 운영 성능으로 제시하지 않는다.

참조 fixture: 366일 학습, 24개월 전망, 60테이블/6층, 200메뉴 구성의 집계,
Photo 10기기, 단독 후보 최대 6개·2영역 조합 최대 15개. 특정 실제 매장 기준이 아니다.
초과 데이터는 조용히 삭제하지 않고 명시적 제한/서버 분할 처리로 대응한다.

| 구간 | 목표 |
| --- | --- |
| 누르기/취소/언어 전환의 시각 반응 | p95 100ms 이내 |
| 데이터 대기 | 300ms 넘으면 상태 표시, 10초 넘으면 지연 안내, 30초 timeout 복구 |
| 집계 입력 조회 | 참조망 10Mbps·150ms RTT에서 p95 5초 이내 |
| 기본 예측 로컬 계산 | 참조 중급 모바일에서 p95 2초 이내 |
| 개선 후보 묶음 | p95 10초 이내, 중간 진행·취소 가능 |
| 스크롤/입력 | 주된 60Hz 여정에서 frame p95 약 16.7ms 이내 목표, 장시간 멈춤 없음 |
| 반복 이동/재계산 | 20회 후 이벤트 구독·작업·메모리의 지속 증가 없음 |

- 원본 이벤트 대량 다운로드 대신 서버 집계/페이지 계약을 사용한다.
- 24개월 그래프/표는 필요한 항목만 렌더링하고 raw 수치 정밀도는 유지한다.
- 네이티브는 필요 시 isolate를 사용한다. **Flutter Web의 compute는 메인 스레드에서
  실행되므로 비차단을 보장하지 않는다.** 웹은 계산을 짧은 작업 단위로 나누어 yield와
  취소를 구현하고, 목표 미달이면 worker 또는 서버 계산 경로를 구현·검증한 뒤 공개한다.
- 별도 ML 서버/worker를 처음부터 무조건 도입하지 않는다. 같은 입력/모델의 결과
  동등성을 유지하는 최소 경로를 선택하며 데이터 보안 계약도 동일하게 적용한다.
- 성능 미달을 “기기 문제”로 종료하지 않는다. 지원 환경과 예산을 바꾸려면 이유와
  사용자 영향을 기록하고 명시적으로 승인받는다.

## 13. 출시 게이트와 운영 확인

| 단계 | 책임 역할 | 산출물 / 종료 기준 |
| --- | --- | --- |
| G0 설계 | 제품·개발 | 본 문서와 계산 계약 충돌 0, 공개 범위 확정 |
| G1 기능 | 개발 | 모든 필수 UI/데이터/계산 연결, stub/no-op 없음 |
| G2 품질 | QA·번역 검수·접근성 검토 | 계산+제품 행렬, 세 언어/실기기 증거 |
| G3 운영 수용 | 권한 있는 매장 담당 | 레스토랑·Photo 대조, 입력/오류 대응 가능 |
| G4 배포 전 | 개발·릴리스 담당 | analyze/tests/check_repo, migration/RLS, exact SHA 필수 CI |
| G5 배포 | 승인된 릴리스 담당 | 정식 배포 스크립트·버전·DB 적용 증거 |
| G6 운영 검증 | QA·매장 담당 | 실제 진입/언어/파일 smoke, 관찰 기록·복구 가능 |

- CRITICAL/HIGH와 핵심 여정 차단 MEDIUM은 미해결 0이어야 한다.
  데이터 누출·잘못된 금액·언어 오해·핵심 터치/접근성 실패를 “나중에”로 남기지 않는다.
- 테스트 실패/NOT RUN/BLOCKED를 평균 통과율로 가리지 않는다.
  잔여 비차단 이슈도 영향/담당/기한을 기록하며 검증 완료라고 과장하지 않는다.
- 테스트 전용 환경에서 migration 적용과 이전 앱/새 앱 호환을 검증한다.
  schema 누락/버전 불일치는 번역된 안전 상태로 처리하고 기존 보고서를 깨지 않는다.
- 운영 DB 적용·공개는 별도 승인 후 수행한다. scripts/deploy_pos_production.sh와
  exact pushed SHA의 GitHub Actions 성공이 release gate다.
- 단계적 공개/비활성화 방법을 검증한다. 접근 준비가 안 된 매장은 설정/근거 안내만 표시한다.
- 배포 후 레스토랑/Photo와 모바일/데스크톱에서 smoke를 수행하고 초기 1영업일의
  오류·지연·파일 실패를 확인할 운영 담당/기록을 정한다. 실제 모니터링 예약은 지금 만들지 않는다.
- 실패 시 기능 진입 차단/직전 검증 앱 복귀를 우선한다. 기존 원장과 저장 프로필을
  삭제하지 않고 additive schema를 보존한다.
- 최종 보고서는 “소스 구현 / 테스트 검증 / DB 적용 / 웹 배포 / 네이티브 배포 /
  운영 확인”을 구분한다. 계획 파일이나 화면 캡처만으로 완료 표시하지 않는다.
