# 설계 브리프: 전체 웹 반응형 전환과 비상 디지털 제공 흐름

Date: 2026-08-10
Source: 사용자 요청 및 현재 GLOBOS POS 코드/DB 구조 조사
Status: 계획 전용 — 구현·배포하지 않음

## 목표

1. 관리자 화면에 한정하지 않고 POS의 모든 실제 사용 화면과 오버레이를 모바일에서 정보 손실 없이 사용할 수 있게 한다.
2. 모든 사용자 화면은 하나의 Flutter Web 배포본과 HTTPS URL로 제공한다. Android/iOS 네이티브 앱, 앱스토어 배포, 별도 설치 파일은 만들지 않는다.
3. 운영 화면별 주 장치를 명확히 한다.
   - 주방 조리: 태블릿 우선
   - 트레이: 모바일 우선
   - 층별 주문확인: 모바일 우선
   - 나머지 화면: 모바일·태블릿·데스크톱 반응형
4. 평상시에는 기존 프린터 출력 흐름을 그대로 사용한다.
5. 프린트 스테이션 또는 운영 프린터가 중단됐을 때만 Super Admin이 매장별 비상 디지털 흐름을 활성화한다.
6. 비상 흐름에서는 주방 → 트레이 → 층별 제공 확인을 품목 수량 단위로 추적하고, 미확인 품목은 캐셔에 `미제공`으로 표시한다.
7. 기존 주문·결제·출력·급여·다국어 기능을 훼손하지 않는다.

## 웹 전용 운영 원칙

- QR, 로그인, 관리자, 캐셔, 주방, 트레이, 층별, 고객 결제 표시를 모두 동일한 Flutter Web 서비스의 역할별 URL로 제공한다.
- 태블릿과 휴대폰에는 앱을 설치하지 않고 브라우저로 접속한다.
- iPhone/iPad의 백그라운드 Web Push가 필요할 때만 브라우저의 `홈 화면에 추가`를 사용한다. 이것은 동일 웹 URL의 바로가기/PWA 실행 방식이며 네이티브 앱 배포가 아니다.
- 포그라운드 주문 알람은 브라우저가 자동 음성 재생을 제한하므로 로그인 후 사용자가 `알람 켜기`를 한 번 눌러 Web Audio를 활성화해야 한다.
- 모든 웹 스테이션은 HTTPS, 알림 권한, 자동 잠금 방지 또는 화면 켜짐 운영 설정, 안정적인 Wi-Fi/LTE 연결을 비상 전환 전 점검한다.
- 표준 브라우저가 프린터의 raw TCP 소켓에 직접 연결하는 것은 현재 출력 구조와 호환되지 않으므로, 기존 물리 프린트 에이전트는 백엔드/장치 서비스로 유지한다. 사용자에게 노출되는 설정과 비상 처리 화면만 모두 웹으로 제공한다.

## 반응형 기준

산발적인 `width < ...` 판정을 공통 화면 등급으로 통합한다.

| 등급 | 기준 | 기본 동작 |
|---|---:|---|
| Phone | `< 600dp` | 한 열, 하단/드로어 내비게이션, 표는 정보 유지형 가로 스크롤 |
| Tablet | `600–1199dp` | 1–2열, 주방은 목록+상세 분할, 세로/가로 방향 지원 |
| Desktop | `>= 1200dp` | 기존 다중 열과 고밀도 운영 화면 유지 |

모든 등급에서 100%, 130%, 200% 글자 확대를 검증한다. 정보를 삭제하거나 요약해서 맞추지 않고, 재배치·접기·스크롤로 모두 접근 가능하게 한다. 최소 터치 영역은 48dp로 유지한다.

## 화면 범위

웹 반응형 검증 대상은 라우터에 등록된 전체 화면과 그 화면에서 열리는 모든 다이얼로그/시트다.

- 인증/공개: QR 주문, 로그인, 최초/일반 비밀번호 변경, 개인정보 동의, 온보딩
- 영업: 웨이터, 캐셔, 결제 상세, 고객 결제 표시, 출퇴근 키오스크
- 운영: Print Station 설정, QC 점검/검토, Photo Ops, 매장 설정
- 관리: Super Admin, Admin 10개 탭, 재고 11개 하위 화면, 매출/적색 세금계산서 내보내기
- 전용 장치: 주방 태블릿, 트레이 모바일, 층별 모바일

Print Station의 기존 물리 인쇄 에이전트는 지원 OS 제약을 유지하되, 사용자용 프린터 설정·상태 정보는 Flutter Web에서 모바일 화면으로 제공한다.

## 비상 모드 데이터 모델

기존 `order_items.status`는 주문 수명주기와 결제에 연결돼 있으므로 트레이/층별 확인 값으로 재사용하지 않는다. 다음 additive 모델을 별도로 둔다.

### `emergency_fulfillment_sessions`

- 매장별 비상 세션
- 상태: `active`, `closing`, `closed`
- 사유: 프린트 스테이션 장애, 프린터 장애, 정전, 네트워크 불안정, 기타
- 활성화/종료 Super Admin, 시각, 강제 종료 사유 감사
- 매장별 활성 세션은 최대 1개

### `emergency_station_assignments`

- 고정 Auth 사용자와 매장, 스테이션 종류를 연결
- 종류: `kitchen`, `tray`, `floor`
- `floor`는 저장용 `floor_label`을 필수로 보유
- 같은 ID가 다른 매장이나 다른 층 데이터를 볼 수 없도록 RLS와 RPC에서 재검증

### `emergency_order_queue`

- 비상 세션에 포함된 주문과 세션 내 순차 대기번호
- 원 주문 UUID, 테이블, 층, 주문 시각을 보존
- 활성화 시점의 미결제/비취소 주문을 포함하고, 활성화 이후 주문·추가 주문도 자동 편입

### `emergency_fulfillment_items`

- `order_item_id`별 주문 수량과 단계별 처리 수량
- `kitchen_done_qty`
- `tray_received_qty`
- `tray_dispatched_qty`
- `floor_served_qty`
- 항상 다음 제약을 만족한다.

```text
0 <= floor_served
  <= tray_dispatched
  <= tray_received
  <= kitchen_done
  <= ordered_qty
```

### `emergency_fulfillment_events`

- 모든 클릭을 append-only 감사 이벤트로 기록
- 단계, 수량 변화, 담당 계정, 장치, 시각, 멱등성 키 저장
- 현재 수량 변경과 이벤트 기록은 단일 RPC 트랜잭션으로 처리
- 중복 탭/재전송은 동일 멱등성 키로 한 번만 반영

## 비상 활성화와 출력 관계

- 기본값은 항상 `printed` 모드다.
- Super Admin만 특정 매장을 `digital_emergency`로 전환할 수 있다.
- 활성화 확인창에서 매장, 장애 사유, 포함될 열린 주문 수와 미처리 품목 수를 보여준다.
- 활성화 순간의 기존 열린 주문은 모두 안전하게 미확인 상태로 편입한다. 이미 종이로 제공됐는지 자동 추측하지 않는다.
- 비상 모드 중 생성되는 주방/트레이/층별 출력 작업은 감사 원장을 유지하되 프린트 에이전트가 claim하지 못하도록 보류한다. 영수증 출력은 별도 목적이므로 기존 동작을 유지한다.
- 종료 시 디지털 완료된 운영 출력은 `비상 처리로 대체`로 감사 종료하고, 미완료 작업은 Super Admin이 재출력 또는 감사 종료 중 하나를 명시적으로 선택한다. 오래된 티켓이 자동 출력되면 안 된다.
- 미제공 주문이 남아 있으면 일반 종료를 막고, 강제 종료는 사유 입력과 감사 로그를 필수로 한다.

## 스테이션별 흐름

### 주방 — 태블릿

- 비상 모드가 아니면 기존처럼 프린터 사용 안내/대기 상태만 표시한다.
- 비상 모드면 왼쪽에 순차 대기번호 목록, 오른쪽에 선택 주문의 메뉴를 표시한다.
- 대기번호는 세션 내 순차 번호이며 원 티켓 코드와 테이블도 함께 표시한다.
- 주문을 선택해야 메뉴 상세가 열린다.
- 메뉴는 수량별 `완료 수량 / 주문 수량`을 보여주고, 한 개씩 체크한다.
- 모든 비취소 품목이 완료돼야 주문을 `조리 완료`로 표시한다.
- 트레이가 이미 수령한 수량은 주방에서 일반 취소할 수 없고 권한 있는 정정 절차를 거친다.

### 트레이 — 모바일

- 조리 완료 수량이 생긴 순서대로 카드가 나타난다.
- 첫 번째 동작은 `주방에서 수령`, 두 번째 동작은 `층으로 발송`이다.
- 테이블, 표시용 층명, 주문 대기번호, 추가 주문 배치를 함께 보여준다.
- 수량 단위로 처리하며, 이전 단계보다 많은 수량을 처리할 수 없다.
- `층으로 발송`이 완료된 수량부터 해당 층 화면에서 도착 대기 상태로 활성화된다.

### 층별 — 모바일

- 계정에 배정된 한 층의 주문만 볼 수 있다.
- 주문 카드에는 전체 비취소 품목을 모두 표시한다.
- 아직 주방/트레이 단계인 품목도 숨기지 않고 현재 위치를 표시한다.
- 트레이에서 발송된 수량만 `테이블 제공 완료`로 체크할 수 있다.
- 주문의 모든 수량이 체크되어야 층별 주문확인서가 완료된다.

### 캐셔

- 비상 세션에 포함된 주문에서 `floor_served_qty < ordered_qty`인 수량을 실시간 계산한다.
- 주문 목록, 주문 상세, 결제 확인창에 빨간 `미제공 N` 배지를 표시한다.
- 어떤 메뉴가 몇 개 미제공인지 현재 선택 언어로 표시한다.
- 이번 범위에서는 경고만 하고 결제를 차단하지 않는다. 결제 차단은 영업 정책 확인 없이 추가하지 않는다.
- 비상 모드가 아니거나 해당 주문이 비상 세션에 포함되지 않았다면 기존 화면과 결제 로직은 그대로다.

## 태블릿·모바일 주문 알람

비상 모드가 활성화된 스테이션 장치에는 단계별 신규 작업이 들어오는 즉시 알람을 준다.

| 대상 장치 | 알람 발생 조건 |
|---|---|
| 주방 태블릿 | 신규 주문 또는 기존 주문의 추가 메뉴가 비상 대기열에 편입됨 |
| 트레이 모바일 | 주방 완료 수량이 새로 생김 |
| 층별 모바일 | 트레이가 해당 층으로 발송한 수량이 새로 생김 |

- 웹 화면이 열려 있으면 Supabase Realtime 이벤트를 기준으로 Web Audio 알림음, 지원 브라우저의 진동, 화면 점멸과 미확인 배지를 동시에 표시한다.
- 탭이 백그라운드이거나 브라우저가 닫혀 있으면 `firebase-messaging-sw.js` Service Worker와 FCM Web Push/Notifications API를 사용한다.
- Realtime, Push, 폴링이 같은 작업을 전달할 수 있으므로 `event_id`를 기준으로 장치에서 중복 알람을 제거한다.
- 알람을 눌렀을 때 해당 주문/품목 상세로 바로 이동하며, 단순히 알림을 닫아도 미확인 작업 배지는 작업 처리 전까지 유지한다.
- 로그인 또는 장치 배정 시 사용자가 `알람 켜기`를 눌러 알림 권한, Web Audio, Push token을 등록하고, 각 스테이션 대기 화면에 `알람 테스트` 기능을 둔다.
- 알림 권한 거부, Push 미등록, 소리 잠금, Service Worker 미등록 상태를 장치 상태와 Super Admin 비상 모니터에 명확하게 경고한다.
- Android 태블릿/모바일은 최신 Chrome/Edge, iPhone/iPad는 최신 Safari를 기준 브라우저로 정한다. iPhone/iPad 잠금 화면 Push는 웹사이트를 홈 화면에 추가하고 사용자 동작으로 알림 권한을 허용한 경우에만 지원한다.
- 브라우저나 OS가 진동 또는 알림 소리를 제한하는 경우 화면 점멸·전체 화면 배너·시스템 알림을 대체 경로로 사용하며, 웹에서 지원되지 않는 기능을 보장한다고 표시하지 않는다.
- 비상 모드가 OFF면 이 주문 단계 알람은 전송하지 않는다.

## 계정 배정안 — BunsikClub Binh Thanh

기존 계정은 용도를 바꾸지 않는다. `bt_tab1`을 트레이로 재사용하면 현재 캐셔 태블릿 기능이 깨질 수 있으므로 새 계정을 추가한다.

| 계정 | 배정 화면 | 비고 |
|---|---|---|
| `bt_kit1@globos.world` | 주방 태블릿 | 기존 주방 계정 재사용 |
| `bt_tray1@globos.world` | 트레이 모바일 | 신규 |
| `bt_floor_1f@globos.world` | 1F | 신규 |
| `bt_floor_2f@globos.world` | 2F | 신규 |

BunsikClub Binh Thanh에는 G층이 없으므로 G층 화면·계정·라우팅을 만들지 않는다. 현재 DB의 legacy 저장층과 실제 운영층 표시가 다르면 구현 전 preflight에서 테이블과 프린터 목적지를 함께 확인하고 1F/2F 계약으로 정렬한다. 화면 코드에서 G층 변환을 하드코딩하지 않는다.

다른 매장은 매장 short code와 실제 층 설정으로 같은 템플릿을 생성한다. 하드코딩된 층 수를 사용하지 않는다.

## 네트워크/정전 한계와 대응

- 여러 장치의 실시간 단계 공유에는 Supabase에 도달할 수 있는 인터넷 경로가 필요하다.
- 정전 시 태블릿/휴대폰과 LTE 또는 배터리 백업 공유기를 운영 전제로 한다.
- 각 브라우저는 마지막 티켓 스냅샷을 IndexedDB에 캐시하고, 클릭은 웹 outbox에 멱등성 키와 함께 보관해 재연결 시 전송한다.
- 서버 확인 전 단계는 `동기화 대기`로 표시한다. 하위 스테이션은 서버가 확인하지 않은 상위 단계 수량을 처리할 수 없다.
- 완전한 인터넷 단절 상태에서 장치 간 실시간 공유가 된다고 주장하지 않는다. 이 경우 종이 수기 체크 절차가 최종 백업이다.
- Realtime과 Push도 인터넷이 끊기면 새 주문을 전달할 수 없으므로, LTE/백업 공유기 연결과 스테이션별 `알람 테스트` 성공을 비상 전환 체크리스트에 포함한다.

## 웹 알람 공식 제약 근거

- Firebase Web Messaging은 포그라운드 `onMessage`와 Service Worker의 백그라운드 메시지 처리를 분리한다: <https://firebase.google.com/docs/cloud-messaging/web/receive-messages>
- FCM Web Push는 알림 권한과 `firebase-messaging-sw.js` 등록이 필요하다: <https://firebase.google.com/docs/cloud-messaging/web/get-started>
- 브라우저는 Web Audio 자동 재생을 사용자 동작 전까지 차단할 수 있다: <https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay>
- iPhone/iPad Web Push는 홈 화면에 추가된 웹사이트에서 사용자 동작으로 권한을 요청하는 방식이다: <https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/>

- 전체 `scripts/check_repo.sh` 및 로컬 릴리스 빌드가 통과한 뒤에도 별도 승인 없이는 배포하지 않는다.
