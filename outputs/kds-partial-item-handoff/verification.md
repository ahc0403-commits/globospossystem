# 트레이·층 개별 메뉴 전달 수정 및 검증

작성일: 2026-10-22 (베트남)

메뉴별 ✓ 버튼이 있는 주문 상세 화면을 수정했다. 실제 부분 전달을 거부하던 수량 검증을 바로잡고, 현재 준비된 수량을 모두 처리하면 주문 목록으로 돌아가도록 했다. 아직 준비되지 않은 나머지는 주문에 남는다. +/− 메뉴 모음 화면의 그룹 구분 문제는 이번 변경에 포함하지 않았다.

## 구현

- 새 마이그레이션 `20261022210000_kds_partial_item_handoff.sql`에서 개별 RPC의 `완료 = 시작` 조건을 `완료 ≤ 시작 ≤ 유효 주문 수량` 조건으로 바꾼다. 층/매장 권한, 이전 단계 상한, 역방향 취소 제약과 이벤트 ID 중복 방지를 유지한다.
- 준비된 음식 전체 서빙은 행·수량별 중첩 호출 대신 기존 집합 처리 커널을 한 번 호출한다. 최대 1,000행·총 1,000개를 유지하고, 준비 lot 잔량도 선택 항목을 묶어 집계한다. 직접 서빙 음료는 기존 개별 처리 경로를 유지한다.
- 개별 명령 결과를 서버 확정·오프라인 대기·거절로 구분한다. 서버 응답 전에는 수량이나 화면을 완료로 바꾸지 않는다. 실패 시 과거 전체 상태로 되돌리지 않아 요청 중 들어온 실시간 변경을 보존한다.
- 한 메뉴의 연속 중복 명령은 차단한다. 오프라인 작업은 동일 이벤트 ID와 매장·주문 범위로 저장하고 해당 주문을 전송 대기로 표시한다.
- 트레이 ✓는 실제 조리 완료 수량까지, 층 ✓는 실제 전달받은 수량까지 활성화한다. 취소된 수량을 직접 서빙 음료의 상한에도 반영한다.
- 남은 준비 메뉴가 있으면 상세 화면을 유지하고 처리한 메뉴를 아래로 이동한다. 준비분을 모두 전달하면 목록으로 돌아간다. 재연결 후 대기 작업이 확정될 때도 같은 규칙을 적용한다.
- 전체 전달 후에는 해당 주문 한 건만 확인한다. 읽기 실패를 이미 확정된 쓰기의 실패로 취급해 재전송하지 않는다. 같은 주문의 진행 중 조회는 공유한다.

## 검증

- 마지막 관련 Flutter 검사: **94개 통과**. 부분 전달, 메뉴 정렬, 버튼 상한, 서버 확정 전 화면 유지, 실패·오프라인 대기·재연결 후 화면 이동을 포함한다.
- HTTP 모의 전송으로 개별 전달은 쓰기 RPC 1회, 전체 전달은 쓰기 1회와 해당 주문 읽기 1회를 확인했다. 실시간 변경이 응답보다 앞서면 해당 주문을 다시 확인한다. 이 수치는 운영 네트워크 측정값이 아니다.
- 격리 SQL 검사: 수정 전 실패 재현, 부분 층/트레이 전달, 중복 이벤트, 과다 전달 방지, 메뉴별 취소, 콤보·부모 수량, 전가복 조리 시작/전달 분리, 공용 층 배정·타 매장 차단, 배달·검토 항목 제외, 준비 lot 누락 시 원자적 실패, 수량 상한을 확인했다.
- 2개·20개 동시 클라이언트의 동일 요청은 각 1회만 반영되고, 서로 다른 개별 요청은 손실 없이 누적됐다. 롤백 후 기존 실패가 재현되었으며 재적용 후 사후 검증이 통과했다.
- 최근 완료 내역에서 메뉴별 취소를 실행하면 실제 수량을 반영하고 진행 목록으로 복귀하는 것을 확인했다.
- `dart analyze --fatal-infos`: 통과.
- 최종 전체 Flutter 재검사: **2,518개 통과, 97개 기존 조건에 따라 건너뜀**.
- `bash scripts/check_repo.sh`: **종료 코드 0**. 전체 정적 분석·Flutter 테스트·SQL/동시성 검사·배포 계약 검사·보안 검사·웹 릴리스 빌드·공백 검사까지 통과했다. 최신 소스의 추가 확인은 위 전체 Flutter 재검사와 관련 94개 검사에 포함된다.
- 웹 릴리스 빌드: **성공**, `build/web` 생성. 운영 배포·운영 DB 마이그레이션 적용은 실행하지 않았다.

SQL 테스트는 외부 네트워크가 없는 Docker의 PostgreSQL 15와 합성 데이터에서 실제 저장소 마이그레이션의 진행 함수들을 추출해 실행한다. 운영의 모든 트리거나 실제 단말·네트워크를 재현한 검사는 아니다. 운영 DB·재고·결제·배포는 변경하지 않았다.
