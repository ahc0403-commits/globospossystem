# 메뉴 언어 매칭 재발 방지 계획

> 범위 갱신: 이 문서는 [전체 POS 화면 개선 계획](app_language_quality_plan_20260915.md)의
> 업무 데이터 트랙 상세다. 전체 작업의 범위와 완료 기준은 상위 계획을 따른다.
> 메뉴 트랙만 통과해도 전체 개선 완료로 선언할 수 없다.

작성일: 2026-09-15
기준 구현: PR #489 / `5c513b535dd9afe0f3c8e9c3f8bd3a8d6ca307e0`
상태: 공통 매칭·전 표시 경계·SQL 회귀 차단 구현 완료. 운영 배포 및 대조 대기.

### 구현 기록

- `MenuNames`와 `MenuNameResolution`이 선택 언어 필드의 정확한 일치, 전체 번역
  미등록 legacy 원본, 일부 번역 누락을 서로 다른 상태로 반환한다.
- 주문·주방·계산대·테이블·QR·Direct Order·비상 운영·프로모션·분석 모델은
  세 등록 필드를 보존하고 공통 resolver를 사용한다.
- 메뉴/카테고리 편집 화면은 비어 있는 EN/VI 입력칸을 한국어로 미리 채우지 않는다.
- DB 읽기 함수와 종이 없는 운영 분석 래퍼는 누락된 선택 언어를 다른 언어로
  채우지 않는다. 실제 PostgreSQL fixture가 필드 교환, 묶음 직원식, 검색,
  과거 원본 보존과 부분 번역 누락을 검사한다.
- 정적 계약은 `fallbackKeys`, 가짜 `메뉴`/`Món`/`Item` 등록값, `name_ko`가 빠진
  중첩 조회가 다시 들어오면 필수 테스트를 실패시킨다.

## 1. 목표와 완료 판단

이미 등록된 3개 메뉴명을 선택 언어에 정확하게 연결한다.

| 선택 언어 | 사용할 등록 필드 |
| --- | --- |
| 한국어 | `name_ko` |
| 영어 | `name_en` |
| 베트남어 | `name_vi` |

정상 데이터의 기본 규칙은 `표시값 = 해당 메뉴의 선택 언어 필드값`이다.
각 필드는 저장 계약에서 정한 공백 정리만 허용한다. 기본 `name`을
한국어 필드로 추정하거나, 다른 언어로 조용히 대체해 성공으로 취급하지 않는다.
콤보·직원식처럼 여러 품목을 묶을 때는 각 품목의 언어를 먼저 선택한 뒤
표시용 문자열을 조합한다. 메뉴 ID, 순서, 수량, 금액은 언어 전환과 무관하다.

완료는 **구현 + 전 표시 지점 검증 + 오류 주입 검증 + 정확한 배포 버전의
운영 확인**을 모두 충족했을 때만 선언한다. 단순 테스트 개수나 ARB 검사로
메뉴 매칭의 완료를 대신하지 않는다.

## 2. 구현 전 위험과 적용 결과

기존 수정은 스크린샷의 조회/표시 누락을 해결한 기반으로 사용한다.
다음은 현재 소스에서 확인한 구조와 추가 검증이 필요한 위험이다.

| 구분 | 구현 전 근거 | 적용 결과 |
| --- | --- | --- |
| 확인 | 공통 `menu_localization.dart`가 문자열 키를 가진 Map을 받고, 선택 필드가 비면 `name`/`display_name`/`label`로 대체한다. | 정형 모델과 명시적인 누락 결과를 도입한다. |
| 확인 | Order, Kitchen, Payment, QR, Direct Order, Table Preview 등에 별도 `localizedName`/fallback 구현이 존재한다. | 기존 `AppLanguage`와 하나의 매칭 규칙으로 통합한다. |
| 확인 | `OrderItem`과 `KitchenItem`은 일부 경로에서 기본 `name`을 `nameKo`에 넣는다. | 원본값과 `name_ko`를 구분하고 필드별 대응을 검증한다. |
| 확인 | 일부 메뉴 편집 폼은 누락된 EN/VI 초기값에 한국어 원문을 넣는다. | 실제 등록값을 편집하고, 다른 언어 복사로 누락을 숨기지 않도록 한다. |
| 확인 | 새 BM/분석/영수증 조회는 현재 메뉴 카탈로그를 조인한다. | 현재 카탈로그 이름과 주문 당시 이름의 출처를 구분한다. |
| 확인 | 콤보와 Direct Order에는 이미 다국어 스냅샷 경로가 있다. | 기존 스냅샷을 재사용하고, 일반 주문의 부족한 경로를 보완한다. |
| 확인 | LocaleController는 저장값 복원과 선택 저장이 비동기이며, 기존 코드에 작업 순서 보호가 없었다. | 선택 저장 직렬화와 revision guard를 적용하고 빠른 전환·늦은 복원·저장 실패 테스트를 추가했다. |
| 확인 | 18개 경로 테스트는 대표 라벨·배치 검증이며 모든 펼침 상세의 메뉴값까지 보장하지 않는다. | 메뉴 표시 지점을 기준으로 커버리지를 다시 산정한다. |

## 3. 고정할 설계 규칙

### 3.1 언어 선택의 기준

- 직원용 POS 화면은 기존 `localeControllerProvider`의 선택값을 따른다.
- 고객이 직접 언어를 선택하는 QR/Direct Order 화면은 해당 고객 화면의
  선택값을 따른다. 직원 단말의 언어가 고객 언어를 덮어쓰지 않는다.
- 고객 디스플레이, 종이/디지털 영수증, 주방의 짧은 베트남어 이름 등
  고정 언어 정책은 현재 구현과 운영 요구를 대조해 각각 등록한다.
  고정값이 있다는 이유만으로 모두 정상 예외로 승인하지 않는다.
- 모든 표시 지점에는 언어 선택의 기준이 하나만 있어야 한다.
- `en-US`, `en_US`, `vi-VN` 등 입력 형식은 기존 `AppLanguage` 경계에서
  한 번 정규화한다. 알 수 없는 코드와 첫 실행 기본값도 같은 정책을 쓴다.

### 3.2 메뉴 데이터와 표시

- 기존 DB의 `name_ko`, `name_en`, `name_vi`를 유지한다.
- 경계에서 JSON을 `MenuNames` 같은 정형 값 객체로 변환한다. 내부에서는
  `AppLanguage`로 이름을 선택하며, 화면별 문자열 키 조합과 별도 switch를 제거한다.
- 원본 이력명은 별도 값으로 보관한다. 일반 메뉴 표시 코드가 원본 문자열을
  바로 쓰는 경로는 제거한다. 편집 폼·원본 이력 열람은 명시적인 예외로 둔다.
- 공통 메뉴 표시 위젯은 현재 화면의 언어를 읽는다. 툴팁·접근성 이름·차트·
  검색 결과와 내보내기도 같은 이름 선택 함수를 사용한다.
- 화면의 번역된 문자열을 캐시하지 않는다. 언어별 필드와 안정적인 메뉴 ID를
  캐시한다. 언어 변경은 매장·메뉴 재조회 없이 현재 데이터로 다시 그린다.
- 고객 영수증 같은 고정 언어 출력은 명시적인 출력 정책을 인자로 전달한다.
  내보내기 시작 시 언어를 확정해 한 파일 내부에서 언어가 섞이지 않게 한다.

### 3.3 누락과 과거 데이터

| 데이터 상태 | 처리 원칙 |
| --- | --- |
| 등록된 현재 메뉴, 정상 응답 | 선택한 필드만 사용한다. |
| 현재 메뉴의 선택 필드가 응답에서 누락 | 계약 위반으로 기록한다. 테스트/배포 검증은 실패한다. 운영에서는 원본명과 선택 언어로 된 누락 안내를 함께 제공해 품목 식별을 유지한다. 정상 매칭으로 집계하지 않는다. |
| 주문 당시 다국어 스냅샷 있음 | 이력 상세에서 해당 스냅샷의 선택 필드를 사용한다. |
| 과거 스냅샷은 없고 동일한 매장·메뉴 ID의 현재 번역은 있음 | 현재 등록명을 참고한 복원값임을 구분한다. 당시 번역이었다고 기록하지 않는다. |
| 메뉴 삭제·스냅샷 없음 | 원본 이력과 메뉴 식별자를 보존하고 누락을 표시한다. 이력을 지우거나 임의 번역으로 채우지 않는다. |

언어 데이터 이상 때문에 이미 진행 중인 주문·결제·주방 처리를 중단시키지 않는다.
대신 정상 데이터의 누락은 배포 전에 차단하고, 예상하지 못한 운영 누락은
감지 가능한 상태로 유지한다.

## 4. 실행 순서와 단계별 통과 기준

### 단계 0 — 표시 지점과 데이터 경로 전수 목록

메뉴를 표시하는 각 지점에 다음 정보를 연결한다.

`화면/팝업/출력 → 위젯 → 모델 → API/RPC/캐시 → DB 또는 스냅샷 → 언어 기준 → 테스트`

범위:

1. 메뉴·카테고리 목록, 검색, 관리, 수정/삭제 확인, 품절 관리.
2. 테이블 미리보기, 주문 선택, 장바구니, 주문 검토, 직원식 선택.
3. 주방, 콤보 구성품, 음료 선택, 추가 주문, 배달 주문.
4. 계산대 주문 상세, 할인 대상 선택, 결제 완료, 취소/복원.
5. BM 서비스·취소·직원식 목록, 상세, 원주문 상세.
6. 레시피·재고 메뉴 선택, 판매 순위·차트·툴팁.
7. 영수증 원장, 고객 화면, QR 주문, 종이/디지털 영수증, Excel/PDF.
8. 관련 펼침 상세, 빈 상태, 누락 상태, 접근성 이름.

메뉴가 없는 화면은 근거와 함께 해당 없음으로 기록한다. 화면 파일 수를
표시 지점 수로 간주하지 않는다. 초기 42개 화면/탭 목록에서 발견한 위젯과
출력 경로를 추가한다.

**통과 기준:** 모든 발견된 표시 지점에 언어 기준·데이터 출처·행동 테스트가
연결되어 있고, 설명되지 않은 직접 원본명 표시가 0건이다.

### 단계 1 — 공통 모델과 매칭 규칙

- 기존 `AppLanguage`를 재사용하고 이름 선택을 한 경로로 통일한다.
- `MenuNames`와 이름 선택 결과에 정상/과거 복원/누락 상태를 표현한다.
- CartItem, OrderItem, KitchenItem, Payment, QR, Direct Order,
  Table Preview, BM, Analytics, Receipt Ledger, Recipe 경계를 전환한다.
- JSON 필드명 차이는 각 API 변환기에서 처리한다. 서로 다른 API를
  추측하는 만능 Map fallback으로 흡수하지 않는다.
- 원본 문자열은 이력 보존과 호환성 용도로 남기되 일반 표시에서 직접
  참조하지 않도록 타입·정적 검사로 제한한다.

**통과 기준:** `name`, `name_ko`, `name_en`, `name_vi`를 모두 다른 값으로
만든 데이터에서 세 언어 매칭이 정확하고, 복사·직렬화·복원으로 값이 유실되지 않는다.

### 단계 2 — 등록부터 조회까지 계약 보장

- 생성·수정·매장 복사·Excel 업로드가 이미 등록하는 세 필드를 정확하게
  전달하는지 검증한다. 기존 서버 필수 입력 검증은 재사용한다.
- 편집 초기값이 타 언어 원문으로 자동 채워져 다시 저장되는 경로를 제거한다.
- 발견된 모든 RPC와 직접 SELECT, 중첩 콤보 JSON, 검색 결과, 페이지네이션,
  실시간 갱신, 로컬 저장/복원에 세 필드가 보존되는지 검사한다.
- 메뉴 ID와 매장 ID로 결합한다. 표시 이름을 조인 키로 사용하지 않는다.
- 묶음 이력은 품목 배열로 전달한다. 서버에서 원문 이름을 하나로 합쳐
  언어별 값을 잃는 경로를 허용하지 않는다.
- 새 필드를 허용하지 않는 엄격한 기존 클라이언트도 고려한다. 호환 테스트를
  먼저 수행하고, 필요한 경로에만 버전 분리 또는 순차 배포를 적용한다.

**통과 기준:** 실제 SQL/API 응답과 앱 변환기를 연결한 테스트에서 필드 누락·
뒤바뀜·다른 매장 조인·다음 페이지 누락이 모두 검출된다.

### 단계 3 — 과거 주문의 메뉴명 보존

- 기존 일반 주문·콤보·QR·Direct Order의 이름 저장 방식을 대조한다.
- 새 주문은 주문 당시 세 언어 메뉴명을 보존한다. 이미 있는 스냅샷은
  재사용하고 부족한 일반 주문 경로에만 추가한다.
- 메뉴명 수정·메뉴 삭제 후에도 이력 상세의 당시 메뉴명은 바뀌지 않도록 한다.
- 기간별 판매 집계는 안정적인 메뉴 ID를 유지한다. 여러 시점의 이름이
  포함된 집계에는 대표 이름의 출처와 이름 변경 여부를 명시한다.
- 기존 이력에 현재 이름을 넣고 과거의 확정값으로 취급하는 일괄 보정은 하지 않는다.
- 원본명·수량·가격·상태·매출 집계와 결제의 원자적 처리 계약을 보존한다.

**통과 기준:** 주문 생성 → 세 언어 확인 → 메뉴명 변경/삭제 → 이력 재조회
시나리오에서 당시 이름과 금액이 유지된다. 과거 누락 자료의 처리도 별도로 통과한다.

### 단계 4 — 언어 전환과 비동기 상태

- 앱 시작 시 저장된 언어 복원과 첫 메뉴 표시의 순서를 명확히 한다.
- 빠른 선택 변경 중 마지막 선택이 화면과 저장값에 남도록 한다.
- 팝업·바텀시트·선택된 주문·장바구니·검색 결과가 열린 상태로 다시 그려지게 한다.
- 이전 언어에서 만들어진 문자열이나 늦게 끝난 요청이 현재 표시를 덮어쓰지 않게 한다.
- 실시간 상태 패치는 기존 세 언어 이름을 보존한다. 새 품목에 이름 정보가
  없으면 정해진 상세 조회 경로로 보완한다.
- 캐시는 매장·데이터 계약 버전으로 분리하고, 구버전 자료 복원 시 누락을 판별한다.
  대기 중인 주문을 캐시 정리 과정에서 버리지 않는다.
- 고객용 독립 화면과 직원 화면의 언어 선택이 서로 영향을 주지 않는지 확인한다.

**통과 기준:** 초기 복원 지연, 저장 실패, 응답 순서 역전, 연속 언어 변경,
매장 전환, 오프라인 복원, 재접속 후에도 최신 선택과 데이터가 일치한다.

### 단계 5 — 전 표시 지점 적용과 행동 검증

단계 0의 목록을 기준으로 적용하고, 표시 지점별로 정상·세부 펼침·누락 상태를
검증한다. 기존 18개 대표 경로와 5개 팝업 검사는 배치 검증으로 유지하고
실제 메뉴값 검증을 추가한다.

| 축 | 필수 사례 |
| --- | --- |
| 이름 데이터 | 일반 메뉴, 카테고리, 콤보, 선택 음료, 긴 이름, 기호, 언어별 동일 이름, 누락·공백, 삭제·이름 변경, 서비스성 항목 |
| 언어 | KO/EN/VI 초기 표시, 서로 다른 언어 간 6개 방향의 전환, 연속 전환 |
| 화면 상태 | 목록·검색·필터·정렬·선택 항목·장바구니·상세·원주문·차트·내보내기 |
| 비동기 | 최초 로드·재시작·캐시 복원·실시간 패치·요청 역전·매장 전환·오프라인/재접속 |
| 크기 | 휴대폰·태블릿·데스크톱, 기본/200% 글자 크기 |
| 불변값 | 메뉴 ID, 품목 순서, 수량, 가격, 할인, 결제 합계, 매출 집계, 주문 상태 |

각 메뉴 표시 지점은 실제 표시값을 기대 필드와 비교한다. 브랜드명·메모처럼
자유 입력된 한글이나 세 언어에서 동일한 메뉴명은 오류로 판단하지 않는다.
한글 문자 포함 여부만 검사해서 통과시키지 않는다.

DB 검증은 운영 DB 버전을 확인한 뒤 그 버전의 격리 환경에서 수행한다.
전용 fixture의 간소화된 권한 helper 테스트 외에 실제 접근 제어 함수·역할·
매장 범위를 포함한 통합 검증을 추가한다. 운영 검증 데이터는 읽기 전용으로 조회한다.

**통과 기준:** 목록의 모든 메뉴 표시 지점이 정확한 이름 비교를 통과하고,
기존 주문/결제/주방 동작에 회귀가 없다. 적용 가능한 필수 사례의 skip은 0건이다.

### 단계 6 — 같은 실수를 CI에서 차단

1. 메뉴 표시 경계의 원본 `name`/`label` 직접 사용과 별도 언어 switch를
   탐지하는 타입 기반 정적 검사를 추가한다. 예외는 근거·해당 테스트가 필요하다.
2. 메뉴 데이터를 반환하는 API와 표시 지점 목록의 변경을 CI에서 검토 대상으로
   감지한다. 새 화면이 기존 테스트 목록 밖에 있다는 이유로 통과하지 못하게 한다.
3. 실제 행동 테스트와 SQL/API 계약 검증을 필수 체크에 연결한다.
4. 다음 오류를 의도적으로 넣었을 때 관련 테스트가 반드시 실패하는지 검증한다.
   - 응답에서 `name_en` 제거.
   - `name_en`과 `name_vi` 매핑 교환.
   - 표시 코드가 기본 `name` 직접 사용.
   - `copyWith`/직렬화/캐시 복원에서 한 언어 유실.
   - 묶음 직원식 이름을 원문 문자열로 미리 합침.
   - 열린 팝업이 이전 언어 문자열을 유지.
   - 다른 매장 메뉴의 번역을 결합.
   - 늦은 응답/언어 저장이 최신 선택을 덮어씀.
5. 파일 해시나 소스 문자열 존재 여부는 보조 검사로만 사용한다.
   동작 검증 없이 해시만 갱신한 결과를 재발 방지 증거로 인정하지 않는다.

**통과 기준:** 알려진 오류 주입 사례 전부를 잡고, 새 표시 지점 누락과
설명되지 않은 우회 코드가 있으면 필수 체크가 실패한다.

### 단계 7 — 배포와 운영 검증

- PR #489의 기존 수정과 새 개선을 의존 관계에 맞춰 검토한다.
  기반 수정의 통과를 전체 개선 완료로 간주하지 않는다.
- DB 변경은 확장 방식으로 적용하고 preflight·검증·rollback을 준비한다.
  구 앱/신 DB와 새 앱/준비되지 않은 DB의 호환 동작을 테스트한다.
- 정확한 최종 커밋에서 필수 GitHub 체크 통과 후 저장소의
  `scripts/deploy_pos_production.sh` 경로로 배포한다.
- 웹 번들, 캐시된 기존 앱, 적용된 DB 함수/마이그레이션 버전을 함께 확인한다.
- 운영의 기존 주문을 읽기 전용으로 열고 실제 저장된 KO/EN/VI 필드와
  스크린샷에 해당하는 직원식 상세·원주문 표시값을 대조한다.
- 계약 누락 진단은 화면/조회 경로/매장·메뉴 ID/선택 언어/데이터 출처/앱 버전으로
  식별한다. 주문 메모·개인정보·전체 응답을 기록하지 않는다.
  같은 누락의 반복 렌더링은 중복 집계하지 않는다.
- 정상 활성 메뉴의 누락은 0건이어야 한다. 분류된 과거 누락을 제외한
  새 누락이 발견되면 완료 상태를 보류하고 원인을 수정한다.

**통과 기준:** 소스 구현, DB 적용, 웹 배포, 운영 표시 검증의 네 상태에
각각 증거가 있고, 운영의 정확한 언어 매칭을 확인한다.
