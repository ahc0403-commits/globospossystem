## 구현 계약

- 새 마이그레이션: `20261023120000_direct_order_address_and_proof_replacement.sql`, `20261023121000_direct_order_chat_updates_and_note_audience.sql`. 과거 마이그레이션과 결제 핵심 함수는 수정하지 않았다. 검증한 수정 파일 해시는 `source-sha256.txt`에 기록했다.
- 증빙 v3는 서비스 역할 전용 RPC다. 파일 검증 전에 소유권을 확인하고, 검증 전용 호출은 파일·메시지·결제에 쓰지 않는다. 이미 commit된 불변 경로는 Storage 장애나 승인 후에도 원래 결과를 복구한다. 실제 commit 직전에 최신 견적·사진·직원 재제출 요청을 다시 검사한다.
- 네트워크 제한: URL 발급 15초, 파일 전송 60초, commit 20초, 상태/채팅 읽기 10초, 사진 시도 전체 120초. Future timeout은 원래 HTTP 요청 취소를 뜻하지 않는다. 늦은 응답은 화면 세대 검사와 서버 멱등성으로 처리한다. 쓰기 자동 반복 재시도는 추가하지 않았다.
- 고객 변경 번호 확인은 한 번에 하나만 실행하고 실패 시 4/8/16/최대 30초로 대기한다. 기존 15초(+분산) 주문 안전 조회도 유지한다. 즉시 WebSocket 전달을 보장하는 방식은 아니다. 화면이 열린 정상 연결에서 메시지 지연은 폴링 간격과 네트워크 응답 시간의 합이다.
- IP 공용망 제한은 빈번한 읽기에서 1,000회/10초, 고객 범위는 60회/분이다. 변경 번호는 인증된 세션·주문별로, 상태/목록은 자격 증명의 HMAC별로 나눈다. 비밀과 IP 원문은 제한 키에 저장하지 않는다. Edge의 IP 제한 RPC, 상태/목록의 자격 제한 RPC는 데이터 RPC와 별도 고정 호출이다.
- 기존 전체 주문 메모의 `both`는 관리자 전용으로 바꾸면서 버전을 증가시켜 이전 화면의 저장을 충돌로 처리한다. 명시적인 `preparation`/`delivery`와 모든 음식 항목 메모는 유지한다. 예전 전체 주문 `both`에 조리 지시를 적은 경우 관리자가 대상을 주방으로 다시 선택할 수 있다. 내용 키워드로 자동 분류하지 않는다. 이미 발행한 출력물은 변경하지 않는다.

## 데이터 접근과 측정

합성 데이터만 든 폐기용 PostgreSQL 15 컨테이너에서 실행했다. 실제 고객·영업 데이터는 복사하지 않았다. 기존 프로세스·메뉴/VAT/영수증 함수와 인덱스를 불러오고 실제 RPC를 호출했다.

- 고객 1/10/50명 × 주문당 일반 메시지 1/20/100건을 조합했다. 증빙 권한 확인과 채팅 변경 확인은 각각 고객당 데이터 RPC 1회다. 메시지마다 별도 조회하지 않는다. 동시에 실행하는 클라이언트 수는 최대 50이다.
- 증빙 권한 응답은 최대 52바이트, 채팅 변경 응답은 최대 47바이트였다(합성 JSON, HTTP 헤더/Edge 래퍼 제외). 실제 Edge에서는 위 고정 요청 제한 조회가 추가된다.
- 최종 측정 수치와 실행 계획은 `sql-final.log`에 보존한다. Docker CLI 실행/프로세스 시작 비용을 포함한 수치이므로 운영 모바일 지연으로 해석하지 않는다.
- 채팅 변경 데이터 조회는 요청 PK 인덱스에서 실제 행 1개, 공유 버퍼 3개를 읽었다. 메시지 이력을 읽지 않는다. 증빙 최신 사진 조회는 기존 `(request_id,created_at,id)` 인덱스를 사용하고 테스트의 100건 메시지 범위를 검사했다.
- 메시지 100건 일괄 INSERT는 부모 요청의 변경 번호를 1회만 증가시켰다. 고객 화면은 동일 변경 번호의 반복 확인에서 추가 상세/목록 조회가 없었고, 직원 이벤트 20건은 선택 상세 1회·목록 0회로 합쳤다.
- 성공한 증빙은 메모리의 사진 바이트를 해제한다. 실제 브라우저 힙·모바일 네트워크 메모리는 측정하지 않았다.

## 남은 제한과 운영 반영

- 소스·폐기용 DB 검증까지 수행했다. 운영에는 새 DB 마이그레이션 2개, `direct-order-public` Edge, 웹 앱을 함께 반영해야 한다. 운영 배포는 `scripts/deploy_pos_production.sh`와 정확한 push SHA의 필수 CI 통과 절차를 따라야 한다.
- 선택 주문 상세 응답과 기존 15초 안전 조회는 전체 대화 이력을 포함한다. 변경 확인 자체는 고정 크기지만 실제 변경 후 상세 응답은 이력 크기에 따라 커진다. 장기 대화의 페이지 조회와 실제 Edge/모바일 부하 측정은 이번 검증에 포함하지 않았다.
- 은행 반환 링크는 자격 증명 없는 매장 주소다. 다른 브라우저로 돌아오면 원래 주문 탭에서 증빙 제출을 이어가야 할 수 있다.
- 실제 iOS/Android 기기, Safari/Chrome 및 Zalo 인앱 브라우저에서 은행 앱 설치/외부 앱 허용 상태는 검증하지 않았다. 실제 송금과 직원의 실제 입금 확인도 하지 않았다. 앱이 열려도 결제 완료로 자동 처리하지 않으며, 고객이 은행에서 확인·승인하고 증빙을 보낸다.
- 공식 지원 목록 밖 은행 앱 또는 수취 은행은 QR·계좌 복사 경로를 이용한다. 은행 앱 목록과 지원 범위는 제공자 변경에 맞춰 갱신이 필요하다.
- 운영 캐시의 구버전 웹 앱에는 새 메모 대상 값이 없으므로 배포 시 새 클라이언트를 로드해야 한다. 기존 v1/v2 증빙 API는 보존했다.
- 원래 장애 사진의 실제 단말 네트워크·Storage 실패 구간은 확인하지 못했다. 검증은 제한 없는 대기와 재전송 제한을 재현하고 해당 경로를 수정한 증거다.
