# 포장·배달 주문 개선 구현 기록

2026-10-08 · Asia/Ho_Chi_Minh

첨부 화면 9장과 요청 내용을 기준으로 소스·마이그레이션·검증을 구현했다. 사용자의 추가 지시인 **이미 낸 배송비보다 실제 요금이 높아졌을 때 차액 추가 결제**와 **계산원의 환불 완료 기록**을 반영했다. 운영 DB·Edge·웹에는 이번 변경을 적용하지 않았다.

## 기능과 확인 기준

| 원문 항목 | 소스 결과 |
|---|---|
| 1. 메뉴 요청사항 | 주문별 주방 화면과 KDS 메뉴 카드·인계 화면에 원문 메모를 표시한다. 같은 메뉴라도 메모가 다르면 다른 그룹으로 처리한다. 메모는 다른 주문에 섞이지 않도록 주문 항목과 큐의 주문 ID를 함께 확인한다. |
| 2. VAT 발행 정보 | 계산원이 세금번호, 회사/구매자명, 주소, 이메일, 연락처를 주문에 저장한다. 결제가 등록되면 기존 MISA intake에 연결한다. 미완성 정보는 추가 정보 대기 상태로 저장하며 MISA 외부 발행은 기존 비동기 경로를 사용한다. |
| 3. 결제 안내 | 최초 견적과 추가 청구를 고객 결제 알림 이벤트로 등록한다. 주문 현황과 결제 QR를 안내한다. 견적·청구 ID로 중복을 방지하고 만료·취소·대체된 견적의 발송은 건너뛴다. 브라우저 푸시는 고객의 알림 허용과 기존 푸시 설정이 필요하다. |
| 4. 배송지 | 전체 주소, 수령인, 전화번호를 필수로 유지하고 층·호수·상세주소는 선택으로 변경했다. 상세주소 없이 서버 주문 제출도 가능하다. 미정인 기사 직접 결제 배송비는 무료처럼 0으로 안내하지 않는다. |
| 5. 채팅 첨부 | 직원이 JPG/JPEG/PNG/WebP 또는 PDF를 선택·확인·전송한다. 최대 5 MiB이며 private Storage를 사용한다. 고객과 직원은 주문 소유권/매장 권한 검증 후 유효기간 300초의 링크로 연다. 업로드 응답 유실 후 동일 경로로 재시도해도 메시지를 중복 저장하지 않는다. |
| 6. 부족 입금 | 실제 은행 입금액과 거래 참조를 계산원이 직접 입력하고 이미지 대조를 확인한다. 부분 입금을 먼저 기록하고 동일 주문의 부족금을 추가 QR로 청구한다. 음식 금액을 모두 확인한 뒤에만 기존 결제와 주방 주문을 한 번 생성한다. |
| 8. 견적 버튼 중복 | 첨부 화면과 달리 작업 시작 시점 소스에는 견적 전송 버튼이 이미 하나였다. 단일 버튼을 유지하고 해당 UI 계약 검사를 통과했다. |
| 9. 배송비 추가 결제 | 음식 먼저 결제한 주문의 배송비 또는 선결제 배송비의 증가분을 계산원이 입력한다. 고객 동의 → 별도 QR → 추가 증빙 → 실제 입금 확인 순서다. 배송비를 여러 번 추가해도 같은 고객 주문에서 이력을 보존한다. 모든 청구가 정산되기 전에는 기사 인계·최종 완료를 차단한다. |
| 10. 취소·환불 | 취소 후에도 양쪽 채팅과 직원 첨부를 유지한다. 환불 계좌 정보를 저장하고 계산원이 실제 환불액·이체 참조·완료를 기록한다. 부분 환불도 지원하며 남은 환불액이 있으면 상담 종료를 차단한다. 날짜가 바뀌어도 열린 취소 상담이 직원 목록에 남는다. |

추가 배송비를 받은 후 매장 픽업으로 전환하면 미결제 배송비 청구를 취소한다. 받은 추가 배송비·부분 입금은 별도 환불 기록을 요구하며 음식 결제는 유지한다. 기존 견적에 포함됐던 배송비의 픽업 환불은 기존 환불 기능을 유지한다.

## 결제·출력 경계

음식과 최초 견적 배송비는 기존 `process_payment(order, store, amount, method)` 경로를 한 번 사용한다. 이후 배송비는 같은 Direct Order 고객 주문에 연결된 **배송비 전용 POS 결제 주문**으로 처리한다. 음식 항목과 재고 차감, 주방 티켓은 추가하지 않는다. Direct Order 분석은 배송비를 합산하되 고객 주문 수는 늘리지 않는다. 일반 POS 거래 수 지표에서는 배송비 전용 거래가 별도 결제 건으로 집계될 수 있다.

입금 증빙은 청구별로 여러 장을 보존하고 확인한 이미지와 실제 입금액·확인자·거래 참조를 연결한다. 같은 증빙 또는 같은 거래 참조를 재사용해 입금액을 중복 합산하지 않는다. 이미지 수신만으로 결제 완료를 처리하지 않는다. 청구 금액을 넘는 입금은 자동 승인하지 않고 계산원의 별도 대조를 요구한다.

최종 완료 시 새 고객 영수증에 음식과 정산된 추가 배송비를 합산한다. 픽업 환불은 환불액과 실제 수령액에 반영하고 배송비 메뉴 줄은 숨긴다. 프린터 큐 생성 실패는 감사 기록에 남으며 계산원이 기존 재출력으로 다시 처리할 수 있다. 실제 종이 출력과 현장 Windows 설치는 미검증이다.

이미 발급한 print job과 디지털 snapshot은 수정하지 않는다. 새 디지털 snapshot 생성 시 추가 배송비를 합산한다. 기존 디지털 영수증 ID가 이미 있으면 기존 API가 그 snapshot을 재사용하므로 과거 디지털 영수증의 금액은 유지된다. 최종 합산 출력은 새 종이 영수증/재출력 경로를 사용하며, 이미 발급한 디지털 문서의 재발급·정정은 이번 변경 범위가 아니다.

VAT 정보와 환불 계좌는 직원 전용 지원 응답에만 포함한다. 종료되지 않은 환불 상담의 증빙은 보존하고, 보존 기간 경과 후 삭제 시 개인정보·첨부는 지우되 확인된 입금/환불 원장은 유지한다. 계좌 정보 전달 메모는 저장하며 회계팀에 외부 메시지를 자동 발송하지 않는다.

## 운영 반영 전 남은 단계

1. 사용자 소유의 기존 tracked/untracked 변경을 보존하며 이번 변경을 최종 release에 통합한다. [task-only patch](evidence/direct_order_support_20261008/task-only.patch)와 [파일 해시](evidence/direct_order_support_20261008/changed-files.json)는 작업 시작 시점 백업과 이번 신규 파일 기준이다. 원본을 백업하지 못한 기존 SQL runner는 patch에서 제외하고 목록에 명시했다. 시작 HEAD는 `cc4de81adb8870fd479cb12edd773cda635a01cd`였다.
2. 신규 `20261008020000_direct_order_support_and_payments.sql`, `20261008021000_kds_menu_requests.sql`을 기존 선행 migration들과 함께 검증한다. 새 DB는 기존 직원 사진 승인 RPC 직접 실행을 제한하므로 새 클라이언트와 DB/Edge를 함께 반영해야 한다.
3. 정확한 pushed HEAD의 필수 GitHub Actions 성공 후 `scripts/deploy_pos_production.sh`의 gate를 통해 반영한다. 이번 작업은 push·PR·운영 배포를 실행하지 않았다.
4. 고객 알림 설정·브라우저 푸시, 음식 부족금과 배송비 차액의 실제 이체, 취소 환불 완료, 주방 메모, Windows 최종 종이 영수증을 현장에서 확인한다. 테스트용 주문·입금을 운영 DB에 생성하지 않았다.
