# 고객 요청·결제·대화·김치찌개 선택 통합 개선

2026-10-26 사용자 요청 1/9, 6, 7, 8, 10, 11을 구현한다. 이 문서는 소스 계약이며 실제 운영 반영·검증 결과는 최종 SHA에 묶인 별도 릴리스 증거로 판정한다.

- 요청 수락: 원래 요청을 한 번 수락하면 서버가 버전·소유권을 확인하고 확정한다. 같은 mutation ID 재시도는 메시지를 늘리지 않는다. 실제 변경 제안은 별도 선택이며 고객 동의를 유지한다. 기존 대기 건을 일괄 확정하지 않는다. 비공개 요청은 출력되지 않으며 조리 요청은 검토된 인쇄 가능 문구가 필요하다.
- 은행: 공식 iOS/Android 공통 은행 앱 목록과 자동입력 지원 여부를 구분한다. QR PNG 저장·공유, 송금액 복사를 제공한다. 미지원 Web Share는 PNG 저장으로 대체한다. 앱 복귀는 입금·결제 완료가 아니다.
- 부서: 캐셔 대화 API의 역할·매장 경계를 유지한다. KDS/Checker에는 비공개 대화 대신 확정된 조리 지시를 집합 조회한다. 수락 응답 문구를 조리 지시로 노출하지 않는다. 변경 제안에 합의한 경우 해당 조리 지시는 유지한다.
- 이미지: 직원 첨부 권한에 구버전 상세 응답 대신 작은 전용 context를 사용한다. 업로드 단계 제한 시간과 불변 경로 재시도를 유지한다. 이미지 열기는 인증된 단기 URL로 앱 안에서 확대하며, 열기 전 이미지별 서명 URL을 발급하지 않는다. 일반 사진은 결제 증빙으로 자동 승격하지 않는다.
- 주문 상세: 결제 카드의 금액 상세 버튼을 기존 주문 상세로 연결한다. 가격·VAT·정산 상세 데이터는 유지한다.
- 메뉴: 관리자 옵션 영역에 선택 옵션을 명확하게 표시한다. 김치찌개는 주재료 1개 필수 선택이며 밥 포함, 돼지고기·참치 59,000 VND, 해산물 69,000 VND를 보존한다. 실제 가격·레시피·할인 범위가 전제와 다르면 전환이 원자적으로 거부된다.

## 메뉴 전환과 호환성

`admin_consolidate_kimchi_jjigae`는 실제 인증된 매장 관리자만 실행한다. 원본 세 메뉴는 가격·레시피·ID·세트 구성 참조를 유지한다. 새 카탈로그 메뉴는 공통 레시피와 선택별 정확한 차이를 저장한다. 원본의 `catalog_parent_id`로 신규 단독 판매만 제거하며, 오래된 원본 장바구니는 서버가 거부한다. 과거 주문·세금계산서·판매를 소급 수정하지 않는다. 다른 매장의 메뉴를 자동 변경하지 않는다. 메뉴 관리의 김치찌개 통합 버튼은 기존 레시피가 있는 원본을 집합 조회로 선택하고 가격·레시피·이력 보존 내용을 확인한 뒤 같은 RPC를 호출한다.

동일 이름이지만 레시피·세트 참조가 없는 중복 원본도 계보에 포함한다. 참치 원본을 쓰는 기존 세트는 같은 구성품 ID로 계속 동작한다. 새 메뉴 등록과 옵션·레시피·계보·감사는 한 트랜잭션이다. 수정 전 전체 소스는 최종 exact-main 검증 뒤 공식 마이그레이션 경로로 적용한다. 메뉴 등록은 해당 배포 뒤 실제 관리자 인증으로 실행하며 계정 생성·권한 변경·비밀번호 재설정을 하지 않는다.

## 데이터 접근과 검증

첨부 context는 주문 1건의 필요한 상태만 반환한다. 대화 길이에 따른 상세 응답 전송을 권한 확인에서 제거한다. 카탈로그·옵션·원료는 목록별로 일괄 처리하고 QR의 기존 메뉴별 음료·프로모션 조회도 집합 집계로 전환한다. 클라이언트가 이미 받은 주문 상세를 재사용한다. 단일 이미지 전송만 활성화하고 기존 5 MiB 제한, 순차 전송, 제한된 멱등 재시도를 유지한다. 메뉴 등록은 원본 3개·선택군 1개·선택값 3개로 제한된다.

초점 Flutter/Deno, 기존 직접 주문 통합 SQL fixture와 메뉴 선택 fixture, 현재 운영 스키마만 복원한 로컬 DB의 실제 권한·세금계산서·주문·레시피 회귀를 확인한다. 운영 고객 데이터를 로컬 fixture로 복사하지 않는다. 격리 DB에서 대화 메시지를 1·20·100건 추가해도 직원 첨부 context는 32 bytes였고 기존 전체 상세는 6,261·15,281·60,181 bytes로 늘었다. 동시 1·10·50개 호출은 모두 같은 작은 응답을 반환했다. 이 지연은 Docker CLI와 로컬 SQL을 포함하며 운영 네트워크 지연이 아니다. 관련 성능 수치는 호출 수·응답 크기·지연을 기록하며 실제 은행 앱·실송금·기기 검증은 실측 없이 통과로 주장하지 않는다.

최종 후보 SHA의 `pos_local_release_gate.py --kind candidate`와 공식 배포의 fresh exact-main 검증을 구분한다. 사용자의 후속 지시로 운영 스모크 테스트는 제외한다. DB-only는 본래 스모크를 실행하지 않으며 웹/Edge 배포는 공식 `--skip-smoke-tests` 경로의 배포 메타데이터·원격 산출물 해시 검증을 사용한다. 제외한 로그인·합성 HTTP 검사는 PASS가 아니다.
