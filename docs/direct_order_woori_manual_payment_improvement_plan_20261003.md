# 고객 송금 사진 확인·배달 주문 승인 개선 계획

작성일: 2026-10-03, 베트남 시간. 상태: 코드 구현·로컬 검증 완료. 신규 migration은 운영에 적용하지 않았고 앱 배포·실주문 승인은 실행하지 않았다.

## 1. 확정한 운영 흐름과 원인

사용자가 확인한 운영 흐름은 **고객이 Woori Bank로 송금하고 사진을 보내면, 직원이 그 사진의 결제 금액을 확인해 승인하는 방식**이다. SePay는 사용하지 않는다. 별도 은행 앱·수취 내역 조회를 승인 요건으로 추가하지 않는다. 사진 자동 판독이나 은행 자동 검증도 이번 범위에 포함하지 않는다.

문제는 현재 코드가 직원의 사진 확인 승인에 **SePay 거래 연결을 필수 조건으로 강제한 것**이다. 사진을 접수해도 화면 버튼이 잠기고 서버도 승인을 거부한다. 결제·주방 티켓은 승인 시 생성되므로 주방 주문도 만들어지지 않는다.

초기 조사의 SePay 연동 복구 제안과 후속 계획의 별도 은행 수취 확인 제안은 모두 사용자 운영 방식과 달랐다. 이 문서는 두 번의 사용자 정정을 반영한 최종 계획이다.

시스템의 역할은 직원이 확인할 주문 금액·사진을 제공하고, 직원 승인 시 기존 결제·주방 처리를 한 번만 실행하고 승인 이력을 기록하는 것이다. 실제 결제 내용을 판단하는 주체는 사진을 보는 직원이다.

## 2. 확인한 증거

운영 프로젝트 `ynriuoomotxuwhuxxmhj`를 읽기 전용으로 조회했다. 아래 상태는 2026-10-03 13:02경 베트남 시간 기준이다.

|---|---|
| 주문 | `D2A54A36B`, 배달 주문 |
| 접수 / 견적 | 12:39:14 / 12:40:09, 견적 버전 1 |
| 최종 금액 | **255,240 VND** |
| 고객 송금 사진 | 12:41 송금 성공, Woori 수취계좌 끝자리 `2976`, 메모 `D2A54A36B` |
| 사진 접수 | 12:42:15, 첨부 파일 존재 |

| 열린 사진 재전송 요청 | 0건 |
| 승인 financial / 배달 주방 티켓 | 각각 0건 |
| 수취계좌 설정 | Woori Bank, 끝자리 `2976` |

수정 전 코드와 운영 함수 정의를 함께 확인했다. 다음 내용은 장애 당시의 원인 증거다.

- `lib/features/direct_order/direct_order_cashier_screen.dart:1368`: SePay 연결 거래에서 얻는 `_verifiedPaymentEvidence`가 없으면 승인 버튼이 비활성화된다.
- 같은 파일의 `_showApproval`: 해당 값이 없으면 직원 확인 창을 열지 않는다.
- `lib/features/direct_order/direct_order_staff_service.dart`: `approve()`가 SePay 검증 거래 전용 `direct_order_approve_verified_payment`를 호출한다.
- `lib/features/direct_order/direct_order_copy.dart`: 사진은 참고 자료이며 SePay 거래 연결이 필수라고 안내한다. 현재 운영과 맞지 않는 문구다.
- `supabase/migrations/20260908120000_direct_order_pilot_safety.sql:341`: 기존 승인 함수의 사진 존재 조건을 SePay 연결 거래 조건으로 교체했다. Git 변경은 `0181dffc`이며 migration은 운영 적용되어 있다.
- 운영의 `direct_order_approve_verified_payment`와 공통 `direct_order_approve_payment` 모두 거래 연결이 없으면 `DIRECT_ORDER_VERIFIED_PAYMENT_REQUIRED`로 차단한다. 화면 버튼만 켜거나 기존 함수 이름만 호출해도 해결되지 않는다.
- 운영의 공통 승인 함수가 결제·financial·배달 주방 티켓을 같은 트랜잭션에서 생성한다. 이번 주문은 그 단계 이전에 막혔다. 승인 후 주방 실시간 갱신은 후속 검증 대상이다.

잠긴 견적은 최초 화면 조회용 TTL 이후에도 승인 가능하도록 구현되어 있다. 최초 만료 시각 13:00:09는 이번 장애 원인이 아니다. 기존 주문과 견적으로 복구하도록 한다.

## 3. 목표 화면과 처리 흐름

1. 고객이 송금 사진을 제출하면 주문은 “사진 접수·직원 확인 대기”로 표시된다.
2. 직원이 “입금액 확인”을 누르면 같은 주문의 사진, 주문번호, 최종 견적 금액을 확인할 수 있다.
3. 직원이 사진을 확인하고 “입금 승인·주방 전달”을 누른다. 별도 은행 연동, 자동 거래 후보 연결, 추가 은행 조회를 요구하지 않는다.
4. 서버는 직원 권한·주문 상태·견적·확인 금액·사진 존재·재전송 대기 여부를 검증하고 기존 공통 승인 처리를 실행한다.
5. 결제·financial·주방 티켓을 한 번만 생성하고 처리자·시각·확인 금액·확인한 사진을 기록한다. Cashier와 주방이 해당 주문을 갱신한다.

사진 제출만으로 자동 승인하지 않는다. 직원의 최종 승인 클릭을 사진 확인에 대한 명시적인 업무 승인으로 취급한다. 별도 확인 체크박스나 필수 은행 거래번호 입력을 추가하지 않는다.

## 4. 우선 수정 작업

### P0 — 화면과 서버의 잘못된 전제 제거

**Cashier 화면·서비스·문구**

- 직원 사진 확인 경로에서 SePay 증빙·후보 조회를 제거한다. `_verifiedPaymentEvidence`와 연결 거래 존재 여부를 버튼 및 확인 창의 필수 조건으로 사용하지 않는다.
- `awaiting_payment_review`, 잠긴 확정 견적, 첨부 사진 존재, 열린 재전송 요청 없음, 처리 중 아님을 기준으로 확인·승인 동작을 제공한다.
- 기존 이미지 보기 기능을 재사용해 현재 주문의 사진을 확인 창과 쉽게 오갈 수 있게 한다. 기대 금액은 서버 견적에서 읽기 전용으로 표시하고 직원이 사진과 대조해 최종 승인한다.
- `approve()`를 직원 사진 확인 승인용 `direct_order_approve_photo_payment`로 연결해 확인 금액·견적 ID·사진 ID를 전달한다. 새 RPC는 기존 `direct_order_approve_payment`를 호출하며, 확인 창을 연 뒤 견적·사진이 바뀐 경우 승인을 차단한다. 은행 거래번호나 추가 체크박스 입력을 요구하지 않는다.
- SePay 연결 필수, 자동 일치 후보 없음, 시스템이 확인한 입금 등의 문구를 “사진을 확인한 후 승인해 주세요”로 교체한다. KO/VI/EN의 의미를 맞춘다.

**공통 승인 함수**

- 최신 `direct_order_approve_payment`에서 같은 매장·같은 주문·같은 견적의 제출 사진만으로 직원 승인이 가능하도록 복구한다. 기존의 선택적 SePay 전용 경로는 호환성을 위해 유지하지만 직원 사진 확인 화면에서는 조회하거나 호출하지 않는다.
- 사진은 현재 잠긴 견적에 귀속된 제출인지 확인한다. 최신 사진과 열린 재전송 요청을 다시 확인하고, 다른 주문 사진·재전송 대기·이미 종료된 주문은 차단한다.
- 직원의 승인 RPC 호출을 명시적인 수동 확인으로 기록한다. 기존 financial의 `approved_by/approved_at/confirmed_bank_reference` 및 `audit_logs`를 재사용하고, 감사 상세에 `review_method=customer_photo`와 `proof_message_id`, 견적·금액을 추가한다. 별도 은행 검증 테이블을 새로 만들지 않는다.
- 역할·매장 권한, 금액 일치, 주문·견적 잠금, 메뉴 검증, 승인 마감, 중복 실행 방지와 기존 정합성 검증을 보존한다.
- 결제·VAT·서비스료·재고·티켓 생성 본문과 `process_payment(..., 'BANKTRANSFER')`를 재사용한다. 기존 고객 영수증 큐잉, 배송비 지급 방식, 비동기 MISA 계약을 유지한다.
- 기존 SePay 전용 함수나 다른 영역을 삭제하는 작업은 포함하지 않는다. 이번 Direct Order 직원 승인 경로가 그 함수에 의존하지 않도록 한다.

화면과 서버를 함께 수정한다. 가짜 SePay 거래를 생성하거나 주문 상태만 직접 변경하는 방식은 사용하지 않는다.

### P0 — 이번 주문 복구

구현 및 배포 후 `D2A54A36B`의 기존 request와 견적 1을 선택하고, 직원이 이미 제출된 사진을 확인해 승인한다. 승인 직전 상태를 재조회하며 다른 직원이 이미 승인했다면 기존 결과를 표시한다.

완료 조건: 원주문에 연결된 financial 1건, payment 1건, 배달 주방 티켓 1건, 메뉴 6종의 정확한 수량, 최종 금액 255,240 VND. 고객 재송금·신규 중복 주문 생성 없이 기존 주문을 처리한다.

이번 조사에서는 주문을 승인하거나 운영 데이터를 변경하지 않았다.

### P1 — 오류 안내와 주방 결과 확인

- `_loadPaymentReview`가 모든 조회 예외를 빈 결과로 바꾸는 현재 처리를 정리한다. 사진 조회 실패, 사진 미접수, 재전송 대기, 주문 상태 변경을 각각 표시하고 재조회 동작을 제공한다.
- 직원이 사용할 수 없는 버튼에는 실제 보류 이유를 표시한다. 사진 접수와 직원 승인 완료를 구분한다.
- 성공 응답의 `request_id/order_id/payment_id/ticket_id`와 재조회 결과로 승인 완료를 확인한다. 응답 유실 또는 화면 갱신 실패 시 같은 주문을 재조회한다.
- DB 티켓 생성과 실제 주방 화면 노출을 별도로 확인한다. 갱신 지연 시 주방 재조회로 복구하며 결제·티켓을 새로 생성하지 않는다.

완료는 소스 구현, migration 적용, 앱 배포, 실제 직원 사진 확인 승인 및 주방 노출을 각각 확인한 뒤 판정한다.

## 7. 구현 내역과 검증 상태

- Cashier의 SePay 조회·자동 거래 후보·필수 연결 조건을 제거했다. 고객 사진과 잠긴 견적이 있으면 “입금액 확인” → 사진 보기·금액 대조 → “입금 승인·주방 전달”로 진행한다.
- 현재 사진이 없거나 재전송을 기다리면 보류 이유를 표시한다. 조회 실패는 재조회 화면으로 표시하며 오래된 상세정보로 승인하지 않는다. 이미지 로딩 실패도 화면에서 안내한다.
- `20261003060838_direct_order_customer_photo_approval.sql`은 최신 공통 승인 함수의 사진 조건과 감사 상세만 수정하고 새 RPC를 추가한다. 새 RPC는 기존 결제 처리와 배송비 방식 스냅샷을 유지한다.
- 사진·견적 변경 검증, 중복 클릭·동시 승인 방지, 권한·금액·마감 검증, 영수증 실패 시 결제 보존을 유지한다. 사진 제출만으로 자동 승인하지 않는다.
- 새 Flutter 동작 테스트 11건과 기존 관련 계약 테스트를 함께 실행한 **17건이 통과**했다. 승인 응답이 유실되었을 때 재조회해 완료 상태를 표시하는 동작도 확인했다. DB 테스트에서 수정 전 차단 재현, 사진만으로 직원 승인, 배송비 방식 보존, 재승인·동시 승인 시 결제·재고·티켓 중복 방지, 결제 저장 실패 시 원자적 롤백, 영수증 실패 시 결제·티켓 보존을 확인했다.

## 8. 격리된 운영 릴리스 준비

최신 `origin/main`에서 새 `codex/direct-order-photo-approval` 작업트리를 생성해 기능 변경만 옮겼다. 기존 작업트리와 관련 없는 변경은 보존한다. 최신 main의 배달·픽업 승인 및 배송비 스냅샷 패치를 실제 SQL 테스트에 적용해 새 사진 승인과의 호환성을 검증한다.

- 범위가 제한된 `rollback_direct_order_customer_photo_approval.sql`을 준비했다. 공통 승인 함수의 사진 조건·감사 상세만 복원하며 결제 데이터와 다른 기능은 유지한다. 격리 DB에서 복원 전후 정의 해시를 대조한다.
- `smoke_direct_order_customer_photo_approval.sql`은 실주문 데이터를 참고해 합성 주문을 만들고 실제 직원 권한의 승인 RPC·멱등 재시도·주방 권한의 티켓 조회를 검사한 다음 모두 롤백한다. 원주문을 대신 승인하지 않는다.
- 운영 반영은 PR 및 main의 정확한 SHA CI 통과 후 `scripts/deploy_pos_production.sh`로 새 migration 한 건과 앱을 배포한다. 기존 고정 POS 계정 로그인 검사도 수행한다.

격리 작업트리의 전체 `scripts/check_repo.sh`가 통과했다. 최신 main 기준 Flutter 1,680건 통과·환경 조건에 따른 94건 건너뜀, 정적 분석·SQL/API·Edge·Node·웹 릴리스 빌드가 포함된다. 마지막 운영 smoke 추가 후 동일 SQL runner를 다시 통과해 권한별 승인·주방 조회 및 시험 데이터 전체 롤백을 확인했다.

이 절은 릴리스 준비 내용이다. 실제 적용·배포·운영 검증 결과는 별도 릴리스 증거에 기록한다.
