# 고객 수령 시 기사 직접 결제 전용·배달 운영·채팅 첨부 개선안

2026-10-10 · Asia/Ho_Chi_Minh · 상태: 소스 구현·기능 로컬 검증 완료 · 전체 저장소의 기존 검사 불일치 별도 기록 · 운영 DB 미적용/미배포

**신규 배달 주문은 고객이 수령할 때 배달비를 기사에게 직접 결제하는 한 가지 방식만 사용한다.** 매장은 음식·옵션·기존 세금/수수료로 계산한 주문 대금만 받는다. Grab 등 기사 비용을 매장 결제 금액에 넣지 않는다. 배달비 선결제/후결제 선택, 지급 방식 협의·고객 확인 gate, 배달비 포함 결제, 매장 선지급·차액 부담·배달비 추가 수금 기능은 새 흐름에서 제외한다.

이 문서가 앞선 통합 계획과 필수 협의 계획, 두 방식 비교 보고 이미지보다 우선한다. 기존 일반 요청사항 확인·실제 입금 확인·주문 취소/환불·개인정보 보호는 별도 계약으로 유지한다. 중단된 구현 턴에서는 소스 확인만 진행했으며 해당 계획의 선결제/협의 기능 코드를 추가하지 않았다.

구현 전 재검증 근거는 [재검증 보고서](/Users/andreahn/globos_pos_system/docs/plans/direct_order_customer_pays_driver_only_revalidation_20261010.md)에 보존한다. 실제 변경 사항과 새 정책 검증 결과는 [구현 보고서](/Users/andreahn/globos_pos_system/docs/plans/direct_order_recipient_delivery_implementation_20261010.md)에 기록한다. 구현 전 기존 검사의 통과를 새 정책 구현 완료로 해석하지 않는다.

## 1. 고객 안내와 결제 화면

- 메뉴/주문 입력, 최종 결제 안내, 배차 안내에 일관된 문구를 표시한다: **“배달비는 주문 금액에 포함되지 않습니다. 음식 수령 시 기사님께 직접 결제해주세요.”**
- 지급 방식 선택이나 협의 완료 버튼을 만들지 않는다. 배달비 안내를 읽었다는 이유로 별도 필수 확인 단계를 추가하지 않는다.
- 고객 매장 결제 금액은 음식·옵션·기존 세금/수수료만 포함한다. 예: 음식 등 합계 200,000동이면 매장 결제 200,000동이다. 기사 비용이 30,000동이든 40,000동이든 이 매장 결제액은 달라지지 않는다.
- 매장 결제 명세에서 배송비 금액 행을 제거하고 별도 안내 문구를 사용한다. 내부 수금 배송비 0을 “무료 배송”으로 표시하지 않는다. 기사 실제 요금이 미정인 상태도 0동으로 표시하지 않는다.
- 예상/배차 요금을 안내하는 경우 `기사 안내 요금 · 별도 직접 결제`로 구분하며 매장 송금 QR·청구 합계·영수증 매출에 합산하지 않는다. 정확한 안내가 어려울 때 캐셔에게 예상 요금 입력을 강제하지 않는다.

## 2. 캐셔 화면 단순화

- 신규 직접 지급 주문에서 배달비 지급 방식 dropdown, 매장 수금 배달비 입력, 배달비 후청구/선지급, 실비 차액 부담 입력, 기사 현금 지급 확인/증빙 기능을 노출하지 않는다.
- 화면에는 `음식 대금 입금 확인`, `주방 진행`, `기사 호출`, `배차 정보`, `기사 인계`를 중심으로 보여준다.
- 목록에 현재 필요한 작업을 표시한다: `입금 확인 필요`, `조리 중`, `기사 호출 필요`, `배차 완료`, `포장 완료·인계 대기`, `인계 완료`. 배차와 포장 완료는 병행 상태로 구분한다.
- 매장 결제 완료는 음식 대금 확인을 뜻한다. 고객이 기사에게 배달비를 냈는지 캐셔가 확인해야 주문을 마칠 수 있도록 만들지 않는다. 기사 인계와 실제 배송 완료도 구분한다.

## 3. 조리·배차·기사 인계

권장 흐름: **음식 대금 결제/입금 확인 → 조리 → 조리 완료 → 기사 호출 → 배차 정보 안내 → 포장 완료 후 인계 → 배송 진행/완료 확인**.

- 모든 대상 음식의 조리 완료를 기준으로 캐셔에게 기사 호출 필요를 보여준다. 포장 완료인 `ready`와 구분하고 실제 인계는 포장 완료 후에 처리한다. 현재 `direct_order_cooking_progress`는 emergency/KDS 수량만 집계하므로 그대로 전체 주문의 배차 조건으로 사용하지 않는다. 종이 출력 주문은 기존 직접 주문 주방 보드에 권한·버전 검사를 거친 `조리 완료` 기록을 추가하고, KDS 주문은 취소/제외 수량과 콤보 구성품까지 포함한 실제 완료 수량으로 판단한다. 완료 대상 누락을 자동 완료로 간주하거나 종이 주문을 영구 대기시키지 않는다.
- **배차 예약과 기사 인계를 서버에서 분리한다.** 현재 `direct_order_set_dispatch_v3/v4`는 `ready`에서 배차 저장과 동시에 `dispatched` 전환·인계 알림을 처리한다. 이 RPC를 조리 완료 시점의 예약 저장에 재사용하거나 `ready` 조건만 완화하지 않는다. 예약 이력과 현재 유효 예약을 별도로 저장하는 계약을 추가한다.
- 예약 저장은 입금 확인된 배달 주문의 조리 완료 후 허용한다. 업체·예약 참조·기사 연락처/추적 링크·선택적 참고 요금·예약/실패/취소 시각을 저장하되 `dispatched_at`, 기존 `sent_at`, 인계 알림과 금융 원장을 생성하지 않는다. 고객은 `기사 배정·포장 중`과 `기사 인계·배송 중`을 구분해서 본다.
- 캐셔가 기존 배차 앱에서 수령자 지급 가능한 상품과 `수령자 결제` 설정을 확인하고 호출한다. 자동 배차 API는 이번 기본 범위에 도입하지 않는다. 서비스/계정에서 실제 지원 여부는 운영 검증 대상으로 둔다.
- 배차 확인 화면에 고정된 지급 주체 `고객 수령 시 기사 직접 결제`를 표시한다. 업체·예약 참조·기사 연락처·지원되는 추적 링크를 한 곳에서 기록한다. 기존 주소/연락처를 복사하거나 기존 호출 링크로 이어지는 동작은 현재 개인정보/권한 계약 내에서 제공한다.
- 고객 배차 안내와 기사 전달 전표에 **“음식 대금은 매장 결제 완료 / 배달비만 고객에게 직접 수금”**을 표시해 기사에게 음식값까지 다시 받는 오해가 생기지 않게 한다.
- 기사 요금을 알고 있으면 고객에게 참고로 안내할 수 있지만 현금 지급 원장·매장 비용/차액 원장에 넣지 않는다. 기사 실비 확인 사진을 인계의 필수 조건으로 만들지 않는다.
- 실제 인계는 포장 완료(`ready`)·최신 유효 예약·최신 주문/예약 버전·음식 대금 정산 조건을 같은 트랜잭션에서 검증한다. 직접 지급 주문의 `actual_grab_fee`는 `NULL`이며 기사 현금 지급 증빙을 요구하지 않는다. 기존 인계/결제의 원자적 계약은 유지한다. 주문 잠금 순서를 픽업 전환/취소/재배차와 일치시키고, 동일 작업 ID의 응답 유실·중복 클릭·두 캐셔의 동시 처리를 검증한다.
- 실제 배송 완료는 인계와 별도 이벤트로 처리한다. 자동 배차/배송 완료 API를 도입한 것으로 안내하지 않으며 현재 수동 확인 계약을 사용한다. 고객의 기사 배달비 결제 확인을 주문 완료의 필수 조건으로 만들지 않는다.

## 4. 배차 실패·취소·환불

- 수령자 지급이 불가능한 배차 상품을 매장 선결제로 자동 전환하지 않는다. 가능한 상품 재검색/다른 업체 호출, 고객과 픽업 전환 또는 주문 취소를 협의한다.
- 배차 실패 사유와 재시도 이력을 남기고 완료·인계 상태를 성공한 것으로 바꾸지 않는다. 재배차 시 최신 유효 예약과 이전 취소를 구분한다.
- 픽업 전환에도 매장이 받은 배송비가 없으므로 신규 직접 지급 주문에 매장 배송비 환불을 만들지 않는다. 음식 대금 취소/환불·부족/초과 입금 처리는 기존 실제 수금에 따른다.
- 고객이 기사에게 지급한 돈을 매장 수금으로 기록하거나 매장에서 자동 환불하지 않는다. 취소 비용/기사 분쟁은 실제 거래와 지급 주체를 확인해 기존 상담에서 처리하며 정상 배송비와 혼동하지 않는다.

## 5. 고객↔매장 채팅 이미지·파일

이전 요청의 첨부 오류 개선은 계속 필수 범위다.

- 고객과 매장 양쪽에서 일반 사진/PDF를 보내게 한다. 배송지 사진·지도·포장 관련 사진은 견적/결제 청구 ID 없이 열린 주문 상담에서 전송할 수 있어야 한다.
- 일반 첨부와 입금 증빙을 분리한다. 음식 대금 입금 증빙의 기존 검토/연결 계약은 유지하며 주소 사진이 결제 증빙으로 처리되면 안 된다.
- 현재 고객 첨부 API/SQL은 고객 파일을 `payment_proof`로 저장하고 청구/견적 상태를 검사하며 고객 PDF를 거부한다. 일반 첨부는 명시적인 별도 action/RPC와 메시지 종류를 추가하고, 기존 증빙 upload/commit 계약은 유지한다. 고객 세션 또는 직원 매장 권한·주문 소유·상담 열림 여부를 확인하되 일반 파일에 결제 청구 ID를 요구하지 않는다.
- 파일 선택·미리보기·취소·전송 중·실패 사유·재시도·상대 표시·열기를 연결한다. 일반 첨부는 JPG/JPEG/PNG/WebP/PDF, 파일당 5 MiB를 지원하는 계획을 유지한다. 미지원 형식/큰 파일은 이해할 수 있는 안내를 제공한다.
- 동일 파일 경로/작업 ID로 upload/commit 응답 유실을 복구하고 중복 파일·메시지를 막는다. 주문 전환 중 전송, URL 만료·재발급, 타 주문/매장 접근을 검증한다. private Storage와 종료 후 정리 계약을 유지한다.
- MIME/확장자뿐 아니라 파일 바이트를 검증한다. `.jpeg`는 허용 경로를 확인한 뒤 JPG 바이트 검증 분기로 정규화한다. 현재 바이트 검사에는 `jpg` 분기만 있어 경로 수용과 검사 결과가 어긋날 수 있다. PDF는 형식 검증과 안전한 열기를 적용한다. 재시도 상태는 주문별로 묶고 주문 변경/위젯 재사용 시 이전 파일·경로를 보내지 않도록 초기화한다.
- 양쪽 실제 전송 실패는 운영 버전·Storage·인증/CORS와 실기기 파일을 대조해 재현한 뒤 수정한다. 현재 소스만으로 매장 전송 실패의 원인을 확정하지 않는다.

## 6. 영수증·기사 전달표·주방 출력

영수증 출력 변경은 필수 구현 범위다. 현재 기사 전달표는 지급 방식 없이 `Phi giao hang Grab`, `Khach can tra: 0 VND`, `KHONG THU THEM TIEN CUA KHACH`를 출력하므로 고객이 배달비를 기사에게 직접 내는 정책과 충돌한다.

| 출력물 | 신규 직접 지급 주문의 표시 | 금액/기존 계약 |
| --- | --- | --- |
| 고객 종이 결제 영수증 | 매장 결제 완료 합계와 `배달비 별도·수령 시 기사 직접 결제` 안내 | 기사 요금 항목/0동 배송비/무료 배송 표시를 만들지 않는다. 음식·옵션·기존 세금/수수료 합계만 유지한다. |
| 고객 전자 영수증·PDF·재출력 | 동일한 결제 합계와 지급 안내를 snapshot에서 읽어 표시 | 화면·PDF·프린터 경로가 서로 다른 안내를 사용하지 않는다. 이미 발행한 금융 snapshot을 덮어쓰지 않는다. |
| 기사 전달표 | `음식 대금 매장 결제 완료`, `음식값 다시 수금 금지`, `배달비만 수령자에게 직접 수금`을 크게 표시 | `고객 결제 0동`과 전면적인 `추가 수금 금지`를 신규 직접 지급 주문에서 제거한다. 매장 결제 합계는 기사 수금액으로 표시하지 않는다. |
| 주방·포장 전표 | 기존 주문번호·배달/픽업·메뉴·인원·식기·확인된 요청사항 유지 | 주방에 수금/기사 현금 지급 작업을 추가하지 않는다. 별도 계산 금액 변경은 필요 없다. 종이 주문 조리 완료 기록은 화면/서버 작업으로 처리한다. |
| 픽업 전표 | 매장 결제 완료와 음식값 추가 수금 없음 | 기사 배달비 안내를 표시하지 않는다. |

- 종이 프린터와 배포용 영수증/PDF는 기존 베트남어 계약을 유지한다. 기사 직접 지급 전표의 예시는 `TIEN MON DA THANH TOAN TAI CUA HANG` / `KHONG THU LAI TIEN MON` / `CHI THU PHI GIAO HANG TU NGUOI NHAN`이다. 고객 앱 안내는 기존 KO/VI/EN을 지원한다.
- 참고 기사 요금을 넣는 경우 `기사 안내 요금·고객 별도 지급`으로 별도 블록을 사용한다. 미정이면 미정으로 표시하고, 참고 요금과 매장 결제 합계를 더해 `고객 결제 총액`을 만들지 않는다. 없어도 출력/인계를 막지 않는다.
- 금액 0이나 `delivery` 여부로 지급 주체를 추측하지 않는다. 서버의 견적/금융 지급 방식·정책 버전·음식 대금 결제 상태를 print payload와 digital snapshot에 명시적으로 담고 `QueuedPaymentReceipt`, `QueuedDeliveryDriverReceipt`, `DigitalReceipt`, renderer까지 전달한다. `customer_due=0`의 범위는 매장 음식 대금 미수금이며 기사 배달비가 0이라는 뜻으로 사용하지 않는다. 검증 trigger도 이 의미와 payload 버전을 검사한다.
- 자동 결제 영수증 enqueue·캐셔 수동 출력·기사 전용 출력/재출력·일반 프린트 에이전트·PDF·공개 전자 영수증 경로를 함께 검사한다. 이미 존재하는 요청사항/번역 snapshot과 후속 메모를 보존한다. 종이/전자 영수증에서 음식명·메모 정렬과 기존 VAT 계산을 훼손하지 않는다.
- 기존 매장 선결제 주문은 해당 주문의 실제 수금·지급 계약대로 출력한다. 기존 직접 지급 주문의 기사 재출력도 저장된 지급 방식을 읽어 음식값 재수금 금지/배달비 직접 지급을 구분한다. 완료된 출력 이력과 발행된 금융 snapshot은 수정하지 않는다. 지급 방식이 없는 대기 전표는 서버 원본을 검증해 유효한 전표를 준비하며 임의의 기본값으로 출력하지 않는다.
- 구 프린트 에이전트는 새 payload가 있어도 기존 금지 문구를 출력할 수 있다. 새 payload 버전을 처리하는 에이전트로 교체한 후 새 정책을 활성화하고, 지원 버전을 확인하지 못한 에이전트가 새 전표를 claim하지 못하게 한다. 실제 80mm 출력에서 강조·줄바꿈·잘림을 확인하며 프린터 장애는 결제를 실패시키지 않고 기존 출력 큐의 재시도로 처리한다.

## 7. 서버·데이터·보고서

- 새로운 견적·결제는 서버에서도 `customer_direct`와 매장 수금 배송비 0만 허용한다. 프런트 버튼 제거만으로 끝내지 않고 구 클라이언트/RPC의 `store_prepaid`, 배송비 후청구, 매장 배달비 포함 금액을 차단한다. 지급 방식 기본값과 기존 `delivery_fee_deferred` 정규화도 검사한다.
- 정책 대상은 서버가 소유하는 버전/표식으로 구분한다. 신규 요청 및 아직 최종 견적 없는 진행 요청에 새 정책을 적용하고 확정 견적·금융 snapshot에 함께 고정한다. 클라이언트 값·생성 시각만으로 결정하지 않는다. 이전 확정/결제 주문의 idempotent 재요청은 기존 결과를 반환하며 새 방식으로 재계산하지 않는다. 기존 확정 견적을 바꿔야 하는 상황은 현재 취소/재주문 계약을 사용하고 확정 금액 잠금을 우회하지 않는다.
- quote의 최신 기본값/구 facade, submit의 후청구 표식, support의 defer/charge, 검증 실비 정산, dispatch, 기사 cash movement, 직접 테이블 권한까지 실행 가능한 진입점을 검사한다. 새 정책의 매장 수금/선지급 진입은 서버에서 차단하고, 기존 일반 음식 대금 부족/초과 입금·취소 환불 계약은 보존한다. 별도 배달비 협의 gate를 추가하지 않고 기존 음식/포장 요청사항 확인 gate를 유지한다.
- 신규 직접 지급 주문은 추가 배송비 청구·매장 기사 지급·실비 차액 부담 원장을 생성하지 않는다. `actual_grab_fee=NULL`인 현재 직접 지급 인계 계약과 필요 시 별도 참고 요금 필드를 구분한다.
- 매출/영수증/MISA/현금 마감은 매장에서 실제 받은 주문 대금 기준이다. 고객이 기사에게 낸 배달비는 매장 매출·금고 차감·매장 부담액에서 제외한다. 기존 원자적 `process_payment`와 비동기 MISA 계약을 유지한다.
- 진행/배차 보고서는 주문 수, 배차 실패/재시도, 조리 완료→기사 호출/인계 시간, 미처리 작업을 우선한다. 새 직접 지급 주문의 배달비 매출·매장 배달비 비용/부담 KPI를 0/미정과 섞어 부풀리지 않는다.
- 조리 완료·예약 요청/확정·예약 실패/취소·실제 인계 시각을 각각 기록한다. 현재 `sent_at`/`dispatched_at`은 실제 인계이므로 예약 소요 시간으로 재사용하지 않는다. 미기록 시각은 0분으로 만들지 않는다. 이전 매장 수금 배달비 KPI는 역사적 실적으로 남기고 새 직접 지급 주문의 외부 참고 요금은 매출/비용 KPI에서 제외한다.
- 이전에 배달비를 수금/지급한 주문의 견적·수금·환불·지급 이력은 삭제하거나 신규 정책으로 소급 변경하지 않는다. 아직 최종 견적 없는 주문은 새 방식으로 확정한다. 이미 확정/결제된 이전 주문은 기존 정산 이력이 남아 있음을 구분하고 정상 종료에 필요한 기존 계약을 보존한다.
- 목록/진행 상태/예약/출력 상태는 페이지 ID 기반 JOIN/집계로 RPC 1회에 반환한다. 직원 1/50/100/200건, 고객 1/10/50건(현재 공개 API 상한 유지)에서 건별 상세/배차/지원 RPC 0회를 목표로 측정한다. 첨부는 메타데이터 묶음과 batch URL 또는 사용자가 열 때 발급하고 메시지마다 자동 호출하지 않는다. 새 필드는 버전이 있는 응답 계약에 추가하고 strict DTO를 사용하는 구 클라이언트의 응답 키를 바꾸지 않는다.
- 기존 취소 환불은 추가 결제별 `payment_adjustments` 합계 조회/개별 adjustment 호출, invoice는 결제 주문별 sync 반복이 남아 있다. 신규 주문에 배송비가 없다고 이 경로를 그대로 두지 않는다. 재사용하는 환불 경로는 대상 결제 일괄 잠금→한 번의 GROUP BY 잔액 집계→누적합으로 배분→집합 기반 adjustment 기록으로 바꾸고 증빙·중복 방지·환불 한도 검증을 보존한다. invoice는 원주문/추가 주문의 대상 집합을 모아 일괄 갱신하고 MISA 비동기 계약을 유지한다. 원장/트리거 내부 반복 조회까지 검사한다. 추가 결제 1/10/50건에서 항목 수에 비례하는 SELECT/원격 호출이 생기지 않도록 측정한다. 단순 병렬화는 해결로 보지 않는다.

## 8. 구현 우선순위와 검증

1. **서버 정책·영수증 계약 준비:** 정책 snapshot, 신규 생성/구 진입점 차단, 지급 주체를 담은 print/digital payload와 호환 에이전트를 먼저 준비한다. 기존 주문은 보존한다.
2. **결제 화면·출력 연결:** 고객/캐셔의 선택·배달비 포함/후청구 진입을 제거하고 고객 영수증·기사 전표·PDF 문구를 연결한다. 구 에이전트의 새 전표 claim 차단을 정책 활성화의 조건으로 둔다.
3. **양방향 첨부 정상화:** 실제 실패 재현, 일반 첨부 API/Storage/고객 작성 버튼, 상태·재시도·열기를 완성한다.
4. **배차 작업 흐름:** 종이/KDS 조리 완료, 별도 예약/실패/재배차 이력, 수령자 결제 배차, 실제 인계·완료를 연결한다.
5. **보고서·회귀·운영 검증:** 환불/invoice 일괄 처리와 보고서를 연결하고 실제 지원되는 배차 상품, 80mm 실물 전표, 모바일 양방향 첨부와 배포 절차를 검증한 뒤 새 정책을 활성화한다.

성공 조건은 고객에게 지급 방식 질문/필수 협의 카드가 없고, 매장 결제액에 기사 요금이 포함되지 않으며, 새 주문에서 매장 선지급·차액 청구·현금 지급 요구가 발생하지 않는 것이다. 음식 대금 결제/증빙·주방 생성·포장·인계·환불·기존 주문을 회귀 검증한다. 고객/기사 안내와 직접 수금 조건의 일치, 첨부 재시도·권한/파일 검증, 목록/URL/환불 SQL 호출 수를 확인한다.

필수 시나리오는 다음과 같다.

- 음식 등 매장 결제액 200,000동 + 기사 요금 30,000/40,000동/미정: 견적·송금 QR·입금 확인·영수증·MISA·현금 마감은 200,000동. 기사 참고 요금이 변해도 매장 결제/비용 원장은 변하지 않는다.
- 종이/KDS 단품·콤보·취소 수량: 조리 완료 후 예약 가능, 예약만 저장하면 포장/배송 완료가 되지 않음, 포장 전 인계 불가, 실제 인계 후에만 배송 알림. 픽업/취소와 예약의 동시 처리 검증.
- 고객/기사 종이·전자/PDF·재출력: 신규 직접 지급, 기존 직접 지급, 기존 매장 선결제, 픽업, 부분 환불, 대기/실패 큐, 구 에이전트를 구분해 금액과 수금 문구 검증. 예전 문구를 유지하는 기존 테스트의 통과만으로 새 출력 계약을 승인하지 않는다.
- 고객↔매장 JPG/JPEG/PNG/WebP/PDF: 결제 전/후 열린 상담, 잘못된 바이트/5 MiB 초과/권한 오류/URL 만료/재시도/응답 유실/주문 전환. 실제 모바일 브라우저와 운영 Storage에서 상대 표시까지 확인.
- 기존 확정 금액 잠금·원자적 음식 결제·일반 요청사항 확인·증빙/환불 한도·PII 정리·비동기 MISA 보존. 새 정책 주문에서 구 RPC로 배달비 청구/선지급을 시도해 서버 거부 확인.

관련 Flutter/Edge/임시 PostgreSQL 검사와 프로젝트 검사·웹 빌드 결과는 구현 보고서에 기록한다. 운영 배포는 정확한 pushed HEAD의 필수 GitHub Actions와 `scripts/deploy_pos_production.sh` 절차를 따른다. 정책 활성화는 호환 클라이언트·에이전트·실제 수령자 지급 상품 검증과 함께 진행한다. 배포를 되돌려도 새 정책으로 확정된 주문의 지급 방식은 바꾸지 않는다. 현재 소스와 신규 마이그레이션은 구현했으며 운영 DB·배포는 변경하지 않았다.
