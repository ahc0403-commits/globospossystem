# 고객 선택과 매장 운영을 고려한 배달비 결제 수정 제안

2026-10-10 · 제안 단계, 정책 확정·기능 구현·운영 반영 전

**최신 계획으로 대체됨:** 고객의 배달비 포함 결제는 최초 1회로 끝내고 실제 비용 증가분은 매장이 부담한다는 확인을 반영한 [전체 통합 계획](/Users/andreahn/globos_pos_system/docs/plans/direct_order_single_payment_delivery_and_chat_attachments_plan_20261010.md)을 따른다. 아래의 기사 직접 지급을 기본으로 하는 추천과 임의 적용 구역 제한은 이전 제안으로 보존한다.

고객이 주문 시 배달비 지급 방식을 선택하도록 한다. 매장은 제공 가능한 방식과 적용 범위를 설정한다. 앞 계획에서 기본으로 제안했던 음식 결제 후 배달비 재입금 요청은 예외 처리로 내린다. 양방향 채팅 첨부 개선은 별도로 계속 필요한 범위다.

## 권장 운영안

| 고객 선택 | 고객 결제 | 매장 업무 | 비용 변동 책임 |
|---|---|---|---|
| 기사님께 배달비 직접 결제 | 음식 대금은 매장에 한 번 결제. 배달비는 수령 시 기사에게 지급 | 음식 입금 확인 → 조리 → 기사 호출 → 수령자 지급 조건 확인 → 인계 | 고객이 실제 배송비를 기사에게 지급. 매장은 배달비 수금·재입금 확인·현금 지급을 하지 않음 |
| 배달비 포함 한 번에 결제 | 음식 대금 + 매장이 확정한 배송비를 한 번에 매장 결제 | 입금 한 번 확인 → 조리 → 기사 호출 → 실제 비용 기록·현금 지급 → 인계 | 확정 고객 배송비와 실제 기사 비용의 차이를 매장이 감수 |

**기본 제안은 기사 직접 지급이다.** 함께 결제는 매장이 비용 변동을 감당할 수 있는 구역·시간·조건에 한해 제공한다. 고객이 현금을 준비하기 어려운 경우 함께 결제가 편리하지만, 모든 주문에 이 선택지를 무조건 제공하지 않는다. UI의 두 방식 이름은 누가 배달비를 받는지를 명확하게 표현한다.

기사 직접 지급을 제공하려면 실제 사용하는 업체·서비스·계정에서 수령자 지급이 가능한지 확인해야 한다. Grab의 특정 서비스 안내에는 발송자/수령자의 현금 지급을 구분하는 설명이 있지만, 이것만으로 매장에서 쓰는 모든 배차 상품이 수령자 지급을 지원한다고 판단하지 않는다. [Grab 공식 안내](https://www.grab.com/vn/blog/driver/grabexpress-nhung-dieu-can-biet-khi-hoat-dong-grabexpress-trong-ngay/)

## 한 번에 결제하는 방식의 핵심 정책

조리 후 기사를 호출하면 주문 결제 시점에는 실제 비용이 미확정이다. 한 번만 결제받으려면 다음 중 하나가 필요하다.

1. 고객에게 확정 배송비를 약속하고 매장이 실제 비용과의 차이를 감수한다.
2. 주문 결제 전에 기사 요금을 확정할 수 있는 배차 계약을 사용한다. 단순 견적 조회가 이후 요금을 보장한다고 가정하지 않는다.

수정 제안은 1번을 제한된 범위에서 사용하는 것이다. 거리에 따른 정액 또는 캐셔가 최종 견적에서 확정한 배송비를 음식 대금과 함께 받는다. 결제 확정 후 기사 요금이 변해도 고객에게 다시 입금을 요청하지 않는다. 고객 배송비는 실비 예치금으로 표현하지 않는다.

설명용 예: 고객에게 확정한 배송비가 30,000 VND이면 실제 기사 비용 35,000 VND의 차액 5,000 VND는 매장 부담이다. 실제 비용이 25,000 VND이면 차액 5,000 VND를 기록한다. 실비 차이에 따른 자동 추가 청구·자동 환불은 하지 않는다. 주문 취소·배송 실패에 따른 환불은 별도다. 이 예시는 도입할 요금표가 아니다.

가까운 배송 구역부터 운영하고 원거리·비용 변동이 큰 조건은 함께 결제 적용 범위에서 제외한다. 구체적인 구역·요금·허용 비용 차이는 기존 기사 비용 데이터를 확인해 정한다. 매장이 차액을 부담하기 어렵다면 함께 결제 옵션을 열지 않고 기사 직접 지급을 운영한다. 음식 완성 후 전체 금액을 받는 방식은 미결제 조리·취소 손실을 늘릴 수 있어 기본안으로 권하지 않는다.

## 고객과 직원 화면

- 고객은 배송지 입력 후 매장이 허용한 방식 중 선택한다. 함께 결제의 배송비가 캐셔 확인이 필요하면 결제 전에 최종 총액을 안내한다. 기사 직접 지급은 매장 결제액에서 배송비가 제외되고 실비는 기사에게 지급한다고 표시한다.
- 기사 직접 지급에도 예상 배송비 또는 안내 범위를 제시할 수 있다. 예상 금액은 확정 금액으로 표시하지 않으며, 배차 비용이 안내 범위를 크게 벗어나면 인계 전에 고객에게 확인한다.
- 고객 선택은 주문 요청에 저장하고, 캐셔가 발행하는 최종 견적에 같은 방식으로 확정한다. 캐셔가 고객 선택을 조용히 바꾸지 않는다. 변경은 결제 전에 고객이 확인한 새 견적으로 처리한다.
- 캐셔 목록, 주문 상세, 포장/기사 전달 정보에 `배달비: 고객→기사` 또는 `배달비: 매장→기사`를 동일하게 표시한다. 음식 대금 수금과 배달비 지급자를 혼동하지 않게 한다.
- 조리 완료 후 기사를 호출한다. 직접 지급 주문은 매장 배달비 입금 확인·금고 차감 단계가 없고, 함께 결제 주문은 원 결제에서 받은 배송비와 실제 기사 비용·실제 현금 지급을 각각 기록한다.
- 함께 결제 주문은 실제 기사 비용과 고객 확정 배송비가 다르다는 이유만으로 미수금·환불 의무를 새로 만들거나 인계를 막지 않는다. 필요한 현금 지급 확인과 포장/인계 조건은 유지한다.

## 구현 시 현재 계약에서 바꿔야 하는 부분

현재 소스에는 `customer_direct`와 `store_prepaid`가 있으나 지급 방식 선택은 캐셔 화면에 위치한다. 고객 주문 입력·서버 검증·최종 견적에 고객 선택을 전달해야 한다. 버튼만 고객 화면에 옮기는 변경으로 끝내지 않는다.

또한 기존 실비 정산은 배송비가 증가하면 추가 청구, 감소하면 환불 대상으로 처리한다. **정액 배송비 주문을 이 경로에 그대로 넣으면 다시 후청구 문제가 생긴다.** 지급자와 별도로 배송비 정책을 구분해야 한다: `기사 실비 직접 지급`, `고객 확정 배송비`, `매장 실비 후청구`. 기존 견적·입금·지급 원장은 보존하고 새로운 확정 배송비 정책을 과거 주문에 자동 적용하지 않는다.

- 고객 확정 배송비 정책에서는 고객 청구액을 잠그고 실제 비용을 별도 원장에 기록한다. 자동 차액 청구·실비 감소 환불과 정산 gate를 해당 정책에 맞게 분기한다.
- 기사 직접 지급 주문은 배달비 청구·매장 현금 지급 원장을 만들지 않는다. 배차 업체가 발송자 지급만 지원하는 경우 고객 동의 없이 매장 지급으로 전환하지 않는다.
- 후청구 기능은 고객의 별도 요청 등 합의된 예외에서 사용할 수 있도록 유지한다. 최초부터 두 번의 매장 결제를 전제로 하는 기본 UX는 제거한다.
- 금액과 지급 방식은 기존 서버 권한·원자적 결제·상태 버전 계약을 유지한다. 결제 이후 옵션 전환은 기존 결제를 덮어쓰는 방식으로 처리하지 않는다.
- 목록 상태·기간별 고객 배송비/실제 비용/현금 지급/차액은 페이지 또는 기간 단위 JOIN·GROUP BY로 일괄 처리한다. 목록 N건마다 상세나 업체 요금을 조회하지 않고 목록 RPC는 1회로 유지한다. 기존 환불/청구별 invoice 처리 루프를 사용하는 예외 경로는 앞 계획의 batch 교체 요구를 유지한다. 구현 후 목록 1/50/100/200건의 실제 호출 수와 SQL 내부 반복 조회를 검증한다.

## 적용 순서와 판단 기준

1. 수령자 지급 가능 여부와 매장이 허용할 옵션을 확인한다. 정액 배송비·적용 범위가 정해지기 전에는 임의 요금표로 함께 결제를 활성화하지 않는다.
2. 고객 선택 → 캐셔 견적 → 입금 확인 → 기사 지시까지 지급자를 일관되게 연결한다.
3. 고객 확정 배송비의 실비 차이 처리·기사 현금 지급·마감 계산을 구현하고 실제 비용의 증가/감소에서 추가 입금 요청이 생기지 않는지 검증한다.
4. 후청구는 예외로 검증하고, 채팅 이미지/PDF 전송 수정은 두 방식 모두에서 별도로 완료한다.

운영 판단 기준은 주문당 입금 확인 횟수, 기사 대기, 고객 재연락, 배송비 차액, 잘못된 이중 수금이다. 목표는 정상 주문의 매장 입금 확인 1회이며, 함께 결제는 고객의 배달비 추가 지급 없이 완료되는 것이다. 구체적인 요금 정책과 옵션 제공 범위는 아직 확정하지 않았다. 이번 작업은 수정 아이디어와 소스 계약 검토이며 기능 구현·운영 변경·새 테스트 실행은 하지 않았다.
