# 신규 매장 식별·신고·구매·품질 구조 재검토 및 개선 계획

작성일: 2026-10-21 · 검토 기준: `49ffc0ff6b380e8fb009c42ee5cdff757958e97a`

보완일: 2026-10-22 · 단층 매장의 층 정보 선택 사항, 홀/구역 중심 배정, 필요한 계정만 생성하는 기준을 명시했다.

대상: 분식클럽·전가복 및 이후 등록하는 매장. 이번 산출물은 **조사와 개선 계획**이다. 애플리케이션 구현, 운영 데이터 수정, 계정 발급, 신고·공급업체 전송, 배포는 하지 않았다.

이 문서는 [기존 개점 구조 계획](store_opening_architecture_review_20261021.md)을 매장 전체 수명주기로 확장한다. 일반 옵션·다중 주방·게시/전환의 실제 구현 범위는 [이행 기록](store_opening_implementation_20261021.md)에 남아 있다. 그 기능을 다시 미구현으로 분류하지 않는다.

## 1. 결론

추가 개선이 필요하다. 핵심은 **매장 하나를 등록하면 필요한 식별자와 권한이 생성되고, 같은 매장 식별자가 판매·신고·구매·검수·재고·회계·폐점까지 유지되는 계약**이다.

현재도 매장 UUID, 계정 자동 발급 작업, 법인/브랜드/매장 관계, 매장별 매출 집계, 발주 승인·검수·원자적 재고 반영이 있다. 문제는 일부 생성 경로가 이 절차 밖에 있고, 계정 생성 틀이 실제 업무 구성과 다르며, 신고 파일과 품질 기준까지 연결된 개점 판정이 없다는 점이다. 새 테이블을 많이 만드는 것보다 **기존 기능을 하나의 개점 절차와 일관된 변경 규칙으로 연결하는 작업**을 우선한다.

우선 해결할 사항은 다음과 같다.

1. 모든 신규 매장 생성 경로를 멱등한 개점 명령으로 통합한다. 내부 ID와 표시 코드는 자동 생성하되 실제 세금번호·은행정보는 검증된 자료로 등록한다.
2. 선택한 업무 구성에서 필요한 계정·장치·주방·층 배정을 산출한다. 전가복의 checker를 다시 만들지 않고, 분식클럽의 트레이를 유지한다.
3. 법인 신고 합계와 매장별 내역이 신고 파일에서도 직접 대사되게 한다. 다운로드, 대표 확인, 외부 신고 증거를 다른 상태로 기록한다.
4. 구매 준비 기준을 역할·품목·거래처·단위·승인 정책·검수 기준·회계 연결까지 확장한다.
5. 품목별 검수 기준과 재고의 로트·보류 상태를 도입한다. 기존 합격 입고 수량·부족분 이월·반품·정산 원장은 보존한다.

‘확인된 제약’은 읽은 소스에서 확인한 사실이다. ‘개선 제안’은 그 사실과 외부 구조를 바탕으로 한 설계 판단이다. 실제 운영 DB 적용 여부나 현장 장애 발생을 이번 조사로 입증한 것은 아니다.

## 5. 목표 계약

### 5.1 ID는 목적별로 분리한다

| 종류 | 생성·변경 규칙 | 사용처 |
|---|---|---|
| 내부 매장 ID | 기존 `restaurants.id` UUID 유지. 신규는 서버 생성. 이름/주소/브랜드 변경으로 재발급하지 않는다. | 모든 FK, 접근 권한, 재고, 매출, 외부 매핑 |
| 표시용 매장 코드 | 서버에서 전역 충돌 없이 할당하고 예약한다. 예: `ST0123`은 현재 2~6자 제약 안의 제안 형식이며 기존 `BT`, `JGBT`는 유지한다. 미리보기는 예약인지 예상값인지 표시한다. | 화면·문서·대사표·현장 지원 |
| 로그인 계정 코드 | 구성의 역할/장치 slot을 기준으로 자동 생성. 코드와 별개인 요구사항 ID로 중복 방지. 계정명을 파싱해 권한을 판정하지 않는다. | Auth 계정과 `users`의 명시적 연결 |
| 작업자·장치·주방·구역 ID | 각각 안정 ID를 가진다. ‘주방2’라는 이름, 태블릿 로그인, 물리 장치는 서로 구별한다. | 배정·권한·알림·작업 기록 |
| 주문/PR/PO/입고 내부 ID | 기존 UUID와 원문서 행 계보 유지. 사람이 보는 문서번호는 별도다. 번호 할당은 동시성 안전한 서버 sequence/할당기로 한다. | 중복 요청 방지·문서 추적 |
| 신고 배치 ID | 생성 시 자동 발급. 포함 원천 목록/해시·세부 scope와 연결한다. | 파일·대표 확인·외부 접수 증거 |
| 외부 시스템 ID | `provider + external_id + 내부 대상 + 유효 기간` 매핑. 실제 응답 또는 검증된 자료로만 등록한다. | Office, MISA, 결제/장치 연결 |
| 법정 세금번호·은행정보 | 자동으로 꾸며내지 않는다. 법인 원본 자료와 담당 확인을 거쳐 등록한다. | 법인 신고·수금·공급업체 지급 |

식별자 규칙은 값의 형식뿐 아니라 **유일성 범위, 발급 주체, 재사용 금지, 변경/폐점 후 보존, 재시도 키**를 명시한다. 문서번호가 중간에 건너뛰어도 UUID를 새로 만들거나 이미 발급된 번호를 재사용하지 않는다. 기존 발급 번호의 형식을 일괄 변경하지 않는다.

자동 발급 명세는 다음처럼 구성에서 계산한다. 이는 신규 기본값 제안이며 기존 계정을 이름에 맞춰 교체하라는 뜻이 아니다.

| 대상 | 신규 매장 등록 시 처리 |
|---|---|
| 브랜드 관리자 | 해당 브랜드의 유효 계정을 재사용한다. 없을 때 필요한 slot만 생성한다. 구매 BM 승인 역할은 부여하지 않는다. |
| 법인 회계·Office buyer | 해당 법인의 기존 회계 계정과 Office의 실제 buyer를 연결한다. 새 법인에서 필요 계정이 없으면 별도 법인 계정 발급 작업으로 연결하고 완료 전에는 구매 준비를 미완료로 표시한다. |
| 점장·POS | 필요한 역할과 승인된 POS 단말 수에 맞춰 생성한다. 사람과 단말 계정을 혼동하지 않는다. |
| 주방 | 선택한 주방 station 수와 담당 장치에 맞춰 생성/연결한다. `kit` 접미사 하나로 모든 주방을 배정하지 않는다. |
| 트레이·홀/구역 | 동선에 트레이가 있을 때만 생성한다. 단층은 홀 하나와 실제 담당 계정/장치를 연결하고 층별 계정을 강제하지 않는다. 다층에서는 구역 ID와 저장 층/고객 표시 층을 명시적으로 연결한다. |
| 발주·입고 | 기존 PR 계정 통합 역할을 기본으로 한다. 기존 `_order` 계정 이력/접근은 자동 삭제하지 않으며 신규 별도 입고 계정은 실제 필요 구성에 따른다. |
| 출력·고객 화면 | 해당 기능을 사용할 때만 계정을 요구한다. 종이 없는 운영에서 print 계정 미생성은 개점 실패가 아니다. |
| 테이블·QR | 새 매장 소유의 테이블 ID와 접근 token을 발급한다. 일반 고객에게 직원 Auth 계정을 만들지 않는다. 기존 QR/token은 이행만으로 바꾸지 않는다. |

계정 발급 성공, 매장 접근권 생성, station/구역 배정, 장치 로그인 확인을 각각 검사한다. ID 문자열을 만들었다는 것만으로 사용 준비가 완료되지 않는다.

### 5.2 개점 작업은 재개 가능한 하나의 절차로 묶는다

```mermaid
flowchart LR
  A[법인·브랜드·매장 등록] --> B[코드·계정·장치 배정]
  B --> C[판매·신고·구매·품질·재고 설정]
  C --> D[검증 증거와 설정 버전 고정]
  D --> E[매장 영업 활성화]
  E --> F[운영 변경·중지·폐점]
```

- 기존 account job을 재사용하고 상위 개점 작업에 하위 상태를 연결한다. DB 저장, Auth 생성, Office 연결, 장치 확인을 하나의 DB 트랜잭션으로 가장하지 않는다.
- 준비 항목은 필수 여부와 `not_applicable / pending / ready / blocked` 상태, 이유·책임자·증거·검사 시각·대상 revision을 가진다. 사용하지 않는 프린터나 배달 채널은 명시적 비대상으로 처리한다.
- 영업 준비: 식별/권한, 메뉴·가격·옵션·세금 mapping, 주문 채널, 동선/장치, 결제·수금, 재고/레시피, 현장 모의 운영. 구매 준비: 역할, Office 연결, 정책, 품목/거래처/단위/품질, 입고·회계 대사.
- 개점 전에 첫 재료 발주·입고가 가능해야 한다. 따라서 `영업 활성화`와 `구매 사용 가능`을 같은 boolean으로 묶지 않는다. 통합 화면에서 각각의 상태를 보여준다.
- 기존 `is_active`는 Office·접근 제어 호환값으로 보존한다. 초기 백필에서는 영업 중인 기존 매장을 `legacy_operational`로 식별하고 부족한 준비 항목을 알림으로 표시한다. 새 기준을 이유로 기존 주문·결제를 즉시 차단하지 않는다.
- 새 매장의 영업 활성화는 검증 revision과 현재 revision 일치, 필요한 장치 확인, 모의 주문 증거로 원자 판정한다. 운영 중 일부 설정의 장애가 생겨도 이미 받은 주문·결제·정산을 끝낼 경로를 유지한다.
- 코드/계정/설정 복사 시 비밀번호·외부 token·입고/매출 이력·테이블 QR·장치 pairing을 복제하지 않는다. 필요한 데이터만 새 매장 소유권으로 생성한다.

개점 준비 화면에는 아래 항목까지 빠짐없이 연결한다. 기존 기능을 새로 만드는 목록이 아니라 설정 소유자·비대상 여부·검증 증거를 모으는 체크리스트다.

| 묶음 | 명확히 할 기준 |
|---|---|
| 기본 운영 | 국가/시간대/통화, 매장 유형, 영업일·요일/휴일·주문 시간, 언어·주소·연락처. 현재 VN/HCM/VND 계약을 유지하고 다국가 기능을 임의 추가하지 않음 |
| 판매 채널 | 매장/POS·QR·직접 포장/배달의 사용 여부, 테이블·구역, 매진·주문 수락/취소 권한, 고객 연락/영수증 전달 방식 |
| 메뉴 | 카테고리·판매 ID·부모/규격·옵션·콤보·가격/VAT·레시피·판매 채널. 알레르기 등 추가 표시가 필요하면 검증된 원재료 자료와 책임자를 먼저 정의 |
| 조리·인계·출력 | station별 담당자/장치·라우팅·부분 수량·포장 담당·화면/소리·프린터 목적·테스트·재출력 증거 |
| 결제·현금 | 허용 결제 수단·수금계좌·거스름/반올림·분할/환불·할인 권한·시재·현금 마감. 매출 신고 확정과 별도 |
| 신고 | 법인 소속·송장 정책·메뉴 mapping·매장별 대사·확인자·외부 연결. 결제 성공은 MISA 가용성과 분리 |
| 구매·재고 | 승인 정책·담당자·거래처·단위·규격·품질·초기 잔액·레시피 연결·안전재고·입고/지급 대사 |
| 장애·운영 인수 | 오프라인 큐·미지원 클라이언트·장치 교체·재시도 책임·담당자 교육·연락 경로·복구 리허설·변경 이력 |

현재 폐기된 Deliberry·Photo 자동 수집은 항목을 추가하여 재활성화하지 않는다. Photo가 신고에 함께 들어오는 경우 기존 수동 Excel 자료만 사용한다. 고객 배달비도 새 기본값이나 0원 항목으로 생성하지 않는다.

#### 단층·다층과 업무 동선을 독립적으로 설정한다

단층 매장은 기본 지원 대상이다. **물리적 층은 선택 정보이며, 서비스 배정은 홀/구역 ID를 기준으로 한다.** 단층이라고 주방이 반드시 하나인 것도 아니고, 다층이라고 트레이가 반드시 필요한 것도 아니다.

| 매장 구성 | 개점 입력과 동선 예시 |
|---|---|
| 단층·홀 하나 | 기본 구역 `홀`을 자동 생성하고 테이블을 배정한다. 층 번호 입력·층 선택 화면 없이 `주방→홀 담당→고객`으로 구성할 수 있다. |
| 단층·트레이 사용 | 같은 홀 구성이어도 업무에 필요하면 `주방→트레이→홀 담당→고객`으로 설정한다. |
| 단층·여러 구역/주방 | 필요할 때 홀 A/B·룸·테라스를 추가한다. `주방1→주방2→홀 담당→고객` 등 조리 순서는 별도로 설정한다. 구역마다 전용 계정을 강제하지 않는다. |
| 포장·배달 전용 | 홀·테이블·층 계정을 요구하지 않고 주방→포장/픽업 담당→인계로 구성한다. 지원하는 채널의 상태 전이와 권한을 검증한 뒤 활성화한다. |
| 여러 층 | 물리적 층 아래에 홀/룸 등 구역을 연결한다. 기존 저장 층과 고객 표시 층, 담당 계정 매핑을 보존한다. |

- 화면에는 기본적으로 `홀`을 표시하고 물리적 층을 추가할 때 층 구분을 노출한다. 단층 사용자가 가상의 2F/3F를 만들거나 불필요한 층별 계정을 발급받지 않게 한다.
- 서비스 구역, 인계 단계, 담당 계정, 실제 장치 수는 별도다. 같은 담당자가 여러 구역을 맡을 수 있지만 배정과 권한은 명시적으로 저장한다. 주방 완료 알림은 해당 주문의 구역 담당 장치로 전달한다.
- 홀 전용 태블릿이 없으면 인계를 받을 지원 화면/담당 계정을 명시한다. 수신 대상이 없는 상태를 준비 완료로 표시하거나 조리 완료를 자동 서빙 완료로 처리하지 않는다.
- 기존 단층 매장의 `1F`나 전가복의 저장 층은 삭제/NULL 변경하지 않는다. 신규 구역 ID와 기존 값의 호환 매핑을 둔다. 신규 모델의 층 선택 사항을 구형 KDS·RPC·출력에서도 안전하게 처리하도록 어댑터를 검증한다.
- 매출 신고·발주·재고의 기본 소유자는 매장 ID다. 층/홀 구분은 필요할 때 쓰는 운영 상세이며, 층이 없다는 이유로 신고·구매 준비를 실패시키지 않는다.

### 5.3 매출 신고에서 법인과 매장을 함께 보존한다

- 신고 주체는 기존 `tax_entity_id`, 사업장 구분은 `store_id`다. 법인×브랜드는 기존 관계를 사용한다. 단순 `법인→브랜드→매장` 트리로 다시 설계하지 않는다.
- 화면/파일의 기본 식별은 `법인 · 매장코드 · 매장명`이며 계산과 권한은 ID로 한다. 동일 명칭 매장, 이름 변경, 폐점 매장, 법인 이전 전후도 식별할 수 있어야 한다.
- MISA 입력 시트의 17열 계약을 유지한다. 보조 시트 `Store Summary`와 버전이 명시된 대사 데이터에 매장 ID/코드/명, 영수증 수, 매출/공급가/VAT, 결제별 수금, 환불/조정, 원천·반올림 차이를 담는다. 소비자가 엄격한 기존 Ledger 형식을 요구하면 새 버전의 별도 보조 시트를 사용한다.
- 신고 파일은 법인 단위가 기본이다. 매장 필터/매장 파일을 지원할 때도 **법인 전체인지 일부 매장인지**, 포함 매장 집합과 제외 이유를 manifest에 기록한다. 한 영수증이 전체 파일과 부분 파일로 중복 신고되지 않게 membership을 관리한다.
- `draft → generated → owner_confirmed → externally_recorded`는 제안 상태다. 파일 생성은 신고 완료가 아니다. 실제 접수 여부는 외부 참조·파일 해시·확인자·시각·증거에 따라 표시한다. 자동 MISA 발행과 수동 업로드도 같은 영수증 범위로 중복 검사한다.
- 대표 확인 뒤 추가 결제/환불이 생겨도 판매를 막지 않는다. 원본 배치는 보존하고 추가분/조정분을 별도 revision과 연결한다. MISA 수정·취소·PDF는 기존 포털 책임으로 둔다.
- 매출 발생·결제·입금·현금 마감·대표 확인·외부 접수 시각을 구분한다. 현재 HCM 영업일과 매출 원천 판정은 유지하며 시간대 일반화가 기존 날짜를 바꾸지 않게 한다. 22:20 자동 확정은 되살리지 않는다.
- 당일 법인 이전은 한 매장이라는 이유로 합치지 않는다. 영수증/원장 시점의 법인과 효력 이력으로 나누고, 과거 데이터의 소속을 현재 매장 법인으로 덮어쓰지 않는다.

### 5.4 구매·품질·재고의 경계를 고정한다

1. **누가 주문하는가:** PR 계정은 요청·입고·검수 가능이라는 2026-10-20 정책을 유지한다. 점장 수량 검토·승인과 buyer 최종 승인은 그대로다. BM 승인을 다시 추가하지 않는다. 법인 회계/Office buyer를 매장마다 중복 생성하지 않는다.
2. **무엇을 사는가:** 원재료 코드, 제품 규격, 공급업체 SKU, 구매 포장, 기준 단위, 환산, MOQ, 납기, 가격/VAT 효력, stock/nonstock를 연결한다. PO 발행 때 이 값을 고정한다. 이후 마스터 수정으로 과거 PO 금액이나 기대 수량이 변하지 않는다.
3. **어떻게 검사하는가:** 기준 템플릿은 품목/규격별 필수 측정·허용 범위·기한·표본·증거·예외권한을 가진다. 승인된 기준 버전을 PO/입고에 연결한다. 검수 당시 변경된 기준이 필요하면 명시적 변경·재검수 기록을 남긴다. 숫자만 입력했다는 이유로 합격시키지 않는다.
4. **어떤 수량이 사용 가능한가:** 실물 수령량=합격+불합격+보류. 검수 확정과 사용 가능 재고 반영은 원자적으로 수행한다. 보류 해제/반품/폐기는 원행·로트 참조와 멱등 키를 가진다. 보류를 부족분 이월에 중복 계상하지 않도록 원 PO의 미이행·보류·이월량을 각각 계산한다.
5. **기존 완납 계약:** 원 PO 각 행의 누적 합격 수량으로 완납을 판단한다. 보류·반품·취소·이월로 분모를 줄여 완납으로 표시하지 않는다. 부족분은 다음 PR에 예약하고 새 PO 발행 때만 기존 미입고 잔액을 이전한다.
6. **증빙과 돈:** 공급업체용 가격 없는 완납/차이 PDF와 내부 금액/지급 자료를 구별한다. 매장 ID/코드/당시 명칭·문서 ID·원 PO·입고 차수·hash로 추적한다. 파일 생성, 전송, 입고, 지급은 각기 다른 상태다. 기존 PDF는 재작성하지 않는다.
7. **사용·회수:** 사용 가능한 로트에서만 출고한다. 유효기한 관리 품목의 FEFO, 유통기한 없는 품목의 기존 방식, 수동 선택 사유를 명시한다. 공급업체 로트→매장 입고→사용/폐기/반품을 추적한다. 과거에 기록하지 않은 로트나 소비 연결은 `unknown_legacy`로 남기며 만들어내지 않는다.
8. **재고와 조리:** 주방 스테이션과 재고 보관 위치는 별개다. 새 주방 단계를 만들었다고 재고를 다시 차감하지 않는다. 기존 레시피 소모 시점과 합계는 유지하고, 로트 연결은 같은 소모 사건에 붙인다. 재조리 시 별도 소모 처리는 후속 계약으로 검증한 뒤 활성화한다.

단계 3은 회계상 거래를 바꾸는 작업이 아니라 식별·대사·확인 증거를 보완하는 작업부터 시작한다. 로트/보류는 재고 소모에 영향이 커서 단계 5의 기준과 기존 재고 대사가 준비된 뒤에만 도입한다. 단계마다 현재 매장 기능을 그대로 통과시키고, 마지막에만 전체 회귀를 하는 방식으로 진행하지 않는다.

## 7. 분식클럽·전가복 이행 및 회귀검증

### 7.1 데이터 이행

- `restaurants` 물리 테이블, 기존 ID/name/address/is_active, `restaurant_id` FK, `stores` 호환 view와 Office 읽기 계약을 유지한다. 기존 계정·메뉴 판매 ID·거래처·PO/입고/영수증 ID를 재발급하지 않는다.
- 기존 매장의 baseline을 캡처해 신규 프로필에 연결한다. 기존 코드는 그대로 등록하고 중복/빈 값만 사람이 확인할 이행 예외로 남긴다. 이름 유사도로 자동 병합하지 않는다.
- 법인 이력은 기존 `store_tax_entity_history`를 재사용한다. 필요한 브랜드/표시명 이력을 추가하되 과거에 알 수 없는 이름·소속·로트를 추측하여 채우지 않는다.
- additive schema→백필→비교 읽기→기능별/매장별 전환 순서로 적용한다. 백필은 재실행 가능하며 쓰기 원장은 하나를 유지한다. 이중 쓰기로 재고/지급을 중복시키지 않는다.
- 기존 거래가 발생한 뒤의 rollback은 DDL 삭제가 아니다. 새 기능의 신규 접수를 보류하고 해당 버전으로 기존 업무를 완료하며, 읽기/호환 어댑터는 유지한다. 신규 버전 기록을 구형 화면에서 안전하게 처리할 수 없으면 무조건 구형으로 돌리지 않는다.

## 8. 데이터 접근·성능 계획

아래 수치는 운영 실측치가 아닌 초기 시험 조건이다. 실제 규모를 단계 0에서 확인해 조정한다.

- 규모: 매장 100개, 매장당 계정 최대 50개·구매 품목 2,000개, 입고 100행, 신고 하루 10,000 영수증으로 기능/부하 시험을 구성한다. 기존 업무의 더 낮은 행 제한은 먼저 유지한다.
- 준비 상태는 매장 ID 최대 100개 batch와 관계별 사전 집계로 읽는다. 매장별로 account→buyer→품목을 따로 호출하는 구조를 만들지 않는다. 상세는 필요할 때 조회하며 초기 목록은 50~100개 keyset page를 사용한다.
- 기존 Auth worker의 DB 준비/대사 2 RPC·Auth 최대 50회·동시 2개 제한을 유지한다. bulk API 없는 Auth 쓰기는 예외를 명시하고 재시도 총시간/횟수에 상한을 둔다. 단순 병렬 호출을 DB N+1 해결로 세지 않는다.
- 신고의 기존 100영수증 page와 source/mapping revision 검증을 재사용한다. 매장별 파일 때문에 같은 법인 전체 원천을 매번 다시 읽지 않는다. 다대다 invoice mapping/결제/행 JOIN은 각각 선집계해 금액 배증을 막는다.
- 현재 Excel 생성은 jobs를 모아 workbook을 만들므로 페이지 조회만으로 메모리가 제한되는 것은 아니다. 대용량은 서버 생성/분할 artifact를 설계하고 각 부분의 범위·합계를 manifest에 남긴다. 현재 대량 시험으로 확인되지 않은 최대 지원량을 광고하지 않는다.
- 품질 검사는 입고 batch의 품목/정책 버전을 한 번에 읽고 집합으로 검증한다. 항목마다 SELECT·외부 사진 확인·가격 조회를 하지 않는다. 증거 파일 검증은 제한된 batch/동시성으로 분리한다.
- 수요 근거는 요청한 품목/기간으로 제한하고 장기 전체 이력은 사전 집계·증분 갱신을 검토한다. 새 로트/품질 기준을 현재 전체 품목 JSON에 무제한 덧붙이지 않는다.
- 폐점의 사용자별 claims 갱신 등 재사용할 반복 경로도 배치로 바꾼다. `(store_id, status, effective_at/id)` 계열 인덱스는 실제 조건과 `EXPLAIN (ANALYZE, BUFFERS)`를 보고 결정한다.
- 캐시 키에 사용자·접근 범위·매장·기간·revision을 포함한다. 권한 변경 시 무효화하고 같은 요청의 진행 중 작업을 공유한다. 쓰기 재시도는 payload와 actor를 고정한 멱등 키로 한다.
- 측정: API/RPC 수, SQL 내부 호출 수, 읽은/쓴 행 수, 응답 bytes, p50/p95, 잠금 대기, export peak memory. 동일 조건에서 전후 비교하며 기존 p95/메모리 10% 이상 악화는 원인 검토 대상으로 삼는다. 수치 통과 목표는 기준선 측정 후 확정한다.

## 10. 업무 기준 확정과 검증 범위

계획과 구조 작업은 진행할 수 있다. 실제 활성화 전에 다음 값은 기존 등록 자료를 먼저 확인하고 담당자가 확정한다: 품목별 온도/잔여 기한·검사 예외 권한, 신규점 초기 재고/원가·안전재고, 법인별 외부 신고 대상과 접수 증거 방식, 공통 코드 표시 형식, 회계 대사 허용 차이, 미결 업무가 있는 폐점의 처리 책임. 이를 임의의 숫자나 외부 POS 기본값으로 채우지 않는다.

이번 조사에서는 전역 및 프로젝트 `CLAUDE.md`, root `AGENTS.md`를 읽었다. 별도 하위 지시 파일은 발견되지 않았다. 깨끗한 작업 트리에서 시작했으며 현재 소스·migration 순서·기존 테스트 정의·외부 공식 자료를 검토했다. 운영 DB, Office 앱 구현, 실제 신고/공급업체 수신, 실 장치는 이번에 검사하지 않았다. 따라서 L15 등 외부 경계는 확인 과제이며 운영 결함으로 단정하지 않는다.
