# Bunsik 원료 코드 전환 및 재고실사 Excel 업로드 계획

작성일: 2026-09-30 · 기준 시간대: Asia/Ho_Chi_Minh

**결정: 첨부 Excel에 이미 배정된 구매 요청 코드 123개를 그대로 사용한다. 먼저 분식클럽 빈탄의 기존 원료 104개 코드를 변경하고 미등록 19개를 추가한다. 그 완료 상태를 기준으로 샘플 매장의 기존 원료를 전부 제거한 뒤 빈탄의 전체 원료 123개를 샘플 매장에 복사한다. 재고실사는 빈탄 매장에서 진행하고, 실사 Excel 업로드로 반영한다. DR, GO를 포함해 원본 코드를 재해석하거나 재번호하지 않는다.**

실행 상태: 코드 전환·샘플 초기화/복제 SQL과 실사 Excel 다운로드·업로드 기능을 구현했다. 로컬 테스트에서 코드·공급처·재고 복제 일치, 임시 저장의 재고 미변경, 중복 업로드 방지, 동시 재고 변동 시 완료 차단을 확인한다. 운영 반영 여부는 실행 보고서에서 별도로 기록한다. 초기 계획용 Excel과 실제 업로드용 Excel은 형식이 다르므로, 배포 후 POS 재고실사 메뉴의 **실사표 다운로드**로 받은 파일을 사용한다.

구현한 실사 사용 순서:
1. 빈탄 매장을 선택하고 영업·입출고를 마감한 뒤 재고실사 → 실사표 다운로드.
2. `재고실사` 시트의 `actual_quantity`에 수량 입력. 빈칸은 미실사이고 0은 실제 재고 없음이다. 기본 단위는 g/ml/ea이며 kg→g, L→ml만 추가 지원한다. 불확실한 박스·봉 단위를 추정해서 바꾸지 않는다.
3. `설정` 시트 B6 `counted_at`에 실사 시각을 한 번 입력한다(예: `2026-09-30T23:30:00+07:00`). 품목별 시간이 다르면 해당 행에 입력한다. 제외 품목은 수량을 비우고 `excluded_reason`을 입력한다.
4. 실사 엑셀 업로드 → 전체 차이 미리보기 → 임시 저장 또는 완료. 임시 저장은 재고를 변경하지 않는다. 모든 품목이 실사되거나 명시적으로 제외되어야 완료할 수 있다.
5. 초안을 저장한 뒤 다시 올릴 때는 갱신된 실사표를 다운로드한다. 그 사이 판매·입고 등 재고 변화가 있으면 완료를 차단하므로 실사 다시 시작으로 새 표를 받고 다시 실사한다.

추가 19개는 Excel에 가격이 없으므로 구매 가능/공급처 링크 활성화를 보류하고 가격·세율·발주 조건 확인 후 활성화한다. 공급처 표기는 원본의 `Đại lý Trinh Dũng`와 `PACKAGING`을 유지한다.

## 3. 빈탄 코드 변경 → 샘플 원료 전량 교체

1. **빈탄 기준 스냅샷과 샘플 의존성 확인:** 빈탄의 원료/재고 UUID, 기존/새 코드, 단위·환산계수, 가격, 이미지, 수량, 공급업체 링크 및 참조 데이터를 백업한다. 샘플은 테스트 데이터이므로 보존 대상이 아니며, 실행 직전에 샘플 발주·입고·가격 이력 등의 참조 건수를 다시 세어 초기화 범위와 삭제 순서를 확정한다. 조사 완료 수량을 전환 전 백업에 섞지 않는다.
2. **빈탄 대조표 고정:** 파일의 기존 코드·원료명과 빈탄의 기존 104개 UUID를 일대일로 검증한다. 중복 UUID/코드, 바뀐 기존 코드, 선점된 새 코드가 있으면 중단한다.
3. **빈탄 코드 전환:** 빈탄 범위의 트랜잭션에서 `inventory_products.product_code`만 104건 갱신하고 감사 이력을 남긴다. 빈탄의 제품/재고 UUID, 재고수량, 레시피, 공급처 링크는 유지한다. 공급업체의 실제 SKU를 구매 요청 코드로 덮어쓰지 않는다.
4. **빈탄 19개 신규 등록:** DR 6개와 GO 13개를 원본 코드로 추가한다. 단위·환산계수·공급처 연결과 누락 가격의 처리 상태를 검증한다. 마스터 생성 시의 기본 수량 0은 실측값이 아니다. 검증 완료 후 빈탄 전체 123개를 기준 스냅샷으로 고정한다.
5. **샘플 테스트 원료 전량 교체:** 샘플에 새 발주/입고/원료 편집이 들어오지 않는 작업 구간을 잡는다. 기존 샘플 원료 104개가 참조된 가격 이력·발주/입고 라인 및 관련 헤더 등 샘플 테스트 데이터를 의존 순서대로 삭제하고, 기존 `inventory_supplier_items`·`inventory_products`·`inventory_items`를 제거한다. 실행 직전에 다른 FK 참조 건수도 확인한다. **샘플 매장 ID로 범위를 제한하고, 거래처 마스터나 빈탄 데이터는 삭제하지 않는다.**
6. **빈탄 원료 복사:** 고정한 빈탄 123개의 제품/재고 속성, 코드, 명칭, 분류, 구매·기준 단위, 환산계수, 이미지, 재주문 기준, 단가, 활성/발주 상태, 현재 재고 및 공급업체 품목 링크·선호 공급처·구매단위·가격을 샘플의 새 원료·재고 UUID로 복사한다. 두 매장은 같은 DB에 있으므로 빈탄 UUID를 샘플에서 재사용하지 않고 `source_product_id → sample_product_id`, `source_item_id → sample_item_id` 매핑을 남긴다. 공유 브랜드 거래처 마스터는 재사용하며, 제품에 연결되는 샘플 거래처 링크는 새 제품 UUID로 생성한다. 빈탄의 판매/입고/폐기 거래 이력, 실사 세션, 발주/입고 문서는 복사하지 않는다. 복사한 현재 재고는 샘플의 시작 상태로 별도 기록한다.
   현재 산출물의 `샘플복제계획` 시트에는 아직 빈탄에 등록되지 않은 DR/GO 19개의 원본 UUID가 비어 있다. 빈탄 신규 등록 후 해당 UUID를 다시 조회해 복제 실행 대조표를 완성한다.
7. **두 단계 검증과 복구:** 빈탄에는 123개 코드, 기존 104개 UUID/재고/레시피 불변을 검증한다. 샘플에는 기존 원료/재고 UUID가 0개 남고 신규 123개가 빈탄과 **코드·원료 속성·단위·환산·초기 재고·공급 링크 기준으로 동일**한지 비교한다. 매장 ID와 새 UUID만 다르다. 샘플 교체가 실패하면 샘플 작업 전체를 롤백한다. 빈탄 코드 변경의 역전환은 별도 이전 코드 매핑으로 처리하며 이미 실사 확정한 재고를 과거 값으로 덮어쓰지 않는다.

기존 원료 등록 업로드로도 UUID를 넣으면 코드 갱신은 가능하지만 이번 전환에는 **코드 전용 일괄 갱신**을 권장한다. 기존 bulk 업로드는 코드 외 필드를 upsert하고 이미지 인자를 NULL로 전달하며 거래처 품목 정보도 갱신한다. 코드를 바꾸기 위해 해당 부수 변경까지 감수할 이유가 없다. 첨부 원본 역시 현재 `원재료등록` 양식과 구조가 다르다.

코드 발급 규칙은 영문 대문자 2자리+001–999, 000 금지다. 최초 배정은 첨부 파일을 그대로 따르고 이후에는 공급업체/그룹별 마지막 번호 다음을 발급한다. 행 정렬·품목명 변경·공급업체 변경 때 재번호를 부여하지 않는다. 삭제된 번호는 재사용하지 않고, 999 도달 시 자동 확장하지 않고 신규 약어 정책을 정한다. 빈탄에 새 코드가 추가될 때 샘플 복제 정책도 함께 적용해 샘플이 다시 뒤처지지 않게 한다.

## 4. 오늘 실사 전에 확인할 단위

파일의 포장/구매 단위와 DB의 g·ml·ea는 다르다. 파일 H열 포장 규격과 I열 수량은 품목 데이터 110개에서 비어 있다. 품목명에 500g이 적혀 있어도 그것이 박스 한 개의 환산값이라는 뜻은 아니다.

| 코드 | 원료 | 현재 DB 값 | 조치 |
|---|---|---|---|
| WR014 | 어묵볼 / 2159 | KG 1개 = 500g | kg 표기와 환산계수 충돌. 실제 구매 단위 확인 |
| NK001 | 떡볶이밀떡 / 50001 | kg 1개 = 10,000g | kg인지 10kg 포장인지 확인 |
| WR050 | 멸치액젓 / 8281 | 병 1개 = 1g | 실물 규격 확인 전 포장 환산 금지 |
| WR054 | 주방세제 / 9608 | 통 1개 = 1g | 실물 규격·기준 단위 확인 |
| WR073 | 몽고간장 / 9090 | 품목명 13L, 환산 15,000ml | 실제 규격 확인 |

이는 대표적인 불일치/의심 사례이며 자동으로 올바른 값으로 고쳤다는 의미가 아니다. 나머지도 등록된 g/ml/ea와 포장 규격을 확인한다. 현재 ea인 치즈·핫도그 등을 품목명 무게만 보고 g로 변경하면 레시피 계산이 깨질 수 있다.

첨부 실사 양식은 **빈탄 실사용**이며 기존 104개의 실사 단위를 현재 DB 기준 단위(g/ml/ea)로 제공하여 검증 안 된 포장 환산을 피한다. 음료와 포장재 19개는 원본 단위 그대로 기록하고, 등록 후 검증된 변환을 적용한다. 박스·봉 단위로 센 경우 반드시 실사 단위를 함께 수정하고 포장 규격을 비고에 적는다. 단위가 확정되지 않은 행도 조사 기록은 보존하되 재고 반영은 보류한다. 샘플 매장에는 이 실사 파일을 업로드하지 않는다.

## 5. Excel 업로드 사용자 흐름

상단의 구현한 사용 순서를 따른다. 전체 품목을 하나의 실사 시트로 제공하며 UUID·구매 요청 코드·명칭을 미리 채운다. `설정` 시트에는 스키마, 매장, 세션, 버전, 다운로드 시각과 공통 실사 시각을 담는다. 셀 보호에 의존하지 않고 서버가 매장·ID·코드·단위를 검증한다.

음수, 비정상 숫자, 3자리를 넘는 기준 단위 소수, 임의 구매단위, 중복 품목, 변경된 이름/코드, 다른 매장 파일, 수식 셀, 오래된 초안 버전은 거부한다. 여러 보관 장소의 같은 품목은 먼저 수량을 합산한다. 제외 사유를 입력한 항목은 재고 0으로 바꾸지 않는다. 미리보기는 실사/미입력/제외 수와 품목별 장부재고·실측재고·차이를 보여준다. 오류 메시지는 행 번호와 원인을 제공한다.

## 6. 서버 처리 및 실사 시점

`prepare_inventory_stock_audit`가 서버 스냅샷을 저장하고 세션을 만든다. `save_inventory_stock_audit_v2`가 버전·권한·전체 행을 검증해 초안을 저장하거나 완료한다. 실제 측정 시각은 저장된 행에, 업무일은 베트남 시간 기준으로 기록한다. 작성자 계정은 세션과 재고 거래에 기록한다.

완료는 한 트랜잭션에서 세션과 재고 행을 잠그고 스냅샷 이후 제품·재고 변동이 없는지 확인한다. 정상 완료 시에만 실재고와 조정 거래를 함께 기록한다. 같은 완료 요청의 재시도는 기존 결과를 반환하며 이중 조정을 만들지 않는다. 일부 성공은 허용하지 않는다. 초안은 전체 파일로 교체되며 버전 확인으로 오래된 파일의 덮어쓰기를 방지한다.

영업·입출고를 마감하고 마지막 매출 소진 반영까지 끝난 뒤 실사표를 받는다. 이동을 계속해야 하는 경우 이전 수량을 자동 보정하지 않고 완료를 차단하며, **실사 다시 시작**으로 새 스냅샷을 받아 다시 실사한다. 결제 흐름은 변경하지 않는다.

## 7. 실행 순서와 완료 조건

| 순서 | 수행 작업 | 완료 증거 |
|---|---|---|
| 1 | 파일 대조표와 빈탄 백업/샘플 FK 참조 집계 | 원본 123개 일치, 샘플 초기화 대상 확정 |
| 2 | 빈탄 기존 104개 코드 변경 및 신규 19개 등록 | 빈탄 123개, 기존 104개 UUID/재고 불변 |
| 3 | 샘플 기존 원료/참조 전량 정리 후 빈탄 123개 복제 | 샘플 기존 UUID 0개, 새 123개, 빈탄과 속성/코드 일치 |
| 4 | 빈탄 실사 Excel 다운로드/업로드/미리보기/초안/확정 구현과 RPC 차이 수정 | 빈탄 123개 UI 처리, 미리보기 재고 변경 0 |
| 5 | 로컬 및 DB 회귀 검증, 독립 검토, GitHub release gate | exact pushed head SHA의 필수 Actions 성공 |
| 6 | 기존 배포 스크립트로 DB/앱 배포, 운영 읽기 검증 | 함수 시그니처, 양 매장 제품 수·코드·연결 비교 |
| 7 | 빈탄 현장 조사 후 업로드, 차이 검토, 한 번 확정 | 빈탄 completed 세션 1개, 조정 이력 1회, 누락 0 |

마감까지 5–6단계가 끝나지 않으면 빈탄 실사 양식에 **실측 수량·단위·실제 시각을 먼저 기록**하고 안전한 업로더가 준비된 뒤 빈탄에 반영한다. 샘플을 실사 대상으로 대체하지 않는다. 현장 기록에는 구코드와 신코드를 함께 유지하여 전환 전후 모두 식별할 수 있게 한다. 늦게 반영할 때는 6절의 시점 조정/재실사 규칙을 적용한다. 검증 안 된 기존 함수를 이용한 당일 강제 반영은 실행 계획에 포함하지 않는다.

구현 파일: `lib/features/inventory_purchase/stock_audit_excel_import.dart`(신규 파서/양식), `lib/features/inventory_purchase/inventory_purchase_screen.dart`(실사 UX), `lib/core/services/inventory_service.dart`, `lib/features/inventory/inventory_provider.dart`, 신규 Supabase migration/preflight/verify/rollback 및 관련 테스트. 원료 코드 변경과 재고수량 확정은 별도 작업/감사 이벤트로 남긴다.

검증은 빈탄 정상 123행, 0·빈칸·소수, 단위 불일치, 19개 UUID 미등록, 중복 코드/UUID, 샘플 매장 파일 오적용, 권한 거부, 잘못된 원본 수식, 파일 재업로드, 네트워크 재시도, 동시 확정, 마지막 행 실패 시 전체 롤백, 실사 이후 입출고, 완료 후 새 실사를 포함한다. 샘플 복제에서는 FK가 남은 상태의 삭제 거부, 샘플 작업 중간 실패 시 전체 롤백, 기존 샘플 UUID 소멸, 두 매장 123개 코드·속성·연결 비교를 확인한다. 빈탄의 기존 레시피·발주서·입고·Office 조회 연결과 코드 표시도 확인한다.

운영 적용은 CLAUDE.md의 `scripts/deploy_pos_production.sh`를 사용하고 exact head GitHub 체크를 통과해야 한다. 현재 작업 디렉터리의 사용자 수정/미추적 파일은 보존하며 배포 준비에는 별도의 깨끗한 변경 집합을 사용한다.
