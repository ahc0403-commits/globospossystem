이 문서는 [통합 개선 계획](/Users/andreahn/globos_pos_system/docs/plans/direct_order_single_payment_delivery_and_chat_attachments_plan_20261010.md)의 고객 선택·최종 견적 단계를 구체화한다. 충돌 시 이 문서의 **협의 → 고객 확인 → 캐셔 최종 금액 확정** 순서를 적용한다. 포함 결제의 1회 결제·매장 차액 부담, 실제 기사 현금 지급·마감, 양방향 첨부 개선 범위는 유지한다.

## 1. 반드시 지킬 업무 기준

배달 주문은 캐셔가 최종 금액을 확정하기 전에 고객과 아래 방식 중 하나를 협의하고 그 결과를 기록해야 한다. 고객 주문 시 선택은 희망 방식이며, 캐셔가 제시한 조건에 대한 확인을 대신하지 않는다. 미선택·무응답·기본값은 동의가 아니다. 매장에서 한 방식만 제공하거나 고객에게 받을 배달비가 0이어도 조건 확인을 생략하지 않는다.

| 고객 안내 | 매장 결제 | 기사 비용 처리 |
|---|---|---|
| **배달비 포함해서 지금 한 번에 결제** | 음식 대금 + 고객에게 안내한 확정 배달비 | 매장이 기사에게 현금 지급. 이후 실비 증가분은 매장 부담이며 감소분도 기록한다. 고객 추가 청구·실비 감소에 따른 자동 환불 없음. |
| **배달비는 받을 때 기사님께 직접 결제** | 음식 대금만 결제 | 고객이 실제 기사 요금을 기사에게 별도로 지급. 실제 배달비가 달라질 수 있음을 먼저 안내. 매장의 배달비 수금·기사 현금 지급·차액 부담 없음. |

두 번째 방식을 “나중에 매장에 추가 결제”로 표현하지 않는다. 포함 결제에만 고객 1회 결제 완료 약속을 적용한다. 기사 직접 지급은 수령자 지급을 지원하는 배차 상품을 확인한 매장에서만 제안한다. 캐셔는 고객과 협의한 결과를 선택하고, 포함 방식을 안내 기본으로 보여주더라도 합의 상태는 처음에 `미협의`다.

## 3. 화면과 정상 처리 순서

1. **고객 주문:** 가능한 방식과 각각의 지급 상대방을 보여준다. 고객은 희망 방식을 선택할 수 있으며 “매장과 협의 후 확정”이라고 안내한다. 선택하지 않은 경우 캐셔 협의 단계에서 결정한다.
2. **캐셔 협의 제안:** 주문 상세 상단에 `배달비 협의: 미협의 / 고객 확인 대기 / 합의 완료`를 표시한다. 희망 방식에 따라 제안을 준비하고 포함 방식이면 안내 배달비를 입력한다. 버튼은 `배달비 결제 방식 확인 요청`이다.
3. **조건 안내:** 제안에는 지급 방식, 음식/기존 세금·수수료를 반영한 매장 결제 예정액, 포함 배달비, 지급 상대방, 실비 변동 시 부담 주체를 표시한다. 포함 방식은 예를 들어 “매장 결제 예정액 230,000동, 배달비 30,000동 포함, 기사 비용이 늘어도 추가 결제 없음”이라고 안내한다. 직접 방식은 “매장 결제 예정액 200,000동, 배달비는 수령 시 기사에게 별도 지급, 실제 요금은 배차 후 결정”이라고 안내한다. 예시는 음식 등 기존 합계가 200,000동인 경우다.
4. **고객 확인:** 기존 주문/채팅 화면에 전용 카드와 `이 방식으로 진행` / `다른 방식 문의`를 표시한다. 확인은 해당 제안 ID·버전에 연결한다. 문의·거절·무응답은 합의 완료로 바꾸지 않는다. 일반 채팅의 “네”를 자동으로 동의 판정하지 않는다.
5. **캐셔 최종 확정:** 고객 확인 완료가 화면에 반영되면 `최종 금액 확정·결제 안내` 버튼을 활성화한다. 아직 미확정인 일반 요청사항도 모두 처리해야 한다. 서버가 합의한 조건과 현재 주문 계산 결과의 일치를 확인하고 한 트랜잭션에서 최종 견적을 만든다. 고객 확인만으로 자동 견적 확정하지 않는다.
6. **고객 결제 이후:** 기존 실제 입금 확인·조리·조리 완료 후 배차·현금 지급과 인계를 진행한다. 고객, 캐셔, 포장/기사 전달 화면과 영수증에 같은 지급 상대방을 표시해 이중 수금을 막는다.

협의 제안은 정식 결제 견적이 아니다. 제안 중에는 결제 QR·송금 요청·결제 증빙 제출을 열지 않으며 원 주문의 견적 확정 시각, 입금 상태, 주방 주문·매출을 생성하지 않는다. 초기 주문 화면의 계좌 정보 노출도 확인해 아직 협의 중인 금액을 결제액처럼 안내하지 않는다. 제안 전달·확인 화면은 기존 채팅/상태 갱신을 사용하고 새 OS 푸시 발송 기능은 이 범위에 추가하지 않는다.

### 전화·현장에서 협의한 경우

고객이 전화 또는 현장에서 실제로 동의한 경우에는 캐셔의 `전화/현장 합의 기록` 경로로 진행할 수 있게 한다. 별도 관리자 승인을 추가하지 않는다. 전용 폼에서 현재 제안의 방식·배달비·매장 결제 예정액·부담 조건을 다시 보여주고, 협의 채널·실제 협의 시각·고객이 동의한 내용의 메모를 필수로 받는다. 기존 고객 채팅을 근거로 사용할 때는 같은 주문의 고객 메시지를 연결한다. 통화 녹음 업로드를 필수로 만들지 않는다.

서버는 직원 ID·기록 시각·확인한 제안 버전·협의 메모/메시지 연결을 남긴다. 고객이 직접 누른 확인과 직원이 대면/통화 결과를 기록한 확인은 구분해 표시하고, 고객 주문 화면/채팅에도 기록된 합의 요약을 남긴다. 기본 선택이나 `협의 완료` 체크박스 하나만으로 완료되지 않게 한다. 고객 미응답을 전화 합의로 대신하는 흐름을 안내하지 않는다. 이 경로는 고객과 협의한 사실에 대한 직원 기록이며, 고객의 디지털 확인을 입증하는 기록과는 구분한다.

## 4. 데이터와 서버 계약

별도 구조화된 배달비 합의 이력을 추가한다. 제안 ID/버전, 주문/매장 ID, 지급 방식, 정산 정책, 고객 안내 배달비 Q, 매장 결제 예정액과 금액 명세, 조건 문구 버전, 주문 계산 조건 fingerprint, 제안 직원/시각, 확인 채널/주체/시각/근거, mutation ID를 기록한다. 실제 기사 비용 C는 기존 배달비 실비 원장에 기록하며 협의 배달비 Q를 덮어쓰지 않는다. 직접 지급의 매장 수금 배달비는 0이며 미정인 실제 기사 요금과 구분한다.

- 합의 상태는 `미협의 → 고객 확인 대기 → 합의 완료 → 최종 견적에 사용`으로 표현한다. 제안/확인/철회·수정 이력은 보존하고 현재 버전을 참조한다. 행이 없으면 미협의다. 일반 요청사항 행의 존재나 확인 상태를 대신 보지 않는다.
- 캐셔 제안 RPC, 고객 확인/문의 Edge action+RPC, 직원의 실제 통화/현장 합의 기록 RPC, 합의에 연결한 최종 견적 RPC를 추가한다. 명칭은 구현 시 계약 문서에 고정한다. 모든 변이는 주문 행 → 합의 행의 동일 잠금 순서와 예상 버전을 사용한다.
- 고객 확인은 기존 세션/추적 링크가 해당 주문에 접근 가능한지 검증한다. 직원은 기존 캐셔/매장 관리 권한과 매장 범위를 검사한다. 합의 테이블 직접 쓰기를 허용하거나 고객이 직원 확인 주체를 지정하게 하지 않는다. 일반 요청사항 답변 RPC가 배달비 합의 상태를 바꾸면 안 된다.
- 최종 견적은 현재 유효한 합의가 있고 지급 방식·Q·정산 정책·주문 계산 조건·매장 결제액이 모두 일치해야 생성한다. 서버 계산을 기준으로 하며 클라이언트가 보낸 합계/번역문을 금액의 권위로 사용하지 않는다. 기존 메뉴 가격·VAT·서비스료·반올림 계약을 협의 미리보기와 견적에서 공통 사용한다. 합의용 계산은 세트 기반 읽기와 계산으로 만들며 최종 견적 생성 함수를 시험 호출해 되돌리는 방식은 쓰지 않는다.
- 새 RPC뿐 아니라 기존 `direct_order_staff_quote`, `direct_order_staff_quote_with_payment_mode`와 내부 wrapper의 실행 권한·호출 경로를 검토한다. 구 클라이언트·직접 RPC도 필수 합의를 우회할 수 없게 서버에서 같은 검증을 적용한다. 오류는 미협의/고객 확인 대기/조건 변경/이미 최종 확정을 구분해 UI에서 해결 방법을 보여준다.
- 기존 `delivery_fee_deferred`·픽업 정규화와 지급 방식 기본값도 검토한다. 실제로 생성될 견적의 방식·Q·정책을 합의 조건과 비교해 구 payload가 선택 방식을 바꾸거나 포함 배송비를 0으로 만드는 우회를 차단한다. 이전 확정 주문의 정규화는 새 주문 정책과 구분해 유지한다.
- 최종 견적에 합의 ID·버전·확인 채널과 금융 조건 snapshot을 연결한다. 고객 증빙 제출·입금 승인에서도 새 정책 주문의 견적과 연결된 합의 일치를 검사해 비정상 견적 유입을 차단한다. 기존 원자적 `process_payment`, 비동기 MISA, 실비 차액에 따른 추가 청구 금지 계약은 유지한다.
- 동일 mutation ID와 동일 입력은 기존 결과를 반환한다. 같은 ID의 다른 조건은 충돌이다. 확인 메시지·견적·결제 QR·원 주문/주방 주문이 재시도마다 중복 생성되지 않게 한다.
- 지급 방식과 금액 조건은 KO/VI/EN의 고정 문구와 기존 VND formatter로 표현한다. 자동 번역이나 자유 메모로 지급 상대방/금액/추가 청구 여부를 바꾸지 않는다. 자유 메모와 연결 메시지는 기존 고객 정보 보존·종료 후 정리 계약을 따르며 금융 조건/감사 참조와 개인정보를 분리한다.

| 합의 후 최종 확정 전에 지급 방식·Q·배송지·품목/수량/가격·세금/수수료 조건 변경 | 기존 합의 이력을 남기고 현재 합의를 무효화해 재협의한다. 최종 금액/부담 조건이 달라지는 변경을 몰래 반영하지 않는다. 비금융 메모 변경만으로 불필요한 재확인을 요구하지 않는다. |
| 직접 지급 상품 제공 불가 | 캐셔가 포함 방식의 새 제안을 보내 고객과 다시 협의. 서버가 기본값으로 자동 전환하지 않음. |
| 미응답·거절 | 최종 확정 불가. 재안내/재협의 또는 기존 취소·만료 흐름 사용. 시간이 지났다고 자동 동의하지 않음. |
| 협의 중 고객이 임의로 먼저 송금 | 실제 입금 이력은 보존·대조하되 송금을 합의로 간주하거나 무협의 견적/자동 승인을 만들지 않음. 캐셔가 먼저 조건 협의를 완료하고 기존 부족/초과 입금·취소/환불 절차로 처리. |
| 최종 견적 확정 후 방식 변경 요청 | 잠긴 견적의 임의 수정·재합의로 금액 변경 불가. 기존 취소/픽업 전환/환불 절차에서 명시적으로 처리. 고객에게 실비 차액 재결제를 요구하지 않음. |
| 포함 결제 후 기사 실비 +5,000/+10,000 또는 감소 | 고객의 최초 합의·결제액 유지. 캐셔가 실제 비용 기록, 매장 차액 부담 계산. 재협의·추가 고객 확인 불필요. |
| 픽업 주문 | 배달비 합의 대상 아님. 배송 주문에서 최종 확정 전 픽업으로 전환하면 제안 종료, 기존 픽업 계약 적용. |
| 여러 캐셔·오래된 고객 카드·확정과 수정 경합 | 같은 잠금·버전/fingerprint로 직렬화. 현재 조건에 대한 확인만 사용. |
| 이미 최종 견적/결제가 있는 이전 주문 | 기존 계약 보존. 과거 고객 동의를 임의로 생성하거나 합의 없음으로 결제·배달 완료를 막지 않는다. `기존 견적 적용`임을 구분한다. |
| 활성화 시 아직 최종 견적이 없는 배송 주문 | 기존 주문이라도 확정 전에 협의 기록을 받아야 한다. activation 시점/대상 정책을 명시하고 구 클라이언트의 무협의 확정을 차단한다. |

## 6. 일괄 조회와 구현 후 측정

| 경로 | 호출·SQL 설계와 검증 |
|---|---|
| 캐셔 배송 주문 N건 | 페이지 ID를 기준으로 현재 합의 상태·지급 방식·버전·확인 대기 수를 JOIN/사전 집계해 목록 RPC 1회로 반환. N=1/50/100/200에서도 주문별 상세/합의 RPC 0회. SQL/RPC 내부의 건별 helper 호출도 검사. |
| 고객 주문 목록 N건 | 현재 합의 요약을 기존 목록의 세트 기반 조회에 포함. 목록 항목마다 status/합의 호출 추가 금지. |
| 단일 주문 상세·채팅 | 현재 합의와 필요한 이력/메시지를 기존 상세 응답에 묶음. 과거 제안·확인 메시지마다 추가 조회하지 않고 이력은 pagination. 이력 1/10/50건에서 SQL 조회 수가 항목 수에 따라 증가하지 않음을 측정. |
| 제안·확인·최종 확정 | 단일 주문당 고정된 변이 호출. 주문 품목·설정·미확정 요청사항·합의 검증을 JOIN/집계해 읽음. 제안 하나를 위해 기존 모든 이력을 반복 조회·집계하지 않음. |
| 변경 감지·감사/표시 | 현재 조건 fingerprint와 snapshot 비교, batch 변경 trigger를 사용. 목록 알림 상태를 위해 주문별 이력 재조회 금지. |

공통 계산/견적 경로와 trigger 내부의 항목별 쿼리까지 검토한다. 병렬 요청으로 호출 수만 숨기는 방식은 사용하지 않는다. 구현 후 실제 클라이언트 호출·SQL 내부 계수/실행계획으로 확인하며 이 계획만으로 N+1이 없다고 주장하지 않는다. 기존 통합 계획의 첨부·환불·원장 일괄 처리 요구도 유지한다.

## 7. 작업 순서·완료 기준

1. **계약 대조:** 현재 운영과 소스의 최종 견적·요청사항·추적 링크·입금 경로를 대조한다. 필수 협의 대상과 이전 확정 주문 처리 기준을 확정한다.
2. **DB/API:** 신규 합의 이력, 세트 기반 금액 미리보기, 제안/확인/통화·현장 기록, 최종 견적 gate와 snapshot, 구 RPC 우회 차단을 구현한다. 기존 요청사항 gate는 유지한다.
3. **고객·캐셔 UI:** 희망 방식, 조건 확인 카드, 문의/재제안, 대면·통화 기록, 미협의/확인 대기/합의 완료 표시와 최종 확정 버튼을 연결한다. 협의 중 결제 안내가 열리지 않게 한다.
4. **후속 연결:** 포함 결제 1회·실비 차액 부담, 직접 지급의 이중 수금 방지, 영수증·기사 전달·마감 표시와 양방향 첨부 개선을 통합 계획에 따라 연결한다.
5. **검증:** 아래 성공 조건을 SQL/Edge/Flutter와 실제 기기에서 검증하고 프로젝트 검사 후 승인된 배포 절차로 반영한다.

필수 성공 조건:

- 무선택/무응답/일반 채팅/요청사항 자동 확정만으로 배송 주문 최종 견적을 만들 수 없음. 단일 제공 방식·무료 배달비도 협의 필수.
- 포함 방식과 직접 방식 각각 현재 조건을 확인한 뒤만 캐셔가 최종 확정 가능. 고객 확인만으로 자동 확정 없음. 직접 방식은 매장 결제에서 배달비 제외·고객이 기사에게 실비 지급 안내 일치.
- 전화/현장 합의는 필수 메모·채널·시각·직원·현재 제안 연결 없이는 불가. 고객 직접 확인과 구분해 양쪽 화면에 기록 표시. 다른 주문/직원 메시지를 고객 동의 근거로 사용 불가.
- 합의 후 금액/방식/배송 조건 수정, 오래된 카드, 구 RPC/직접 DB 쓰기/다른 매장·고객 접근, 동시 캐셔 확정과 수정에서 우회 불가.
- 협의 제안만으로 활성 견적·결제 QR·매출·주방 생성 없음. 동일 요청·응답 유실 후 중복 메시지/견적/결제 없음.
- 200,000+30,000 포함 결제 뒤 C=35,000/40,000/25,000이어도 고객 230,000 유지, 실비 기록과 부담액·전체 기사 현금 지급 차감은 기존 통합 계획대로 동작.
- 픽업 제외, 기존 최종 견적/결제 주문 보존, 아직 견적 없는 활성화 대상 주문 협의 강제. 마감·환불·개인정보 종료 정리 회귀 없음.
- KO/VI/EN, iPhone/Android/캐셔 브라우저에서 조건/금액 이해와 확인·재조회/추적 링크 복구, 양방향 첨부와 호출 수 측정.

관련 `supabase/tests/`, Edge `index_test.ts`, Flutter 테스트와 `bash test/direct_order_integrated_sql_test.sh`를 확장한다. 기존 요구사항 합의 검사를 함께 실행하고 구현 후 `flutter analyze`, `flutter test`, `bash scripts/check_repo.sh`, 웹 release build와 필요한 format을 실행한다. 현재 확인한 소스의 존재나 이전 테스트 통과를 새 기능 검증으로 대체하지 않는다.

신규 migration과 Edge/호환 UI를 준비하고 서버·고객·캐셔가 모두 준비된 시점에 필수 협의를 활성화한다. 추가 전용 action의 주문 접근 허용 목록과 rate limit도 함께 적용한다. 배포는 정확한 pushed HEAD의 필수 GitHub Actions 성공 후 `scripts/deploy_pos_production.sh`로 수행한다. 되돌릴 때 신규 주문 진입을 닫더라도 이미 협의 중인 주문의 확인·확정 경로는 유지한다. 이미 확정/결제된 주문의 합의·견적·원장을 삭제하거나 새 활성화 해제로 정책을 바꾸는 롤백은 하지 않는다. 이번 요청은 계획 수립이며 코드 변경·테스트 실행·운영 DB 변경·배포는 하지 않았다.
