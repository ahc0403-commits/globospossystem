## 1. 개선 방향과 우선순위

**매장의 구매 필요 발생부터 PR, 3단계 승인, PO, 공급업체 확인, 입고, 증빙 대조, 결제, 사후 관리까지 하나의 연결된 업무로 운영한다.** PR은 구매요청, PO는 승인된 공급업체 발주, 지급요청은 회계 업무로 구분한다. 승인 전에 공급업체에 주문하거나 입고 후 구매요청을 소급 작성하는 흐름을 정상 경로에서 제거한다.

기존 구매 v2의 PR·PO·견적·검수·입고·반품·회계 대조 구조를 확장한다. 가장 먼저 고칠 부분은 다음 다섯 가지다.

1. 매장관리자 Adjust → 브랜드매니저 Agree → 구매팀 Approval을 독립된 필수 단계로 만든다.
2. PR 작성자는 공급업체 예상 단가를 확인하고, 공급업체에 전달하는 PO는 가격 없이 출력한다.
3. PR 작성일·제출일과 PO 발주일을 분리하고 구매 이력에서 연결해 보여준다.
4. 주방 검수, 재고 반영, 회계 증빙 대조, 지급 완료를 각각의 상태와 책임으로 관리한다.
5. 원재료 외 도구·사무용품·기타 구매와 Shopee 선결제도 승인·증빙·정산 기록 안에 포함한다.

조회 구조는 **N+1 호출을 만들지 않는 일괄 조회·페이지 단위 집계**를 필수 조건으로 한다. 기존 업무 기능 재사용은 기존 조회 SQL·bridge의 성능까지 그대로 재사용한다는 뜻이 아니다. 12.4장의 성능 계약과 T14를 핵심 구현 단계에서 함께 완료한다.

전체 구축은 **① 업무 기준 확정 → ② 승인·양식·이력 개선 → ③ 입고·회계 연결 보강 → ④ 구매 유형 확장 → ⑤ 시범 운영 → ⑥ 반복 구매·분석 확대** 순서로 진행한다. 일정은 14장의 조건부 추정치를 사용한다.

### 2.3 추가 제안과 운영 확정 사항

이하의 부분 입고·반품 처리 고도화, 승인 대상 변경 시 재승인, 중복 지급 방지, 역할별 작업함, 반복 구매 제안, 공급업체 평가·KPI는 전체 프로세스를 완성하기 위한 추가 제안이다. 두 입력 파일이 모두 이를 상세 명세한 것으로 해석하지 않는다.

금액·가격 상승률·수량 배수 기준, 긴급 승인 범위, 입고 확정 담당자 변경, 품목의 자산/비용 분류, Shopee 선결제 한도는 운영 책임자가 확정해야 한다. 계획 수립은 이 값들을 임의로 운영 환경에 적용하지 않는다.

## 4. 현행 구현과 요구의 차이

여기의 “구현 확인”은 현재 소스·migration·로컬 테스트 근거다. 운영 DB에 migration이 적용되었는지, 앱이 배포되었는지, 해당 매장에서 활성화되어 현장 업무가 가능한지는 이번에 확인하지 않았다.

| 기능 | 현재 구현 확인 | 차이 및 처리 | 우선순위 |
|---|---|---|---|
| PR·PO 분리 | 구매 v2에 `inventory_purchase_requests`, 견적, 할당, 기존 PO 테이블 연결 | 새 구매 원장을 다시 만들지 않고 확장 | 재사용 |

| 매장관리자 수량 조정 | v2 PR 수정은 작성자의 draft/returned에 제한 | Adjust를 관리자의 감사 가능한 조정과 작성자 재확인으로 구현 | P0 / HIGH |

| 공급업체용 무가격 PO | POS 문서 서비스와 Office 구매 v2 PDF가 단가·VAT·총액 출력 | 외부 PO용 데이터·파일·이미지를 별도 생성 | P0 / HIGH |

| 공급업체 선정 | 견적, MOQ, 납기, 선정 사유, 비교 견적, 가격 상승·금액·수량 추가 승인 구현 | 고정 거래처의 유효 가격 재사용과 예외 경로를 명확하게 운영 | 재사용·보강 |
| 발행·발송·업체확인 | `issued/sent/confirmed`, 증빙 참조, 확인 시 조건 hash 검증 | 실제 발송 파일 버전과 업체 회신 결과를 기록 | P1 |
| 입고 검수 | 규격·품질·포장·유통기한·냉장/냉동 온도·사진·이슈 구현 | 검수자 서명·회차별 잔량·불량 후속 작업 연결 보강 | 재사용·보강 |
| 재고 반영 | 별도 POS `inventory_accounting` 계정의 최종 검증에서 확정 수량을 원자적으로 반영 | 주방 수령과 재고 반영 사이의 지연을 표시하고 입고 확정 책임을 정한다 | P1 / HIGH |
| 부분 입고·반품 | 회차별 입고, 품목별 완료, 공급업체 반품 재고 차감·잔량 취소 구현 | 반품·차감·환불·교환의 실물/회계 완료를 연결 | 재사용·보강 |
| PO·입고·Invoice 대조 | Office의 POS snapshot·Invoice line matching·AP gate 구현 | v2 원본 누락, 지연, 변경, 부분 지급·선결제에 대한 차단/예외 검증 보강 | P1 / HIGH |
| 도구·비재고 구매 | v2 요청 품목은 `inventory_products`를 참조하고 재고 입고 확정에 매핑이 필요 | 비재고·자산 수령을 재고 입고와 구분해 연결 설계 | P2 / HIGH |
| 반복 구매·평가 | Office에 보충 정책·제안·공급업체 평가가 있음. 자동 제안 hook은 환경 설정·매장 범위에 의존 | 추가 제안 단계에서 활성화·현장 검증. 자동 발주로 확대하지 않는다 | P3 |
| 구매 v1/v2 진입 | 기존 발주 화면의 상단 아이콘으로 v2 작업공간을 별도 연다 | 활성 매장에서는 새 구매요청을 기본 진입으로, 기존 발주는 진행 건 처리로 제공 | P0 / MEDIUM |

**중요한 구현 확인:** 기존 테스트는 일부 의도된 가격 비공개와 v2의 현재 승인 순서를 검증한다. 로컬 테스트 통과가 이번 입력 문서와의 일치를 의미하지 않는다. 요구가 달라지는 부분은 테스트의 업무 계약도 함께 바꿔야 한다.

## 5. 목표 프로세스와 역할

```mermaid
flowchart LR
    A[주방·매장 PR 작성] --> B[매장관리자 Adjust]
    B --> C[브랜드매니저 Agree]
    C --> D[구매팀 견적·Approval]
    D --> E[PO 발행·업체 발송·확인]
    E --> F[주방 검수·입고 확정]
    F --> G[재고 반영·증빙 대조]
    G --> H[Office 지급·사후 관리]
```

브랜드 승인은 구매 필요성과 수량·예상금액을 검토한다. 구매팀은 실제 선정 거래처·견적 조건으로 최종 승인한다. 선정 조건이 브랜드가 승인한 범위를 바꾸면 브랜드 재검토를 요청한다. 공급업체용 PO는 가격이 없어도 내부 승인용 구매 조건에는 확정 가격·VAT·지급 조건을 유지한다.

### 5.1 역할과 책임

| 역할 | 책임·권한 | 기본 사용 위치 |
|---|---|---|
| 주방/발주 담당자 | 재고 확인, PR 작성·제출·반려 수정, 예상 공급업체 가격 확인, 수령·검수·증빙 등록 | POS 모바일/태블릿 |
| Store Manager | 필요성과 재고·수량 검토, Adjust 사유 기록, 매장 단계 확정, 입고 지연·차이 관리 | POS |
| Brand Manager | 담당 브랜드·매장 PR의 필요성·예산·거래처 적합성 검토, Agree 또는 반려 | 권한이 있는 POS/Office 승인 작업함 |
| 구매팀 | 견적·공급업체 선정, 최종 Approval, PO 발행·발송·회신, 차이·반품·증빙 후속 처리 | Office |
| POS 입고 검증자 | 주방이 제출한 검수·증빙을 확인, 수령자와 다른 계정으로 입고 확정 | 현재 POS `inventory_accounting` 역할 |
| Office 회계/지급 담당자 | PO·실제 입고·Invoice 대조, 지급요청·미지급금·선결제·환불 처리, 지급 결과 기록 | Office |
| 관리자 | 매장 범위·정책·담당자·위임 관리, 예외 감사·운영 모니터링 | 관리 화면 |

계정은 담당자 실명과 매장 범위에 연결한다. Word의 특정 이름·이메일을 승인 규칙에 하드코딩하지 않는다. POS와 Office의 인증 사용자는 독립적이므로 이름이나 이메일만으로 동일 사용자라고 판단하지 않는다. 승인 기록에 인증 시스템·subject ID·역할·성명 스냅샷·담당 범위를 남긴다.

기본 정책은 요청자 자신의 승인 금지, 매장·브랜드 승인자 분리, 구매 승인자와 조건부 상위 승인자 분리다. Store Manager가 직접 PR을 작성하면 지정된 대리 검토자를 사용한다. 소규모 매장의 겸직·긴급 예외는 사유·위임 범위·유효기간이 있는 별도 정책으로 확정한다.

Office는 구매팀 승인과 회계 처리를 계속 담당한다. 승인 단계의 위치가 추가되어도 Office의 POS 쓰기는 `pos-bridge`와 범위 검증 RPC만 사용한다. POS 사용자에게 구매팀 최종 승인 권한을 함께 주는 방식으로 우회하지 않는다.

## 6. PR 개선 상세

### 6.1 입력·조회·출력

PR 헤더는 번호, 매장·브랜드·법인, 작성자·작성일, 제출일, 희망 입고일, 구매유형, 사유, 비고, 품목수로 구성한다. 번호와 작성시각은 서버가 부여하며 제출·수정 때 원래 작성일을 변경하지 않는다. 목록에 작성일, 제출일, 희망 입고일을 각각 표시한다.

PR 라인은 품목 코드·이름·규격, 요청 수량·단위, 기준 단위와 환산값, 현재 재고·기준시각, 권장 거래처, 예상 단가·금액, 가격 기준일·출처, 비고를 가진다. 재고와 발주 단위가 다르면 두 값을 같이 보여준다. 예: 요청 2박스, 1박스=10kg, 기준 수량=20kg.

작성 시 PR 예상가격은 유효한 거래처 마스터/계약 가격을 서버가 읽어 고정한다. 아직 가격이 없으면 “견적 필요”로 표시하고 0원 확정으로 오인하지 않게 한다. 작성자는 가격을 조회할 수 있지만 마스터 가격을 직접 바꾸지 못한다. 수량을 바꾸면 예상금액을 서버에서 다시 계산한다.

예상 공급가·예상 VAT·예상 총액을 구분한다. 원본 양식의 “단가”에는 VAT 포함/별도 여부를 명시한다. VAT는 유효한 품목·거래처 조건을 사용하며 이 계획에서 세율을 새로 정하지 않는다. 재고 비대상 품목은 0 대신 “재고관리 비대상”으로 표시한다.

하나의 PR은 여러 거래처 품목을 포함할 수 있다. 양식의 헤더 공급업체는 단일 업체일 때 표시하고 여러 업체이면 “복수/구매팀 선정”으로 표시한다. 업체 선택은 권장 거래처이며 최종 공급업체는 구매팀이 확정한다.

### 6.2 승인·수정·반려

- 제출 후 요청자는 일반 편집을 하지 못하며 반려/회수 경로를 사용한다.
- Store Manager Adjust는 라인별 변경값과 사유를 기록한다. 요청자는 변경 내역을 확인할 수 있다.
- 브랜드·구매 승인에는 대상 revision, 승인자·시각·결정·사유가 남는다. 반려는 단계·사유를 필수로 한다.
- 품목·수량·규격·단위환산·납품일·거래처·가격·VAT·지급 조건 중 승인 대상 변경은 영향을 받는 승인부터 다시 받는다. 전체 감사 이력은 유지한다.
- 임계값 안의 가격 변경을 자동 허용하려면 브랜드가 승인한 허용 범위를 정책 스냅샷에 명시한다. 첫 도입의 기본값은 상업 조건 변경 시 재검토다.
- 제출 전 삭제, 제출 후 취소, PO 할당 후 잔량 취소를 서로 다른 작업으로 구현한다. 감사 기록이 있는 PR은 물리 삭제하지 않는다.

### 6.3 권한별 가격

| 자료 | 요청자·주방 | 매장/브랜드 관리자 | 구매팀 | 회계 | 공급업체용 PO |
|---|---|---|---|---|---|
| PR 예상 단가·금액 | 조회 | 조회 | 조회 | 조회 | 미포함 |
| 승인 대상 내부 견적·확정 조건 | 요청자 정책에 따른 요약 | 승인 범위 조회 | 편집·확정 | 조회 | 미포함 |
| 실제 Invoice 가격·은행정보 | 기본 미표시 | 필요한 범위 | 필요한 범위 | 업무 권한 | 미포함 |
| 품목·규격·수량·단위·납품 정보 | 조회 | 조회 | 조회 | 조회 | 포함 |

단일 `can_view_prices`를 전역적으로 true로 바꾸면 실제 Invoice·은행정보까지 넓게 공개될 수 있다. PR 예상가격 조회, 내부 상업 조건 조회, 회계 자료 조회, 외부 문서 생성을 별도 권한으로 판정한다. 견적·정산 자료 조회는 기존 서버 범위 검증을 유지한다.

## 7. PO 문서와 공급업체 확인

### 7.1 문서 종류

| 문서 | 목적·표시 | 생성 조건 |
|---|---|---|
| 내부 PR | 요청 정보·재고·예상가격·3단계 승인 이력 | 작성본은 draft 표시, 승인본은 해당 revision 사용 |
| 공급업체용 PO | 원본 PO 양식의 번호·업체·납품장소/일·품목·규격·수량·단위·비고 | 3단계 승인 완료·정상 PO 발행 |
| 내부 구매 조건/회계 대조표 | 확정 단가·VAT·총액·지급 조건·PR/PO 연결 | 업무 권한자 조회 |
| 입고 확인서 | 회차·실제 수령/합격/거절량·검수자·서명·증빙·차이 | 제출본과 확정본 구분 |

공급업체용 PO는 **단가·공급가·VAT·총액을 표시하지 않는다.** 원본 문구대로 수령 확인과 납기/수량 불가 통보 안내를 넣는다. PR 번호 참조, revision, 발행 시각, 납품 연락처를 추가해 추적한다. 필요하면 내부 문서와 별도로 업체와 확정 가격을 협의·기록한다.

포맷 선택으로 가격 열만 숨기지 않는다. 서버에서 외부 PO용 허용 필드만 반환하고 해당 projection으로 PDF·PNG·인쇄물을 만든다. 제목·파일명·페이지 합계·주석·QR 링크·메모에도 내부 금액·은행정보가 포함되지 않는지 확인한다. 자유 입력 비고는 외부 전달 전에 확인한다.

문서 저장은 같은 PO revision이라도 `internal`과 `supplier` audience를 구분한다. 현재 `v{snapshotVersion}.pdf` 단일 경로를 확장하여 외부/내부 파일·hash·template version·생성자·시각을 구별한다. 서명 URL은 문서 audience와 사용자 권한을 확인한다. 과거 승인 문서는 덮어쓰지 않고 새 버전으로 발행한다.

한국어·베트남어 표기와 영문 명칭을 양식에 맞춰 지원한다. 긴 품목명·규격, 베트남어 성조, 다중 페이지, 20개 초과 품목에서 품목 누락과 합계 중복이 없어야 한다. 원본의 20행은 출력 레이아웃이며 시스템 품목 수 상한으로 사용하지 않는다.

### 7.2 발송·회신

초기에는 구매팀이 파일을 내려받아 기존 Zalo 등 채널로 직접 전송한다. POS/Office에 전송 시각·전송자·채널·문서 revision/hash·수신 업체·증빙을 기록한다. 별도 메시징 연동 구축 없이 업무 통제를 먼저 완성한다.

업체 회신은 수락, 부분 공급 가능, 납기 변경 제안, 품목 대체 제안, 거절로 구분한다. 업체가 제안한 변경은 구매팀 검토와 필요한 재승인 후 새 조건/문서로 확정한다. 이전 문서는 취소/대체 표시한다. “발송 완료” 버튼만으로 “업체 확인”이 되지 않는다.

브랜드·구매 승인과 공식 문서 준비가 완료되어야 발송할 수 있다. 업체 확인은 승인 조건 hash 및 발송 문서 버전과 연결한다. 확인 전 실제 상품이 도착하면 정상 상태를 위조하지 않고 긴급 입고·사후 확인 예외로 처리한다.

## 8. 입고·재고·차이·반품

### 8.1 재고 반영 책임

현재는 주방 제출 후 다른 POS `inventory_accounting` 계정이 검증해야 재고가 증가한다. 첫 전환에서는 이 원자적 처리와 수령/확정 담당자 분리를 유지한다. 화면에는 “현장 검수 제출 / 재고 미반영”을 분명히 표시하고 검증 대기 시간·담당자·미처리 건을 보여준다.

추가 개선안은 매장에 지정된 입고 검증자가 실물 검수를 확정할 수 있게 하고, 회계의 Invoice·지급 승인은 따로 유지하는 것이다. 이를 선택하려면 `can_verify_inventory_receipt`의 역할 정책, 실제 담당자, 검수 책임, 감사 테스트를 함께 변경해야 한다. **계획 수립만으로 주방 제출 즉시 재고가 반영되는 것으로 간주하지 않는다.**

운영 목표 초안은 납품 당일, 조리 투입 전에 검수·재고 반영을 완료하는 것이다. 늦어질 때는 미반영 입고량을 별도로 표시해 재고와 실물 차이를 운영자가 확인하게 한다. 미확정량을 판매 차감용 확정 재고에 더하지 않는다.

### 8.2 회차별 수량·검수

주방은 해당 PO의 잔량을 불러와 실제 수령량, 거절량, 합격량, 차이 사유를 입력한다. “전량 수령” 초기값을 저장값으로 자동 확정하지 않는다. 규격·품질·포장, 해당 시 유통기한·온도, 증빙·검수자 확인을 완료한다. 서명 방식은 본인 계정의 최종 확인을 기본으로 하고 필기 서명이 필요한 현장은 추가한다.

```text
회차 합격 수량 = 실제 수령 수량 - 현장 거절 수량
재고 증가량 = 그 회차에서 새로 확정된 합격 수량
PO 미입고 잔량 = 주문량 - 누적 합격 입고량 - 승인된 미납 취소량
회계 순입고량 = 누적 합격 입고량 - 확정된 공급업체 반품량
```

동일 입고 확정 재시도는 같은 결과를 반환하며 재고를 다시 늘리지 않는다. 서로 다른 회차의 합격 수량은 합산한다. 수량 비교는 기준 단위로 수행하며 주문 당시 단위환산을 고정한다. 반품 후 재납품은 추가 입고/교환 기록으로 처리하고 과거 확정 수량을 직접 고치지 않는다.

| 예외 | 처리 |
|---|---|
| 부족 납품 | 부분 입고, 잔량 유지, 추가 납품 또는 승인된 잔량 취소 |
| 초과 납품 | 초과분 거절 또는 변경 PR/PO 승인 후 수용; 미승인 초과분 자동 지급 금지 |
| 다른 품목·규격 | 대체품 승인 또는 거절/교환; 품목 ID를 몰래 바꾸지 않음 |
| 불량·파손·품질·온도·기한 문제 | 거절량·사진·사유 기록, 검수 합격량에 포함하지 않음 |
| 입고 후 반품 | 반품 승인·반출 확정 시 재고 차감, 공급업체 차감/환불 상태 별도 처리 |
| 전량 미납·수령 0 | 입고 확정 없이 납품 불가/지연 사건 기록, 새 납기·취소 처리 |
| 실제 단가 차이 | 현장 검수와 별도로 구매팀 확인·재승인·Invoice 대조 보류 |

입고 이슈의 “처리 완료”는 설명 입력만으로 종결하지 않는다. 추가 납품은 새 입고, 교환은 반품/재입고, 차감은 credit 증빙과 회계 반영, 취소는 잔량 취소 명령에 연결한다. 현행 `resolve_issue`는 재고·지급 조정을 실행하지 않으므로 처리 결과 연결이 필요하다.

확정 검수 당시 단위환산·가격·VAT와 증빙 번호/일자를 고정한다. 최근 실제 구매가격은 확인된 입고·증빙 기준으로 표시하며 마스터의 예상 공급가격과 구분한다. 새 실제 가격을 이유 없이 마스터 가격에 자동 덮어쓰지 않는다.

## 9. 증빙·지급·Office 연결

### 9.1 3자 대조와 미지급금

Office에서 내부 PO의 확정 조건, 반품을 반영한 실제 합격 입고, 공급업체 Invoice를 라인 단위로 대조한다. 거래처·매장/법인·품목·단위환산·수량·단가·VAT·금액·증빙 중복을 검증한다. 부분 입고에 대응하는 일부 청구는 허용하되 같은 수령량이 여러 Invoice에 중복 배분되지 않게 한다.

일치하지 않는 청구는 지급 보류 작업함으로 이동하고 원인과 처리 책임자를 보여준다. 부족 수량 미납, 가격 변경, 반품 credit, 증빙 누락, 원본 동기화 지연은 다른 사유로 분류한다. 지급 완료는 실제 지급 결과·은행 참조/영수증을 기록했을 때만 표시한다.

```text
공급업체 미지급 잔액 = 승인된 청구액 - 적용된 credit - 지급액 - 적용된 선급금
```

잔액이 음수가 되면 단순 미지급 상태로 두지 않고 공급업체 환불/선급 잔액으로 구분한다. 지급요청 작성과 지급 승인은 분리하며, 관련 문서·입고량·반품량 변경 시 대조 결과를 다시 검증한다. POS는 Office가 소유한 지급/회계 상태를 읽는다.

### 9.2 이미 있는 연결의 보강

Office의 `procurement_pos_snapshots`·`procurement_invoice_allocations`와 Invoice/AP 상태 전환 gate를 재사용한다. 현재 대조 함수에는 snapshot이 없으면 레거시 비대상으로 처리하는 분기가 있으므로, 신규 구매 v2가 원본 동기화 누락으로 이 경로를 타지 않도록 **workflow/외부 PO 연결상 신규 대조 대상이면 snapshot 부재를 차단**하는 검증을 추가한다. 이는 확인된 소스 분기의 검토 과제이며 운영에서 우회가 발생했다는 판정은 아니다.

대조 전 POS 원본을 갱신하고 revision/hash를 확인한다. 현재 10분 source freshness gate가 있으므로 새 PO revision, 부분 입고, 반품 발생 후 재갱신·재대조 UX를 제공한다. 최신 원본 확인이 실패하면 이전 자료로 새 지급 승인을 진행하지 않는다.

두 DB 사이에 분산 트랜잭션이 없으므로 다음 복구 절차를 유지·보강한다.

- POS PO 발행 성공 / Office snapshot 저장 실패: 같은 명령 키로 재시도하고 새 PO를 중복 생성하지 않는다.
- Office 보충 제안 확정 중 POS PR 생성 성공 / Office 최종 저장 실패: 저장된 payload와 동일 PR 결과로 복구한다.
- POS 입고/반품 성공 / 회계 반영 지연: 동기화 대기와 재시도 상태를 보여주고 지급 대조는 보류한다.
- 외부 구매 건을 Office에 가져올 때 동일 외부 PO·Invoice·지급 참조의 중복을 막는다.

### 9.3 증빙 보관

PR·승인, 견적, 내부/외부 PO, 발송·업체 회신, 입고 회차·사진·서명, Invoice, credit/반품, 지급 기록을 ID로 연결한다. 입고 사진과 Invoice는 가격정보 공개 여부가 다르므로 권한을 나눈다. 예외 증빙은 파일 위치와 해당 업무 record를 검증한다.

문서 번호·발행일·업로드 시각·업로더·파일 hash·대상 매장/법인을 저장한다. 공급업체 증빙 중복은 법인/거래처/증빙 번호 등을 조합해 검토한다. 보존 기간과 회계 인정 요건은 기존 회사 정책으로 확정하며 이번 계획에서 법적 기간을 임의 지정하지 않는다. 매출용 MISA 전자세금계산서 흐름을 구매 증빙 보관 시스템으로 재구축하지 않는다.

## 10. 도구·사무용품·기타·Shopee 경로

구매유형과 채널은 독립적으로 관리한다. 구매유형은 NVL(원재료), CCDC(도구/소모품), VPP(사무용품), Khác(기타), 채널은 일반 공급업체·Shopee 등이다. 각 품목에는 처리 방식 `재고성 / 비재고성 / 자산 검토`를 별도로 둔다.

| 유형·경로 | PR/승인 | 수령·처리 | 회계 연결 |
|---|---|---|---|
| 원재료 | 공통 3단계 | 검수 합격량 재고 반영 | 순입고량 기준 Invoice 대조 |
| 재고로 관리하는 소모품 | 공통 3단계 | 품목 마스터·단위 등록 후 재고 반영 | 원재료와 같은 연결 계약 활용 |
| 비재고 사무용품/도구 | 공통 3단계 | 수령 확인·사용 부서/담당자 기록, 원재료 재고 차감 대상에서 제외 | Office의 적합한 일반 구매/비용 업무로 연결 |
| 자산 검토가 필요한 장비 | 공통 승인 + 회사 자산 기준에 따른 추가 검토 | 설치/인수 담당자·위치·보증 자료 | Office 자산/회계 업무 연결 여부 확정 |
| Shopee 선결제 | 구매 전 PR·승인, 플랫폼 주문번호 연결 | 주문확인·배송·실제 수령·환불 추적 | 선급금/이미 지급한 거래로 대조, 중복 지급 금지 |
| 이미 발생한 구매 | 사후 PR 별도 표시·사유·승인 | 실제 구매/수령/지급일 보존 | 정상 사전 승인 구매와 구분하여 감사 |

원재료가 아닌 품목을 받기 위해 가짜 `inventory_items` 재고를 만드는 방식은 사용하지 않는다. 재고 매핑 없는 라인은 비재고 수령 경로를 사용하도록 PR/PO line 처리 유형과 Office 연결 계약을 확장한다. 현행 원재료 Invoice 테이블을 모든 비용/자산의 회계 원장으로 사용하지 않는다.

Shopee 주문 캡처는 보조 증빙이다. 플랫폼 주문번호, 주문 상품·수량·가격, 판매자, 결제일·금액·수단·결제자, 배송·환불 기록, 최종 수령 기록을 함께 저장한다. 플랫폼 주문 행위는 사람이 수행하고 시스템은 승인된 PR/내부 구매 조건에 연결한다. 선결제를 일반 후불 지급 대기 건으로 다시 생성하지 않는다.

배송료·할인·쿠폰·환불은 품목가와 별도 금액 요소로 보관하고 청구/지급 대조 시 반영한다. 개인 선결제의 비용 보전과 법인 결제의 선급 정산은 서로 다른 지급 대상으로 처리한다. 세부 증빙 인정 기준은 회계팀이 확정한다.

## 11. 화면·양식·마스터 개선

### 11.1 역할별 화면

| 화면 | 구성 | 사용자 작업 |
|---|---|---|
| 새 구매요청 | 재고·가격·납품일·사유·유형·라인, 예상 합계 | 주방/매장의 PR 작성·제출 |
| 승인 작업함 | 매장 검토 / 브랜드 검토 / 구매 검토, 지연·반려 | 본인 역할의 확인·조정·승인 |
| 구매팀 발주 작업함 | 견적·선정·승인된 PR·업체별 PO·발송/회신 | PO 발행·공급업체 후속 처리 |
| 입고 작업함 | 납품 예정·회차·잔량·검수·증빙·확정 대기 | 주방 수령과 별도 입고 검증 |
| 구매 이력 | PR 작성일·제출일·번호, 연결 PO·업체·입고·지급 요약 | 검색·상세·문서 조회 |
| 회계 대조 작업함 | 미대조·차이·보류·지급대기·지급완료·선급/환불 | 회계·구매팀 협업 |
| 거래처·구매 정책 | 매장 범위, 유효 가격·단위·MOQ·납기, 승인자·위임 | 권한자 마스터 관리 |

활성 매장에서는 메뉴의 “새 발주”를 “새 구매요청(PR)”로 정리하고 새 PR 화면으로 진입한다. 기존 v1 진행 건은 기존 번호·승인·입고 자료로 계속 처리한다. v1 화면에서 신규 구매를 생성해 필수 3단계를 우회하는 경로는 서버에서 막는다.

PR/PO/입고/지급 상태를 하나의 “완료” 뱃지로 합치지 않는다. 예: “PR 승인 완료 / PO 업체 확인 / 2회 부분 입고 / Invoice 대조 보류”를 각각 보여준다. 모바일은 한 번에 처리할 작업을 중심으로, 데스크톱은 비교 표와 필터 중심으로 구성한다.

PR 상세에서 작성·조정·승인·견적·PO·입고·회계 연결을 타임라인으로 확인한다. 사람 이름과 역할을 표시하고 원시 UUID를 기본 설명으로 사용하지 않는다. 목록/검색은 서버 페이지네이션으로 구현한다. 현재 v2의 최근 100건 제한으로 과거 PR이 누락되지 않게 작성일·매장·담당자·상태·번호 필터와 이전 페이지를 제공한다.

한·영·베트남어 화면·오류·문서와 베트남 현지 업무일을 지원한다. 날짜 원본은 서버 timestamp로 저장하고 사용자 표시 시 베트남 업무 시간 기준을 명확히 한다. 통신 실패 시 성공 여부 불명확·확정 거절을 구분하고 저장된 동일 명령으로 재시도한다.

### 11.2 Excel 양식에서 확인한 수정 사항

| 위치 | 확인된 내용 | 수정 |
|---|---|---|
| PR!C6:C7 | 매장 목록 검증이 작성일 입력 영역 C7까지 걸려 있음 | 매장 선택은 C6, C7은 날짜 형식/날짜 검증 |

## 12. 데이터·상태·서버 설계

### 12.1 소유권과 최소 확장

POS가 PR·PO·견적·할당·입고·재고·실물 반품의 원본을 소유한다. Office는 보충 제안·공급업체 평가·Invoice·미지급금·지급 업무를 소유하며 POS와 bridge로 연결한다. `restaurants`와 기존 결합 컬럼, 기존 일반 Office 구매 도메인은 유지한다.

| 대상 | 재사용·확장 방향 |
|---|---|
| `inventory_purchase_requests` | 구매유형·정책 스냅샷·제출시각·브랜드 단계·요청 revision·취소 사유 |
| `inventory_purchase_request_lines` | 품목/규격·예상가격 기준·합계·단위·처리 유형 스냅샷, 관리자 Adjust 이력 |
| `procurement_events` | 브랜드 결정·조정·회수/취소·위임·재승인 이벤트, 이름/역할 스냅샷 |
| `procurement_store_policies` | 필수 3단계 정책 버전·적용일·담당자 범위·위임·신규 생성 gate |
| `procurement_quotes` / quote lines | 유효 계약가격 참조·공급업체 선정 사유·최종 조건 확정 |
| `procurement_allocations` | PR→PO 품목별 연결·배분량, 부분 발행·잔량 추적 |
| `inventory_purchase_documents` | audience·template version·revision·hash·권한별 보관 위치 |
| `inventory_receipts` / lines / issues / returns | 검수·서명·회차·입고확정, 후속 입고/취소/credit 연결 |
| Office snapshot / Invoice / payable | v2 원본 필수 여부·순입고 대조·선급/지급/환불 연결·상태 조회 |

이는 권장 변경 항목이며 확정 DDL은 구현 전 현행 제약과 데이터 분포를 확인해 작성한다. 별도 PR/PO 복제 테이블을 만들어 두 시스템이 독립 승인·재고를 기록하지 않는다.

### 12.2 상태 계약

| 기록 | 목표 상태·전환 |
|---|---|
| PR | draft → 매장검토 → 브랜드검토 → 구매검토 → 필요시 추가승인 → approved → 일부 PO 할당 → 전체 할당/잔량 취소 |
| PR 반려 | 각 검토 단계 → returned → 새 revision 제출. 이전 결정 이력 유지 |
| PO 상업 처리 | issued → sent → confirmed. 변경·취소는 별도 revision/이벤트 |
| PO 실물 처리 | 미입고 → partially_received → received 또는 잔량 취소 완료 |
| 입고 회차 | 작성·검수 제출 → 별도 검증 → confirmed, 실패는 재고 미반영 |
| 이슈 | open → 처리 진행 → 실물/회계 후속 증거 확인 → resolved |
| 회계 | 증빙 대기 → 대조 중 → matched/held → 지급요청·승인 → 일부 지급/지급완료 |

현행 `status`와 `procurement_status`는 서로 다른 의미로 사용 중이다. 표시용 단어 교체만으로 전환하지 않고, 승인 정책·허용 작업·서버 전환·구버전 읽기 호환을 함께 정의한다. 필수 브랜드 단계가 추가되면 상태 제약·`procurement_allowed_actions`·POS actor·Office actor와 command allowlist를 모두 수정한다.

기존 v1/v2 진행 건은 생성 당시 정책 스냅샷으로 처리한다. 신규 PR에 새 3단계 정책을 적용하며, 이전 건을 완료/재승인으로 임의 덮어쓰지 않는다. 이전 승인자료가 부족한 위험 건은 개별 검토 대상으로 표시한다.

### 12.3 서버가 보장할 불변식

1. 매장 범위 밖 조회·승인·입고·문서 다운로드를 거부한다.
2. 각 역할은 현재 단계에서 허용된 작업만 수행한다. UI 버튼 숨김만으로 권한을 보장하지 않는다.
3. 브랜드 Agree와 구매 Approval이 없는 신규 PR로 PO 발행·발송을 할 수 없다.
4. 발송은 해당 외부 PO 파일의 준비·revision/hash가 확인된 경우만 허용한다.
5. 승인 대상 변경 후 이전 승인을 재사용하지 않는다.
6. PR의 승인·취소 수량을 넘는 중복 PO 할당을 막는다.
7. 입력·수량·금액·단위환산·VAT는 서버 검증·계산하며 NaN/Infinity를 거부한다.
8. 검수 합격량만 입고 확정하며 제출자와 검증자가 분리된다.
9. 같은 idempotency key·같은 actor·같은 payload는 같은 결과, 다른 payload는 오류다.
10. stock·입고 원장·PO 잔량은 한 트랜잭션에서 반영하거나 모두 실패한다.
11. v2 회계 대상 원본이 없거나 최신성/대조 조건을 만족하지 않으면 새 지급 승인을 보류한다.
12. 비재고 수령과 선결제로 확정 재고·미지급금이 중복 생성되지 않는다.

### 12.4 N+1 방지와 조회 성능 계약

2026-10-05 추가 검토 결과, 현재 코드 전체를 “N+1 없음”으로 판정할 근거는 없다. 이번에는 계획만 작성했고 새로운 조회 구현은 하지 않았다. 기존 기능 테스트도 성능·조회 횟수를 검증하지 않는다.

| 영역 | 확인된 구조 | 판정·개선 |
|---|---|---|
| POS v2 화면 | `InventoryService.fetchProcurementWorkspace`가 초기 workspace를 RPC 한 번으로 조회 | 이 진입에서 행별 HTTP 호출은 확인되지 않음. RPC 한 번이라는 사실만으로 DB 내부 효율을 보장하지 않음 |
| PR/견적·입고 목록 SQL | 부모별 라인·견적·입고 라인을 상관 서브쿼리로 집계 | 반복 실행 위험. 선택한 페이지의 ID 집합에 대해 라인·견적·입고를 미리 집계한 뒤 JOIN |
| 수요 SQL | 품목별 `LATERAL` 사용량·입고예정·요청량·구매 이력과 추가 상관 집계 | 실제 비용은 실행계획 확인 필요. 매장/기간/품목 집합으로 각각 GROUP BY 후 결합 |
| 업체 성과 SQL | 업체별 주문·입고·납기·이슈·해결시간의 상관 집계 | 대상 업체 집합을 정한 뒤 업체별 사전 집계·JOIN으로 변경 |
| Office 통합 발주 조회 | `handleInventoryPurchaseOrders`가 매장별로 `office_get_inventory_purchase_orders` 호출 | 매장 수에 따라 원격 호출 증가 확인. 서버에서 검증한 접근 가능 매장 집합으로 일괄 페이지 조회 |
| Office 입고/회계 동기화 | 입고 목록은 PO ID 100개씩 일괄 조회, 회계 가져오기는 후보 PO별 상세·snapshot 호출 | 기존 입고 배치를 유지. 동기화 원본 읽기는 변경 건을 모아 제한된 배치로 조회하고 건별 원자 저장·재시도는 유지 |
| workspace 응답 크기 | PR/PO는 최근 100건이지만 입고·이슈·반품·전체 품목 등이 함께 반환됨 | 목록·선택 상세·수요/성과 탭을 분리하고 각 반환 범위·페이지 크기를 제한 |

**목록과 상세의 조회 계약**

- PR/PO 목록은 헤더·상태·작성일·업체·입고/지급 요약만 페이지 단위로 반환한다. 목록의 각 행에서 품목·업체·승인자·재고를 별도 요청하지 않는다.
- PR/PO를 선택했을 때 해당 1건의 상세를 읽는다. 상세에서도 품목별 가격·재고·규격·담당자를 반복 RPC로 가져오지 않고 관련 ID 집합을 한꺼번에 조회한다.
- 목록 요약의 입고량·잔량·승인·지급은 페이지의 부모 ID 집합을 먼저 정하고 각각 집계한 뒤 결합한다. 여러 1:N 테이블을 그대로 JOIN하여 수량/금액이 중복 합산되지 않게 한다.
- 품목 검색·공급업체 가격 조회는 필요한 품목/업체 집합을 받는 일괄 조회를 사용한다. 같은 매장·가격 revision의 중복 요청은 합치며 권한별 자료가 캐시에서 섞이지 않게 한다.
- 다중 매장 조회는 Office가 인증·scope를 확인한 매장 집합을 서버에 전달하고 POS RPC에서도 신뢰 경계를 검증한다. 클라이언트가 보내는 매장 ID 배열만으로 service_role 조회 범위를 결정하지 않는다.
- 선택하지 않은 입고·이슈·반품·원본 파일·수요/성과를 매번 전부 읽지 않는다. 검색 조건·cursor·상한을 서버가 적용하며 날짜/상태/매장/외래키 조건에 맞는 인덱스를 실행계획으로 선택한다.
- `Promise.all`로 행별 요청을 병렬화하는 것은 N+1 해소로 인정하지 않는다. 호출 수를 줄이는 일괄 API/SQL과 결과 집합 제한이 필요하다.

**쓰기·동기화 계약**

여러 품목의 PR 저장·PO 발행·입고 확정은 화면에서 품목마다 RPC를 호출하지 않고 기존 원자적 배치 명령을 유지한다. SQL 내부 품목 검증도 필요한 품목·가격·잔량을 집합으로 읽는 방식을 우선한다. 잠금·검증·원장 기록·승인 이벤트는 정확성을 유지하고, 필요한 개별 쓰기까지 무조건 제거하지 않는다.

회계 동기화는 제한된 건수의 변경 PO/snapshot을 일괄 읽고, 처리량·동시성·재시도에 상한을 둔다. 건별 실패 격리·revision/hash·동일 명령 키 복구를 유지한다. 전체 건수만큼의 상세 HTTP 호출을 단순 병렬화하거나 두 DB의 원자 저장을 하나의 분산 트랜잭션으로 가정하지 않는다.

**수용 기준과 검증 증거**

1. 같은 페이지 크기·조회 조건에서 전체 저장 건수를 100→1,000→10,000건으로 늘려도 목록 초기 로드의 원격 요청 수가 행/매장 수에 비례해 증가하지 않아야 한다. 매장 범위가 API 상한을 넘으면 상한이 명시된 청크 수와 실제 호출 수를 기록한다.
2. 목록 20행·100행, 상세 1라인·20라인·200라인의 요청 trace를 비교한다. 행·품목마다 가격/담당자/입고 HTTP 조회가 추가되지 않아야 한다.
3. 새 목록·수요·업체 성과·snapshot 조회의 `EXPLAIN (ANALYZE, BUFFERS)`를 대표 데이터가 있는 로컬/staging에서 수집한다. SQL 함수는 내부 SELECT 실행계획도 확인한다. 행별 SubPlan이 큰 원장 범위를 반복 스캔하는 비용을 확인하고 개선 전후 시간·buffers·실행 횟수를 비교한다. 정상적인 인덱스 JOIN의 nested loop 자체를 N+1 실패로 판정하지 않는다.
4. 반환 행 수·응답 byte 수·p50/p95 지연·DB 시간·원격 호출 수를 남긴다. 총 이력이 커져도 고정 페이지의 payload에 전체 이력이 섞이지 않아야 한다. 지연 목표는 배포 대상 환경의 기준선과 동시에 정의하며 측정 전 달성을 주장하지 않는다.
5. 일괄 조회 후에도 타 매장 접근 차단·가격 projection·품목별 잔량·부분 입고·반품·중복 방지 결과가 동일해야 한다. 캐시나 사전 집계가 최신 승인/재고 상태를 잘못 확정하지 않아야 한다.

## 13. 구현 작업 목록과 완료 기준

각 항목은 작업 화면과 서버 계약·검증을 함께 완료하는 단위다. “확장”은 기존 기능 변경, “신규”는 현재 확인하지 못한 업무 계약/화면의 추가다. 완료 체크는 구현·검증 후 진행한다.

| ID | 우선순위·구분 | 작업 / 재사용 대상 | 선행 | 완료 기준 |

### 14.1 데이터·운영 전환

대기 시간 목표 초안은 매장·브랜드·구매 검토 각 다음 업무일 이내, 긴급 요청은 필요 시각 전, 입고 확정은 납품 당일, 회계 대조는 증빙 수령 후 2업무일 이내다. 공급업체 납기·주말·회사 근무일에 맞춰 책임자가 확정한다. 알림은 새 할당·반려·기한 초과·입고 차이·원본 동기화 실패 등 필요한 변화에만 보낸다.

### 15.2 검증 구분과 release gate

POS SQL은 `scripts/test_procurement_v2.sh`의 격리된 로컬 DB 테스트를 확장하고, 요청 화면·문서·권한별 작업은 Flutter 테스트와 역할별 UAT로 검증한다. Office는 bridge actor/command, Invoice/AP, 보충 제안의 기존 테스트와 회사 다국어 검사·wrapper를 사용한다. 전체 변경의 검사는 각 저장소 CLAUDE.md에 맞춰 수행한다.

계획 검토, 로컬 검사, migration 적용, 배포, 현장 확인을 별도로 기록한다. 실제 릴리스에서는 두 저장소의 호환 코드·migration을 준비하고 **정확한 pushed head SHA의 GitHub Actions 필수 검사가 성공한 뒤** release gate를 통과한 것으로 판정한다. POS 배포는 `scripts/deploy_pos_production.sh`, Office는 해당 저장소의 정해진 production 절차와 확인 요건을 따른다. 독립 Judge가 필요한 릴리스 단계에서는 사전 점검 자료로 사용한다.

기존 정책과 데이터를 읽을 수 있는 서버·앱을 먼저 배포하고 매장별 새 정책을 활성화한다. 과거 건의 승인·재고 상태를 전체 일괄 전환하지 않는다. 초기 시범 성공 후 매장을 점진 확대한다.

### 15.3 중단·복구

새 PR 생성/새 정책 적용 중단과 이미 생성된 건의 입고·정산 처리를 별도 gate로 둔다. 현재 enabled 하나를 무조건 끄면 진행 건의 명령까지 막힐 수 있으므로 복구 계약을 먼저 검증한다. 이미 확정된 입고·반품·지급을 되돌리는 destructive rollback은 하지 않는다.

새 업무 오류가 나면 신규 생성만 중단하고 기존 PR/PO·입고·회계 처리를 지속한다. 문서 생성 실패는 승인 취소나 중복 PO 생성 대신 해당 revision의 재생성으로 복구한다. 회계 sync 실패는 원본과 동일 명령으로 재시도한다. 수기 비상 처리 시에는 실제 날짜·담당자·증빙·예외 사유를 남기고 사후 대조한다.
