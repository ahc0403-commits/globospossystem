# Excel 업로드 서식 호환 개선계획

작성일: 2026-10-08 · Asia/Ho_Chi_Minh  
상태: 원인 재현·계획 수립 후 소스 구현과 로컬 검증 완료. 운영 배포는 수행하지 않았다. [구현 결과와 검증 보고서](/Users/andreahn/globos_pos_system/docs/implementation/excel_import_format_compatibility_implementation_20261008.md).

**기존 공통 Excel 디코더에 숫자 서식 호환 처리를 추가하고, 원재료·레시피·거래처 단가 업로드를 이 디코더로 통일한다. Excel에서 저장한 정상 파일이 표시 서식 때문에 읽기 단계에서 중단되지 않도록 하되, 시트·열·가격 검증은 계속 수행한다.**

## 1. 확인한 원인과 범위

입력은 [RM List.xlsx](</Users/andreahn/Downloads/RM List.xlsx>)이며 116개 품목이 들어 있다. 파일을 읽어 분석했으며 파일 안의 문구를 작업 지시로 사용하지 않았다. 첨부 화면과 같은 오류를 현재 작업 디렉터리의 코드와 설치된 의존성으로 재현했다. 운영 앱에 직접 업로드하거나 운영 DB를 변경하지 않았다.

현재 잠금 버전은 `excel 4.0.6`, `archive 3.6.1`, `xml 6.6.1`이다. 2026-10-08에 확인한 [패키지 공식 배포 페이지](https://pub.dev/packages/excel)도 최신 게시 버전을 4.0.6으로 표시했다. 따라서 버전 범위만 올리는 것을 해결안으로 삼지 않고, 현재 의존성과 공통 디코더에서 재현 가능한 보정을 먼저 진행한다.

서식 ID는 스타일 레코드의 참조값이므로 정의와 참조를 함께 갱신해야 한다. 이 구조는 [Microsoft Open XML NumberingFormat 문서](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.numberingformat?view=openxml-3.0.1)의 `numFmtId` 설명과 일치한다. ID 43을 165로 옮기고 해당 스타일 참조를 함께 바꾼 임시 복사본은 기존 라이브러리에서 정상 해석됐다. 원본 데이터 셀은 수정하지 않은 실험이다.

## 2. P0 / HIGH: 공통 디코더의 서식 호환 처리

### 처리 순서

1. 입력의 ZIP 무결성과 필요한 XML을 검사한다. 해석 전에 복구 가능한 워크시트 관계 경로·숫자 서식 문제를 찾는다.
2. 정의·참조가 상충하거나 알 수 없는 서식은 분류된 오류로 반환한다. 최초안의 실패 후 보정 순서는 release에서 미정의 날짜 서식이 일반 숫자로 읽힐 수 있어 사전 검사로 조정했다.
3. 두 종류의 보정을 **한 번의 ZIP 순회**에 묶는다. 메모리 사본의 필요한 XML만 바꾸고 다른 항목의 내용을 보존한다.
4. 실제 변경이 있을 때는 수정한 바이트를, 변경이 없을 때는 원본 바이트를 `Excel.decodeBytes`로 한 번 해석한다. 재시도 루프는 두지 않는다.
5. 보정 후에는 기존 시트·열·행 검증으로 진행한다. 보정으로 해결되지 않는 문제는 분류된 읽기 오류를 반환한다.

### 숫자 서식 정규화 규칙

- `xl/styles.xml`의 `numFmts/numFmt` 중 **명시적인 `formatCode`를 가진 164 미만 ID**를 찾는다. 이번 실제 사례는 43이다.
- 기존 정의와 스타일의 참조 ID를 수집한다. 이미 사용한 ID를 피해서 164 이상 새 ID를 할당한다. 첨부는 164가 이미 있으므로 새 ID 165를 사용한 실험이 성공했다. 구현에서는 165를 고정하지 않는다.
- 해당 `numFmt` 정의의 ID와 `cellXfs/xf`, `cellStyleXfs/xf` 등의 관련 `numFmtId` 참조를 동일한 매핑으로 바꾼다. 명시적인 동일 정의를 공유하는 다른 스타일 참조도 함께 처리한다.
- 서식 문자열 `formatCode`는 그대로 둔다. 문자열 길이·소수·백분율·날짜 등의 의미를 임의로 바꾸지 않는다.
- 정의 없이 참조되는 내장 서식 41~44 등도 별도 fixture로 확인한다. 설치된 라이브러리가 지원하지 않는 것으로 확인되면 검증된 숫자 서식 정의를 제공한다. 날짜·시간 형식이나 알 수 없는 지역별 형식에는 일반 숫자 대체를 적용하지 않는다.
- 동일 ID에 서로 다른 정의가 있거나 해석 의미를 확인할 수 없는 서식은 조용히 덮어쓰지 않는다. 문제 위치와 함께 호환 오류로 반환하고 추가 대응 여부를 결정한다.
- XML은 `xml` 패키지로 구조적으로 처리한다. 기존 기본 네임스페이스와 접두사를 보존한다. 시트 XML·셀 스타일 인덱스 `s`·셀 값 `v`·수식 `f`·공유 문자열은 수정하지 않는다.
- ZIP 입력 파일을 디스크에서 덮어쓰지 않는다. 암호화 파일·손상 ZIP은 서식 정규화 대상으로 취급하지 않는다.

단순히 모든 `numFmtId`를 0으로 만들거나 서식을 삭제하면 날짜·가격·비율이 다르게 해석될 수 있다. 보정은 정의와 참조의 연결을 유지하는 범위에서 수행한다. 지원하지 않는 파일까지 무조건 성공으로 돌리는 것은 완료 기준이 아니다.

### 구현할 결과·오류 계약

공통 디코더 안에서 원래 예외와 보정 후 예외를 개발 진단에 보존하고, 호출자에는 `invalidContainer`, `invalidXml`, `unsupportedNumberFormat`, `decodeFailed` 등의 구분 가능한 읽기 오류를 전달한다. 필요하면 보정된 서식 ID 수와 보정된 관계 수만 진단 정보에 포함한다. 사용자 파일 내용이나 단가·품목 전체를 로그에 복사하지 않는다.

원본 오류의 문자열만으로 보정 여부를 판단하지 않고 실제 XML 구조로 판단한다. 라이브러리 예외 문구가 바뀌어도 동일 입력 구조를 처리할 수 있어야 한다.

## 3. P0 / HIGH: 업로드 연결과 데이터 검증 유지

원재료·레시피·거래처 단가의 직접 호출을 공통 디코더 호출로 교체한다. 메뉴·Photo는 이미 공통 디코더를 사용하므로 새 보정의 영향을 테스트한다. 같은 보정 코드를 각 화면에 복사하지 않는다.

원재료 등록에서 읽기가 성공하면 기존 계약을 유지한다.

- 시트: `원재료등록`.
- 열: `원재료ID`, `원재료코드`, `원재료명`, `분류`, `구매단위`, `소진단위`, `제품중량`, `보관방법`, `유통기한(일)`, `발주가능(Y/N)`, `거래처`, `가격`.
- 원재료ID·분류·보관방법·유통기한 값은 선택이지만 해당 열은 필요하다.
- 소진단위: `g`, `ml`, `ea`. 제품중량: 구매단위 1개에 대한 소진단위 환산 수량, 0보다 큰 숫자.
- 발주가능: `Y` 또는 `N`. 가격: 0 이상의 숫자이며 공란은 오류.
- 기존 원재료 ID·코드 매칭, 코드 중복, 거래처명 모호성, 1,000행 제한, 전체 검증 후 등록 확인 절차를 유지한다.

시트나 열을 자동으로 추정해서 바꾸거나, 가격 공란을 0으로 채워 통과시키지 않는다. 원재료 이름에서 박스 중량을 추정하지 않는다. 모든 검증이 끝나고 사용자가 미리보기를 확인하기 전에는 저장 RPC가 호출되지 않아야 한다.

## 4. P1 / MEDIUM: 실제 문제를 알려주는 안내

각 업로드 예외를 읽기 오류와 양식·값 검증 오류로 구분하고 KO/EN/VI 문구를 제공한다. 원시 스택이나 라이브러리 코드가 기본 사용자 화면에 노출되지 않도록 한다.

| 상황 | 제안 안내 |
|---|---|
| ZIP/파일 읽기 실패 | “Excel 파일을 읽지 못했습니다. 파일이 손상되었거나 지원되지 않는 형식일 수 있습니다.” |
| 보정되지 않는 숫자 서식 | “이 파일의 일부 셀 서식을 처리하지 못했습니다. 등록 양식에 값을 붙여넣어 다시 저장해 주세요.” |
| 시트 불일치 | “원재료등록 시트가 없습니다. 현재 시트: RM List.” |
| 열 누락 | 누락된 열 이름을 구체적으로 표시 |
| 가격 공란 | “38행: 가격을 입력하세요. 0 이상의 숫자를 입력할 수 있습니다.” |

복구 가능한 서식이 정상 보정되면 사용자에게 오류를 띄우지 않고 기존 미리보기까지 진행한다. 실제 데이터 오류는 그대로 보여 준다. 양식·값 안내 문구 변경은 해당 importer의 예외 변환 위치와 `inventory_purchase_screen.dart`의 표시 연결을 함께 검증한다.

## 5. 검증 항목과 완료 기준

새 테스트는 외부 작성기 구조를 흉내 낸 최소 파일을 포함한다. `excel` 자체로 생성한 파일만 다시 읽는 테스트로 끝내지 않는다. 실제 거래가격·작성자 정보가 들어 있는 전체 원본을 저장소 fixture로 복사하지 않고, 문제를 재현하는 서식 구조와 합성 데이터를 사용한다.

| 검증 | 기대 결과 |
|---|---|
| 명시적 서식 ID 43 + 기존 사용자 서식 164 | 충돌 없이 보정하여 읽기 성공. 숫자 원본 값 동일 |
| 보정이 필요한 워크시트 경로와 숫자 서식이 한 파일에 동시 존재 | 한 번의 보정으로 두 문제 해결 |
| 이미 지원되는 사용자 서식, 내장 서식, 정의 없는 41~44 | 지원 범위를 명시하고 정상 데이터 해석. debug/release에서 결과 일치 |
| 숫자·소수·0·음수·백분율·문자열 코드·날짜·시간 | 보정 전후 값과 유형을 비교. `00123` 문자열은 그대로 유지 |
| 수식·수식 캐시가 있는 파일 | 수식과 캐시를 보존. 수식을 새로 계산하거나 숫자로 임의 평가하지 않음 |
| 단가 적용일과 날짜 셀 | 정상 날짜 의미 유지. Excel 일련번호로 조용히 변환하지 않음 |
| 상충하는 정의, 손상 ZIP/XML, 빈 파일 | 구분된 오류. 크래시나 반복 재시도 없음 |
| 첨부 원본 RM List.xlsx | 서식 오류가 사라지고 **원재료등록 시트 없음** 검증까지 진행 |
| 시트 이름만 맞춘 첨부 구조 | 필수 열 누락 안내 |
| 올바른 양식 + 가격 공란 | 해당 행 오류, RPC 호출 0회 |
| 올바른 양식 + 유효한 가격 | 원재료 신규/수정 건수 미리보기 정상. 기존 저장 방식 유지 |
| 메뉴·메뉴 수정·레시피·거래처 단가·Photo 수동 파일 | 기존 지원 입력의 결과와 오류 계약 유지 |
| 1,000행 및 초과 파일 | 기존 행 제한 동작 유지. 행마다 파일 재해석·네트워크 요청 없음 |

구현 시 관련 importer/decoder 단위 테스트와 원재료 업로드 위젯 검증을 먼저 실행한다. Flutter 정적 분석과 프로젝트의 관련 검사·빌드를 통과한 뒤 배포를 진행한다. 공통 디코더에 연결되는 메뉴·Photo 테스트도 포함한다. 정상 파일 경로가 재압축을 수행하지 않는지, 보정 경로가 ZIP을 한 번 순회하고 재해석을 한 번만 하는지 확인한다.

운영 배포가 필요해지면 프로젝트의 `scripts/deploy_pos_production.sh`와 실제 push된 head SHA의 필수 GitHub Actions 게이트를 따른다. 로컬 테스트 통과는 운영 배포 확인과 별도로 기록한다. 롤백은 이 변경의 공통 디코더·연결·문구 변경만 되돌리는 앱 릴리스이며 DB 롤백은 필요하지 않다.

**완료 판단:** 정상 Excel 숫자 서식 때문에 원재료 업로드가 중단되지 않고, 유효하지 않은 시트·열·가격은 정확히 안내하며, 데이터와 기존 등록 동작이 보존되어야 한다. 현재 첨부는 별도의 양식·가격 보완이 필요하다.

## 6. 이번 요청에서 완료한 결과물과 증거

- [노란 셀과 설명을 넣은 검토 사본](</Users/andreahn/Downloads/RM List_등록검토_20261008.xlsx>): `검토안내`, `RM List`, `양식비교`, `가격누락`의 4개 시트.
- 원본 헤더 `A1`, `C1:H1`, 가격 공란 `F38`, `F112:F117`에 노란 셀과 설명을 추가했다. 가격 누락 품목명·설명 열도 표시하고 셀 메모를 넣었다.
- `G16`, `G110`의 VAT 금액 계산 수식도 노란색으로 표시하고 현재 등록에서 처리되지 않는 이유를 설명했다.
- 116개 품목의 기존 셀 값·수식과 수식 캐시를 원본과 대조했다. 가격을 임의로 입력하지 않았다. 원본 파일 SHA-256은 `2ba67b68878d6b6471ff4e58fc99256d9f53c74d2b17e3cda3fec7d1ce21e612`이며 검토 사본 생성 후에도 동일했다.
- 1차 조사에서 기존 원재료 importer 테스트 6개가 통과했고, 별도의 실제 첨부 파일 실행에서 읽기 예외가 재현됐다. 이번 계획 수립에서는 기존 공통 디코더에서도 같은 예외가 나는 것을 추가 확인했다.
- 계획 수립 당시에는 Excel 검토 사본과 이 문서를 작성했다. 이후 사용자 요청에 따라 앱 구현과 관련 테스트 76개·정적 분석·웹 빌드 검증을 완료했으며, [구현 보고서](/Users/andreahn/globos_pos_system/docs/implementation/excel_import_format_compatibility_implementation_20261008.md)에 결과를 기록했다. DB 작업·운영 배포는 수행하지 않았다.
