## 2. 목표 업무 흐름

1. 최초 견적에서 **매장이 배달비를 받아 기사에게 현금 지급 / 실제 배달비는 조리 후 별도 청구**를 선택한다. 음식·옵션·기존 세금 및 수수료를 포함한 주문 대금만 안내하고, 배달비는 “미확정·별도 결제 예정”으로 표시한다. 배달비를 무료로 오해하게 하는 `0 VND` 표시를 피한다.
2. 고객의 음식 대금 입금을 확인하면 기존 주문을 결제 완료하고 주방 작업을 시작한다. 배달비 미확정 상태가 조리나 포장 진행을 막지 않게 한다.
3. 모든 대상 음식의 **조리 완료**를 확인하면 캐셔에 “기사 호출·배달비 확인” 작업을 표시한다. 기존 `cooking_complete`를 사용하고, 포장 완료인 `ready`와 구분한다. 이번 범위의 기사 호출은 직원이 Grab/Be 등에서 수행하며 자동 배차 API를 새로 도입하지 않는다.
4. 직원이 기사 호출 결과의 업체·참조·실제 비용·사진 또는 PDF 근거를 기록하고 **배달비만 결제 요청**을 보낸다. 기사 예약/비용 확인을 음식 인계와 구분한다. 예약을 기록하기 위해 먼저 인계 완료를 눌러야 하는 구조를 만들지 않는다.
5. 고객 주문 화면과 채팅에 배달비 전용 결제 카드를 표시한다. 실제 배달비, 받은 배달비, 이번 요청액, 사유, 결제 QR/계좌와 증빙 제출을 보여준다. 음식 대금은 다시 청구하지 않는다.
6. 고객이 증빙을 보내면 “입금 확인 대기”로 표시한다. 캐셔가 실제 입금을 확인하면 배달비 결제를 확정한다. 이미지 전송만으로 결제 완료로 처리하지 않는다.
7. 포장 완료와 배달비 정산을 확인한 뒤 매장이 기사에게 현금을 지급한다. 실제 지급액·직원·시간·참조·지급 확인을 원장에 기록하고 인계한다. 미수금이 남으면 인계를 차단한다.

예: 음식 주문 대금 200,000 VND를 먼저 결제 → 조리 완료 후 실제 배달비 35,000 VND 확인 → 고객에게 35,000 VND만 추가 요청 → 입금 확인 → 기사에게 현금 35,000 VND 지급. 원 음식 결제·재고 소비·주방 작업은 한 번만 발생한다.

### 화면과 서버 보완

- 최초 견적의 주 화면에 후청구 옵션을 배치한다. 고객에게도 결제 전 배달비 별도 청구 조건을 안내한다. 이미 확정된 견적을 후청구 설정만으로 덮어쓰지 않는다.
- 캐셔 목록과 상세에서 음식 결제 상태와 배달비 상태를 따로 보여준다: `미확정 → 결제 요청 → 입금 확인 대기 → 결제 완료 → 기사 현금 지급`.
- 조리 완료 후 미확정 배달비를 캐셔의 다음 작업으로 표시한다. 조리 완료 상태와 후청구 생성 조건은 서버도 검증한다. 기존 배송비 차액 정산 등 다른 경로의 유효 조건을 일괄 변경하지 않는다.
- 기존 실비 확인·차액 계산·별도 청구·입금 원장·`process_payment`를 연결한다. 실제 비용 확인과 청구 생성, 메시지 기록은 같은 트랜잭션에서 처리한다. `operation_id`와 상태 버전으로 재시도·중복 클릭을 통제한다.
- 고객 결제 카드는 주문 링크 재접속 후에도 복원한다. 일반 첨부 전송과 배달비 증빙 제출을 구분한다. KO/VI/EN의 결제 상태와 안내를 함께 정리한다.
- 고객 수금, 실제 비용, 기사 현금 지급을 별도 금액으로 유지한다. 현재 VAT·매출·비동기 MISA 계약을 유지하고, 배달비 회계용 주문이 음식 주문 건수·주방·재고를 중복 증가시키지 않는지 검사한다.

## 3. 양방향 사진·파일 전송 개선

### 원인 확인을 먼저 수행

매장→고객, 고객→매장 각각에서 작은 PNG/JPEG와 PDF로 재현한다. 파일 선택 → 미리보기 → upload token 발급 → Storage 전송 → commit → 상대 화면 표시 → 열기 단계 중 실패 지점을 확인한다. 사용 기기·브라우저, 파일 유형/크기, HTTP 상태와 정제된 오류 코드만 기록한다. 고객 파일 원문, 세션 비밀, signed URL과 토큰을 로그에 남기지 않는다.

운영 migration 이력, 배포된 Edge action, 웹 빌드 버전, private `direct-order-chat` bucket과 제한, 함수/Storage CORS 및 인증 경로를 대조한다. 코드만 보고 매장 전송 실패 원인을 “권한 오류” 또는 “미배포”로 단정하지 않는다.

### 일반 첨부와 결제 증빙의 계약 분리

- 고객 일반 첨부 전용 upload/commit action과 저장 RPC를 추가한다. 주문 접근 권한과 `chat_open`을 확인하고, 견적·청구 ID 없이 `message_type='attachment'`로 저장한다. 결제 전·조리 중·후청구 중 등 열린 상담에서 사용할 수 있게 한다.
- 결제 증빙은 기존 proof 계약을 유지한다. 대상 견적/배달비 청구에 연결하고 `payment_proof`로 저장한다. 일반 사진을 최신 입금 증빙으로 선택하거나 결제 검토 상태로 바꾸지 않는다.
- 매장 일반 첨부도 같은 파일 검증과 재시도 규칙을 사용한다. 기존 증빙·URL 열기 API와 메시지 기록을 호환 유지한다. 과거 고객 증빙을 일괄 일반 첨부로 바꾸지 않는다.
- 고객 채팅 작성 영역에 사진·파일 버튼을 추가하고, 양쪽 모두 선택/미리보기/취소/전송 중/실패/재시도 상태를 제공한다. 미지원 유형·용량 초과·접근 종료·네트워크·서버 일시 오류를 구분해 안내한다.
- 1차 지원 범위는 양쪽의 JPG/JPEG/PNG/WebP/PDF, 파일당 최대 5 MiB로 맞춘다. 결제 증빙은 이미지만 허용한다. 모바일 사진 선택과 실제 MIME을 검사하고, HEIC 등 미지원 입력은 전송 성공처럼 표시하지 않는다. 실제 실패 샘플이 HEIC이면 변환 가능성과 검증 방법을 확인해 지원 여부를 확정한다.
- 서버에서 확장자·MIME·실제 바이트·기존 이미지 크기 제한을 함께 확인한다. PDF는 일반 파일 열기로 제공하고, 이미지에는 미리보기를 제공한다. Storage는 private으로 유지한다.
- 같은 전송 작업은 동일한 객체 경로/작업 ID로 복구한다. 업로드 또는 commit 응답 유실 시 중복 메시지를 만들지 않는다. “업로드 성공·채팅 표시 실패”는 상태 재조회로 복구한다. 주문을 바꾼 뒤 이전 파일이 새 주문으로 전송되지 않게 한다.
- 전송 직후 발신자와 상대 화면을 갱신한다. 파일 URL 만료 시 소유권을 다시 확인해 재발급하고, 보존 기간 후 객체 정리와 금융 증빙 보존의 현재 경계를 유지한다.

| 열린 주문 상세/상태 | 기존 단일 주문 응답에 음식·배달비·현금 지급 상태를 포함한다. 별도 청구 C건마다 잔액 조회를 호출하지 않는다. |
| 첨부 목록 A건 | 메시지/메타데이터는 한 번에 조회한다. 썸네일이 필요하면 페이지의 경로를 모아 batch signed URL 발급을 사용한다. 파일 하나를 사용자가 열 때만 단일 URL 발급을 허용한다. |
| 파일 1개 전송 | 정상 새 전송은 객체 존재 확인/복구, token 발급, Storage 업로드, commit의 고정 단계로 처리한다. 화면 메시지 수에 따라 호출 수가 늘어나지 않게 한다. |
| 여러 배달비 결제의 환불 | 기존 SQL에는 결제별 환불 합계를 조회하고 `record_payment_adjustment`를 반복 호출하는 루프가 있다. 대상 결제를 일괄 잠그고 환불 합계를 GROUP BY, 배분을 누적합으로 계산한 뒤 검증된 batch 조정 경로로 기록한다. 내부 트리거/함수도 항목별 재조회가 없는지 검사한다. |
| 여러 회계 주문의 invoice intake | 기존 지원 action은 청구별 `direct_order_sync_invoice`를 호출한다. 대상 주문 ID를 한 번에 모아 일괄 조회·upsert로 처리하고 외부 MISA 발행은 기존 비동기 경로를 유지한다. |

기존 루프 근거는 [지원/취소/픽업 환불](/Users/andreahn/globos_pos_system/supabase/migrations/20261008020000_direct_order_support_and_payments.sql:443)와 [배송비 감소 환불](/Users/andreahn/globos_pos_system/supabase/migrations/20261009151000_direct_order_verified_delivery_cost.sql:113)이다. 이번 개선에서 사용하는 관련 분기들을 일괄 처리로 교체한다. 목록·첨부·환불 데이터량을 늘렸을 때 DB 왕복은 고정 횟수 또는 정해진 batch 크기의 청크 수로 증가해야 한다. 행 처리 자체의 비용과 DB/API 호출 수는 구분한다.

추가 결제 요청의 필수 전달 방식은 **고객 주문 화면과 채팅의 저장된 결제 카드**로 정한다. 새 SMS·외부 메신저 전송은 도입하지 않는다. OS 푸시의 기존 [dispatcher](/Users/andreahn/globos_pos_system/supabase/functions/direct-order-notification-dispatcher/index.ts:50)는 장치 D개에 전송 D회와 결과 저장 RPC D회를 수행한다. 이를 그대로 재사용하는 계획은 N+1 규칙을 충족하지 않는다. 결과 저장은 lease 검증을 포함한 batch 완료 RPC로 교체해야 한다. Firebase `sendEach`도 메시지마다 RPC를 수행하므로 단순 SDK 교체나 동시 실행으로 해결됐다고 보고하지 않는다. [Firebase 공식 계약](https://firebase.google.com/docs/reference/admin/node/firebase-admin.messaging.messaging)

후청구의 OS 푸시는 실제 batch 전송 방식을 확보한 후 별도 적용한다. 1차 후청구 요청은 채팅 기록/화면 갱신으로 전달하고, 기존 `direct_order_payment_notice_trigger`에서 신규 후청구가 위 dispatcher를 자동 호출하지 않도록 이벤트 발행 분기를 설계한다. 다른 기존 알림을 일괄 끄지 않는다. 푸시를 포함하는 후속 범위에서는 공급자 호출까지 실제 횟수로 검증하며, 지원되지 않는 batch API를 가정하지 않는다.

이번 변경에 맞는 SQL/Edge/Flutter 회귀를 추가하고 기존 관련 검사를 다시 실행한다. 구현 후에는 `flutter analyze`, `flutter test`, `bash scripts/check_repo.sh` 및 release build를 수행한다. 운영 반영 시에는 정확한 pushed HEAD의 필수 GitHub Actions 성공과 `scripts/deploy_pos_production.sh`를 따른다. 과거 검사나 로컬 부분 통과를 운영 gate PASS로 대신하지 않는다. 기존 전체 검사 불일치는 현재 상태에서 다시 확인한다.

새 DB/API 계약은 기존 클라이언트와 호환되게 준비하고 서버를 먼저 적용한다. 새 API가 없을 때 버튼이 실패하는 UI 선배포를 피한다. 운영에서 두 기능을 같은 주문으로 확인한 후 완료로 판단한다. 되돌릴 때도 이미 받은 돈·기사 지급·견적·첨부/증빙 기록을 삭제하지 않고 새 진입점만 닫을 수 있어야 한다.
