## 목표와 적용 원칙

화면·업무에 필요한 데이터만 읽고, 동일 자원의 중복 요청을 합치며, 입력 규모와 동시 사용자 증가에도 요청·메모리 상한이 유지되게 한다. “RPC 한 번”이나 “병렬화”만으로 완료 판정하지 않는다.

결제 원자성, 매장/테넌트 권한, 정확한 금액·건수, 영수증/분할 결제 의미, MISA 비동기, Office 호환성, 은퇴 서비스 계약을 보존한다. 고객 데이터 삭제나 기능 중단으로 성능 목표를 맞추지 않는다.

아래 수치는 **초기 구현 예산**이다. 업무상 필요한 입력·실제 API 제한·대표 기기에서 검증한 뒤 조정한다. 현재 운영 성능이나 최적값을 측정했다는 뜻은 아니다.

## W0 — 기준선·측정 범위

1. 감사의 `source_manifest_initial/final.json`과 현재 변경을 비교한다. 이후 바뀐 함수·호출자만 재검토한다. 미커밋 사용자 변경을 숨기거나 초기화하지 않는다.
2. 이번 mock/최소 SQL fixture를 빠른 회귀 재현으로 유지하고, 실제 Supabase 버전·현재 migrations·RLS·trigger·grant가 적용된 격리 통합 환경을 별도로 구성한다. mock의 응답 행을 DB 스캔 행으로 기록하지 않는다.
3. 사용자 상호작용 ID마다 HTTP/RPC 수, 내부 SQL 횟수, 관계별 스캔 행/loops, 반환 행, 요청/응답 bytes, p50/p95/p99, 최대 동시성, timeout·오류를 수집한다. DB `BUFFERS`·temp spill과 클라이언트/worker RSS 또는 heap peak도 관련 경로에서 기록한다.
4. 테넌트/매장/역할, 날짜, 필터, 정렬, 페이지 크기, 캐시 상태, 버전/revision을 workload 키에 포함한다. cold/warm cache를 구분하고 raw samples를 보존한다.
5. 같은 환경·seed로 최소 20개 warm 반복과 별도 cold 반복을 비교한다. 부하 검증은 동시 사용자 1/10/50부터 시작해 예산 내에서 확대한다. 측정 자체의 병렬성에도 상한을 둔다.

일반적인 10% 시간 차이는 공유 호스트 잡음일 수 있으므로 단일 측정으로 개선률을 주장하지 않는다. 요청·행·bytes의 구조적 감소와 시간 분포를 함께 판정한다.

## W1 — 갱신 요청 중첩과 범위 확대 차단

### 설계

- `WaiterTableNotifier`와 Super Admin catalog를 **점포·자원 키별 진행 중 1개 + 후속 dirty 1개**로 직렬화한다. `force`는 대기자마다 새 요청을 만드는 대신 후속 갱신 필요 상태만 표시한다. 완료·오류·dispose·매장 전환 때 상태를 정리한다.
- 100–350ms 범위의 이벤트 병합 창을 해당 화면의 최신성 요구에 맞춘다. 변경 주문 ID는 중복 제거 후 **50개씩, 동시성 1**로 처리한다. ID가 누적되면 무제한 Set을 유지하지 않고 정해진 임계치에서 전체 복구 1건으로 전환한다.
- 테이블 배치/좌석 정보는 해당 테이블 변경에만 갱신한다. 주문 항목 변경은 영향받은 주문·테이블 미리보기만 갱신한다.
- 주방/결제 데이터 갱신의 책임을 provider 한 곳으로 모은다. 공통 피드·직접 구독·poll이 동일 변경에 각각 전체 조회하지 않도록 조정하고 연결 복구용 전체 동기화는 보존한다.
- `PosLiveEvent`에 영향 매장 ID 집합을 유지한다. 전체 복구 신호와 여러 매장 변경 신호를 구분한다. 보고서 조회는 변경 매장만 **100개 이하씩**, 서버의 기존 500개 상한 안에서 처리한다.
- 캐시 키는 사용자/역할·매장·필터·날짜·revision을 포함한다. 오류나 권한 변경 때 이전 권한의 결과를 재사용하지 않는다.

### 상한과 검증

- 최초 조회 중 100개 강제 요청: 실제 읽기 **≤2회, 같은 키 최대 동시성 1**. 테이블 전체 갱신 fallback은 현재 2-쿼리 구조 기준 **≤4 HTTP**로 제한한다.
- E개 이벤트의 고유 변경 주문이 D개이면 정상 delta 조회 수는 `ceil(D/50)`에 페이지·복구 확인을 더한 값이다. 여러 ID를 묶었지만 SQL 내부에서 단건 helper를 D번 조회하는 구현은 금지한다.
- 500개 매장 중 2개 변경: 반환/집계 범위 2개. 나머지 매장 결과 유지. 전체 복구 신호 때만 전체 범위 갱신.
- 정상/오류/늦은 응답/매장 전환/연결 복구/지속 이벤트 입력에서 stale UI·누락·무한 후속 갱신이 없는지 검증한다. 실시간 전달 지연도 전후 비교해 병합 때문에 최신성이 훼손되지 않게 한다.

## W2 — 범위가 제한된 SQL과 발주 이력

### 발주 상세 (F03)

- 권한 검증된 공급상품 ID 최대 **100개**와 현재 발주 ID를 받는 이력 batch 계약을 추가한다. 현재 발주의 행은 제외하고 기존 권한 내 이력 범위를 유지한다. 초과 입력은 클라이언트에서 100개씩 나누고 **동시성 ≤2**로 처리한다.
- 상품별 `(created_at DESC,id DESC)` 최신 3건을 먼저 선정한다. 그 선택된 발주행 집합에 대해서만 입고를 사전 집계하고 JOIN한다. 최종 반환은 최대 `3S`개이며 서로 다른 1:N 관계를 바로 곱하지 않는다.
- 목표 추가 읽기: `ceil(S/100)` HTTP, S≤100이면 1회. 전체 H건 ID를 URL에 넣는 경로 제거.
- S=1/10/100, 과거 H=100/1,000/100,000, 입고 0/1/다건으로 검증. 현재 발주가 가장 최신이어도 그 이전 3건을 반환해야 한다. 상품별 최신 3건과 수량이 동일하고, 응답 크기는 H보다 S에 비례해야 한다. index top-k가 적절한 경우까지 일괄 금지하지 않되, 쿼리 내부 작업량은 실제 계획으로 입증한다.

### 메뉴 분석 (F04)

- 날짜 범위의 결제가 있는 **후보 주문 ID**를 먼저 고른다. 후보의 전체 결제 이력에서 마지막 결제 시각을 구한 뒤 원래 기간 의미를 적용한다. 무관한 주문 전체를 집계하지 않는다.
- 최고 판매 시간대는 메뉴별 상관 CTE 검색 대신 순위/`DISTINCT ON`으로 한 번 계산한다.
- 현재 인덱스를 먼저 활용한다. 신규 인덱스는 읽기 효과와 쓰기 비용을 EXPLAIN/BUFFERS로 확인한 뒤 추가한다.
- 일/월/장기 범위, 분할 결제, 기간 이후 추가 결제, 취소·서비스 품목·콤보·다국어별 결과 동등성을 검사한다. 조회일 주문 고정·과거 이력 100배 증가 시 후보 밖 전체 스캔이 없어야 한다.

### 재고 원가·overview (F05)

- 권한 있는 대상 매장 상품 집합을 먼저 만들고 공급가·소비 집계에 재사용한다. 공급가 우선순위와 최신 가격 선택은 동일하게 유지한다.
- overview와 stock status가 같은 매장·기준일의 소비량을 한 번만 계산하도록 공유한다. 필요한 발주 상태를 집계 입력의 WHERE로 제한한다.
- 대상 매장 상품 100개 고정, 타 매장 자료 100→100,000개 증가 시 대상 외 공급가 스캔이 전체 규모에 비례하지 않아야 한다. 같은 상호작용의 7일 소비 집계는 1회가 목표다.

## W3 — 첫 화면·요약·상세·내보내기 분리

- **재고 탭:** 선택되지 않은 탭의 목록/카탈로그를 읽지 않는다. 첫 상품 목록은 **50개, 최대 100개** 키셋·서버 검색으로 제공한다. 대시보드 진입의 공급상품 상세 조회는 0회가 목표다. Excel 전체 내보내기는 **500개 순차 배치, 동시성 1**로 읽고 점진적으로 기록한다.
- **영수증(F06):** 헤더·검색에 필요한 경량 필드로 페이지를 먼저 고른 뒤 선택 ledger key의 품목·배분을 일괄 조회한다. 기본 50·최대 100개, `(sold_at,receipt_id)` 안정적인 커서. 정확한 합계/총건수는 경량 집계로 유지하고 사용자·매장·날짜·revision별로 공유한다. 결제/환불 이벤트 무효화가 필요하다. 정확한 총건수가 필요 없는 `has_more`만 `limit+1`로 처리한다.
- **요약/추이(F07):** aggregate-only 응답 계약을 만들고 예외 상세는 열 때 **50개, 최대 100개** 키셋 조회한다. 최초 요약·추이는 `O(D)` 크기, 예외 X건 증가에 무관하게 만든다. 기존 배열길이=건수 검증은 버전 전환과 함께 변경하며 정확한 총건수를 삭제하지 않는다. 큰 기간은 서버 rollup/월별 결과와 필요 구간 상세를 사용하고, 사용자가 필요한 기간을 임의로 잘라 버리지 않는다.
- **개인 급여(F08):** 직원 조건을 기존 paged RPC·revision 범위까지 전달한다. 페이지 **500행, 동시성 ≤2**; 선택 직원 로그 L개 기준 `ceil(L/500)` 데이터 페이지 + 명시된 종료/revision 확인으로 제한한다. 다른 직원 E가 늘어도 개인 조회량이 늘지 않아야 한다. 개인 결과와 전체 급여 계산의 해당 직원 결과를 비교한다.

검증 데이터: 페이지 경계의 같은 시각/누락/삭제, 단독·합산·분할 영수증·부분 환불, 역할별 가격 숨김, 예외 10/1,000/100,000건, 직원 1/100/1,000명. 첫 페이지 응답과 보유 메모리가 전체 목록 크기에 비례하지 않아야 한다. 장기 export 자체가 전체 데이터를 처리하는 것은 허용하되 배치 크기·메모리는 고정한다.

## W4 — Excel 입력과 메모리 예산

- 초기 제안: 압축 파일 **10 MiB**, 총 해제 **50 MiB**, 시트 **10개**, 총 **200,000셀**, 기존 업무 행 제한 유지. 정상 파일 분포와 기기 메모리를 검토해 확정한다.
- 파일을 전부 읽기 전에 길이를 검사한다. ZIP 중앙 디렉터리의 선언 크기만 믿지 말고 실제 해제 과정에도 누적 바이트·파일 수 예산을 둔다. 메타데이터 확인에 쓰는 라이브러리가 이미 전체 해제하는지도 확인한다.
- XML/행 순회 중 한도를 넘으면 즉시 중단한다. 10,001번째 유효행에서 제한 오류를 내기 전에 전체 Excel 객체·모든 시트 행렬을 만들지 않도록 parser 경로를 바꾼다.
- 필요한 시트·컬럼만 처리하고 불필요한 재압축·재디코딩을 제거한다. 지원하지 않는 형식의 명확한 오류와 기존 외부 Excel 호환성을 유지한다.
- 작업 동시성 **1**. Native는 isolate, web은 worker 또는 취소 가능한 단계적 처리로 UI 응답성을 확보한다. isolate로 옮긴 것만으로 메모리 상한을 해결했다고 판단하지 않는다.
- 같은 100/1,000/10,000행 정상 파일과 10,001행/다수 빈 셀/여러 시트/큰 문자열/높은 압축률 fixture에서 정확성, 거절 시점, RSS/heap peak, 프레임 지연을 측정한다. 업무상 상한 초과 자료는 전체 객체 생성 전에 거절돼야 한다.

## W5 — 재시도 단계를 보존하고 worker 작업량 제한

### 결제 증빙(F10)

- 증빙 작업에 안정적인 ID와 업로드/첨부 완료 상태를 보관한다. 같은 파일은 성공한 Storage 경로를 재사용하고 첨부만 재시도한다. URL 서명 실패·첨부 응답 유실도 별도 단계로 처리한다.
- 403/42501 같은 권한 오류는 사용자 조치 상태로 남긴다. 데이터는 삭제하지 않는다. 네트워크 오류/429/일시 5xx만 제한 재시도한다.
- 초기 예산: 동시성 **1**, flush **최대 10건**, 호출 timeout **10초**, 한 실행의 총 예산 **30초**, 자동 시도 **최대 3회** 후 사용자 조치/재개 상태. 지수 대기·jitter를 적용하고 재연결·SDK·큐가 각자 중복 재시도하지 않게 한다.
- 2회 flush에 업로드는 **1회 이하**가 목표다. 업로드 성공·첨부 실패·앱 종료·재연결·권한 회복·응답 유실을 주입해 동일 증빙이 중복 저장되지 않는지 검증한다.

### 긴급 푸시(F11)

- 초기 claim **50건**, 외부 동시성 **4**(대표 부하 검증 후 최대 8 검토), 요청 timeout **10초**, 총 실행 예산 **45초**를 적용한다. 남은 작업은 안전하게 다음 실행으로 넘긴다.
- 완료 결과를 50건 이하 배치 RPC로 저장한다. 50건 정상 완료의 DB 목표는 claim+완료 **2회**, 외부 전송은 디바이스별 최대 50회다.
- claim lease와 남은 시간에 맞춰 입력을 받고, 중단/timeout 후 재획득과 중복 알림 정책을 정의한다. 외부 전송이 성공했는지 불명확하면 무조건 재발송하지 말고 시스템이 허용하는 멱등성·중복 표시 방식을 먼저 확정한다.
- FCM 상태와 body를 함께 분류한다. UNREGISTERED 같은 영구 오류는 종료/토큰 무효화, 429/일시 5xx는 Retry-After·jitter·시도/기간 상한으로 처리한다. 기존 최대 시도 10회의 필요성도 검토한다.
- 작업 1/50/1,000건·동시 dispatcher 1/2/8개에서 최대 in-flight, claim 중복, 누락, 실패·오류별 재시도 수와 총 실행시간을 검증한다.

## W6 — 고정 계정 탐색을 정확 조회로 변경

- service-role 전용 정확 이메일 조회 또는 관리되는 이메일→auth ID 매핑을 설계한다. 필요한 반환은 ID·이메일 최대 1행이며 사용자 metadata 전체는 반환하지 않는다.
- 공개 RPC나 넓은 Auth 권한을 새로 부여하지 않는다. 호출자 권한·고정 계정 소유 범위·동시 생성 충돌·기존 사용자 연결 조건을 현재 정책과 비교한다.
- 디렉터리 100/10,000/100,000명에서 **조회 1회·최대 1행**, 최초 계정 생성·기존 계정·대소문자 정규화·다른 매장 소유 계정·동시 요청을 검증한다.

## W7 — 조건부 경로

### MISA(F13)

현재 저장소 기본값은 비활성이다. 이 개선을 이유로 운영 dispatch를 켜지 않는다. 활성화 작업의 선행 조건으로 처리한다.

- `FOR UPDATE SKIP LOCKED` claim, lease와 만료, 완료 시 소유권 검증을 설계한다. 기존 UUIDv7 RefID와 공급자 중복 처리 계약을 검증한다.
- 최대 50개 claim에서 고유 법인 ID를 묶어 설정·토큰을 **3회 이하의 일괄 읽기**로 가져온다. 요청 내/가능한 공유 범위의 토큰 갱신을 합치고 법인 격리를 유지한다.
- 상태 변경·이벤트 저장은 bounded batch completion으로 처리한다. 필수 공급자 발송 N회를 DB 3N 중복 조회와 분리해 계수한다.
- 초기 외부 동시성 **2**, API별 timeout·실행시간 예산은 공급자 제한을 확인해 확정한다. 멱등성 검증 전에 timeout 쓰기를 자동 재시도하지 않는다.
- 작업 1/10/50, 고유 법인 1/50, 동시 dispatcher 2/8, 토큰 만료·응답 유실에서 작업별 소유자가 하나이며 불필요한 중복 발송 시도가 없어야 한다. 결제 완료는 계속 독립적으로 성공해야 한다.

### SePay

Windows polling 전환 migration과 실제 사용 provider를 확인한 뒤 불필요한 FCM 기동을 제거하거나 provider 조건으로 제한한다. polling 알림 전달을 유지하며 비활성 provider의 dispatcher/OAuth/빈 claim은 0회가 목표다.

## 단계별 완료·릴리스 기준

1. 해당 단계의 기능·권한·금액·순서·멱등성 테스트를 통과한다. 성능 개선으로 접근 범위나 최신성을 약화하지 않는다.
2. 동일 입력의 전후 요청 수, 관계별 스캔 행, 응답 bytes, 동시성 상한이 각 작업 목표를 충족한다. SQL JOIN 변경은 독립된 자식 관계 1/10/100개를 조합해 행·합계 증폭이 없는지 확인한다.
3. 실제 호출자부터 RPC 내부까지 검증한다. 예를 들어 단건 batch API가 있어도 UI가 기존 전체 조회를 계속 쓰면 완료가 아니다.
4. 대표 기기/통합 환경의 지연 분포와 메모리 peak를 비교한다. 정확한 합계나 전체 export 때문에 필요한 작업은 범위와 비용을 명시하고, 실행계획·실측 없이 인덱스나 캐시를 무조건 늘리지 않는다.
5. 신규 RPC·응답 버전은 기존 앱 호환 기간과 rollback을 갖춘다. 전역 캐시 무효화 대신 영향 범위별 revision/invalidation을 적용한다.
6. 릴리스 시 관련 테스트·`scripts/check_repo.sh`, DB preflight/검증/rollback 절차를 수행하고, 정확한 pushed SHA의 필수 GitHub Actions 성공을 확인한다. production은 `scripts/deploy_pos_production.sh` 절차를 따른다.
