# 배달 주문 입금 캡처 버튼 분리와 전송 재시도 개선 계획

> **통합 문서로 대체됨 — 2026-10-06.** 현재 구현·검증·배포 기준은 [배달 주문 통합 개선 계획](direct_order_integrated_customer_and_packing_improvement_20261006.md)이다. 아래는 당시 조사와 개별 계획의 이력이며 별도 실행 계획으로 사용하지 않는다.

작성일: 2026-10-06, Asia/Ho_Chi_Minh.

작성 당시 상태: **계획 수립 완료, 구현 전**. 고객 배달 주문 `/order/:slug`의 주문 현황·입금 캡처 전송을 대상으로 한다. 현재 코드를 조사했으며 운영 화면 재현, 운영 DB 조회, 테스트 실행, 구현·배포는 수행하지 않았다.

조사 기준은 HEAD `cc4de81adb8870fd479cb12edd773cda635a01cd`와 기존 로컬 수정이 포함된 작업 디렉터리다. 기존 사용자 수정과 untracked 파일을 보존한다. 상단 카테고리 개선 계획과는 별도 작업이며, 직원의 사진 확인 승인 계약을 따른다.

## 1. 현재 흐름과 원인

현재 고객 동작:

```text
주문 현황 → 결제하기 → 계좌이체 안내창
          → 입금 캡처 보내기 → 안내창 닫힘
          → 사진 선택 → 미리보기·전송 확인 → 업로드

업로드 실패 → 오류 안내 → 주문 현황
           → 결제하기부터 다시 진입해야 사진을 보낼 수 있음
```

`결제하기`는 실제 결제 처리나 은행 송금을 실행하지 않고 QR·계좌 안내창을 연다. 사진을 보내는 진입점이 그 안내창 안에만 있어, 이미 송금한 고객도 실패 후 같은 결제 버튼을 다시 눌러야 한다.

| 조사 항목 | 현재 소스 | 개선 필요 |
|---|---|---|
| 주문 현황 버튼 | `_quoteCard()`에 `direct_open_payment_details` 하나만 있다. 최초에는 ‘결제하기’, 직원 재요청 때는 ‘이미지 다시 보내기’로 바뀐다. | 계좌 안내와 사진 전송을 독립 동작으로 표시한다. |
| 사진 전송 진입점 | `_showPaymentDetails()` 안내창 안의 `direct_upload_payment_proof`가 창을 닫고 `_uploadProof()`를 실행한다. | 주문 현황에서 안내창을 거치지 않고 직접 실행할 수 있게 한다. |
| 실패 후 파일 | 선택 이미지와 bytes는 `_uploadProof()`의 지역 변수다. | 현재 화면에서 같은 파일로 재시도할 수 있도록 보관한다. |
| 오류 표시 | 업로드 예외는 공통 SnackBar로 표시한다. | 전송 영역에 실패 상태와 재시도 버튼을 남긴다. |
| 업로드 단계 | 서비스가 URL 발급 → Storage 업로드 → `proof_commit_v2`를 한 메서드에서 처리한다. | 실패한 단계와 저장 경로를 보관해 접수 확인·재시도를 구분한다. |
| 중복 방지 | SQL은 동일 경로·견적·재요청 ID의 commit 재실행에 같은 message ID를 반환한다. | 응답 유실 시 새 사진 등록 대신 같은 경로의 commit을 재시도한다. |
| Storage 조회 오류 | Edge는 object 목록 조회 오류를 `PROOF_UPLOAD_INCOMPLETE`로 처리하며, 이미지 다운로드 오류도 `INVALID_PROOF`로 처리하고 경로 삭제를 시도한다. | 재시도를 안전하게 하려면 일시적인 조회·다운로드 오류와 확인된 이미지 불량을 구분해야 한다. |
| 성공 후 화면 | commit 이후 `_refreshStatus()`를 호출하며, 재조회 오류는 내부에서 처리한다. 별도 전송 완료 상태는 없다. | 사진 접수 성공과 주문 현황 갱신 실패를 다른 상태로 표시한다. |
| 기존 테스트 | 계좌 안내창과 직원 재요청 안내는 검증하지만, 독립 버튼·파일 선택·전송 실패 재시도는 검증하지 않는다. | 사용자 행동 및 서비스 실패 단계 테스트를 추가한다. |

## 2. 권장 화면

**주문 현황의 최종 입금액 아래에 두 버튼을 분리한다.** 모바일에서는 세로로 쌓고 두 버튼 모두 충분한 터치 영역을 확보한다.

```text
주문번호 · 최종 입금액 · 포함 VAT

[ 계좌이체 안내 ]                 QR·계좌 확인
[ 입금 캡처 보내기 ]              사진 선택·전송

이미 송금했다면 입금 캡처만 보내 주세요.
매장에서 사진을 확인한 후 주문을 승인합니다.
```

- 기존 ‘결제하기’ 표시명은 실제 동작에 맞춰 **‘계좌이체 안내’**로 변경한다. 기존 `paymentDetails` 다국어 문구를 재사용할 수 있다.
- **‘입금 캡처 보내기’는 계좌 안내창을 열지 않고 사진 선택으로 바로 진입한다.** 계좌 안내를 먼저 열었는지는 전송 버튼의 활성 조건이 아니다.
- 계좌 안내창은 QR·계좌번호·금액·송금 메모 확인과 닫기 기능을 담당한다. 창 안의 업로드 버튼은 주문 현황으로 이동시켜 전송 진입점을 명확히 한다.
- 이미지 미리보기에서 주문번호와 대상 입금액을 함께 표시하고, 고객이 전송을 확인하면 업로드한다.
- 채팅 아래로 별도 전송 진입점을 숨기거나, 실패 후 결제 안내를 다시 여는 흐름을 만들지 않는다.

실패한 경우의 같은 영역:

```text
선택한 입금 캡처 미리보기
사진 전송에 실패했습니다. 같은 사진으로 다시 시도해 주세요.
이미 송금했다면 다시 송금하지 마세요.

[ 입금 캡처 다시 보내기 ]
  사진 바꾸기
```

## 3. 주문 상태별 버튼

| 주문/전송 상태 | 표시와 동작 |
|---|---|
| 견적 대기 | 사진 전송 버튼을 표시하지 않는다. |
| `quoted` + 유효한 `active` 견적 | ‘계좌이체 안내’와 ‘입금 캡처 보내기’를 각각 표시한다. |
| 사진 선택 취소·미리보기 취소 | 주문 상태를 바꾸지 않고 기존 버튼으로 돌아간다. 업로드 API를 호출하지 않는다. |
| 이미지 전송 중 | 전송 버튼을 비활성화하고 ‘이미지 전송 중…’을 표시한다. 중복 파일 선택·중복 전송을 막는다. |
| 명확한 전송 실패 | 이미지와 실패 안내를 유지하고 ‘입금 캡처 다시 보내기’·‘사진 바꾸기’를 제공한다. |
| 접수 결과 확인 중 | ‘전송 결과 확인 중…’을 표시한다. 새 전송을 시작하지 않고 기존 시도의 접수 여부를 확인한다. |
| `awaiting_payment_review`, 열린 재요청 없음 | ‘입금 캡처 전송 완료 · 매장 확인 대기’를 표시한다. 결제/사진 전송을 다시 요구하지 않는다. |
| 직원 재요청, `canResubmit=true` | 재요청 사유와 ‘다시 송금하지 마세요’를 표시한다. ‘입금 캡처 다시 보내기’가 새 사진 선택으로 직접 연결된다. 계좌 안내·QR을 다시 제시하지 않는다. |
| 승인·조리·배달·완료 | 기존 진행 상태를 표시하고 새 사진 전송 버튼을 숨긴다. |
| 취소·거절·만료 또는 상태 충돌 | 새 전송을 차단하고 최신 상태·견적을 확인하도록 안내한다. |

**전송 실패 재시도**와 **직원의 사진 재요청**은 다른 상황이다. 전자는 선택한 사진을 그대로 다시 보내며 ‘사진 바꾸기’도 제공한다. 후자는 직원 사유를 확인하고 새 사진을 선택하며, 정확한 `review_request_id`에 연결한다.

최초 전송의 active 견적 만료 검사와, 이미 잠긴 견적에 대한 직원 재요청 조건을 구분한다. locked 견적의 과거 만료 시각만으로 허용된 사진 재제출을 막지 않는다. 최종 허용 여부는 기존 서버 계약을 따른다.

## 4. 실패 복구와 중복 방지

1. **주문별 전송 시도 보관:** 현재 화면 메모리에 이미지 bytes·MIME, `requestId`, `quoteId`, nullable `reviewRequestId`, 발급된 Storage 경로, 처리 단계를 보관한다. 사진을 브라우저 영구 저장소에 추가 저장하는 기능은 이번 범위에 포함하지 않는다.
2. **선택부터 중복 방지:** 파일 선택·미리보기·전송 전체에 처리 상태를 적용한다. 현재처럼 업로드 시작 직전에만 `_proofUploading`을 켜면 빠른 연속 클릭에서 선택창을 여러 번 열 수 있으므로 진입 시점부터 방지한다. 이미지 선택/읽기 오류도 같은 전송 영역에서 처리한다.
3. **URL 발급 실패:** 이미지를 유지한다. 아직 확보한 경로가 없다면 재시도 시 URL 발급부터 시작한다.
4. **Storage 전송 결과 불확실:** 성공 응답만 유실됐을 수 있으므로 같은 경로의 commit으로 접수 가능 여부를 확인한다. Edge에서 목록 조회·다운로드 오류는 일시 오류로 반환하고 해당 파일을 삭제하지 않는다. 정상적으로 읽은 bytes가 이미지 검증에 실패한 경우에만 기존 invalid-image 삭제를 실행한다. 재업로드가 필요하면 최신 주문의 전송 허용 여부를 확인한 뒤 진행한다.
5. **commit 실패·응답 유실:** 보관한 동일 경로·견적 ID·재요청 ID로 `proof_commit_v2`를 다시 호출한다. 정상 완료된 commit은 기존 message ID로 복구하며 새 파일 경로와 사진 메시지를 만들지 않는다.
6. **확인 전 사진 교체 방지:** commit 결과가 불확실한 동안에는 기존 시도를 먼저 확인한다. 이미 접수됐으면 완료 상태로 전환하고, 아직 접수되지 않았고 서버가 새 전송을 허용하는 경우에만 사진을 바꾼다.
7. **commit 성공·현황 조회 실패:** ‘사진 전송 완료, 주문 현황을 갱신하지 못했습니다’와 ‘상태 다시 확인’을 표시한다. 전송 실패로 되돌리거나 다시 송금을 요청하지 않는다. commit의 성공 결과를 받으면 현황 갱신 전에도 같은 사진의 중복 전송을 막는다.
8. **동시 상태 변경:** 파일을 선택하는 동안 견적·재요청·주문 상태가 바뀌면 ID를 새 주문에 임의로 바꿔 보내지 않는다. 충돌 응답 후 최신 상태를 확인한다. 주문 선택을 바꾸더라도 완료 응답이 다른 주문의 UI를 덮어쓰지 않게 한다.
9. **최신 상태 우선:** 동일 경로 commit의 재실행 응답은 `awaiting_payment_review`를 반환할 수 있다. 그 사이 이미 승인됐을 수 있으므로 실제 주문 상태를 과거 상태로 되돌리지 않고 최신 조회 결과를 따른다.
10. **페이지 재접속:** 서버 주문 현황을 다시 읽는다. 이미 접수된 사진에는 매장 확인 대기를 표시한다. 메모리에만 있던 미전송 파일은 재접속 후 다시 선택해야 하며, 영구적인 파일 복원 기능은 이번 계획에 포함하지 않는다.

JPEG/PNG/WebP, 최대 5 MiB의 기존 제한을 유지하고 클라이언트에서 가능한 크기·형식 오류를 먼저 안내한다. 기존 서버의 실제 이미지 검증·private Storage·세션 소유권 검증은 그대로 사용한다.

사진 접수는 입금 승인이나 주문 확정을 뜻하지 않는다. 기존 직원 사진 확인 승인 후 결제·주방으로 전달하는 계약을 유지하며, 업로드나 재시도에서 결제 RPC·신규 주문 제출을 호출하지 않는다.

## 5. 구현 순서와 범위

### 1단계 — 두 버튼과 전송 상태 영역

- `direct_order_storefront_screen.dart`: `_quoteCard()`에 계좌 안내·사진 전송을 분리한다. `_showPaymentDetails()`는 계좌 안내만 담당하게 한다.
- 같은 화면에 파일 미리보기, 전송 중, 실패·재시도, 전송 완료 상태를 표시한다. 기존 SnackBar만으로 실패를 알리지 않는다.
- 현재 화면을 유지하면서 실패 지점에서 재시도할 수 있게 한다. 접수 실패로 장바구니·주문·견적을 초기화하지 않는다.

### 2단계 — 기존 서비스의 단계별 재시도

- `direct_order_service.dart`: URL 발급·Storage 전송·commit 단계를 재사용하되, 화면이 같은 시도를 재개할 수 있게 경로와 단계별 결과를 제공한다.
- commit 성공의 message ID와 결과를 화면이 받을 수 있게 한다. 전송 완료와 주문 현황 재조회 실패를 분리한다.
- 이미지 선택과 Storage 호출을 테스트에서 주입할 수 있도록 최소한의 경계를 둔다. 새로운 업로드 프레임워크나 자동 백그라운드 재전송 기능은 만들지 않는다.
- Edge의 `proof_commit_v2` 처리에서 목록 조회·다운로드 일시 오류를 기존 임시 오류 응답으로 분리한다. 해당 오류에서는 `remove()`를 호출하지 않는다는 테스트를 추가하고, 실제 invalid bytes의 삭제 검증은 유지한다. V1/V2가 공유하는 분기이므로 양쪽 호환성을 검증한다.
- Edge/SQL에 이미 있는 V2 전송·중복 방지 API를 사용한다. 새 migration이나 서버 API는 필요하지 않으며, Edge 변경은 전송 확인의 일시 오류 처리에 한정한다.

### 3단계 — 문구·테스트·사양

- `direct_order_copy.dart`: 계좌 안내, 전송 실패, 접수 결과 확인 중, 전송 완료, 현황 재조회 실패, 재송금 금지, 사진 바꾸기의 KO/VI/EN 문구를 맞춘다.
- 기존 storefront widget 테스트와 서비스 재시도 테스트에 실패 복구를 추가한다. 필요 시 전송 전용 테스트 파일을 만든다.
- 구현과 함께 기존 `UI_SPEC.md`와 해당 API 설명에 고객 진입점·재시도 동작을 반영한다. 현재 계획을 이미 구현된 상태로 기록하지 않는다.

예상 변경은 고객 storefront, 전송 서비스·필요한 결과 모델, copy, public Edge의 Storage 오류 처리, 관련 테스트와 설계 문서다. 캐셔 승인, 은행 연동, 결제 계산·VAT·재고·주방 처리 변경은 이번 범위에 포함하지 않는다.

## 6. 완료 기준

| 검증 | 통과 기준 |
|---|---|
| 독립 진입점 | 계좌 안내를 열지 않고 주문 현황의 사진 버튼으로 선택·미리보기·전송을 할 수 있다. |
| 실패 복구 | 최초 전송 실패 후 결제 버튼을 누르거나 사진을 다시 선택하지 않고 같은 사진으로 재시도할 수 있다. |
| 취소 | 파일 선택·미리보기 취소 시 주문과 사진 접수 상태가 그대로이며 API 호출이 없다. |
| 중복 클릭 | 빠른 연속 클릭으로 이미지 선택창·업로드·commit이 중복 시작되지 않는다. |
| 단계별 오류 | URL 발급, Storage 전송, commit 각각의 실패를 주입해 파일 보존과 적절한 단계 재개를 검증한다. |
| Storage 조회 실패 | object 목록 조회·다운로드 일시 오류에 파일 삭제가 0회이며, 실제 잘못된 이미지의 거절·삭제는 유지된다. |
| 응답 유실 | commit 완료 후 응답 유실 시 동일 경로로 복구하고 사진 메시지는 1개다. |
| 전송 성공 후 조회 실패 | 전송 완료를 유지하며 ‘상태 다시 확인’만 제공한다. |
| 직원 재요청 | 직접 새 사진 선택, 재요청 ID 보존, 사유·재송금 금지 표시, 성공 후 확인 대기 전환이 동작한다. |
| 주문·견적 경합 | 주문 전환, 새 견적, 승인·취소, 다른 기기의 사진 접수에서 잘못된 주문 귀속이나 과거 상태 덮어쓰기가 없다. |
| 금액·주방 | 사진 전송/재시도만으로 신규 주문·결제·조리 티켓이 생성되지 않는다. 직원 승인 계약이 유지된다. |
| 화면·언어 | 360/390/768/1024/1440 폭과 KO/VI/EN에서 두 버튼·오류·재시도 조작이 잘리지 않고, 큰 글씨·48px 터치 영역을 지원한다. |
| 재접속 | 접수된 사진은 서버 상태로 복구되며 미접수 파일의 재선택 안내가 맞다. |

구현 후 변경 Dart 파일 format·`flutter analyze`를 실행한다. storefront widget 테스트, 전송 재시도 테스트, `direct_delivery_ui_contract_test.dart`, `direct_order_customer_payment_status_test.dart`, `direct_order_photo_approval_test.dart`, `direct_delivery_regression_isolation_test.dart`와 public Edge 테스트를 검증한다. 기존 SQL의 동일 경로 commit 검증은 격리 테스트 환경에서 필요한 범위로 실행하며 운영 DB에 실패 주입을 하지 않는다.

그다음 `bash scripts/check_repo.sh`와 해당 변경의 필수 GitHub Actions 체크를 확인한다. 운영 반영 시 독립 리뷰·로컬 검증을 사전 증거로 기록하고 정확한 배포 대상 SHA의 필수 CI 성공 후 `scripts/deploy_pos_production.sh`를 사용한다. 구현 완료, 운영 배포, 실제 사용 검증을 구분한다.
