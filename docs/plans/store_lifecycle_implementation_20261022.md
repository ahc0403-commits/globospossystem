## 검증 경계

- 운영 DB 쓰기, 실제 Auth 계정 발급, 배포, Office 수정은 하지 않는다. 로컬 Auth fixture로 실제 reconciliation SQL을 실행한다.
- 실 장치의 출력/인계, Office 접수, 공급업체 수신은 로컬 테스트의 증거 범위 밖이다.
- 품목 온도·기한·초기 재고 수량 등 실제 업무 값은 임의로 입력하지 않는다.
- 기존 매장 식별자, 저장 1F/2F/3F, 전가복 계정 매핑과 checker 비활성 상태를 보존한다.

## 단층 다구역 담당자 보완

한 계정에 여러 구역을 명시적으로 배정할 수 있도록 등록 구성·KDS 조회·서빙 권한·알림을 연결했다. 두 구역/한 계정의 두 번째 구역 서빙·푸시·주제 구독과 외부 구역 거부 SQL을 검증했다. 구형 단일 층 속성과 전가복 매핑을 유지한다. 신규 트레이는 설정된 구역 목록을 받으며, 단층을 `1F`로 표시해도 임의의 `2F` 화면을 추가하지 않는다. 포장 전용의 명시적 빈 구역도 구형 설정 미확인 상태와 구분해 가상의 층을 표시하지 않는다. 두 매장의 기존 workflow 원천 JSON을 migration 전후 비교하여 동일함을 확인했다.

## 데이터 접근 및 실측

품목별 원격 호출 대신 집합 SQL/한정된 페이지를 사용한다. 준비 상태는 최대 100매장 일괄 RPC, 설정 품목 100행, 수요·규격 검색·로트/실사 50행 키셋 페이지다. 영수증 내역은 기존 100영수증 페이지를 사용하고 신고 배치 목록은 20개·생성시각+ID 커서로 읽으며 원천 상세 본문을 목록에 싣지 않는다. 같은 법인 내 매장별 Excel 집계는 원천을 한 번 순회한다. 폐점 claims 갱신과 추천 거래처 조회는 집합 연산으로 바꿨다.

로컬 PostgreSQL에서 100매장×2,000품목(총 200,000개)을 넣고 10회 측정했다. `test/sql/store_lifecycle_scale_test.sql`, 로그 `/tmp/globos-lifecycle-scale.log`.

| 경로 | p50 | p95 | 응답 최대 | 반환 행 |
|---|---:|---:|---:|---:|
| 100매장 구매 준비 일괄 조회 | 145.19 ms | 153.69 ms | 45,100 bytes | 100 |
| 한 매장 수요 50/2,000품목 | 3.14 ms | 6.59 ms | 49,992 bytes | 50 |
| 2,000품목 매장의 빈 로트 목록 | 0.71 ms | 1.02 ms | 89 bytes | 0 |

수요 페이지 선택의 실제 실행계획은 index scan, 실행 0.040ms, shared hit 54였다. 이는 승인 자료가 미완성인 합성 카탈로그·warm cache·단일 로컬 DB 조건이다. 실제 네트워크/다수 동시 사용자, 가득 찬 로트·승인 데이터의 최악 조건 p95를 뜻하지 않는다. 로트 경합과 등록 경합은 별도의 위 동시성 테스트로 검증했다.

Excel 실측은 5,690영수증/10,340행, 약 3,852ms, 파일 약 3.05MB, 프로세스 peak RSS 약 1.328GB(같은 기준선 약 1.218GB, 약 9% 증가)였다. 최종 전체 검사에서는 같은 5,690영수증/10,340행이 5,212ms·3,056,749bytes·peak RSS 1,233,551,360bytes로 통과했다. 동시 테스트 실행과 프로세스 상태가 달라 단독 기준선과 직접 p95 비교하지 않는다. 서버 신고 배치의 10,000영수증 상한 전체를 Excel 메모리 시험한 것은 아니다. 이보다 큰 파일의 무제한 일괄 생성이나 메모리 안전을 보장하지 않는다.

설정 상한은 8주방/16구역, 직원 200명, 출력 목적지 20개/endpoint 100개, 활성 재료·구매 품목 각 2,000개, 메뉴 4,000개/레시피 연결 20,000개다. 기준을 넘으면 누락된 일부 자료로 개점 승인하지 않고 명시 오류를 반환한다. Auth 발급은 기존 제한·동시성 정책을 유지한다.

## 운영 적용 시 확인할 항목

1. 정확한 배포 SHA의 필수 CI와 프로젝트 배포 절차를 거친 후 두 매장의 현재 설정/계정/기존 주문·매출·구매 잔액을 비교한다. 신규 준비/품질/로트 기준은 기존 매장에 일괄 강제하지 않고 실제 승인·실사 후 매장별로 적용한다.
2. 실제 프린터·주방·홀 장치에서 단층/다구역 알림, 부분 인계, 오프라인 재전송과 현재 장치 인수를 확인한다. 기존 두 매장의 저장 층/표시 층·checker 정책은 그대로 검증한다.
3. 실제 Office 매장 ID/법인 계약과 청구·credit·지급 자료, 공급업체 문서 수신, MISA 외부 신고 접수는 담당 시스템의 실제 증거로 확인한다. 로컬 fixture 성공을 외부 완료로 표시하지 않는다.
4. 장애 시 새 접수를 중지하고 이미 받은 주문·입고·로트/신고 배치는 해당 버전으로 마무리한다. 거래가 생성된 뒤 새 원장을 삭제하거나 구형 화면으로 무조건 되돌리지 않는다.

새 주방별 인쇄, 세트 구성품별 독립 일반 옵션, 별도 재조리 소모, 중앙창고·매장 간 이동, 반제품 제조 원장은 승인 계획의 후속 범위로 남아 있으며 이번 완료 범위에 포함하지 않는다.

검사 종료 후 작업용 `pos-lifecycle-development-20261022` 컨테이너를 제거했다. 기존 POS/Messenger 등 사용자의 로컬 컨테이너는 유지했다. 커밋·push·운영 migration 적용·배포는 수행하지 않았다.
