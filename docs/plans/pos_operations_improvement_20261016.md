최신 사용자 요청은 전체 개선 후 안전한 운영 배포다. 앞선 현금 입금액 작업의 배포 금지 지시는 이번 요청으로 해제됐으며, 그 수정도 이번 릴리스에 포함한다. 기존 작업 폴더의 미커밋 변경은 보존하고 최신 origin/main 기반의 별도 작업 공간에서 배포 변경을 준비한다.

## 개선 범위와 완료 기준

1. 고객·Cashier 채팅 전송 버튼: 사용 가능한 버튼의 아이콘은 흰색으로 표시한다. 전송 중과 실제 비활성 상태는 구분하며 중복 전송을 방지한다.
2. 고객 메뉴 검색: 현재 로딩한 해당 매장 메뉴에서 한국어·베트남어·영어 이름을 검색한다. 검색·카테고리·장바구니를 함께 사용할 수 있어야 한다. 검색마다 원격 조회를 만들지 않는다. 화면 복귀/재로딩 때 매장별 세션·진행 주문·작성 중 장바구니를 복원하고 만료·완료·접근 불가 상태는 구분한다. 고객의 닫기 버튼이나 운영체제의 브라우저 종료 자체를 막는다고 보장하지 않는다.
3. 부족 결제: 52,920동 중 5,292동 수취 사례에서 정확한 잔액 47,628동의 결제 안내와 QR을 제공한다. 재조회·부분 추가 수취 뒤에는 최신 잔액을 반영하고 완료·취소·오래된 요청의 QR은 결제 대상으로 사용하지 않는다. 실제 입금 검증과 기존 중복 결제 방지 계약을 유지한다.
4. 채팅 이미지: 한 대화에 여러 파일을 차례로 전송할 수 있어야 한다. 성공한 파일의 재업로드와 새 파일 전송을 구분하고, 새 파일 선택 취소·네트워크 실패·업로드 후 확인 응답 유실·대화 전환을 시험한다. 이미지/PDF 제한과 매장·대화 접근 범위는 유지한다.
5. 입고·검수 전용 계정: 로그인 직후 입고 화면을 표시하고 구매 요청 화면과 구매 동작을 해당 역할에서 숨긴다. 전용 화면 명칭을 원재료 입고 관리로 바꾸고 입고 대기/입고 완료를 구분한다. 입고 품목에는 현지화 이름, 원재료 코드, 발주·누적·남은 수량, 현재 재고, 수량 입력과 비고를 명확히 표시한다. 수량 차이의 부동소수점 잔여 자릿수를 제거한다. 전용 화면에서 승인 발주서 카드와 명세서 번호 입력을 제거하되 기존 문서·기록은 보존한다. 명세서 날짜·검수자·증빙 및 원자적 재고 반영 계약은 유지한다.
6. 매출·일일 마감: 입금 예정액은 장부 현금 − 환불 − 현금 지급 + 현금 회수로 계산하고 1동까지 표시한다. 실사 현금 − 시재 및 과부족을 별도 보존한다. 요약·미리보기·이력·합계에 동일한 계산을 반영한다.

## QR 동작

사용자의 후속 설명에 따라 QR을 스캔하면 은행 앱에 수취 계좌·정확한 금액·각 QR의 식별번호가 자동 입력되도록 한다. 고객이 금액을 별도로 입력할 필요가 없어야 한다. 부족액을 화면과 VietQR에 동일하게 반영하며, 입금 확인은 기존 Cashier 절차를 유지한다.

## 데이터 접근 및 성능

- 메뉴 검색은 기존 매장 메뉴 스냅샷에서 처리하며 입력당 추가 RPC는 0회다. 검색 대상은 해당 매장으로 한정한다.
- 상태 갱신은 기존 일괄 상세 응답을 사용한다. QR이나 첨부 목록을 위해 메시지별·품목별 조회를 추가하지 않는다.
- 업로드는 한 대화에서 한 번에 1건씩 처리하며 기존 크기 제한을 유지한다. 동일 시도는 같은 파일 경로/멱등 키로 재시도하고 새 전송은 새 식별자를 사용한다.
- 입고 목록은 기존 페이지 조회와 일괄 상세 응답을 이용한다. 현재 재고가 응답에 없으면 품목별 조회를 추가하지 않고 일괄 제공 경로를 검토한다.
- 기존 백그라운드 조회 제한·세션 변경 응답 폐기·테넌트 접근 경계를 유지한다. 모의 RPC 호출 수와 응답/렌더 측정을 운영 측정과 구분해 기록한다.

배포 절차나 실제 자격 증명 등 외부 조건이 충족되지 않으면 우회하지 않으며, 완료된 변경과 구체적인 차단 사유를 남긴다. 사용자의 실거래 메시지 전송이나 판매·입고·결제 기록 생성을 배포 검증용으로 임의 실행하지 않는다.

## 구현 확인 기록

- 정확한 47,628동 QR을 실제 렌더한 이미지와 계좌·금액·참조번호를 입력한 VietQR의 렌더 결과를 비교했다. 추가 입금 카드에 QR을 바로 표시하며 검토 중·완료·취소 상태의 중복 송금을 억제하는 기존 UI 계약을 유지한다.
- 검색 입력에 따른 추가 서버 조회 0회, 매장별 장바구니 재진입 복원, 새 파일 두 번 전송 및 전송 후 갱신 실패, 입고 전용 화면 진입과 구매 UI 숨김을 검증했다.
- 전체 Flutter 테스트 2,249건이 통과했다. 기존 조건부 제외 98건은 통과 수에 포함하지 않는다. 정적 분석은 fatal-info 설정으로 통과했다.
- 운영 Supabase/Vercel 프로젝트 연결과 운영 계정 준비 상태는 읽기 검사로 확인했다. 이 기록만으로 DB 마이그레이션 적용 또는 운영 배포 성공을 의미하지 않는다.
- SQL 통합·성능 검사, 필수 로컬 검증과 배포 결과는 각 실행 로그 및 최종 릴리스 기록에 남긴다. 로컬 DB 측정은 네트워크와 운영 지연을 포함하지 않는다.

변경 마이그레이션은 기존 권한·입금 원장·원자적 결제 함수를 보존한 래퍼다. 수취 확인 1회로 부족액 안내를 만들고 동일 증빙 재시도는 안내를 중복 생성하지 않는다. 입고 상세의 현재 재고는 선택한 PO의 기존 품목에 단일 JOIN으로 붙이며 행별 RPC를 추가하지 않는다. 배포 전 preflight와 배포 후 verify는 구조·권한만 읽고 실거래를 만들지 않는다.

되돌리기가 필요한 경우 이전 검증된 프런트엔드로 복구할 수 있다. DB의 추가 응답 필드는 기존 클라이언트와 호환되며, 이미 수취한 입금·생성된 안내·재고를 삭제하는 파괴적 롤백은 실행하지 않는다.
