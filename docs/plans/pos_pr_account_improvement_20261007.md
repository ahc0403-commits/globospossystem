후속 “개선 진행해” 요청에 따라 소스와 격리 로컬 DB 검증을 진행했다. 최신 구현·검증·미적용 항목은 [구현 결과](/Users/andreahn/globos_pos_system/docs/implementation/pos_pr_account_implementation_20261007.md)를 따른다.

- [10월 5일 전체 구매 개선 계획](/Users/andreahn/globos_pos_system/docs/plans/pos_procurement_process_improvement_20261005.md)과 [구현 결과](/Users/andreahn/globos_pos_system/docs/implementation/pos_procurement_process_implementation_20261005.md)는 배경 자료다. 이번 요구의 직접 근거는 지정된 PPTX다.

## 5. 화면 구성안

PR 역할로 진입하면 **구매요청 관리 → 구매내역**을 기본 동선으로 한다. 한 화면의 구매요청 목록·선택 상세에서 작성, 수정, 제출, PDF 확인을 수행한다. 권한이 있는 수령 담당자는 입고 영역에도 접근할 수 있도록 유지한다.

```text
구매요청 관리
  구매요청·승인  |  입고·검증(권한이 있는 경우)

구매내역                                      [+ 구매요청 작성]
  구매 유형 [전체 ▼]   PR 검색 [번호·사유]   기간 [최근 1개월 ▼]
  구매요청 현황
  [초안·승인대기]  [승인완료·발주진행]  [취소]

  PR-20261007-예시   · 매장 검토 대기
  요청일 2026-10-07  / 필요일 2026-10-09
  원재료 · 3개 품목 · 요청 사유

  선택한 요청 상세
  품목 · 수량 · 단위 · 요청 당시 재고 · 예상 단가
  [수정] [삭제] [승인 요청] — 현재 상태·권한에 따라 표시
  [PR PDF] [승인 이력] [연결 PO]
```

- 초안·승인대기: draft, returned, submitted, brand_review, office_review, senior_review. 반려는 명시 표시한다.
- 승인완료·발주진행: approved, allocated. 연결 PO의 발송·입고 상태는 상세에서 별도로 보여준다.
- 취소: cancelled. 초안 삭제도 이력 확인이 가능하도록 여기에서 발견할 수 있다.
- 상태별 건수는 서버에서 필터 범위 전체를 집계한다. 현재 페이지의 20건을 전체 건수로 표시하지 않는다.
- 기존 v1 PO는 별도의 ‘기존 발주’ 진입에서 실제 번호·승인·입고 이력을 유지한다. 과거 PO 번호를 PR로 덮어쓰거나, PO를 PR인 것처럼 표시하는 것으로 R06을 해결하지 않는다.
- ‘구매 운영지표·담당자’ 제거는 PR 계정 화면에 적용한다. 관리자·구매팀의 관리 기능 삭제 요구로 확대하지 않는다.
- ‘구매요청 현황’은 요청 상태·건수·목록을 보여준다. 기존 재고·수요 분석 데이터에 제목만 바꾸어 붙이지 않는다.

## 6. 저장·수정·삭제와 목록 계약

### 6.1 생성과 저장 후 표시

1. 생성 성공 응답에서 실제 PR ID·번호·상태·row_version을 받는다.
2. 요청 페이지와 상세 이력 커서를 초기화한다. 새 PR의 유형·작성일이 현재 필터와 다르면 생성한 요청을 볼 수 있는 필터로 전환하고 변경 이유를 표시한다.
3. 서버에서 첫 페이지와 생성 PR 상세를 조회하고 해당 PR을 선택한다. 정상 기본 정렬에서는 첫 행에 표시한다.
4. ‘PR 번호 … 저장 완료·초안’처럼 결과 상태를 알려준다. **저장**은 초안 생성, **승인 요청**은 submitted로 제출하는 별도 동작으로 유지한다. 첨부의 “PR 완료”만으로 자동 제출 요구를 추정하지 않는다.
5. 페이지를 닫거나 다시 로그인해도 같은 문서가 있어야 한다. 서버 저장 실패에는 완료 메시지를 표시하지 않는다. 명령 성공 후 조회만 실패했다면 ‘저장은 완료됐으나 목록 갱신 필요’로 구분한다.

동일 요청의 재시도는 현재 idempotency_key를 재사용한다. 화면 재조회나 앱 재진입 때문에 같은 PR을 새로 생성하지 않는다.

### 6.2 수정·삭제

- 초안/승인대기라는 묶음 안에 있어도 모든 문서가 수정 가능한 것은 아니다. 본인 draft/returned에만 수정·삭제를 제공하고, submitted 이후에는 기존 반려·승인 통제를 따른다.
- 수정은 PR의 `save_request`로 처리한다. 기존 PO용 `save_inventory_purchase_order_draft`를 새 PR에 사용하지 않는다. 품목·수량·단위·필요일·사유·비고 변경이 서버에 반영되어야 한다.
- 삭제는 기존 계약과 같이 감사 이력을 보존하는 상태 처리로 설계한다. PR은 `cancel_request`, 기존 PO는 현재 초안 삭제 RPC를 사용한다. 사용자에게는 ‘초안 삭제’로 안내하되, 활성 목록에서 제외되고 취소 이력에는 남는다는 점을 삭제 확인 창에 설명한다.
- 삭제 성공 후 선택 상세를 비우고, 다음 유효한 요청을 선택하며, 목록·건수를 갱신한다. 새로고침·재접속 후에도 활성 목록에서 제외되어야 한다.
- 취소 사유와 삭제 이벤트를 기록한다. 필수 사유를 빈 값으로 보내 실패하는 UI를 만들지 않는다.
- 버튼과 서버 판정 모두 현재 allowed_actions·소유 계정·매장 범위·row_version을 사용한다. 화면에 버튼이 보이는 것만으로 권한을 판단하지 않는다.
- stale version, 권한 거절, 통신 실패를 구분해 안내한다. 서버에서 거절한 변경을 화면에서 성공 처리하지 않는다. 실패 시 입력은 유지하고 필요한 재조회·재시도를 제공한다.

### 6.3 정렬·검색·기간·유형

- 기본 정렬: `(created_at DESC, id DESC)`. 페이지 커서도 `(created_at, id)`로 동시에 바꾸고 해당 매장·정렬 인덱스를 검토한다. updated_at 커서를 그대로 둔 채 ORDER BY만 바꾸지 않는다.
- 필터 변경 시 첫 페이지로 이동한다. ‘처음으로’ 버튼을 없애도 이전/다음 페이지 이동과 필터 초기화 동선은 유지한다.
- 기간 기준은 **PR 작성일**, 시간대는 Asia/Ho_Chi_Minh이다. 예를 들어 2026-10-07의 최근 1개월은 2026-09-07~2026-10-07로 정의한다. 시작일 포함, 종료일 다음 날 00:00 미만으로 서버에서 조회한다.
- PR 검색은 번호·사유를 기본 범위로 한다. ‘품목 검색’ 필터를 유형으로 바꾸더라도 작성 창의 품목 검색·추가 기능은 유지한다.
- 유형은 원재료/raw_material, 도구·비품/tools, 음료/beverage, 기타/other를 신규 선택값으로 한다. DB 제약·저장 검증·조회 필터·문서·KO/EN/VI를 함께 보강한다.
- 기존 stationery 기록은 삭제·일괄 재분류하지 않는다. 제안: 기존 사무용품은 도구·비품 필터에서 함께 조회하고 원래 저장값은 유지한다. 유형 변경을 명시 선택했을 때만 새 값을 저장한다.
- 음료라는 구매 유형이 재고/비재고/자산 분류나 세율을 결정하지 않는다. 기존 입고 분류·가격·VAT 원본 계약은 별도로 유지한다.
- 새 유형을 받는 Office 연계의 허용값·번역·표시도 영향 검토 대상이다. 이번 작업에서는 Office 코드를 검사하거나 변경하지 않았다.

### 6.4 날짜와 재고 표시

- 요청일 = 원래 PR created_at의 매장 현지 날짜. 수정·제출 시 요청일이 바뀌지 않는다.
- 필요일 = requested_delivery_date. 기존 필드 값을 요청일이라고 이름만 바꾸지 않는다.
- 2장의 요청일 변경과 4장의 요청일/필요일 요구를 두 개 날짜로 함께 충족한다. 미확정 해석은 구현 전에 양식·화면 리뷰에서 확인한다.
- 일반 목록은 `YYYY-MM-DD`, 승인 이력은 `YYYY-MM-DD HH:mm`로 표시한다. UTC ISO 문자열·마이크로초·`+00:00`은 기본 화면에 표시하지 않는다.
- 품목의 요청 당시 재고 수량은 유지한다. 재고 갱신 시각은 기본 상세에서 숨기고 원본 데이터는 남긴다. 데이터가 오래됐거나 음수일 때는 별도 확인 안내를 제공하는 것을 추가 제안한다. 수량을 0으로 바꾸거나 정상 재고처럼 보이게 하지 않는다.

## 7. PR 작성 창 단순화와 필요한 데이터 보강

필수 입력은 구매 유형, 사유, 필요일, 품목·수량·단위다. 선택 입력은 요청 비고·품목 비고다. 현재고·예상 단가·예상 합계는 조회 전용으로 표시한다.

**권장 공급업체를 제거하면서 예상 단가를 유지해야 한다.** 현재 화면과 SQL은 선택한 업체 ID로 가격을 찾기 때문에 UI 삭제만으로는 충족되지 않는다.

- 서버가 같은 매장/브랜드 범위의 활성 품목·유효 공급업체 가격에서 기준 예상가격을 선택한다. 기존 preferred 기준을 사용하되 동순위 후보가 여러 개라면 임의 업체를 최종 선정하지 않고 ‘견적 필요’로 표시한다.
- 기준가격의 출처·단위·환산·VAT·기준시각을 PR 라인 스냅샷에 고정한다. 기준가격 선택은 최종 PO 공급업체 확정과 구분한다.
- 클라이언트 표시와 서버 저장은 동일한 기준가격·환산값으로 계산한다. 여러 품목의 가격·재고 조회는 한 번에 묶는다.
- 가격이 없으면 0원 확정 대신 ‘견적 필요’로 표시한다. 요청 초안은 저장할 수 있도록 하고, 다음 승인에 필요한 가격이 없을 때는 현재 견적 보강·승인 조건을 명확히 안내한다. 승인 조건을 제거하여 통과시키지 않는다.
- 기존 PR 수정 시 숨긴 preferred_supplier_id·추정 스냅샷을 무조건 null로 덮지 않는다. 품목·수량 변경에 필요한 스냅샷 재생성은 현재 revision/재승인 계약에 맞춘다.

**구매채널은 입력 화면에서 제거하되 업무 기록을 보존한다.** 신규 요청은 서버 기본값 ordinary를 사용한다. 기존 shopee 요청 수정은 기존 값을 유지한다. 구매팀이 채널을 나중에 지정할 필요가 있는 경우 담당 단계·서버 명령·재승인 영향을 별도로 설계하고, 선결제·상환 통제를 누락하지 않는다. 숨긴 필드가 기존 shopee를 ordinary로 바꾸는 것은 허용하지 않는다.

|---|---|
| 제목 | 구매요청서 / Purchase Request, PR 번호·현재 상태 |

| 요청 내용 | 구매 사유·전체 비고. 기본 양식에서 구매채널과 미발행 PO 정보는 제외 |
| 품목표 | 번호, 품목·규격, 수량, 단위, 요청 당시 재고, 예상 단가, 금액, 비고. 규격은 품목명 아래에 표시해 좁은 독립 열을 줄임 |

| 하단 | 출력일시, 페이지 번호, 검토용/실제 문서 구분. 추가 제안: 문서 revision 표기 |

서식 기준:

- A4 세로, 고정 여백과 명시적인 열 폭, 숫자 오른쪽 정렬. 긴 품목·규격·비고는 문자열을 자르지 않고 행 높이를 늘린다.
- 금액에는 천 단위 쉼표를 사용한다. 정수 금액은 불필요한 `.00`을 생략하고, 소수가 있는 원본 금액은 정해진 금액 정밀도를 유지한다. 표시 형식 변경으로 합계·원본 금액을 바꾸지 않는다.
- 수량은 필요한 소수 자릿수만 표시하고 단위는 한 곳에 일관되게 표시한다. 단가 기준 단위가 요청 단위와 다르면 기준 단위를 작은 보조 문구로 표시한다.
- 미등록 가격은 ‘견적 필요’, 불완전 합계는 ‘산출 대기’로 구분한다. 가격이 없는 품목을 0원으로 합산해 완전한 총액처럼 출력하지 않는다.
- 승인 전 문서는 ‘초안/승인 대기’를 표시한다. 실제 승인자의 이름·역할·일시만 출력하며 서명·승인을 만들어 넣지 않는다.
- 여러 페이지에서는 제목·PR 번호·표 머리글을 반복하고 페이지 번호를 표시한다. 합계와 승인표는 읽을 수 있는 영역에 함께 둔다.
- 한글·베트남어·영어 폰트와 긴 베트남어 품목/단위가 깨지지 않아야 한다.

내부 PR에는 예상금액을 표시한다. 공급업체용 PO의 무가격 출력·allowlist·private Storage·source_hash/file_hash 계약은 유지한다. 새 서식으로 재생성된 파일은 기존 파일을 덮어쓰지 않고 새 파일 해시로 보존한다. 요청자 표시명 보강이 필요하면 현재 인증/역할 원본에서 조회하며 첨부의 이름을 하드코딩하지 않는다.

구현 단계에서는 해당 구매 Flutter·SQL·PDF 검사를 실행하고 `flutter analyze`, `scripts/check_repo.sh` 및 필요한 저장소 검사를 완료한다. PDF는 파일 생성 성공뿐 아니라 렌더링·실제 출력 폭까지 확인한다. 관련 없는 기능의 반복 검사를 늘리는 대신 변경된 업무 계약·권한·데이터 보존을 검증한다.

운영 반영은 정확한 pushed head SHA의 필수 CI 성공, 기존 배포 스크립트, DB 적용 후 읽기 검증, 역할별 UAT로 확인한다. 실제 앱 배포와 현장 확인이 끝나기 전에는 소스 구현을 운영 완료라고 보고하지 않는다.

## 11. 확정이 필요한 해석과 이번 작업 결과

다음은 구현 리뷰에서 확인할 항목이다. 계획 수립을 중단할 필요는 없지만 새로운 운영 정책으로 자동 적용하지 않는다.

1. 요청일은 작성일, 필요일은 희망 입고일로 표시하는 해석.
2. 삭제는 활성 목록에서 제외하되 취소 이력을 보존하는 방식. submitted 이후 요청자의 회수 기능은 첨부에 없으며 별도 요구로 다룬다.
3. 기존 사무용품을 도구·비품 필터에 포함하는 표시 규칙과 음료 유형의 실제 품목 구성.
4. 7장의 구체 양식이 없으므로 제안 PDF의 열 구성·승인표·요청자 표시를 최종 출력 기준으로 사용할지 여부.

이번 결과물은 개선 계획과 예시 양식이다. 원본 PPTX·기존 사용자 변경은 보존했다. 앱 테스트·운영 로그인·DB 변경·배포는 실행하지 않았다. 예시 PDF는 별도로 생성·텍스트 확인·렌더링 확인하여 검토 가능한 산출물로 제공한다.
