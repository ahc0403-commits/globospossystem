## 1. 확정할 업무 기준과 범위

**배달비 포함 결제를 선택한 고객은 음식 대금과 안내된 배달비를 최초에 한 번 결제하면 끝난다.** 조리 완료 후 실제 기사 비용이 더 나오면 매장이 부담하고 캐셔가 기록한다. 실제 기사 비용이 적게 나와도 고객에게 확정한 배송비는 유지하고 차액을 기록한다. 실제 비용 변동을 이유로 고객에게 추가 청구·자동 환불을 만들지 않는다. 취소·배송 실패·픽업 전환의 환불은 별도 업무로 유지한다.

앞선 고객 선택 요청도 반영한다. 주문 시 매장이 허용하는 `배달비 포함 한 번에 결제` / `기사님께 배달비 직접 결제` 중 고객이 희망 방식을 선택할 수 있다. 안내 기본 흐름은 배달비 포함 결제지만 선택/기본값을 고객 동의로 처리하지 않는다. 캐셔는 최종 확정 전에 지급 상대방·매장 결제 예정액·안내 배달비·실비 변동 부담 조건을 고객과 협의하고 확인된 결과를 기록한다. 직접 지급에서는 음식 대금만 매장에 결제하고 배달비는 수령 시 기사에게 실제 요금으로 지급한다. 이 선택에는 매장 차액 부담·기사 현금 지급을 적용하지 않는다. 실제 배차 상품이 수령자 지급을 지원하는지 확인한 매장만 직접 지급 옵션을 제공한다.

이번 필수 범위는 고객 선택과 최종 견적, 1회 결제 유지, 조리 완료 후 기사 호출, 실제 비용·매장 부담액·현금 지급 기록, 마감/보고서, 양방향 사진·파일 전송 정상화다. 새 자동 배차 API, 임의 요금표, 고객 배송비 재수금 기능 확대는 도입하지 않는다. 배달비 차액 5,000/10,000 VND 기록에 새 관리자 승인 절차를 붙이지 않고 기존 캐셔/매장 권한으로 처리한다.

## 3. 목표 주문 흐름

1. **주문과 희망 선택:** 고객이 배송지·메뉴·요청사항을 입력하고 배달비 지급 희망 방식을 선택할 수 있다. 아직 고객 합의나 최종 견적을 생성하지 않는다.
2. **캐셔 협의 제안:** 지급 방식·고객 안내 배송비·음식/옵션/기존 세금·수수료를 반영한 매장 결제 예정액과 부담 조건을 안내한다. 새 정액 구역표 없이 기존 캐셔 배송비 입력을 우선 사용한다. 협의 중에는 결제 QR·송금 요청을 만들지 않는다.
3. **고객 확인:** 고객이 제안한 조건을 확인하거나 문의한다. 전화/현장에서 실제 동의했다면 캐셔가 해당 채널·시각·합의 내용·현재 제안 연결을 기록한다. 고객의 직접 확인과 직원의 협의 기록을 구분하고 무응답은 미합의로 유지한다.
4. **최종 견적:** 유효한 현재 조건의 합의와 일반 요청사항 확정을 서버에서 검증한 뒤 캐셔가 견적을 확정한다. 방식/금액/배송 조건이 변경되면 확정 전 재협의한다. 함께 결제는 “이 총액으로 결제가 완료되며 기사 비용 변동은 매장이 부담”이라고 표시한다.
5. **고객 1회 결제:** 고객이 확정 총액을 송금하고 기존 증빙·실제 입금 대조 절차로 확인한다. 입금 확인은 정상 주문 기준 한 번이다. 의도한 금액보다 부족/초과 송금한 경우의 기존 처리까지 없애는 의미는 아니다.
6. **조리:** 원 주문의 기존 원자적 결제와 주방 생성 흐름을 사용한다. 실제 기사 비용은 아직 미정일 수 있으며 이것이 조리·포장을 막지 않는다.
7. **기사 호출:** 모든 대상 음식의 `cooking_complete` 후 캐셔의 다음 작업에 기사 호출을 표시한다. 직원이 기존 Grab/Be 등에서 호출한다. 조리 완료와 포장 완료인 `ready`, 기사 인계를 구분한다.
8. **실제 비용 기록:** 캐셔가 실제 비용·업체·예약/거래 참조·근거를 저장한다. 서버가 고객에게 받은 배송비와의 차액을 계산하고 매장 부담액을 표시한다. 이 단계에서는 현금 지급을 완료한 것으로 기록하지 않는다.
9. **현금 지급과 인계:** 포장 완료 후 매장이 실제 기사 비용을 현금으로 지급하고 지급 여부를 확인한다. 동일 주문의 비용 근거를 재사용해 같은 사진을 여러 번 올리지 않게 한다. 지급 기록과 기사 인계는 기존 원자적 계약으로 처리한다.
10. **완료와 마감:** 고객에게는 기존 결제 완료와 배송 진행 상태를 유지한다. 매장은 실비·차액·현금 지급을 주문별/기간별로 확인한다. 실제 비용과 고객 배송비가 다르다는 이유로 재협의·추가 청구하거나 인계를 막지 않는다.

직접 지급 선택에서는 2~5단계의 매장 결제액에 배송비를 넣지 않고, 8~9단계의 매장 부담·현금 지급을 만들지 않는다. 캐셔/포장/기사 전달 정보에 지급자를 일관되게 표시해 이중 수금을 막는다.

## 4. 금액·원장·마감 설계

일반적으로 배송이 완료되고 별도 환불이 없는 주문의 금액 정의는 다음과 같다. VND는 기존 정수 검증과 금액 formatter를 사용한다.

| 금액 | 정의/기록 방식 |
|---|---|
| 고객 확정 배송비 Q | 최초 확정 견적의 배송비. 실제 기사 요금 변경으로 덮어쓰지 않는다. 결제 전 견적 값과 실제 결제로 수금된 값은 구분한다. |
| 실제 기사 비용 C | 주문별 비용 확인 이력의 최신 유효 총비용. 재배차 시 최종 배차 비용과 실제 발생한 취소 비용을 포함하며, 과거 견적 변경 이력을 모두 더하지 않는다. 미확정은 NULL, 실제 무료는 0으로 구분한다. 입력 직원·시간·업체·참조·근거·작업 ID를 기록한다. |
| 배송비 차액 | `Q - C`. 양수는 고객 배송비가 실제 비용보다 많고, 음수는 매장 부담이 생긴 경우다. |
| 매장 부담액 | `max(C - Q, 0)`. 서버에서 계산한다. 고객 미수금이나 추가 매출로 기록하지 않는다. |
| 기사 실제 지급액 | 현금 지급 원장의 지급 합계. 실비 확인만으로 자동 지급 처리하지 않는다. 지급 직원·시간·참조·근거·작업 ID를 기록한다. |
| 기사 지급 회수 | 기존 지급에 연결한 회수 이력. 현금/은행 회수를 구분한다. 비용 자체의 정정과 돈의 회수는 별도다. |

예: 음식 주문 대금 200,000 + 고객 확정 배송비 30,000 = 고객 결제 230,000 VND. 실제 기사 비용 40,000이면 매장 부담은 10,000이고 기사에게 지급할 현금은 40,000이다. 실제 비용이 35,000이면 부담은 5,000, 25,000이면 부담은 0이고 배송비 차액은 +5,000이다. 세 경우 모두 고객 결제는 230,000으로 끝난다.

### 주문별 정책과 호환성

- 지급 주체와 비용 정산 정책을 분리한다. 정책 값은 `고객 확정 배송비`, `기존 실비 정산`, `고객 기사 직접 지급`을 구분할 수 있도록 설계한다. `store_prepaid` 하나만으로 새 계약과 과거 계약을 판별하지 않는다.
- 주문 요청·견적·결제 시 정책을 일관되게 연결하고 확정 견적에 snapshot을 남긴다. 견적 확정 후 고객 청구액·정책·지급 주체는 임의 변경하지 않는다.
- 최종 견적에는 현재 배달비 합의 ID·버전·확인 채널과 조건 snapshot을 연결한다. 일반 요청사항의 직원 자동 확정으로 배달비 필수 합의를 대신할 수 없다. 이미 확정된 이전 주문은 보존하며 아직 최종 견적 없는 활성화 대상 배송 주문에는 협의를 요구한다.
- 기존 주문을 새로운 정책으로 자동 전환하지 않는다. 새 정책을 과거 금융 행 전체의 기본값으로 채우는 migration을 피한다. 기존 진행 주문의 실제 청구/입금 상태를 먼저 대조하고 이전 계약을 보존한다.
- 신규 고객 확정 배송비 주문에 실비 차액 청구를 요청하는 구 API도 서버에서 거절한다. 버튼을 숨기는 것만으로 차단하지 않는다. 기존 배송비 추가 청구/입금/환불 이력은 삭제하지 않고 과거 계약에 따라 읽고 정산한다.
- 실제 비용 저장·support 응답·`refund_due`·인계 gate·픽업 환불·고객 접근 종료·개인정보 정리를 모두 정책별로 검토한다. 고정 배송비의 실비 감소가 환불 의무나 무기한 열린 주문 링크로 이어지지 않게 한다.
- `process_payment`의 원자적 결제, 원 결제 금액·VAT·영수증·비동기 MISA 계약을 유지한다. 매장 부담액을 가짜 결제나 추가 음식 주문으로 만들지 않는다.

### 직원 입력과 정정

캐셔 상세의 한 영역에서 `고객 배송비 / 실제 기사 비용 / 매장 부담 / 현금 지급 상태`를 함께 보여준다. 배달비 증빙을 채팅에서 먼저 찾아 올리고 다른 창에서 다시 선택해야 하는 흐름을 줄인다. 실제 비용 입력 창에서 기존 첨부 선택 또는 업로드 후 해당 메시지 ID를 바로 사용할 수 있게 한다.

실제 비용 저장과 실제 현금 지급은 구분하되 같은 화면에서 이어 처리한다. 필요한 기존 근거·실제 지급 확인은 유지한다. 매장 부담액은 자동 계산되므로 캐셔가 차액과 총비용을 별도로 입력하지 않는다. 중복 클릭/네트워크 재시도는 동일 `operation_id`로 기존 결과를 반환하고 상태 버전·행 잠금으로 동시 처리를 검증한다.

인계 전 비용이 다시 바뀌면 새 비용 확인 이력을 추가한다. 인계/지급 후에는 원 비용·지급을 덮어쓰지 않고 기존 관리자 정정/추가 지급/회수 계약을 사용한다. 지급 정정이 비용 변경인지 단순 과지급 회수인지 구분하며 보고서가 두 금액을 혼동하지 않게 한다. 마감된 영업일의 현금 원장을 소급 변경하지 않는 현재 계약을 유지한다.

### 마감과 보고서

금고 차감은 **기사에게 실제 지급한 전체 현금**을 기준으로 한다. 위 예에서 40,000을 차감하며 매장 부담액 10,000을 다시 차감하지 않는다. 비용 확인만 저장한 주문은 금고 차감이 없다. 고객이 은행으로 낸 배송비는 금고 현금을 늘리지 않는다.

기존 마감의 현금 기대액 계약을 유지한다: 준비금 + 현금 매출 - 기사 현금 지급 + 기사 현금 회수 - 고객 현금 환불. 은행 회수는 금고 현금에 더하지 않는다. 다른 기존 마감 구성요소도 유지한다.

주문별/일별/기간별로 고객 배송비 수금, 실제 비용, 미확정/미지급 수, 매장 부담 합계, 비용이 더 적었던 차액 합계, 실제 현금 지급/회수를 표시한다. 부담 합계는 `sum(max(C-Q,0))`로 계산하며 비용 절감액과 상계한 순차액과 별도로 보여준다. 5,000 손실 주문과 5,000 절감 주문이 있어도 매장 부담 총액을 0으로 표시하지 않는다.

취소/픽업 환불과 기사 지급 회수는 별도 열로 표시한다. 원 고객 배송비, 실제 받은 금액, 고객 환불액, 기사 비용, 실제 지급/회수의 원장을 기준으로 순액을 계산한다. 정상 배송의 차액 공식을 취소 주문에 무조건 적용해 환불·회수를 이중 반영하지 않는다. 수금/원 주문은 기존 결제 영업일, 현금 지급/회수는 발생 영업일을 사용하고 양쪽의 날짜 차이를 보존한다. 미확정 비용을 0으로 넣어 절감액을 부풀리지 않는다.

## 5. 양방향 채팅 사진·파일 정상화

### 재현과 운영 대조

고객→매장, 매장→고객 각각에서 작은 JPEG/PNG와 PDF로 파일 선택 → 미리보기 → token 발급 → Storage 전송 → commit → 상대 화면 표시 → 열기를 재현한다. 실제 기기·브라우저와 파일 종류/크기, 정제된 오류 코드·HTTP 상태로 실패 지점을 확정한다.

운영 migration·Edge action·웹 빌드 버전, private `direct-order-chat` bucket 제한, 함수/Storage 인증·CORS를 대조한다. 현재 매장 전송 실패는 소스만으로 원인이 확정되지 않았다. 고객 사진 원문, 개인정보, 세션 비밀, signed URL과 토큰을 일반 로그에 남기지 않는다.

### 구현 계약

- 고객 일반 첨부 전용 action/RPC를 추가하고 기존 upload/commit 검증 구조를 공통으로 사용한다. 견적/청구 ID 없이 주문 소유권과 열린 채팅을 확인해 `message_type='attachment'`로 저장한다. 결제 전 상담·조리 중·배송 전과 환불 상담 등 현재 접근 가능한 열린 채팅에서 사용한다.
- 결제 증빙은 `payment_proof` 및 대상 견적/청구 연결을 유지한다. 일반 고객 사진을 최신 입금 증빙으로 사용하거나 결제 검토 상태를 바꾸지 않는다. 기존 고객 증빙을 일괄 일반 첨부로 변환하지 않는다.
- 고객 작성 영역에 사진·파일 버튼을 추가한다. 양쪽 모두 선택/미리보기/취소/전송 중/실패/재시도를 제공하고, 서버 commit 성공 후 발신자와 상대 화면을 갱신한다.
- 일반 첨부는 양쪽 JPG/JPEG/PNG/WebP/PDF, 파일당 5 MiB를 지원한다. 결제 증빙은 이미지로 제한한다. 실제 확장자·MIME·바이트와 기존 이미지 크기 제한을 검증한다. JPEG 확장자 정규화와 이미지 검증의 일관성도 확인한다.
- iPhone/Android 사진 선택, 실제 MIME과 큰 사진을 확인한다. HEIC 등 미지원 유형이면 분명한 안내를 제공한다. 실제 실패 원인이 해당 유형이면 변환 가능성과 검증 경계를 확인해 지원 결정을 한다. 파일 형식을 임의로 바꿔 성공처럼 표시하지 않는다.
- 같은 작업의 객체 경로와 ID를 재사용해 upload/commit 응답 유실을 복구한다. 메시지/파일 중복을 막고, 화면 갱신 실패는 업로드 재실행보다 상태 재조회로 복구한다. 전송 중 주문이 바뀌면 이전 파일을 새 주문에 붙이지 않는다.
- 이미지는 미리보기/확대, PDF는 파일명·크기·열기를 제공한다. private Storage와 주문별 접근 검증을 유지하고 URL 만료 시 다시 발급한다. 증빙 보존과 종료 후 파일 정리 계약을 구분한다.
- 사진 한 번을 실비 확인과 지급 근거로 함께 사용할 수 있게 하되, 해당 주문의 적절한 매장 첨부인지 서버에서 검증한다. 실제 지급 여부는 첨부 유무와 별도로 확인한다.

| 음식/전체 취소 | 기존 주문 결제 조정·수금 환불 계약으로 처리한다. 매장이 기사에게 지급한 돈의 회수는 별도다. |

예상 변경 경로는 `lib/features/direct_order/`의 모델·서비스·캐셔·고객·지원 패널·분석 화면, 기존 마감 provider/화면, `supabase/functions/direct-order-public/`, 신규 `supabase/migrations/`, 관련 `supabase/tests/`와 `test/`다. `direct_order_copy`/지원 문구와 KO/VI/EN 계약도 함께 갱신한다. API/상태/화면 설계 문서는 구현 시 최신 계약으로 맞추며 이번 계획만으로 이미 구현된 API라고 쓰지 않는다. 다른 프로젝트/Office 앱·Deliberry·Photo Objet 자동 수집을 변경하지 않는다.

필수 검증:

- 고객 포함 결제 230,000 / 고객 배송비 30,000 / 실비 35,000·40,000·25,000·0·NULL에서 원 결제 금액, 부담/차액, 현금 지급 확인.
- 실비 변동 전후에 `delivery` 추가 청구·고객 추가 QR·실비 감소 환불·추가 결제용 매출·주방/재고 중복이 생성되지 않음.
- 비용 저장 전에는 조리/포장 진행 가능, 비용 차이만으로 인계 차단 없음, 필요한 실제 비용/현금 지급 확인과 포장 완료 조건 유지.
- 고객 지급 방식 선택의 요청/견적/영수증/캐셔/기사 전달 일치, 결제 후 임의 변경 차단, 직접 지급 주문의 매장 비용 원장 없음.
- 배달비 미협의/고객 미확인·오래된 제안·구 RPC 우회는 최종 확정 불가. 실제 전화/현장 합의 기록과 고객 직접 확인의 구분, 확정 전 조건 변경 재협의, 협의 단계의 결제 QR/정식 견적/매출·주방 생성 없음. 상세 성공 조건은 필수 협의 계획을 적용한다.
- 차액 부담 10,000을 별도 금고 차감하지 않고 기사 지급 전체 40,000만 한 번 차감. 비용 확인만 저장할 때 차감 0. 현금·은행 회수, 수금/지급 날짜 차이와 마감된 날짜 정정 계약.
- 비용 손실/절감의 개별 합계, 최신 유효 비용 선택, 미확정 제외, 원장 JOIN으로 인한 합계 증폭 없음.
- 취소/픽업 전환/재배차 비용/환불/기사 지급 회수, 기존 진행 주문과 증빙·접근 종료·정리 계약.
- 고객↔매장 JPG/JPEG/PNG/WebP/PDF, 5 MiB 경계·위장 MIME·손상 파일, 일반 첨부가 결제 증빙으로 처리되지 않음.
- 파일 선택 취소·업로드/commit 유실·주문 전환·URL 만료·타 매장/타 고객 접근 차단, 화면 갱신 실패 복구.
- iPhone Safari / Android Chrome / 매장 실제 브라우저에서 파일 선택·미리보기·열기, 좁은 화면과 KO/VI/EN.
- 목록·보고서·첨부·환불 batch의 실제 호출 수, SQL/RPC 내부 실행계획과 동시 비용 저장·지급·인계 재시도.

검증 명령은 관련 Flutter 테스트, `deno test --config supabase/functions/direct-order-public/deno.json supabase/functions/direct-order-public/index_test.ts`, `bash test/direct_order_integrated_sql_test.sh`를 우선 확장하고, 구현 완료 후 `flutter analyze`, `flutter test`, `bash scripts/check_repo.sh`, 웹 release build를 실행한다. 필요한 정적 검사/format과 migration 적용 전후 `process_payment` 계약 동일성도 확인한다.

DB/API는 기존 클라이언트와 호환되게 준비한다. 신규 migration과 Edge를 먼저 반영하고 정책 지원이 확인된 클라이언트를 적용한다. 구 클라이언트가 새 주문의 고객 확정 배송비를 실비 후청구로 바꾸려 해도 서버가 차단해야 한다. 신규 정책 활성화는 서버와 UI가 준비된 뒤 수행한다. 배포는 정확한 pushed HEAD의 필수 GitHub Actions 성공 후 `scripts/deploy_pos_production.sh`를 사용한다. 로컬 부분 통과나 과거 검사로 release gate PASS를 대신하지 않는다.

운영에서 테스트 주문으로 포함 결제 1회, 실비 증가/감소, 기사 지급, 마감과 고객↔매장 첨부를 확인한 뒤 운영 검증 완료로 판단한다. 되돌릴 때 새 주문의 진입만 닫고 이미 결제한 고정 배송비 주문은 같은 정책으로 완료할 수 있게 한다. 기존 견적·수금·원장·첨부/증빙·감사 이력을 삭제하는 롤백은 사용하지 않는다.

## 9. 이번 재계획의 검증 상태

이번 턴에서는 지침·현재 소스·이전 계획을 읽고 계획 문서만 재작성했다. 기능 코드를 수정하거나 새 회귀 테스트, 운영 DB 변경, Edge/웹 배포를 실행하지 않았다.

같은 대화의 앞 조사에서 기존 Flutter 19개, 고객 Edge 25개, 삭제 가능한 PostgreSQL 통합 검사와 관련 목록 측정이 통과했다. 이는 **기존 계약**의 근거이며 이번 고객 확정 배송비 정책과 일반 첨부 개선이 구현되거나 검증됐다는 뜻은 아니다. 새 정책은 위의 추가 검증을 완료해야 한다.
