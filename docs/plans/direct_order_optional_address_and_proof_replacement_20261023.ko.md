## 1. 상세주소 오류의 원인

실제 흐름은 `선택 입력 화면 → submit_v3 → direct_order_public_submit_v3 → submit_v2 → 주소 테이블 INSERT`이다.

1. `_composeAddress()`는 배송 기본 주소·이름·전화번호를 검사하고 상세주소는 빈 문자열로 보낼 수 있다. 입력란에도 선택 항목으로 표시한다.
2. 2026-10-08 변경은 제출 함수의 상세주소 길이를 `0~300`으로 완화했다. 현재 운영 `submit_v2`에도 이 조건이 있다.
3. 테이블의 `direct_order_address_detail_valid`는 여전히 `length(btrim(detail_address)) BETWEEN 1 AND 300`이다. `''` 또는 공백은 INSERT에서 거부된다.
4. 알 수 없는 DB 제약 오류는 Edge에서 일반 오류로 정제되고, 고객 화면은 이를 “배달 주문 페이지를 불러올 수 없습니다”로 표시한다. 첨부 화면의 메시지와 부합한다.
5. 필수 입력 안내 `requiredFields`도 아직 상세주소를 필수로 안내한다.

읽기 전용 진단 결과: `empty_detail_rpc_accepts=true`, `empty_detail_table_accepts=false`, `whitespace_detail_table_accepts=false`. null로 우회해도 배달 주소의 `direct_order_address_location_mode_valid`가 상세주소의 non-null을 요구하므로 해결되지 않는다.

후속 장애도 확인했다. 운영의 `enqueue_direct_delivery_driver_receipt`와 `guard_direct_delivery_driver_receipt_job`은 상세주소가 비어 있으면 기사 전달용 영수증을 거부한다. 따라서 접수 제약만 고쳐서는 전체 업무 흐름이 끝나지 않는다. 확인한 결제 승인 함수에 이 영수증 함수의 직접 호출은 없었으므로, 이를 현재 결제 실패의 원인이라고 확대 해석하지 않는다.

### 개선안 A — 우선 적용

- 새 마이그레이션에서 상세주소 길이 제약을 `0~300`으로 맞춘다. 배달 주소는 필드 누락·JSON null·빈 문자열·공백을 서버에서 `''`로 정규화하고, 픽업은 기존처럼 주소 필드를 null로 유지한다. v1/v2 및 v3 위임 경로 모두 확인한다. 현재 고객 클라이언트가 보내는 빈 문자열도 그대로 호환한다.
- 기본 배송 주소 3~500자, 수령인, 전화번호와 위치 출처 검증은 유지한다. `manual/search/map_pin` 및 픽업의 주소·좌표 조합을 계속 검증한다.
- 기사 영수증 생성·검증에서 상세주소만 선택으로 바꾸고, 빈 상세주소 행은 출력에서 생략한다. 가짜 층·호수나 임의 대체 문자열은 저장하지 않는다.
- KO/VI/EN 필수 입력 안내에서 상세주소를 제외하고, 입력 검증 오류와 일시적인 서버 오류를 구별한다. 내부 SQL·고객 주소를 오류 메시지에 노출하지 않는다.
- 과거 마이그레이션은 수정하지 않는다. 기존 정상 주소에 데이터 보정은 필요하지 않다.

## 2. 사진 재전송 오류의 원인

### 상태 제한

주 결제 증빙은 `quoted / active → 업로드 → commit → awaiting_payment_review / locked`로 이동한다. 이후 `_canSendProof`, Edge의 `proof_upload_url_v2`, DB의 `direct_order_public_commit_proof_v2`는 담당자가 생성한 유효한 `review_request_id`가 있어야 새 사진을 허용한다. 고객이 잘못 보낸 사진을 즉시 직접 교체하는 동작은 지원하지 않는다.

### 로딩 종료와 복구

- `resumePaymentProof()`가 URL 발급·Storage 전송·commit을 순차 대기한다. 명시적인 시간 제한이 없다.
- 화면 `_uploadProof()`는 업로드 뒤 `_refreshProofStatus()`까지 기다린 다음 `finally`에서 전송 상태를 해제한다. 오류 처리에서도 같은 상태 조회를 기다리므로, 업로드 실패 뒤 상태 조회까지 멈추면 로딩이 유지될 수 있다.
- 기존 재시도는 동일 파일·경로의 결과 유실을 복구한다. 응답이 오류로 종료되는 상황은 다루지만 응답 자체가 끝나지 않는 상황은 종료하지 못한다.
- 일반 첨부도 별도 업로드·상태 갱신 대기를 사용한다. 이 경로 역시 제한된 시간 안에 UI가 복구되도록 다뤄야 한다.

### 증빙과 일반 첨부

하단 클립 버튼은 `customer_chat_attachment_*`를 호출한다. 결과는 일반 `attachment`이며 결제 상태를 변경하지 않는다. 담당자는 현재 견적의 고객 `payment_proof`만 승인 대상으로 선택한다. 일반 첨부를 모두 결제 증빙으로 취급하면 대화 중 올린 다른 사진까지 승인 대상이 되므로, 고객에게 사진 용도를 명확하게 선택·안내해야 한다.

최근 24시간의 Postgres 로그에는 `PROOF_UPLOAD_INCOMPLETE`가 4건 있었지만 이것만으로 사고 원인을 확정할 수 없다. 첨부 경로는 처음에 commit을 시도해 객체 존재 여부를 확인하기 때문에 정상적인 최초 전송에서도 미업로드 응답이 나올 수 있다. `PROOF_NOT_ALLOWED` 로그가 없다는 사실 역시 제한이 없음을 증명하지 않는다. Edge가 처리한 오류와 고객 브라우저에서 멈춘 요청이 모든 로그에 남는 것은 아니다.

### 개선안 B — 승인 전 직접 교체

- 담당자 승인·입금 기록 전 `awaiting_payment_review / locked`에서 고객이 `사진 교체`를 누를 수 있게 한다. 담당자가 재제출 요청을 만든 경우에도 동일한 교체 화면으로 처리한다. 고객에게 이미 이체했으면 사진만 다시 보내면 된다고 안내한다.
- 교체 요청은 주문·현재 견적·기존 유효 증빙 ID를 함께 고정한다. 서버는 주문 행 잠금 안에서 소유권·견적·미승인 상태와 기존 증빙 ID를 다시 확인한다. 오래된 탭이나 다른 기기의 교체는 충돌로 돌려 최신 사진을 다시 보여준다.
- Storage 기존 객체를 덮어쓰지 않고 새 UUID 경로에 저장한다. 새 사진이 검증·commit된 시점에만 유효 증빙을 전환하고 이전 증빙과 교체 관계는 감사 이력으로 보존한다. 실패 시 기존 유효 증빙은 유지한다.
- 담당자 화면은 새 사진의 미리보기·수신 시각을 보여주며, 이전 사진으로 열린 승인 창은 서버에서 거부한다. 교체·승인을 같은 주문 잠금 규칙으로 직렬화하고, 기존 최신 증빙 확인 및 결제 멱등성을 유지한다.
- 이미 입금 기록에 사용된 사진은 교체하지 않는다. 추가 청구의 미승인 사진은 해당 청구 범위로만 처리하고 기존 입금 증빙을 바꾸지 않는다. 사진 교체 자체는 입금·결제·재고·주방 전송을 발생시키지 않는다.
- 최초 증빙·교체·일반 첨부의 용도를 UI에서 분명히 표시한다. 필요하면 일반 채팅 사진에 `결제 증빙으로 제출`이라는 명시적인 동작을 제공하되, 동일한 서버 검증을 통과하게 한다. 임의의 채팅 사진을 자동 승격하지 않는다.
- 응답 필드와 상태 계약이 달라지는 API는 버전을 분리한다. 구버전 캐시 클라이언트를 유지하고 Dart 모델의 엄격한 키 검증을 함께 갱신한다.

### 개선안 C — 제한 시간과 중복 없는 복구

- URL 발급 15초, Storage 전송 60초, commit 20초, 후속 상태 조회 10초를 초기 제안값으로 두고 전체 작업에도 최대 120초 제한을 둔다. 실제 모바일 측정 뒤 조정한다. 파일 선택과 사용자의 미리보기 확인 시간은 네트워크 제한 시간에 포함하지 않는다.
- 전송 단계와 상태 동기화 상태를 나누고, 후속 상태 조회 실패가 업로드 버튼을 계속 잠그지 않게 한다. `준비 / 전송 / 확인 / 완료 / 재시도 필요`를 구분한다.
- timeout은 실패 확정이 아니다. Storage 또는 commit이 늦게 성공했을 수 있으므로 같은 시도 ID·경로로 먼저 결과를 확인한다. 객체 부재가 확인됐을 때만 같은 사진을 재전송한다. 서명 만료 시에는 같은 경로에 대한 권한을 재발급한다.
- `.timeout()`만으로 원래 네트워크 요청이 취소되는 것은 아니다. 지원되는 전송에는 취소를 적용하고, 늦은 응답은 작업 세대·주문·견적·시도 ID를 검사해 현재 UI를 덮어쓰지 못하게 한다. 서버의 경로 멱등성도 함께 유지한다.
- 쓰기 자동 재시도는 멱등성 확인 후 제한적으로 허용한다. 복구 조회는 최대 2회와 지수 대기·무작위 분산을 적용하고 전체 제한 시간을 공유한다. 여러 계층에서 재시도를 중첩하지 않는다. 이후 사용자가 재시도하거나 상태를 다시 확인할 수 있게 한다.
- 재시도 가능한 사진은 메모리에 보존하고, 서버 결과 확인 전 새 사진으로 조용히 바꾸지 않는다. 완료·주문 전환 시 불필요한 이미지 메모리를 해제한다. 화면 재진입은 서버의 유효 증빙 상태로 복구한다.

## 데이터 접근·부하 계획

- 선택 주문 1건의 전송·교체·승인만 갱신한다. 주문 목록 전체 재조회, 메시지별 권한 RPC, 사진별 자동 서명 URL 발급을 추가하지 않는다. 첨부 파일은 사용자가 열 때만 읽는다.
- 최초 주 증빙은 기본적으로 URL 발급 API 1회 → Storage PUT 1회 → commit API 1회 → 선택 주문 상태 조회 1회이다. 이는 클라이언트 HTTP 단계 수이며 DB 쿼리 수를 뜻하지 않는다. 일반 첨부의 기존 선행 commit 조회는 복구 시에만 필요한지 검토한다.
- 업로드 권한 검사는 주문·견적·현재 증빙의 필요한 컬럼만 조회하도록 한다. 현재처럼 전체 상태/채팅 본문을 권한 검사 목적으로 반복 반환하지 않도록 범위를 줄인다. UI 갱신 요청은 진행 중 요청을 공유하고 같은 이벤트의 중복 조회를 막는다.
- 화면당 활성 업로드 1건, 파일 최대 5 MiB를 유지한다. 사진 수나 주문 목록 길이에 비례해 원격 호출이 증가하는 루프를 만들지 않는다. 여러 주문 운영 점검은 ID 집합으로 일괄 집계하며 일괄 크기 100건·동시 요청 2개 이하로 제한한다.
- 운영에서 기존 `attachment_storage_path`의 부분 UNIQUE 인덱스, 메시지 `(request_id, created_at, id)`, 열린 재제출 요청의 부분 UNIQUE 인덱스, 입금 증빙 UNIQUE 인덱스를 확인했다. 새 조건의 실행 계획을 확인한 뒤 추가 인덱스 필요성을 판단한다.
- 구현 검증은 1/10/50개 동시 고객, 주문당 1/20/100개 메시지를 기준으로 HTTP 호출 수·DB 호출 수/읽은 행·응답 크기·p50/p95 지연·브라우저 이미지 메모리를 측정한다. 목록 크기가 커져도 단일 전송의 호출 수가 늘지 않아야 한다. 이번 조사에서는 실행 계획, 이 지표들의 실측과 처리량 개선을 검증하지 않았다.
- 진단 로그에는 단계·소요 시간·HTTP 상태·정제된 오류 코드·상관 ID만 남긴다. 사진, 주소, 전화번호, 계좌정보, 세션 비밀, 서명 URL·토큰·객체 경로를 기록하지 않는다. 사고 단말의 네트워크 로그 확보 시에도 같은 정제 기준을 적용한다.

원인 검증 테스트는 최신 운영 제약까지 포함해야 한다. 기존 `test/sql/direct_delivery_manual_addresses_test.sql`은 상세주소 빈 문자열을 오류 입력으로 취급한다. 이 과거 동작 검증만 통과해도 현재의 선택 입력 요구를 만족하는 것은 아니다. 새 요구와 전체 마이그레이션을 반영하는 회귀 검증을 추가한다.

운영 확인은 고객 주문에 시험 입금·일괄 승인을 하지 않고, 승인된 시험 범위에서 진행한다. 현재 Pending 주문은 유효 결제 증빙·재제출 요청·입금 기록 유무를 집합 조회로 대조한 뒤 실제 담당자가 새 사진을 확인한다. 기존 일반 첨부를 자동 증빙 처리하거나 주문을 일괄 승인하지 않는다.

복구 시에는 새 교체 기능을 차단하더라도 이미 저장된 증빙·이력을 보존하고 기존 재제출 경로를 유지한다. 빈 상세주소가 정상 저장된 뒤에는 다시 최소 1자 제약으로 되돌리지 않는다.

## 추가 승인 범위 (3~5, 2026-10-23)

3. **자동 채팅 갱신:** 고객의 15초 안전 폴링은 완료 주문의 열린 채팅을 갱신 대상에서 제외하고, 응답 지연 시 후속 폴링도 중단될 수 있었다. 선택 주문의 변경 번호를 2초 간격(+최대 0.5초 분산)으로 확인하고, 변경이 있을 때만 해당 주문 상세를 조회한다. 메시지·번역 변경을 집합 트리거로 변경 번호에 반영한다. 요청은 하나씩, 조회 시간은 최대 10초로 제한하며 실패 시 지수 대기(최대 30초), 복귀 시 즉시 재동기화한다. 전체 목록은 기존 낮은 주기로 유지한다. 직원은 기존 인증된 매장 실시간 알림을 사용하고 선택 주문 채팅을 별도로 갱신한다. 통신 실패 중에는 자동 재연결 상태와 수동 갱신 안내를 표시한다. 각 고객당 주기당 RPC 1회, 변경 시 상세 1회로 제한하며 대화 길이에 따른 조회 증가를 측정한다.

4. **은행 앱 연결:** QR·계좌 정보 아래에 은행 앱 선택/연결을 추가한다. 공식 VietQR HTTPS 딥링크로 수취 계좌, 금액, 주문 참조를 전달한다. 고객의 은행 앱과 가게의 수취 은행을 구별한다. 공식 지원 목록과 은행 식별자를 검증하고, 미지원 환경은 QR·복사로 계속 결제할 수 있게 한다. 반환 주소에는 주문 키·세션 비밀을 넣지 않는다. 은행 앱에서 고객이 확인·승인하며, 앱 복귀는 결제 완료로 취급하지 않는다. 실제 송금 없이 링크/금액/계좌/미지원·실패 경로를 검증한다.

5. **메모 대상 분리:** 주문 전체 메모는 관리자/캐셔 전용, 음식 항목 메모는 주방·포장 대상으로 기본 분리한다. 직원이 답변 시 대상을 명시적으로 선택할 수 있게 한다. 관리자 전용 메모는 주방·체커·기사·고객 출력물에서 제외하고 관리자 주문 상세와 고객 대화에는 유지한다. 기존에 주방/기사 대상으로 확정한 메모는 유지한다. 기존 일반 주문 메모 중 기본값 `both`는 관리자 전용으로 전환하고, 조리 요청은 해당 음식 메모 또는 직원의 명시적인 주방 대상 선택으로 전달한다. 내용 키워드를 추측해 분류하지 않는다. 원본/확정 이력과 이미 발행된 전표는 보존하며 이후 생성되는 화면·전표를 검사한다.
