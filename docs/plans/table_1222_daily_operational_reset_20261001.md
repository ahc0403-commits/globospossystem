# 1222번 테이블 복구 및 날짜 변경 시 운영 상태 자동 정리 계획

작성일: 2026-10-01 · 기준 시간대: Asia/Ho_Chi_Minh(UTC+7)

상태: 소스 구현·필수 릴리스 검사·운영 마이그레이션 적용 및 이력 등록·POS 앱 배포 완료. 운영 DB와 QR 화면에서 1222번 복구를 확인했고 사용자가 현장 POS에서 빈 테이블 표시와 선택 성공을 확인했다. 운영 cron 실행도 성공했으며, 실제 다음 자정은 미관측이다.

## 1. 목표와 처리 원칙

손님이 없는 1222번 테이블을 빈 테이블로 복구한다. 이후에는 캐셔가 주문 취소·결제·서빙 처리를 놓치더라도 전날의 운영 상태가 다음날 테이블 사용을 막지 않도록 한다.

사용자가 요청한 “날짜가 지나면 모두 정리”는 전날의 운영 주문, 테이블 점유, 해당 주문의 주방·트레이·서빙 대기와 QR 표시를 종료하는 것으로 구현한다. 주문·결제·영수증·매출·재고 거래·감사 이력은 보존한다. 실제 결제 기록을 지우거나 결제하지 않은 주문을 결제 완료로 바꾸지 않는다.

이번 자동 정리 대상은 식당의 테이블 운영 주문이다. 배달 주문, 외부 매출, 회계 문서, 인사·재고 업무를 날짜가 지났다는 이유로 일괄 삭제하는 범위로 확장하지 않는다. 매장별 적용 설정을 두고 빈탄 매장부터 검증한다.

## 2. 확인한 사실

운영 Supabase 프로젝트 `ynriuoomotxuwhuxxmhj`를 읽기 전용으로 조회했다. 첫 상태 조회 시각은 2026-10-01 10:49 베트남 시간이다.

| 항목 | 확인 결과 |
|---|---|
| 매장 | BunsikClub Binh Thanh |
| 매장 ID | `8bc9eef5-dcd5-46b1-b931-23f77132322c` |
| 테이블 | 1222 · `0bf44e2a-3ba1-49d7-9859-25aa527e5a3e` |
| 테이블 DB 상태 | `occupied` |
| 연결된 미완료 주문 | `a797c8d3-0315-4f91-8a71-66c40c8db945` |
| 주문 생성 | 2026-09-30 22:23:14 베트남 시간 |
| 주문 상태 / 출처 | `serving` / `qr` / `dine_in` / `paperless` |
| 품목 | 치즈김밥 1개: 전날 22:23 생성, 콜라 1개: 오늘 10:32 추가. 둘 다 `ready` |
| 결제 | 0건, 결제금 0 |
| 해당 매장의 전날 미완료 테이블 주문 | 1건: 위 주문 |
| 활성 주문 없이 점유 상태만 남은 테이블 | 조회 당시 0개 |
| 9/30 자동 작업 | 22:20 매출 확정, 23:00 일 마감 cron 모두 성공 |
| 빈탄의 주문 cutoff 정책 | `restaurant_cutoff_policies`에 해당 매장 행 없음 |

전날 주문에 오늘 추가 주문이 붙었다는 것은 주문 품목 생성 시각과 `qr_place_order` 감사 기록으로 확인했다. 당일 추가 주문으로 부모 주문의 `created_at`은 바뀌지 않았다.

현행 코드와 운영 DB 함수의 조합으로 다음 문제가 설명된다.

1. `lib/features/table/table_provider.dart`의 활성 주문 미리보기는 날짜 조건 없이 미완료 주문을 읽고 테이블을 사용 중으로 표시한다.
2. `lib/features/order/order_provider.dart`의 직원 활성 주문 조회도 날짜 조건이 없다.
3. `lib/features/payment/payment_provider.dart`는 오늘 생성된 `serving` 주문만 캐셔 결제목록에 올린다. 따라서 9/30 생성 주문은 10/1 결제목록에서 빠진다.
4. `lib/features/cashier/cashier_screen.dart`는 테이블을 눌렀을 때 결제목록 안에서 해당 주문을 찾는다. 목록에 없으면 결제 대상을 불러오지 못한다.
5. 운영 DB의 `qr_place_order_pre_takeout_core`는 날짜 제한 없이 마지막 활성 주문을 재사용한다. 오늘 추가 주문도 어제 주문에 붙는다.
6. 운영 DB의 `run_scheduled_daily_closings`는 집계·스냅샷을 저장하며 주문이나 테이블을 종료하지 않는다. cron 성공만으로 테이블 초기화가 보장되지 않는다.

관련 마이그레이션의 운영 적용 기록도 확인했다: `20260716190000`, `20260804010000`, `20260901130000`, `20260909160000`, `20260917120000`, `20260923010000`.

이번 상태가 남은 경로는 확인했다. 전날 첫 주문이 실제 손님 주문이었는지, 테스트였는지, 직원이 어떤 처리를 누락했는지는 DB 상태만으로 단정하지 않는다.

## 3. P0 — 1222번 긴급 복구

1. 위 매장·테이블·주문 ID로 복구 대상을 고정하고 관련 주문·품목·이행·인쇄 상태의 복구 전 스냅샷을 보관한다.
2. 실행 직전 트랜잭션 안에서 주문을 잠그고 결제 0건, 현재 미완료 상태, 새 활성 주문 유무를 다시 확인한다. 조사 이후 새로운 결제나 정상 주문이 생겼다면 조건 불일치로 중단한다.
3. 기존 `cancel_order`의 원장·품목 취소·이행 트리거·대기 인쇄 취소 계약을 지키는 경로로 남은 두 품목과 주문을 취소한다. 복구 사유는 “손님 없음 확인 / 전일 잔존 주문 / 오늘 복구 확인용 추가 주문 포함”으로 기록한다.
4. 다른 현재 활성 주문이 없음을 확인하고 테이블을 `available`로 변경한다. 테이블 상태만 바꾸면 활성 주문 미리보기가 다시 점유 상태를 만들 수 있으므로 주문 종료와 함께 처리한다.
5. DB에서 활성 주문 없음·결제 변경 없음·테이블 `available`을 확인한다. 운영 캐셔 화면과 QR 화면에서 빈 상태를 확인하고, 테스트 매장에서 새 주문→주방 준비→캐셔 선택 흐름을 검증한다.

기존 취소 RPC는 로그인한 사용자와 매장 권한을 검사한다. 서비스 작업에서 캐셔 계정을 임의로 가장하거나 감사 이력을 생략하는 직접 UPDATE로 대체하지 않는다. 필요한 복구 경로와 시스템 실행 주체는 사전에 명시한다.

## 4. P1 — 날짜 변경 시 서버 자동 정리

서버 기준으로 베트남 날짜가 바뀌면 이전 날짜의 테이블 운영을 종료한다. 기준은 부모 주문의 영업일이며, 다음날 추가 주문으로 `updated_at`이 바뀌었다고 전일 주문을 오늘 주문으로 취급하지 않는다.

| 대상 상태 | 자동 정리 결과 | 보존할 기록 |
|---|---|---|
| 전날 미완료, 결제 기록 없음 | 주문·품목 자동 취소, 운영 대기 종료, 테이블 해제 | 품목·금액·이전 상태·자동 종료 사유·시각 |
| 전날 미완료, 일부 결제 있음 | 운영 종료 표시, 테이블 해제, 관리자 확인 대상으로 이동 | 결제금·잔액·원래 품목과 회계 상태 |
| 결제 완료 / 이미 취소 | 종료를 중복 적용하지 않음 | 기존 영수증·취소 원장 |
| 활성 주문 없이 `occupied`인 테이블 | 현재 활성 주문을 재검사하고 `available`로 보정 | 보정 전후 상태·사유 |
| 오늘 생성된 정상 주문 | 오늘 운영으로 유지 | 모든 정상 운영 기록 |

부분 결제 주문을 `cancelled` 또는 `completed`로 허위 전환하지 않는다. 기존 주문 상태와 별도로 운영 종료 시각·사유를 표현한다(예: `operational_closed_at`). 이 표시가 있는 주문은 테이블 점유와 신규 추가 주문의 대상에서 제외한다. 원래 `table_id`를 유지해 과거 주문 위치도 추적할 수 있게 한다.

자동 취소는 기존 수동 취소의 금액 계산과 이행 종료 로직을 공유하되, 실행 주체를 시스템으로 명시한다. 기존 취소 원장의 `created_by NOT NULL`·불변성 계약을 확인하고 시스템 종료 감사 기록을 설계한다. 가짜 사용자 ID를 넣지 않는다. 준비·서빙된 메뉴의 재고 소비를 실제로 없던 일로 처리하지 않도록 현재 재고 차감·취소 계약도 검증한다.

실행 경로는 하나의 재실행 가능한 정리 함수로 통일한다.

- 베트남 시간 **00:00** 서버 배치 실행. 00:00에 놓친 대상은 이후 짧은 재시도 주기로 따라잡는다.
- POS 시작·날짜 전환·재접속과 QR 신규 주문 처리에서 같은 매장의 정리 누락을 확인한다. 주문 재사용 전에 전일 운영 종료를 보장한다.
- 서버 장애가 하루 이상 지속돼도 “어제만”이 아니라 오늘 이전의 모든 미종료 운영 주문을 정리한다.
- 매장·주문 단위로 잠그고 잠금 후 결제·활성 주문 상태를 재검사한다. 기존 결제/QR 주문의 잠금 순서와 맞춘다. 오늘 주문이 존재하면 테이블을 빈 상태로 덮어쓰지 않는다.
- 종료 기록을 주문별로 유일하게 남겨 같은 배치가 재실행돼도 중복 취소·중복 원장·재고 중복 처리가 생기지 않게 한다.
- 다른 매장의 실패가 빈탄 매장의 정리를 막지 않게 매장 단위로 처리한다. 처리 건수·예외·최근 성공 시각을 남긴다.
- 매장별 정책과 마지막 성공 영업일을 이용해 이미 정리된 매장 전체 이력을 매 주문 요청마다 재검색하지 않는다.

현재 21:30 주문 cutoff, 21:45 유예 종료, 22:20 매출 확정, 23:00 현금 마감은 각각 유지한다. 자정 운영 정리는 별도 책임으로 추가한다. 빈탄의 cutoff 정책 누락은 실제 영업시간 설정과 함께 별도로 확인하며, 자정 초기화 구현의 전제로 일괄 활성화하지 않는다.

## 5. P1 — 화면과 주문 RPC의 운영 기준 통일

모든 운영 화면과 RPC가 **오늘 영업일 + 운영 미종료**라는 동일한 활성 주문 규칙을 사용한다. 클라이언트 표시 조건만 바꿔 DB에 막힌 상태를 남기지 않는다.

- 테이블 점유 미리보기, 직원 활성 주문, 캐셔 결제목록, QR 활성 주문, QR 추가 주문, 주방/KDS·트레이·서빙 대기에 동일한 기준 적용.
- QR 함수는 public wrapper뿐 아니라 실제 주문을 재사용하는 내부 core와 현재 적용된 wrapper chain까지 수정·검증.
- 전날 QR 페이지나 오래된 주문 ID로 추가 주문하면 서버에서 날짜/주문 컨텍스트 변경을 반환. 화면은 이전 주문·장바구니를 정리하고 오늘 상태를 다시 불러온다.
- 전날 오프라인 생성/추가 주문을 오늘 자동 재전송해 주문을 부활시키지 않도록 영업일 검증. 만료된 요청은 이유를 기록하고 재시도 대상에서 제외하며 오늘 새 주문에 자동 합치지 않는다.
- 취소 복원, 품목 복원, 뒤늦은 주방·서빙 처리도 전일 운영 종료를 되돌려 테이블을 점유하지 못하게 서버에서 검사.
- 오래 열어 둔 직원·캐셔·QR 화면은 날짜 변경 시 선택 주문·운영 초안을 갱신. 기존 실시간 이벤트와 재접속 갱신 경로를 사용.
- 조회 실패를 “주문 없음”으로 판단해 정상 테이블을 강제로 비우지 않음. 정리 결과가 확정된 경우에 상태를 갱신.

예약 기능은 현재 단순 `reserved` 상태와 미래 예약을 구분할 수 있는지 먼저 확인한다. 날짜가 특정된 미래 예약을 전일 잔존 상태로 지우지 않는다. 전일 임시 예약까지 자동 해제하려면 예약의 적용 영업일을 명시한다.

이미 배달 주문으로 확정된 기록, 은행 이체 확인 대기, 결제·환불·영수증·MISA 작업은 테이블 운영 종료를 이유로 취소하지 않는다. 특히 도착이 늦은 결제는 종료된 주문의 금융 확인 대상으로 연결하고 새 손님의 테이블 운영에 붙이지 않는다.

## 6. P2 — 캐셔 복구 동선과 관리자 확인

사용 중 테이블을 눌렀는데 결제 대상이 없을 때 무반응으로 보이지 않게 한다. 서버가 확인한 사유에 따라 “준비 중”, “전일 주문 정리 중”, “결제 내역 확인 필요”를 표시한다.

캐셔가 손님이 없는 당일 미결제 주문을 잘못 남겼을 때도 테이블 상세에서 사유를 남기고 기존 취소 기능으로 비울 수 있게 한다. 결제 기록이 있으면 금융 조정 경로로 안내한다. 매장 관리자는 전일 자동 취소 건수와 부분 결제 확인 대상을 조회할 수 있게 한다.

## 7. 검증과 배포 순서

1. 운영 복구 전 상태를 재확인하고 1222번 복구를 좁은 범위에서 실행·검증한다.
2. 로컬/테스트 DB에서 이번 사례를 재현한다: 9/30 생성 주문이 10/1 점유 표시에 남고 캐셔 결제목록에는 없으며 QR 추가 주문이 이전 주문에 붙는 상황.
3. 회귀 테스트를 수행한다.
   - 전날 `pending`, `confirmed`, `serving`과 빈 주문·준비·서빙 누락 모두 자동 종료.
   - 전날 주문에 오늘 추가된 품목도 새 손님의 주문으로 승격되지 않음.
