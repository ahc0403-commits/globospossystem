# 배달·포장 주문과 캐셔 주문 수정 통합 개선계획

작성·갱신일: 2026-10-09 · Asia/Ho_Chi_Minh

고객 최종금액 확정, 입금 증빙 접수, 주문 전용 임시 링크, 홀 주문 메뉴 이동·일부 수량 취소와 **캐셔 금액 입력 안정화**를 하나의 실행 계획으로 정리한다. 대화에서 수립한 계획과 이후 정책 수정을 모두 반영한다.

2026-10-09에 아래 항목의 **소스 구현과 로컬 검증을 완료했다.** 신규 migration은 삭제 가능한 PostgreSQL에서 적용·검증했으며 운영 DB·Edge·웹에는 반영하지 않았다. 소스 구현, 운영 migration 적용, 운영 배포, 현장 검증을 각각 구분한다. 기존 사용자 소유의 tracked/untracked 변경과 과거 계획·운영 기록을 보존했다. 구현 경계와 검증 근거는 [구현 기록](/Users/andreahn/globos_pos_system/docs/implementation/direct_order_and_cashier_integrated_20261009.md)에 정리한다.

## 확인된 문제와 근거

| 영역 | 확인된 내용 | 구분 |
|---|---|---|
| 입금 증빙 접수 실패 | 실제 조사 주문에서 사진 업로드는 성공했으나 견적 재발행으로 이전 견적이 무효화돼 접수가 거절됐다. 이후 같은 사진을 새 견적에 접수했다. | 운영 기록 확인 |
| 견적 금액 | 조사 주문의 두 견적은 모두 171,720 VND였고 배송비·결제 조건도 같았다. 최종 실제 입금 확인액도 171,720 VND였다. | 운영 DB 확인 |
| 캐셔의 재발행 이유 | 금액 입력 오류 때문에 견적을 재발행했는지는 기록으로 확인되지 않았다. | 미확인 |
| 금액 입력 | 기존 formatter가 편집할 때마다 커서를 맨 뒤로 옮기고 모바일 입력 조합 영역을 제거했다. 중간 자리 수정으로 170,720을 입력하려던 값이 177,200으로 바뀌는 현상을 재현했다. | 소스·회귀 테스트 확인 |
| 입금 확인과 견적 | 해당 입력창은 실제 은행 입금액을 기록하는 용도다. 입력값 수정 자체가 고객 견적 금액을 바꾸거나 재발행하지 않는다. 입금 확인에는 접수된 증빙이 필요하다. | 소스 확인 |
| 브라우저 종료 후 복원 | 서버 주문은 남아 있지만 고객 복원이 브라우저에 저장된 세션에 의존하며 주문 전용 링크가 없다. 실제 모바일에서 저장 정보가 사라지는 정확한 경로는 미확인이다. | 소스·운영 세션 확인 / 현장 재현 필요 |
| 테이블 이동 | 기존 기능은 주문 전체를 빈 테이블로 옮긴다. 주문이 있는 테이블로 메뉴만 이동하는 기능이 필요하다. | 소스 확인 |
| 무료 처리 | 서비스 제외는 해당 주문에 다른 유료 메뉴가 남아 있어야 한다. 두 주문의 합산 결제만으로 이 조건이 합쳐지지는 않는다. | 소스 확인 |
| 일부 수량 취소 | 기존 수량 수정은 웨이터 등 제한된 역할의 조리 전 메뉴에만 허용한다. 캐셔는 메뉴 전체 취소 경로를 사용한다. | 소스 확인 |

금액 입력 오류와 견적 재발행에 따른 증빙 거절은 각각 확인된 문제다. **전자가 캐셔의 재발행을 유발했다는 인과관계는 확정하지 않는다.** 두 문제를 모두 수정 대상으로 포함한다.

## 적용 원칙

- 최종견적을 제공한 뒤 캐셔가 기본 메뉴 금액·수량·세금·결제 조건을 임의로 바꾸지 못하게 한다. 견적 금액 확정과 실제 입금 확인은 서로 다른 단계다.
- 변경 사유가 확인되는 실제 배송비 차액만 제한적으로 정산한다. 자유 입력 사유만으로 일반 금액 변경 권한을 열지 않는다. 고객 동의 버튼을 차액 정산의 조건으로 두지 않는다.
- 기존 견적·증빙·입금 기록은 보존하며 추가금과 환불금은 별도 기록으로 연결한다.
- 홀 주문의 이동·일부 취소 기능이 확정된 배달·포장 주문을 임의 수정하는 경로가 되지 않게 한다.
- 주문 전용 링크 종료는 고객 접근 권한을 무효화하는 작업이다. POS 결제·회계 기록을 삭제하지 않는다. 배송지는 기존 저장 설정에 따라 유지한다.
- 메뉴 이동과 취소를 재주문으로 구현하지 않는다. 조리 지시·재고 차감·입금·결제가 중복 발생하지 않아야 한다.
- 기존 매장 범위, 역할, 서비스 제외의 관리자 PIN, 결제 후 수정 제한, 마감 계약을 유지한다. 메뉴 이동·일부 취소에 불필요한 새 승인 절차를 추가하지 않는다.
- `process_payment`의 원자적 결제 처리와 비동기 MISA 처리를 유지한다. 목록별 개별 조회를 추가하는 N+1 구조를 만들지 않는다.

## 실행 항목

### 1. 캐셔 금액 입력 안정화 — 소스 수정·관련 검증 완료, 운영 반영 전

천 단위 구분자를 표시하더라도 커서와 선택 영역을 같은 숫자 위치에 유지한다. 모바일 키보드가 조합 중인 입력을 강제로 다시 쓰지 않고 조합 완료 후 형식을 적용한다. 붙여넣기, 전체 선택 후 교체, 중간 자리 삽입·삭제, 연속 입력, 기존 금액 상한을 검증한다.

현재 수정은 공통 [금액 formatter](../../lib/features/direct_order/direct_order_money.dart)에 적용했다. 이를 사용하는 최초 입금 확인, 추가 입금·환불, 배송비 및 실제 기사 비용 입력에 함께 적용된다. 실제 입금액을 자동으로 미수금에 맞추거나 견적 금액으로 덮어쓰지 않는다.

입력액이 미수금을 초과하면 별도 대조가 필요하다는 안내를 표시한다. 실제 초과 입금을 자동 승인하지 않으며, 입력창 문제를 해결하려고 견적을 재발행하도록 유도하지 않는다.

완료 기준: 사용자가 의도한 숫자와 화면 표시·실제 입금 기록이 일치한다. 숫자 수정만으로 견적 변경·재발행 요청이 발생하지 않는다. 현재 회귀 테스트는 키보드 편집 이벤트를 모사한 검증이며 실제 모바일·운영 웹 확인은 별도로 필요하다.

### 2. 최종견적 확정과 동일 조건 재발행 차단

최종금액과 입금 QR을 제공할 때 금융 조건을 고정한다. 증빙 접수 때까지 금액을 변경 가능하게 두는 현재 간격을 제거하되 `quoted`, 입금 검토, 승인 상태를 결제 완료와 혼동하지 않는다.

같은 메뉴·배송비·세금·결제 조건으로 다시 안내하면 기존 견적 ID를 반환하고 새 버전을 생성하지 않는다. 합계만 같은 다른 조건을 동일 견적으로 취급하지 않는다. 동시에 누른 요청과 응답 유실 재시도도 같은 결과를 반환해야 한다.

주문 상태는 유효한데 견적의 표시 유효기간만 지났다는 이유로 이미 송금한 고객의 증빙을 거절하지 않도록 만료 계약을 조정한다. 실제 취소·종료된 주문의 결제 요청은 차단한다. 진행 중 주문에 적용할 때 기존 견적 ID와 증빙 연결을 보존한다.

### 3. 확인 가능한 실제 배송비 차액 정산

Grab 등 실제 배송비의 변경 전·후 금액, 제공업체, 확인 근거를 기록하고 서버가 차액을 계산한다. 배송비 조정은 일반 견적 수정과 분리한다. 고객에게 사유·기존 배송비·실제 배송비·추가금 또는 환불금을 알린다.

고객이 기사에게 직접 지급하는 경우 POS가 배송비를 중복 청구하지 않는다. 매장이 받는 경우 증가분은 별도 입금으로, 감소분은 환불 의무로 기록한다. 필요한 정산이 끝나기 전에 기사 인계·최종 완료가 진행되지 않도록 기존 정산 계약과 연결한다.

추가 배송비의 고객 동의 대기 경로를 실제 비용·업체·예약 참조·직원 첨부를 요구하는 경로로 개편했다. 서버가 차액을 계산하며, 기존 자유 배송비 청구와 배송비 미발생 확정 API는 차단한다. 기사 직접 결제는 매장 추가 청구·기사 지급을 만들지 않는다. 부분 입금 후 실비가 다시 바뀌어도 기존 입금·증빙을 보존해 정산하며, 실비 감소 환불과 포장 전환 환불이 같은 배송비를 중복 환불하지 않게 한다.

### 4. 입금 증빙 접수와 재시도 안정화

업로드 성공, 메시지 접수 완료, 접수 결과 불확실, 일시적 통신 오류를 구분한다. 동일 경로·견적·재요청 ID로 접수 여부를 먼저 확인하고 이미 접수된 사진을 중복 저장하지 않는다.

견적 안내 반복으로 전송 중인 증빙의 대상이 무효화되지 않게 한다. 다른 주문·다른 증빙으로 변경되면 최신 상태를 확인하며, 이전 전송 대상을 새 주문에 자동으로 붙이지 않는다. 기존 private Storage, 주문 소유권, 실제 이미지 검증을 유지한다.

### 5. 주문 전용 임시 링크와 재접속

주문 생성과 함께 예측하기 어려운 주문별 접근 키를 발급하고 고객 주소창을 주문 전용 링크로 전환한다. 중복 제출은 같은 주문을 반환하며, 유효한 기존 접근 키를 무분별하게 교체하지 않는다. 키의 서버 저장·복구 방식은 원문을 일반 로그에 노출하지 않는 계약으로 설계한다.

같은 링크에서 주문 상태·내역·채팅·결제 안내·접수된 증빙을 서버에서 복원한다. 브라우저 종료, 새 탭, 캐시 삭제 뒤에도 해당 주문만 접근할 수 있어야 한다. 다른 주문·다른 고객의 주소나 채팅을 조회할 권한을 주지 않는다.

모든 조회·채팅·첨부·결제 관련 경로에 같은 주문 범위 검증을 적용한다. 브라우저 캐시는 일반 매장 링크에서 진행 중 주문을 찾는 보조 수단으로 사용한다. 링크 키를 내부 탐색 이력·분석·오류 로그에 그대로 기록하지 않는다.

### 6. 종료 후 링크·캐시 정리와 배송지 유지

서버가 실제 배송·수령 및 정산 종료를 확인하면 주문 링크를 무효화한다. 취소 후 환불이 남아 있으면 환불과 상담 종료까지 접근을 유지한다. 결제 승인만으로 링크를 닫지 않는다.

고객 캐시는 열려 있는 화면의 상태 갱신 또는 다음 접속 때 해당 주문 항목만 정리한다. 닫힌 브라우저의 저장소를 서버가 즉시 지울 수 있다고 가정하지 않는다. 통신 실패를 주문 종료로 판단해 캐시를 삭제하지 않는다. 저장한 배송지와 다른 진행 중 주문은 유지한다.

기존 주문은 유효한 소유권을 확인한 고객에게 전용 링크를 제공하는 호환 경로를 마련한다. 세션의 기본 유효기간이 진행 중 주문 링크를 예기치 않게 종료하지 않도록 접근 계약을 분리한다. 금융 기록은 기존 보존 정책을 유지하고 고객 개인정보·첨부 정리는 실제 종료 및 보존 규칙에 따른다.

### 7. 캐셔의 메뉴 단위 테이블 이동

메뉴 행에 `다른 테이블로 이동`을 제공하고 이동 수량과 대상 테이블을 선택한다. 빈 테이블뿐 아니라 같은 매장의 진행 중 주문이 있는 테이블에도 이동할 수 있게 한다. 고객이 자리를 옮긴 경우 선택한 메뉴 또는 전체 메뉴를 함께 이동한다.

첨부 사례의 목표는 **1103 소떡소떡을 1104 주문으로 이동한 뒤 기존 서비스 제외 절차로 무료 처리**하는 것이다. 이동만으로 자동 무료 처리하지 않는다. 이동 후에는 대상 주문을 기준으로 기존 무료 적용 조건을 평가한다.

원래 단가·VAT 기준·옵션·메모·서비스 제외 승인 정보·조리 및 제공 이력을 보존한다. 동일 메뉴명만으로 행을 합치지 않는다. 수량 일부를 나누면 원래 항목과의 연결을 남긴다. 원본·대상 주문, 관련 주방·트레이·층 데이터의 소속과 목적지를 하나의 처리로 갱신한다. 조리 진행을 초기화하거나 새로운 메뉴 주문으로 출력하지 않는다.

이동으로 순수 메뉴 수량·세전금액이 늘거나 줄지 않아야 한다. 양쪽 주문의 할인 조건이 바뀌면 기존 규칙에 따라 재검토하고 캐셔에게 표시한다. 비게 된 테이블은 다른 진행 중 주문이 없는지 확인한 뒤 정리한다. 결제가 있는 주문이나 마감된 주문을 이동으로 재작성하지 않는다.

### 8. 캐셔의 일부 수량 취소

`3개 중 1개 취소 → 남은 수량 2개`처럼 취소 수량을 선택하고 전·후 수량과 차감 금액을 확인한다. 전부 취소하면 기존 전체 메뉴 취소 처리와 연결한다. 반복해서 일부 취소한 뒤 전부 취소해도 취소 수량·금액을 중복 집계하지 않는다.

조리 전·조리 중·준비 완료·일부 제공·전부 제공를 구분한다. 미제공 수량 취소는 남은 작업 수량을 줄인다. 캐셔가 제공된 수량을 취소하는 경우 실제 제공 사실과 취소·정정 사유를 각각 기록한다. 조리·제공 이력을 삭제하거나 실제 제공 수량을 단순히 청구 수량으로 덮어쓰지 않는다. 웨이터의 기존 제공 후 취소 제한은 유지한다.

콤보는 취소한 세트 수량에 맞춰 구성 메뉴도 함께 처리한다. 무료 메뉴의 취소는 수량·사유를 남기되 현금 차감액을 발생시키지 않는다. 조리된 음식이나 이미 소비한 재료를 취소만으로 재고에 자동 복원하지 않는다.

현재 항목별 취소 원장의 중복 제한과 변경 불가 계약을 고려해 여러 부분 취소를 기록할 구조를 설계한다. 각 요청 ID, 취소 수량·금액, 전·후 값, 행위자, 사유를 추가 기록하고 기존 취소·복원·매출 집계와 연결한다. 결제가 있는 주문은 별도 조정·환불로 처리하고 원 결제 기록은 보존한다.

### 9. 공통 금액·주방 동기화와 동시 실행 검증

메뉴 이동·취소 후 양쪽 주문 또는 해당 주문의 금액·VAT·서비스 제외·할인·상태를 서버에서 함께 재계산한다. 두 주문을 다루는 처리에는 일관된 잠금 순서를 사용하고, 재시도는 같은 결과를 반환한다. 결제와 이동·취소가 동시에 실행돼 금액이 뒤늦게 바뀌지 않게 한다.

캐셔·웨이터·고객 표시·주방·트레이·층 화면과 새 출력물에 변경 결과를 반영한다. 과거 출력 완료 문서와 금융 snapshot은 보존하고 이동·취소 알림은 변경 내용으로 구분한다. 다른 층 이동 시 목적지와 권한도 함께 검증한다. 목록·진행 수량은 배치 조회하며 주문마다 detail RPC를 추가하지 않는다.

필수 시나리오: 금액 중간 자리 수정·모바일 조합·붙여넣기, 동일 견적 동시 재안내·전송 중 사진 접수, 실제 배송비 증가·감소·기사 직접 결제, 브라우저 종료·캐시 삭제·링크 종료, 첨부 테이블 사례의 이동 후 무료 처리, `3→2→1` 반복 취소와 잔량 전체 취소, 제공 완료·콤보·서비스 메뉴, 응답 유실·중복 클릭·매장 범위·결제와 수정의 경쟁 상태.

### 10. 구현 순서·검증·배포

순서는 **금액 입력 안정화 → 견적·입금 증빙 안정화 → 실제 배송비 정산 → 주문 전용 링크·종료 처리 → 메뉴 이동·일부 취소**다. 각 단계가 이전 단계의 권한·금액 보존 계약을 유지해야 한다.

SQL/Edge/Flutter의 관련 검증과 실제 모바일 브라우저 확인을 수행한다. 필요한 migration·Edge 호환 변경을 먼저 준비하고 클라이언트와 단계적으로 적용한다. UI를 먼저 배포해 없는 서버 계약을 호출하지 않는다.

전체 저장소 검증과 정확한 pushed HEAD의 필수 GitHub Actions를 확인한 뒤 `scripts/deploy_pos_production.sh`를 따른다. 이전 현장 설치·프린터·모바일 확인을 이번 변경의 검증으로 대신하지 않는다. 되돌릴 때도 이미 발급한 주문 링크·확정 견적·입금·취소 이력을 보존하는 호환 경로가 필요하다.

## 운영 반영 순서

최신 origin/main에서 만든 깨끗한 별도 worktree에 기능 변경만 통합한다. 기존 v1~v5 주문 조회 응답을 보존하고, 확정 금액 정보를 새 status_v6에서만 제공하여 배포 중 기존 고객 화면을 보호한다. 최신 세션 활동 갱신 수정도 유지한다.

전체 저장소 검사와 exact main SHA의 필수 GitHub Actions가 성공한 뒤 공식 배포 스크립트의 DB-only 경로로 신규 migration 세 개를 순서대로 적용한다. 각 적용 전 실제 운영 함수의 선행 정의를 확인하고, 적용 후 권한·RLS·trigger·결제 금융 계산의 보존을 읽기 전용으로 확인한다. 그 다음 Edge와 웹을 배포한다.

사용자 지시에 따라 스모크 테스트를 실행하지 않는다. 공식 --skip-smoke-tests 경로를 사용하여 Edge의 ACTIVE 상태와 허용 origin digest, Vercel production alias의 READY 배포 일치 여부를 확인한다. 테스트 주문·로그인 시도·실제 이체는 운영 검증으로 수행하지 않는다. 원래 작업 사본의 모든 기존 파일 해시와 Git 변경 상태를 대조하여 관련 없는 작업이 보존됐는지 확인한다.
