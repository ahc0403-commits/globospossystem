## 1. 목표와 우선순위

1. **P1: 로그인 직후 화면 이동을 막는 상단 카테고리 선택창 누락 해결.** 초기 조회 부하를 줄이고, 느린 응답·실패·화면 높이 변화에도 선택창을 계속 표시한다.
2. **P2: 매출 추이의 평균 계산 기간을 선택 기간과 일치시킨다.** 빠른 기간 선택과 사용자 지정 기간에 동일한 계산 규칙을 적용한다.

평균선의 의미는 질문으로 제시했으며 아직 답변 전이다. 아래 기본안은 기존 표현인 **이동평균**을 따라 선택한 N일에 대해 N일 이동평균을 표시하는 것이다. 선택 기간 전체의 일평균을 수평선으로 표시하려는 의도라면 3.5의 간단한 대안으로 확정한다. 구현 전에 이 계산 계약을 확인한다.

## 3. 매출 추이 평균선 개선

### 3.1 계산 계약

- `N = 종료일 - 시작일 + 1`: 양 끝 날짜를 포함한 달력 일수.
- 빠른 선택 7일·14일·30일과 임의의 사용자 지정 기간에 같은 규칙 적용.
- 각 표시일 D의 이동평균 = D를 포함한 직전 N일의 일매출 합계 ÷ N.
- 예: 14일 선택 시 범례·툴팁에 `14일 이동평균`을 표시하며 계산에도 14일을 사용한다.
- 날짜 경계와 오늘 판정은 기존 보고서 기준인 `Asia/Ho_Chi_Minh`로 통일한다.
- 한국어·베트남어·영어 문구가 같은 계산 의미를 전달하도록 수정한다.

### 3.2 그래프 처음부터 평균선을 표시할 데이터 확보

- 표시 시작일 이전 N−1일의 일별 매출을 계산용으로 추가 조회한다. 30일 그래프에는 최대 59일의 일별 데이터가 필요하다.
- 화면의 X축, 선택 기간 합계, 시간대별 매출, 팀 수, 테이블 평균 및 Excel의 조회 기간은 선택한 구간으로 유지한다.
- 추가 구간은 일별 매출에 필요한 데이터만 조회한다. 전체 보고서의 주문·취소·전자송장 조회까지 기간을 확장하지 않는다.
- 기존 매출 집계와 동일한 매출 인정·결제 분할·외부 매출·Photo 수기 신고 규칙을 재사용한다. 평균선용 별도 회계 규칙을 만들지 않는다.
- 기존 조회 API의 행 수 제한 및 페이지 처리를 확인해 긴 기간에서 조용히 일부만 집계하지 않도록 한다. 서버 일별 집계가 필요한지는 데이터량을 측정한 뒤 결정한다.

### 3.3 빈 날짜, 오늘, 오류 처리

- 조회가 성공한 과거 날짜의 실제 무매출은 0으로 포함한다. 조회 실패·잘린 응답·미등록 데이터와 실제 0원을 구분한다.
- 오늘 매출이 0이면 마지막 평균점을 제외하는 현재 동작을 우선 보존하고, `오늘 미집계 제외`를 설명한다. 오늘 매출이 있으면 현재까지의 값임을 표시한다. 매출 0 여부로 확정 마감을 판정하지 않는다.
- 추가 과거 구간 조회가 실패하면 기존 매출 차트는 보여주고 평균선에만 재시도 상태를 제공한다. 실패한 값을 0으로 대체해 평균을 낮추지 않는다.
- 완전한 N일 구간을 확인할 수 없으면 해당 평균점을 생략하고 이유를 표시한다. 임의로 분모를 줄이지 않는다.
- 1일 조회는 점·금액으로 식별 가능하게 표시하고, 전체 0원 구간도 빈 화면과 구분한다.

### 3.4 날짜 선택과 응답 정합성

- 날짜 입력 중인 값과 적용 완료된 조회 기간을 분리한다. 차트·평균 계산·범례는 실제 결과의 기간을 사용한다.
- 빠르게 7일 → 30일 → 14일로 바꾸어도 마지막 요청의 결과만 반영한다. 이전 요청의 늦은 응답이 새 기간을 덮지 못하도록 한다.
- 매장·기간·평균 계산에 필요한 과거 범위를 결과와 함께 관리한다.

### 3.5 선택 기간 일평균 수평선 대안

사용자가 수평선을 선택하면 선택 구간의 일매출 합계 ÷ 집계 대상 일수로 상수선을 표시한다. 과거 N−1일 조회가 필요 없어 변경량과 조회 비용이 작다. 범례는 `선택 기간 일평균 · 30일`처럼 표시하고 오늘 제외 시 실제 분모를 함께 안내한다. 날짜 적용 정합성, 시간대, 0원·오류 구분은 동일하게 적용한다.

### 3.6 완료 기준

- 1·7·14·30일 및 사용자 지정 10·45일의 계산값을 독립적으로 계산한 예상값과 비교한다.
- 1부터 14까지의 매출 예제에서 마지막 14일 평균은 7.5가 된다. 라벨만 변경하는 테스트로 끝내지 않는다.
- 과거 데이터가 있는 경우 표시 구간의 첫날부터 마지막 날까지 계산값과 점 위치가 일치한다.
- 0원인 날, 오늘 포함, 월·연도 경계, 기기 시간대 차이, 조회 실패, 응답 순서 역전, 매장 변경을 검증한다.
- 그래프를 위한 과거 데이터가 선택 기간 합계나 Excel에 섞이지 않는지 확인한다.
- `test/sales_revenue_analysis_widget_test.dart`의 현재 `14일 조회 → 7일 평균` 기대값을 새 계약으로 변경한다.

## 4. 첫 로그인 및 상단 선택창 개선

### 4.1 재현과 기준 측정

- 앱 최초 열기와 로그인 버튼 이후를 구분해 측정한다: 웹 앱 준비 → 인증 응답 → 필수 프로필·권한·매장·동의 확인 → 관리자 화면 첫 표시 → 카테고리 클릭 가능 → 첫 탭 데이터 완료.
- 단계별 소요 시간, 첫 탭이 준비되기 전 조회 개수·중복 요청·프레임 지연을 기록한다. 인증 정보와 개인 식별값은 기록하지 않는다.
- 첨부 증상은 실제 사용 기기·브라우저를 확인한 뒤 동일 조건에서 재현한다. iOS Safari, Android Chrome, 태블릿 가로·세로 및 데스크톱도 확인한다.
- 깨끗한 브라우저 캐시, 세션 복원, 키보드를 열고 로그인, 자동완성, 느린 네트워크, 일부 요청 실패, 200% 글자 확대, 주소창 높이 변경을 테스트한다.
- 카테고리 선택창의 존재뿐 아니라 실제 화면 내 위치·가려짐·터치 가능 여부를 검사한다.

### 4.2 처음에는 선택한 탭만 생성

- 모든 탭을 즉시 생성하는 구조를 변경해 첫 선택 탭만 마운트한다. 나머지는 최초 선택 시 생성한다.
- 방문했던 탭은 필요한 입력·조회 기간·스크롤 상태를 보존한다. 매장이나 권한이 달라지면 이전 범위의 상태를 재사용하지 않는다.
- 미방문 탭에 대한 조회·구독이 실제로 시작되지 않는지 요청 기록으로 확인한다.
- 실시간 이벤트의 현재 탭 갱신과 다음 진입 시 새로고침을 검증한다. 보고서 기간이나 편집 중인 설정이 이벤트 때문에 초기화되지 않게 한다.
- 앱 루트가 소유하는 인쇄·필수 운영 알림의 수명은 탭 지연 생성과 분리해 유지한다.

### 4.3 로그인 준비 작업 중복 제거

- 명시적 로그인·인증 이벤트·세션 복원에서 같은 사용자의 동일 초기 프로필 조회를 공유해 동시에 한 번만 수행한다.
- 로그아웃 또는 다른 로그인 이후 도착한 이전 응답이 인증 상태를 덮지 않도록 사용자·세션 세대를 확인한다.
- 최초 로그인에 필요한 권한·매장 접근·비밀번호 변경·개인정보 동의 확인은 완료한 뒤 업무 화면을 연다.
- 의존성이 없는 준비 조회만 병렬화한다. 시간초과·재시도에서 필요한 확인을 생략하지 않는다.
- 로그인 이후 경로 이동은 중앙 라우터를 단일 기준으로 정리한다. 직접 링크의 복귀 경로와 필수 확인 화면을 회귀 검증한다.

### 4.4 상단 선택창 표시 안정화

- 권한 확인 뒤 관리자 화면이 생성되면 상단 메뉴를 즉시 표시한다. 본문에는 별도 로딩·오류·재시도 상태를 둔다.
- 이미 본문 스크롤 밖에 있는 상단 메뉴 구조는 활용한다. 재현 없이 상단 전체를 다시 만들지 않는다.
- 로그인 제출·화면 전환에서 입력 포커스를 정리한다. 실제 재현 결과에 따라 키보드 종료 후 화면 높이·위치 복원을 보완한다.
- `SafeArea`, 고정 높이 상단 바·선택창, 웹 루트의 높이와 스크롤 제한을 함께 검증한다. CSS 변경이 필요하면 `index.html`과 `flutter_bootstrap.js` 양쪽의 중복 규칙을 일치시킨다.
- 브라우저 전체 스크롤을 항상 강제로 초기화하거나 임의의 지연 시간을 추가하는 방식은 피한다. 재현된 경로 전환과 화면 변화에 한정해 고친다.

### 4.5 완료 기준

- 필수 인증 확인을 마친 뒤 본문 응답을 10초 지연하거나 실패시켜도 상단 선택창이 보이고 클릭된다.
- 미방문 탭은 첫 진입에 조회하지 않으며, 동일 세션의 초기 프로필 조회가 겹치지 않는다.
- 실제 문제 기기에서 키보드 로그인·세션 복원·회전·확대 조건별 반복 검증에 상단 누락과 스크롤 불능이 없다.
- 목표: 같은 기기·네트워크 조건에서 로그인 클릭부터 메뉴 사용 가능까지의 p95를 개선 전 대비 50% 단축한다. 이는 실측 전 잠정 목표이며, 단계별 측정 후 병목과 함께 재확정한다.
- 별도 목표: 필수 인증 확인 완료부터 메뉴 사용 가능까지 p95 1초 이내. 본문 조회 완료 시간과 혼합하지 않는다.
- 속도 측정은 같은 release 빌드 조건에서 전후 각각 최소 30회 수행한다.
- 탭 첫 방문·재방문, 매장 전환, 권한 변경, 로그아웃 중 늦은 응답, 보고서 조회 기간 유지, 설정 입력 유지, 인쇄 및 필수 알림을 확인한다.

## 5. 실행 순서와 검증·출시

1. 평균선 정의와 문제 발생 기기·브라우저를 확정하고, 로그인 단계별 측정과 재현 시나리오를 준비한다.
2. 프로필 조회 중복 제거와 탭 최초 선택 시 로딩을 구현해 초기 부하 감소를 검증한다.
3. 느린 네트워크·키보드 로그인에서 상단 누락을 재현하고, 원인이 확인된 화면 배치·전환 경로를 수정한다.
4. 선택 기간 평균선을 구현하고 계산·기간 정합성을 검증한다. 로그인 개선과 별도 변경 단위로 검토할 수 있게 한다.
5. 수정된 Dart 파일 포맷, `flutter analyze`, 관련 계산·위젯·인증·라우터 회귀 테스트, 웹 release 빌드 및 실제 브라우저 검증을 수행한다. 저장소가 요구하는 `bash scripts/check_repo.sh` 등 필수 검사도 수행한다.
6. 구현 완료 시 사용자에게 변경 사항, 전후 측정, 재현 해결 증거를 제시한다. 현재 요청은 계획 수립이므로 운영 적용은 이번 작업에 포함하지 않는다.
7. 후속 배포는 `CLAUDE.md`의 게이트를 따른다. 정확한 pushed head SHA의 필수 GitHub Actions 성공을 확인한 뒤 `scripts/deploy_pos_production.sh`를 사용한다. 배포 후 실제 로그인·메뉴 전환·기간별 평균선을 확인하며, 악화 시 직전 검증 버전으로 되돌린다.

상태 보고는 계획 수립, 소스 구현, 테스트 검증, 운영 배포, 운영 확인을 구분한다. 이 문서는 계획 수립과 소스 조사만 완료한 상태다.
