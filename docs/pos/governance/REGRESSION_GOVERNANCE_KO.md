# POS 변경·회귀 방지 거버넌스

이 문서는 지금부터 적용하는 변경 규칙이다. Office 최초 법인 연결·전역 상태
전환·실단말 장시간 시험 등 제품 잔여 작업의 완료 여부와 구분한다.
공통 작업 원칙과 프로젝트 업무 불변식·기존 공식 릴리스 게이트를 함께 따른다.

## 현재 적용되는 자동 검사

`python3 -B scripts/governance/check.py`는 로컬 파일/Git만 읽는다.
`scripts/check_repo.sh`의 첫 단계와 공식 배포의 전체 검증 진입 전에 실행한다.
기존 owner 재검증 면제를 사용할 때도 이 검사는 생략되지 않는다.

검사하는 내용은 다음과 같다.

- `lib/features/`의 모든 기능이 `FEATURE_CONTRACTS.json`에 등록돼 있는가.
- 기능 소유 영역과 실제 존재하는 검증 파일/공식 recipe가 연결돼 있는가.
- `ACTIVE_CHANGE.json`의 기준 commit이 조상이며, 변경·추가·삭제 파일 해시가
  실제 변경 전체와 같은가. ACTIVE_CHANGE 자체만 자기 해시 대상에서 제외한다.
- 변경 기능 및 공유 Dart 모듈의 역방향 import/export 소비 기능이 선언됐는가.
  삭제된 모듈의 영향은 기준 commit의 의존 관계에서도 찾는다.
- DB/Edge/bootstrap/웹·플랫폼의 광역 영향이 검토됐는가.
- 제품 변경을 문서/도구 변경으로 분류해 전체 recipe를 누락시키지 않았는가.
- 업무 불변식·위험·롤백·필수 검사와 성능 지침 11개 항목이 검토됐는가.
- 기능 목록/계획의 체크박스만으로 검증 완료·운영 완료·성능 향상을 주장하지 않는가.

이 검사는 **변경 영향과 검증 선언의 누락을 차단**한다. 정적 import 분석에는
동적 RPC·설정·이벤트 관계를 모두 이해하는 능력이 없다. DB/Edge 등은 보수적으로
전 기능을 영향 검토 대상으로 삼고, 추가 관계는 작성자가 명시한다.
이 PASS를 실행 커버리지, N+1 부재, 안전한 금융 처리 또는 운영 정상의 증거로
바꾸지 않는다. 실제 UI/API/SQL·권한·성능·운영 검사는 기존 절차로 수행한다.

## 변경할 때

1. 최신 기준 main에서 사용자 작업을 보존한 별도 작업 공간을 사용한다.
2. ACTIVE_CHANGE의 `baseSha`를 이번 변경의 실제 기준 commit으로 지정한다.
3. 영향 기능/공유 영역, 변경 종류, 위험, 보존할 업무 불변식, 롤백과 필수 검사를 작성한다.
4. 성능 지침 11개 항목을 각각 검토한다. 비대상은 근거를 쓰고, 대상은 데이터
   규모·동시성 가정과 실제 확인할 검사/측정을 명시한다. 단순 병렬화나 작은
   응답만으로 DB 작업량 감소를 주장하지 않는다.
5. `python3 -B scripts/governance/check.py --refresh-inputs`로 입력 해시를 갱신한다.
   이 명령은 검토나 검증을 대신하지 않고 PASS를 생성하지 않는다.
6. checker와 위험에 맞는 영향 검사를 수행한다. 결과와 미실행·실패·면제를 구분한다.
7. 제품 릴리스는 최종 main의 공식 전체 recipe와 DB/웹/운영 검증을 수행한다.
   동일 입력에서 이유 없이 후보/DB/웹마다 전체 검사를 반복하지 않는다.

새 기능·공유 계약·검증 명령을 추가하면 registry도 같은 변경에서 갱신한다.
기존 공개 계약을 사용하는 기능을 제외하려면 코드·권한·업무 의존 근거가 필요하다.
N+1, 무제한 재시도/동시성, 전체 재조회, 캐시 범위 누락, JOIN 곱셈, 반복 집계,
대용량 전송, 취소되지 않는 요청과 화면 자원 누적을 함께 검토한다.

## 결과·scope·DB·Office 기준

- 확정된 쓰기와 후속 조회 실패를 분리한다. 결과 불명은 동일 operation 결과를
  조회하며, 결제/입고/인쇄/발행을 자동으로 중복 실행하지 않는다.
- 사용자·법인·매장·권한 revision·조회 조건과 비동기 요청 세대를 검토한다.
  전환/로그아웃 뒤 이전 응답·캐시·구독이 현재 범위에 반영되면 안 된다.
- 함수의 유효 최종 정의·트리거·RLS/GRANT·인덱스와 실제 migration 이력을 확인한다.
  원장·발행 문서·과거 소유 귀속·샘플 제외·퇴역 연동 차단을 보존한다.
- Office는 별도 DB/Auth이며 POS/Office 업무 ID와 로그인 ID를 혼동하지 않는다.
  최초 법인 연결 구현과 실제 두 DB 검증은 별도 G2 산출물이다.
- 전역 결과 타입·scope 규약을 아직 전 기능에 적용한 것은 아니다. registry의
  `legacy_or_partial`은 이 사실을 명시한 상태이며 정상/완료 판정이 아니다.

## 완료 증거와 잔여 작업

`FEATURE_CONTRACTS.json`은 G0–G7의 필수 증거 종류를 추적한다. 목록에서는
`open / in_progress / implemented`만 허용한다. 검증/운영 완료는 Git 체크박스가
아니라 기존 공식 검증 receipt, 실제 DB/배포 기록과 장시간·실단말 결과를 근거로
별도 결과물에 기록한다. 실패·미실행·면제를 PASS로 바꾸지 않는다.

전체 완료 결과를 자동 판정하는 장시간/두 DB 증거 연결은
[잔여 완료 계획](../resilience/COMPLETION_PLAN_20261101.md)의 G6–G7에서 구현한다.
현재 구조 검사가 그 판정을 이미 수행한다고 보고하지 않는다.

이 거버넌스 변경은 제품 기능·DB/계정의 변경을 포함하지 않는다. 공식 프로젝트
지침과 검증 진입점에 적용되면 개발/릴리스 운영 규칙으로 효력이 생긴다.
이를 위해 관련 없는 POS 웹을 다시 배포하거나 DB migration을 만들지 않는다.
