# 면·밥 선택, 편집 장바구니와 전가복 층 실시간 전달

사용자 승인: 2026-10-21 구현·테스트 후 커밋·푸시·운영 배포. 전가복은 트레이를 쓰지 않는다.

## 동작

- 관리자 메뉴 등록/수정과 Excel 왕복의 `면밥선택`으로 필수 면·밥 선택을 관리한다. 열이 없는 구버전 Excel은 현재 설정을 보존한다.
- 메뉴 하나에 기존 S/L 가격과 면·밥 선택을 함께 둔다. 내부 판매 ID는 규격/선택별로 안정적으로 유지하며 기존 L ID와 주문·세금 이력을 보존한다. 선택 가격은 등록 가격을 사용한다.
- QR·직접 주문에서 `다른 옵션 추가`로 S 하나와 L 하나, 면 하나와 밥 하나를 각각 담는다. 같은 선택만 합치며, 포장 구분과 메모를 유지한다.
- 장바구니에서 사진·설명·가격 확인, 옵션 변경, 수량 수정, 삭제와 계속 쇼핑을 제공한다. 합계는 현재 장바구니에서 다시 계산하며 명시적 주문 제출 전에는 주문을 만들지 않는다.
- 기존 `menu_option_key` 배치 검증을 유지하고 주문 당시 `meal_choice`·규격·다국어 이름·가격을 고정한다. 오래된 가격의 임시 장바구니는 서버가 거부한다.

## 전가복 조사와 수정

운영 조회에서 직접 전달 설정과 층 대기 수량은 존재했고 활성 트레이 배정은 없었다. 트레이 수량 필드는 호환 투영이며 실제 트레이 인계의 근거가 아니다. 다만 전가복에는 `kds_realtime_rollouts` 설정이 없어 legacy 방식으로 동작했고 최근 변경 원장이 없었다.

`20261021100000_jeongabok_floor_live_sync.sql`은 전가복만 active로 전환하고 주방 완료 이벤트의 대상에 해당 저장 층을 명시한다. 1F/2F/3F를 구분하고 배달/픽업은 층 대상에서 제외한다. 층 대기 시간도 주방 완료부터 계산한다. 다른 매장 rollout과 checker 동작을 유지하며 실제 조리/고객 전달 수량은 변경하지 않는다. 기존 단말은 다음 정상 갱신에서 설정을 다시 읽는다.

기존 bootstrap/ticket 경로의 품목·콤보별 반복 조회 두 개는 집합 JOIN/관계별 사전 집계로 교체한다. 읽기 범위는 호출된 큐/품목 ID 집합이다. 중복 큐를 한 번만 집계하고 입력 순서를 유지한다. 장바구니 편집은 기존 메뉴 캐시에서 처리하며 편집마다 서버를 조회하지 않는다.

## 검증

- QR: S→L/L→S, 면/밥 동시 담기, 옵션 병합과 수량 한도, 상세·삭제·실제 제출 스냅샷, 편집 중 불필요한 조회/주문 없음.
- 직접 주문: KO/VI/EN에서 S·면 + L·밥, 수량·옵션·상세·삭제, 빈 장바구니, 제출 전 주문 없음.
- SQL: 네 조합·안정 ID·가격 변경 후 스냅샷 보존, 해제/재활성화, 오래된 옵션 차단, 익명 관리 금지, 500개 메뉴 일괄 변경.
- KDS SQL: 기존 legacy 갱신 공백 재현 후 실제 deferred private floor:2F/floor:3F broadcast, tray 대상 없음, 배달 제외, 다른 매장 유지. 실제 메뉴/콤보 조회·취소 제외·순서·빈 입력과 500개 입력의 중복 방지를 확인한다.
- 합성 PostgreSQL에서 500개 메뉴 변경 약 145 ms, 500개 입력 KDS 보강 약 7 ms(단일 로컬 실행). 운영 네트워크·단말·동시 부하·메모리 측정값이 아니다.
- 전체 검증은 `bash scripts/check_repo.sh`, 정확한 main SHA의 `POS release contract`, 공식 배포 스크립트로 구분해 기록한다. 로컬 검증만으로 운영 완료를 선언하지 않는다.

## 운영 반영 순서

두 변경은 독립적인 메뉴 호환 스키마와 매장 KDS 활성화이므로 공식 스크립트의 단일 migration 제한을 유지하여 DB-only를 두 번 실행한 뒤 web-only를 실행한다. 매 실행은 깨끗한 exact main과 동일 SHA CI 성공을 요구한다.

1. `20261021090000_menu_meal_choices_cart.sql` — 관리자 옵션과 서버 스냅샷.
2. `20261021100000_jeongabok_floor_live_sync.sql` — 해당 매장 실시간 갱신 활성화.
3. 앱 배포·HTTP·지정 운영 계정 로그인 확인.
4. 실제 로그인한 관리자로 기존 면/밥 메뉴에 선택 설정 저장. 계산서 정책은 실제 등록자를 기록하며 스키마 migration에서 인증을 가장하지 않는다.
5. 운영 메뉴의 가격/ID/면·밥 투영과 직접 층 경로를 읽기로 검증. 운영 테스트 주문이나 가상의 조리/고객 전달을 생성하지 않는다.

새 판매 ID로 주문이 생긴 후 열/스냅샷 삭제나 트레이 계정 재활성화로 되돌리지 않는다. 장애는 주문 이력을 보존하는 후속 수정으로 처리한다. 현장 태블릿의 실제 가청 알림과 물리 전달은 원격 SQL 검사만으로 입증할 수 없다.
