## 배포 순서와 보호 조건

1. 기존 계획과 첨부 요구사항의 구현·검증을 완료하고 이번 릴리스에 포함할 소스·마이그레이션·정책·승인 데이터·미발행 재검증 대상을 명시한다. 기존 사용자 변경을 일괄 커밋하거나 버리지 않는다.
2. 변경 Dart 포맷, 관련 Flutter/SQL 테스트, `dart analyze --fatal-infos`, `bash scripts/check_repo.sh` 및 저장소 필수 검사를 완료한다. 로컬 결과와 운영 결과를 구분한다.
3. [정식 배포 런북](POS_PRODUCTION_DEPLOYMENT_RUNBOOK.md)에 따라 깨끗한 작업 공간과 freshly fetched `origin/main`이 같은 exact pushed SHA인지 확인하고, 그 SHA의 필수 GitHub Actions gate 성공을 확인한다.
4. `scripts/deploy_pos_production.sh`로 드라이런과 운영 반영을 진행한다. 필요한 마이그레이션은 명시한 파일만 의존 순서대로 정식 DB-only 경로로 적용하고 이력·사후 검증을 확인한다. 운영에 적용된 초기 마이그레이션을 다시 적용하거나 `supabase db push`로 관련 없는 변경을 밀어 넣지 않는다.
5. 실제 자동 정책·승인 데이터는 승인된 범위와 실제 주체·시각·근거로 기록한다. 과거 적용일과 실제 승인 시각을 구분하고, 기존 하루짜리 승인 이력을 덮어쓰지 않는다. UI만 배포하고 전체 메뉴 데이터 등록이나 서버 자동 매핑을 미완료 상태로 남기지 않는다.
6. DB/RPC와 앱의 호환성을 확인하며 관련 서버 변경과 POS 앱을 동일 통합 릴리스에 반영한다. 각 배포의 실제 SHA와 마이그레이션 적용 결과를 남긴다.
7. 운영 내부에서 전체 메뉴 대조, 신규 등록·첫 판매 경로, 보호되지 않은 미발행 대상 재검증, 원장·Excel 계약과 성능을 확인한다. 시험 거래를 실제 신고·발행·전송하지 않는다. 운영에서 측정하지 못한 항목은 로컬 시험 결과와 구분한다.
8. 최종 보고는 소스 검사 / 운영 DB·정책·승인 데이터 / 배포 SHA와 해당 SHA의 gate / 실제 매출·보존·성능 검증으로 나눈다.

기존 계획의 **MISA 외부 시험 제외** 조건을 유지한다. MISA 접속·가져오기·발행·세무당국 전송·이메일 외부 시험을 추가하지 않는다. Photo는 수동 Excel 업로드, 기존 8%와 `Dịch vụ chụp ảnh / Lần` 계약을 유지하며 자동 수집을 재활성화하지 않는다. 배송비 품목을 추가하지 않는다.

1. 목표와 완료 기준

문제의 원인은 최근 며칠 동안 주문된 메뉴만 매핑하고 전체 등록 메뉴를 매핑하지 않은 것이다. 아래 재현 메뉴 3개는 회귀 검증 사례이며 작업 대상 전체가 아니다.

반드시 다음 두 가지를 모두 완료해.
- 기존 전체 등록 메뉴를 메뉴 마스터 기준으로 점검하고 실제 승인 매핑을 완성한다.
- 향후 메뉴 생성·복제·가져오기·재활성화 시 계산서 매핑이 자동으로 생성되거나 갱신되도록 서버 저장 경로까지 연결한다.

최근 주문, 선택 영업일, 수정 Excel에 등장한 메뉴로 매핑 대상을 한정하지 마. 판매 이력이 없는 메뉴, 숨김 메뉴, 일시 품절 메뉴, 비활성 메뉴, 콤보 및 구성품도 전체 등록 메뉴 점검에 포함해. 보관·삭제 이력은 상태와 과거 거래를 별도로 검증하고 임의로 재활성화하지 마.

전체 메뉴 수, 현재 유효한 승인 매핑 수, 누락·만료·범위 불일치·필수 원본정보 부족 건수를 지점/법인별로 대조해. 문제 메뉴를 조회 대상에서 제외하거나 모두 기본 단위로 채워 누락 0건이라고 보고하지 마.

일부 메뉴 수정, 후보값 생성, 경고 UI 추가, Excel 보완만으로 완료하지 마. 정상적인 신규 메뉴 등록 후에는 별도 수동 매핑 작업 없이 첫 판매부터 유효한 실제 승인 프로필이 적용되어야 한다.

2. 기존 전체 메뉴 매핑 완성

메뉴 마스터를 기준으로 실제 restaurant_id와 소속 restaurants.tax_entity_id를 대조하고 승인 프로필을 일괄 조회해.
- 판매 이력과 무관하게 등록 메뉴 전체를 점검한다.
- 메뉴 표시 필드만 채워졌지만 승인 프로필이 없는 경우도 누락으로 판정한다.
- 승인 프로필이 있어도 현재 만료되었거나 지점/법인이 다르거나 판매 시점에 적용되지 않으면 정상으로 판정하지 않는다.
- 기존의 유효한 승인명·단위·승인 이력을 보존한다.
- NULL 만료일은 무기한 유효이며 기간은 [effective_from, effective_to)로 일관되게 처리한다.

실제 POS name_vi를 계산서명 원본으로 사용하고, 단위는 기존 유효한 승인 또는 검증된 품목별 판매 단위에서 가져와.
일반 식당 품목의 Phần, 음료 및 콤보 등의 기존 별도 단위를 구분하고 전체 메뉴에 Phần을 일괄 대입하지 마. 확인할 수 없는 원본정보는 실제 자료나 메뉴 관리 입력으로 해결하고 임의 번역·추정으로 승인하지 마.

Super Admin 화면에서 전체 메뉴의 매핑 상태를 조회하고 검토·일괄 승인할 수 있게 해. 승인 프로필과 menu_items의 invoice_name_vi/invoice_unit_name은 기존 approve_invoice_mapping_batch RPC의 검증·기록 계약을 통해 함께 저장해.

소스의 20261012030000_sales_invoice_initial_mapping.sql에는 2026-10-11 하루만 유효한 초기 승인이 있으므로 현재·미래 유효기간도 점검해. 기존 유한기간 승인 이력을 무기한으로 덮어쓰지 말고, 필요한 현재·향후 승인을 실제 새 기록으로 추가해.

과거 판매 시점 적용과 앞으로의 유효기간을 구분해. 과거 적용에는 실제 승인 근거와 기록을 남기고 기간 중첩을 막아. 승인 시각은 실제 서버 기록 시각이며 과거 적용일과 혼동하지 마.

3. 신메뉴 자동 매핑과 변경 연동

실제 메뉴 생성·복제·Excel 가져오기·일괄 수정·재활성화 경로를 모두 찾아 공통 서버 로직으로 연결해. Flutter 화면에서 저장 후 별도 호출하는 방식에만 의존하지 마.

Super Admin이 실제로 승인한 자동 매핑 정책을 등록·관리할 수 있게 해.
- 계산서명 원본, 품목별 단위 규칙, 적용 지점/법인, 유효기간, 정책 버전과 승인 근거를 명시한다.
- 유효한 정책과 필수 원본정보가 있는 정상 메뉴는 등록 저장 과정에서 실제 메뉴별 승인 프로필과 표시 필드를 자동으로 생성한다.
- 메뉴 생성과 필수 매핑 저장을 원자적으로 처리한다. 대량 작업은 배치별 원자성과 중단 후 재시도 안전성을 보장한다.
- 자동 매핑은 후보나 대기 상태만 만드는 것으로 끝내지 않는다.
- 원본정보나 적용 가능한 정책이 부족한 경우 등록 단계에서 구체적인 입력 오류를 보여줘 누락된 정상 등록을 예방한다. 기존 거래의 결제 자체는 매핑 누락으로 막지 않는다.

현재 승인 RPC의 Super Admin 권한 제한을 일반 메뉴 편집 권한으로 풀지 마. 일반 권한의 메뉴 등록에서도 승인된 정책을 서버가 적용할 수 있도록 정책 적용 경로를 마련하되, 기존 승인 RPC의 범위·기간·검증 로직을 공유해.

실제 정책 승인자, 정책 ID/버전, 실제 등록·실행자, 서버 기록 시각, 근거를 구분해 기록해. auth 문맥을 조작하거나 임의의 Super Admin을 승인자로 지정하지 마. 가짜 프로필 UUID나 인간이 승인한 것처럼 꾸민 이력을 만들지 마.

복제 메뉴에는 새 메뉴 ID와 대상 지점/법인에 맞는 실제 프로필을 생성해. 원본의 프로필 ID나 승인자·승인 시각을 그대로 복사하지 마.

계산서명·단위가 실제로 변경되면 새 버전의 승인 프로필을 생성하고 이전 기간을 정확히 종료해. 과거 판매 스냅샷은 당시 승인 버전을 유지해. 가격·이미지·표시 순서처럼 매핑과 무관한 변경에는 중복 승인을 만들지 마.

미래 매핑은 특별한 만료 사유가 없는 정상 정책에서 effective_to=NULL로 유지해. 하루짜리 매핑으로 신메뉴가 다음 날 다시 누락되는 구조를 만들지 마.

전체 판매 대상의 필수 정보를 한 번에 검증해 첫 오류에서 중단하지 말고 메뉴별 누락 원인과 영향받은 영수증 전체를 보여줘.
이 재현 사례에서는 ‘누락 메뉴 3종 / 품목 행 5개 / 영수증 5건’과 각 영수증 내부 품목 순번을 별도로 표시해. 전체 조회에서 추가 문제가 발견되면 그 결과도 포함해.

메뉴 마스터 전체의 매핑 완전성 검증과 선택 영업일 판매 행 검증을 모두 구현해. 선택 영업일에 문제가 없다는 이유로 미판매 메뉴까지 정상이라고 판단하지 마.

결제는 MISA 매핑 누락 때문에 막지 말고 비동기 계산서 상태에서 수정 대기와 원인을 표시해.

5. 스냅샷과 이미 처리된 신고 보호

실제 승인 완료 후 아직 미발행이며 외부 처리 보호 대상이 아닌 스냅샷만 revalidate_meinvoice_export_snapshots로 갱신·재검증해.

이미 발행/전송된 영수증, 사용자가 수동 완료한 날짜, 자동화에서 별도 수정 Excel로 처리한 날짜는 재발행하거나 원본을 덮어쓰지 마. 기존 보호 기록과 실제 증빙을 확인하고 갱신·제외·보호 건수를 구분해.

오늘의 Excel 보완에는 원장의 실제 베트남 메뉴명과 기존 식당 품목 단위 Phần을 사용했고 수량·금액·VAT·연락처를 대조했다. 실제 POS 승인 프로필 ID는 꾸며 넣지 않았다. 상세 수정 행은 수정명세 JSON과 Excel의 ‘수정 내역’ 시트에 남겼다.

이 Excel 보완은 POS 승인 등록이나 미래 매핑 완료를 대신하지 않는다. 해당 날짜의 신고 보호와 별개로 전체 메뉴의 현재·미래 매핑을 완료해. 증빙 파일이 없으면 파일명·해시·처리 결과를 추정해 만들지 마.

6. Excel 및 금액 계약 유지

Hóa đơn GTGT 시트의 8행 A:Q 기존 17열 계약을 유지해.
- A의 인보이스 순번은 해당 인보이스의 모든 품목 행에 기록한다.
- 일반 정보 B:J는 첫 품목 행에만 기록하고 이어지는 행은 실제 빈 셀로 만든다.
- K 품목명, L 단위, M 수량, N 할인 반영 단가, O 공급가액, P VAT율, Q VAT액을 모두 기록한다.
- 할인 열이 없으므로 출력 단가는 공급가액/수량으로 계산한다.
- 원단가·할인·원장 ID·실제 승인 메타데이터는 부속 원장에 보존한다.
- 제공된 고객 이메일/전화번호를 유지하고 일반 영수증의 빈값을 허용한다.

TM/CK 결제 구분, 원장 금액, 수량, 콜라·환타 등의 기존 8%/10% 판정과 콤보 세율 분리를 바꾸지 마. 기존 반올림 계약을 지키고 공급가액+VAT가 원장 결제금액과 일치하는지 검증해.

Photo는 기존 8% 업로드 계약과 Dịch vụ chụp ảnh / Lần을 유지해. Photo 자동 수집을 다시 활성화하거나 배송비 품목을 추가하지 마.

7. 집합 처리·대량 입력·멱등성

메뉴·지점/법인·승인 프로필·영수증 관계는 집합 기반 SQL/RPC 또는 사전 일괄 조회로 처리해. 클라이언트뿐 아니라 SQL 함수와 트리거 내부에서도 메뉴마다 반복 조회·승인하는 N+1 구조를 확인하고 해결해.

현재 InvoiceMappingImport.parse는 입력 전체가 100건을 넘으면 거부한다. 전체 메뉴 점검·가져오기는 100건을 넘는 정상 입력을 지원하고, resolve_invoice_mapping_scope·approve_invoice_mapping_batch·재검증 등 제한된 RPC 호출만 각각 100건 이하로 나눠 처리해.

지점/법인별로 배치를 분리하고 동시 호출 상한을 명시해. 서버 페이지 제한 때문에 뒤쪽 메뉴가 누락되지 않게 안정적인 페이지 처리와 전체 건수 대조를 구현해.

동일 요청 재시도에서 승인 프로필·버전·유효기간·재검증 작업이 중복되지 않게 해. 매번 새 UUID나 현재 시각을 생성해 멱등성을 깨뜨리지 마. 부분 완료 후 재개와 동시 등록·동시 승인도 안전하게 처리해.
