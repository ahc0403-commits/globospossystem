# 분식클럽 KDS 조회 제한·성능 검증과 적용

2026-10-23, 베트남 시간. 사용자 승인 범위: 분식클럽부터 조회 범위와 동시 요청 제한을 지켜 수정하고 실제 데이터 규모·동시 단말 조건으로 검증한 뒤 적용.

## 변경

기존 완료내역 조회는 트레이에서 중앙값 8.063초와 100% 오류를 기록했다. 완료내역을 기다리는 동안 다음 화면 갱신이 잠기는 구조를 분식클럽에서 제거한다. [이전 운영 조사](KDS_HANDOFF_LATENCY_AUDIT_AND_PLAN_20261023.ko.md)의 시간은 당시 운영 API 값이며 아래 격리 시험과 직접적인 전후 비교 표본은 아니다.

- 분식클럽의 현재 카드 갱신 1개와 보조 조회 1개를 독립 직렬화한다. 단말당 동시 읽기는 최대 2개다. 이력·타이밍·모드 조회는 보조 1개를 공유한다. 중복 클릭/갱신은 합치고 오래된 타이밍 응답은 버린 후 한 번 다시 읽는다.
- 이력은 탭 진입/새로고침/페이지 이동 시만 조회한다. 기본 50건, 서버 상한 100건이며 `(completed_at, queue_id)` 커서를 사용한다. 매장·현재 베트남 날짜·배정 station/층/영역을 서버에서 제한한다. 클라이언트는 현재 페이지 하나만 보관하고 실패 시 이전 페이지를 유지한다. 계정·매장·세션·배정·날짜가 바뀐 응답은 버린다.
- 큐별 반복 집계 대신 당일 큐/이벤트를 집합 집계한다. 상세 품목·콤보·직접 음료·타이밍·포장·메뉴 선택 스냅샷은 요청된 큐/주문 ID로만 보강한다. 관계별 선집계로 다중 JOIN 곱셈을 막는다. 기존 부분 인덱스 조건을 사용하며 신규 인덱스는 추가하지 않는다.
- 이미 열려 있는 구버전 분식클럽 화면의 기존 이력 RPC도 최신 100건으로 제한해 서버 병목을 줄인다. 새 50건 페이지 UI는 새 웹 버전을 읽어야 한다.
- 주방→트레이→층 수량 원장·명령 RPC·배정·workflow·rollout을 변경하지 않는다. 다른 매장은 기존 함수로 분기한다. 전가복은 active 경로와 트레이 없음, 저장 층/고객 층 매핑을 유지한다.
- 기존 2초 음성 묶음과 25~35초 복구 주기는 이번 변경에 포함하지 않는다.

## 실제 규모와 격리 시험

운영에서 개인정보 없이 집계한 초기 규모는 당일 3건을 포함한 전체 큐 4,463건, 최근 7일 628건, 하루 최대 117건이다. 주문당 품목 평균 4.45개·p95 9개·최대 15개, 활성 역할은 주방·트레이·1F·2F의 4개다.

운영 **스키마·함수·인덱스만** 추출해 격리한 PostgreSQL 17.6에 합성 행을 넣었다. 고객/직원/주문 데이터는 복사하지 않았다. 위 품목 분포와 오늘 120건을 고정하고 과거 큐 4,463→5,000→50,000건으로 늘렸다. 최종 품목 원장은 약 22.3만 행이다. 축소 스키마 SQL 회귀에서는 오늘 300건까지 검증한다.

DB CPU 2개/메모리 2GiB, PostgREST CPU 1개/512MiB, pool 10개다. HTTP로 주방·트레이·각 층 역할을 4/8/40단말에 배치했다. 각 단말의 두 읽기 경로가 5회 연속 config→snapshot과 history→timing을 반복하고 20~60ms 간격으로 동시 시작하는 집중 부하다. 총 3,120 HTTP 요청, 오류 0건, 단말당 최대 동시 읽기 2개를 확인했다. 실제 현장 Wi-Fi·물리 태블릿 시험은 아니다.

활성 배정 4개로 구성한 4단말 시험에서는 이력 p95 65~161ms, 현재 카드 p95 120~149ms다. 8대 이력 p95는 280~467ms이고, 40대 집중 부하에서는 1.67~2.66초다. **40대에서 이력 300ms 목표를 충족한 것으로 판정하지 않는다.** CPU/풀 대기까지 포함된 격리 시험이며 현장 전달 시간이나 운영 처리 용량 보증으로 해석하지 않는다.

이력 최대 응답은 268,002 bytes(50건), 현재 카드 최대는 586,750 bytes(오늘 120건)였다. Docker 표본 메모리 최고값은 DB 451.4MiB, PostgREST 171.5MiB다. 이는 shared/cache를 포함한 컨테이너 표본이며 Flutter heap 측정이 아니다. Flutter 상태는 50건 페이지 교체/51건 응답 거부를 검사했다.

50,000건에서 nested `auto_explain ANALYZE/BUFFERS` 36개를 수집했다. 당일 큐는 120행, 당일 완료 이벤트는 1,602행을 읽었고, 상세 보강은 선택한 50개 큐/주문에 대한 인덱스 읽기로 제한됐다. 검사 대상 업무 테이블의 단일 scan node에서 검사한 행은 10,000행 미만이었다. 초기 수정에서 발견한 과거 품목 223,034행 전체 스캔은 요청 주문 ID 사전 조회와 부분 인덱스 조건 적용 후 사라졌다. 인덱스 nested-loop의 행별 접근을 별도 원격 API 호출이나 항목별 집계와 혼동하지 않는다.

## 검증

- 실제 스키마에서 구/신 함수 결과 동등성: 4역할, 다중 담당 영역, 수량·당일/완료 조건·취소/재개, 직접 음료/콤보/옵션 스냅샷/포장/요구사항, snapshot header/포장 task를 비교한다. 새 tray 순서 메타데이터 외 기존 계약은 일치한다.
- 키셋 동률/이전·다음 페이지/범위 오류/미인증·다른 매장 거부, 기존 RPC 최대 100건을 검사한다.
- 완료내역 지연·HTTP500·40회 중복 갱신 중에도 현재 카드 갱신, 배정 변경 응답 폐기, 이력 오류 보존, 오래된 이력의 중복 알림 방지, 오래된 보조 응답 폐기와 null 완료 타이머 해제를 Flutter 회귀로 검사한다.
- rollback→기존 함수 사전조건 재확인→재적용→동등성 검사를 실제 스키마에서 통과했다.
- 상세 지표와 재현 정보: [evidence.json](../measurements/bunsik-kds-bounded-20261023/evidence.json), 같은 폴더의 HTTP·실행 계획·scan·메모리 JSON.
- 재현: `bash scripts/test_bunsik_kds_history.sh`; 전체 스키마 부하: `bash scripts/measure_bunsik_kds_history.sh <schema-only.sql> <output-dir>`; 최종 전체 검사: `bash scripts/check_repo.sh`.
