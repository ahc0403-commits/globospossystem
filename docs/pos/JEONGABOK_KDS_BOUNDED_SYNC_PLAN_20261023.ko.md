# 전가복 KDS 제한된 일괄 조회·알림 개선안

2026-10-23 베트남 시간. **설계·운영 읽기 점검이며 구현·배포 완료 문서가 아니다.** 사용자의 “전가복에는 왜 적용안하냐”에 대한 후속 구체화다. 분식클럽은 PR #622로 먼저 적용한다.

## 현재 증거

전가복은 active revision/Broadcast로 동작한다. `KdsRealtimeSync.catchUp()`이 change마다 `await onChange()`를 실행하고, provider가 주문마다 `get_kds_ticket_v2`를 순차 호출한다. 동일 주문도 앞선 요청이 끝난 후 다음 change에서 다시 읽는다. 같은 주문의 진행 중 요청만 공유하므로 이 반복은 없어지지 않는다.

기존 24시간 HTTP 집계에서 두 층의 단건 조회 p50은 126/173ms, p95는 700/710ms다. 표본은 359/16건으로 두 번째 층의 혼잡 성능을 확정하기에는 작다. 버튼→표시/첫 음성 전체 시간은 측정하지 않았다.

추가 운영 집계(13:47): 과거 큐 80건·오늘 15건·최근 7일 하루 최대 38건, 품목 평균 4.09개/p95 9개/최대 22개다. 활성 배정은 주방 1개·저장 2F 1개·저장 3F 2개다. 배정 수는 현재 접속 중인 물리 단말 수가 아니다. 같은 층을 두 계정이 동시에 읽는 조건을 포함해야 한다.

저장 2F의 초기 bootstrap을 읽기 전용으로 한 번 실행한 DB 시간은 331.675ms, 현재 카드 13개·완료내역 12개·JSON 97,303 bytes였다. HTTP·렌더링·음성·p95 측정이 아니다. 증거는 `docs/measurements/kds-handoff-20261023/jeongabok-followup.json`이다.

## 변경 경로와 상한

| 경로 | 수정안 |
|---|---|
| delta | 제어 이벤트 경계 안에서 queue ID 중복 제거, 일반 invalidation 묶기 |
| ticket | set-based batch RPC 신설. 최초 배치 50개·서버 입력 상한 100개, 배치 순차 실행 |
| SQL | 허용된 큐/주문 ID만 사전 조회. 기본/콤보/직접 음료·이벤트를 관계별 집계 |
| 동시성 | foreground/bootstrap·watchdog·catch-up 읽기 coordinator 하나로 직렬화. 최대 읽기 1개 |
| 알림 | 데이터 적용 직후 시각 알림. 음성은 첫 수신 기준 최대 500ms 묶고 뒤 이벤트가 timer를 연장하지 않음 |
| 유실 복구 | 가벼운 revision/config 확인 5초±0.5초 목표. 부하 검증 후 적용 |
| 이력 | 필수 bootstrap에서 분리하고 현재 날짜·배정 영역/커서 페이지로 별도 검증 |

새 RPC는 현재 사용자/배정, 전가복, 활성 세션, 현재 베트남 영업일, 담당 층/영역을 서버에서 확인한다. 입력은 중복 제거 전에도 길이를 검사한다. SQL 내부에서 기존 단건 함수를 큐마다 호출하는 구현을 사용하지 않는다. 여러 일대다 JOIN으로 행이 곱해지지 않게 하고 기존 부분 인덱스 조건을 지킨다.

요청한 각 queue ID에 ticket 또는 명시적 null(tombstone), 읽은 revision을 반환한다. 다른 층/매장·종료 세션·층 비대상 배달/픽업의 제외 계약을 보존한다. 단일 주문의 품목을 임의로 자르지 않는다. 50개 배치의 실제 bytes를 먼저 재고 1MiB를 넘으면 배치를 25개 등으로 줄여 재검증한다.

고유 주문 U개이면 기본 요청량은 **delta 1회 + ceil(U/50) ticket batch**다. 100개 change의 고유 주문이 10개면 2회, 100개면 3회다. 모두 순차 실행하며 watchdog이 처리 중 조회를 중복 실행하지 않는다. 정상 revision 확인은 D단말에서 약 D/5 RPC/초다(4개 0.8회/초, 40개 8회/초). 변경 조회는 별도다. 일시 오류만 최대 3회·총 15초, backoff/jitter로 재시도하고 권한/입력 오류는 반복하지 않는다. 실패 후 단건 조회를 무더기로 보내는 fallback을 만들지 않는다.

## 정합성과 운영 계약

1. `bootstrap_required`, 세션/설정 변경, leftover 포장 이벤트는 경계와 순서를 보존한다. 일반 ticket invalidation만 합친다.
2. 모든 ticket/tombstone을 성공 적용한 뒤 `scanned_through_revision`을 저장한다. 부분 실패로 cursor를 앞당기지 않는다. 기존 50페이지 상한·revision 검증을 유지한다.
3. bootstrap·배정·세션·영업일 변경 전 응답은 버린다. 오래된 revision이 최신 카드를 덮지 못하게 한다. null ticket은 카드/해당 이력 항목을 제거한다.
4. 추가 주문·원복·부분 전달·취소의 수량 차이는 서버 원장으로 계산한다. 중복 revision/재접속은 같은 수량을 다시 알리지 않는다.
5. 전가복에 트레이/체커를 만들거나 `jgbt_tray1`을 재활성화하지 않는다. 고객 1F/2F는 저장 2F/3F 매핑을 보존한다.
6. 주방 항목 탭은 조리 시작만, 명시적 층 전달은 `kitchen_done`과 해당 수량의 준비만 기록한다. 배달/픽업 준비는 테이블 층에 알리지 않는다. 직접 음료·콤보·포장·음성 언어/fallback을 보존한다.
7. 수량 명령/멱등성을 바꾸거나 서버 확인 전 준비 상태를 만들지 않는다. 다른 매장의 batch 기능은 기본으로 켜지 않는다.

## 검증과 적용

수정 대상은 `kds_realtime_sync.dart` gateway/catch-up, provider의 delta/읽기 coordinator, screen의 알림 timer, 신규 batch SQL이다. 현재 유효 단건 reader와 실제 schema-only export를 결과 동등성 기준으로 사용한다.

- 활성 배정 4개를 모델로 4/8/40단말, 동일 저장 3F의 동시 2계정 조건을 포함한다. 물리 단말의 현재 접속 대수는 별도 확인한다.
- 실제 80건·하루 최대 38건, 평균 품목 4.09/p95 9/최대 22개를 반영하고 과거 큐 5,000/50,000건·100개 change·중복/동시 주문으로 확장한다.
- 요청 수, 읽기 동시성 1, SQL 집계/스캔 행, bytes, DB buffers·컨테이너/Flutter heap, p50/p95/p99를 측정한다. 인덱스는 실행 계획과 쓰기 비용 근거가 있을 때만 추가한다.
- 누락/중복/역순, catch-up 중 재배정, tombstone, 세션/날짜 경계, 복귀/오프라인 재전송, 부분 수량·원복·음료·콤보·포장을 검사한다.
- 데이터 반영→시각 알림 p95 100ms 이하, 음성 묶음 실행 첫 수신부터 최대 500ms, 정상 REST 전경의 유실 복구 6초 이내를 목표로 한다. 버튼→대상 카드 p95 1.5초 목표는 실제 단말 계측으로 별도 판정한다.
- 새 서버 RPC→지원 클라이언트→전가복만 활성화 순서로 적용한다. 기존 active rollout을 legacy로 바꾸거나 트레이를 복구하지 않는다.
- 관련 회귀→전체 `check_repo.sh`→정확한 SHA 필수 CI→공식 배포→층별 운영 읽기·현장 표시/가청 확인 순서를 따른다.

이 문서는 전가복 성능 개선 완료 증거가 아니다. 분식클럽의 검증 수치를 전가복에 대입하지 않는다.
