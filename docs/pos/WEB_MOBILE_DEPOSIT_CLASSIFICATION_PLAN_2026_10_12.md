# 웹·모바일 계좌이체 및 익일 법인통장 입금액 구분 개선계획

작성일: 2026-10-12 / Asia/Ho_Chi_Minh. **계획 문서이며 앱 구현·운영 변경·배포 완료 보고가 아니다.** 전역·프로젝트 지침을 확인했고, 문서 경로에 추가 하위 지침은 없었다. 기존 사용자 변경과 앞선 QR 보완 작업은 보존한다.

## 1. 확정한 표시 기준

사용자의 마지막 정정을 반영해 **포토도 내일 입금할 매출**로 분류한다. 웹과 모바일은 아래 세 금액을 각각 표시한다.

| 항목 | 화면의 주요 제목 | 금액 기준 | 입금일/의미 |
|---|---|---|---|
| 고객 계좌이체 | 고객 계좌이체 매출 | 선택 기간의 BANKTRANSFER 실제 결제 부분 금액 | POS 수금 기록. 직원이 다시 입금할 현금에 합산하지 않음 |
| 포토 | 포토 · 내일 법인통장 입금 예정액 | 선택 매출일의 중복 제거된 수동 등록 매출 | 매출일 D의 다음 날짜 D+1 |
| 분식클럽 현금 | 분식클럽 현금 · 내일 법인통장 입금 예정액 | 마감 실사 현금 − 마감에 유지할 시재 | 마감일 D의 다음 날짜 D+1 |

예: **2026-10-12 매출/마감 → 2026-10-13 입금 예정**. 과거 날짜를 선택하면 ‘내일’ 대신 ‘2026-10-13 입금 예정’처럼 실제 날짜를 표시한다. 날짜는 브라우저·휴대폰의 로컬 시간대가 아닌 베트남 영업일로 계산한다. 수동 등록을 늦게 했다는 이유로 원래 매출일이나 입금 예정일을 오늘/내일로 다시 쓰지 않는다.

분류별 금액을 먼저 보여주고, 아래에 **익일 입금 예정 합계 = 포토 + 분식클럽 마감 현금**을 보조 정보로 제공한다. 고객 계좌이체 금액은 이 합계에서 제외한다. 서로 다른 법인/입금 예정일의 금액도 합치지 않는다.

## 2. 현재 코드에서 확인한 문제

1. `DailySalesSummary.nextDeposit`은 `photoGross + restaurantCash`다. 분식클럽의 실제 마감 입금액이 아니라 현금 결제 매출을 더한다. 환불·배달비·과부족이 있으면 실제 입금할 돈과 달라진다.
2. 매출신고 화면은 한 개 ‘익일 매출 입금 예정액’ 안에 포토와 현금을 합쳐 보여준다. 계좌이체는 이 영역 안의 작은 문구라 주요 금액으로 구분하기 어렵다.
3. 매장 보고서의 상단 요약에는 계좌이체 전용 지표가 없다. 모바일의 결제수단 세부 목록과 날짜별 넓은 표에는 계좌이체가 존재하지만, 목록 아래나 가로 스크롤에 의존한다. 따라서 **서버에 분류가 없는 문제와 주요 화면에서 보이지 않는 문제를 구분해 수정**한다.
4. 마감은 `depositTotal = countedCashAmount - openingCashAmount`를 이미 계산하지만 제목이 ‘입금 총액’이고 입금 예정일·법인 계좌를 연결하지 않는다. 미마감은 0을 반환해 실제 0원과 미확정 상태를 혼동할 수 있다.
5. 통합 `depositConfirmed`는 포토 등록 완료와 모든 매장 마감 완료를 함께 요구하고, 실사 입금액과 현금 매출이 같아야 확정한다. 포토 미등록이나 정상적인 환불·현금 지급 때문에 분식클럽의 확정 금액까지 잠정으로 표시될 수 있다.
6. 마감 입력창은 현금 배달비 회수 값을 보여주지만 `_expectedCash` 계산에는 포함하지 않는다. 이번 계획에서는 서버 preview·마감 계산·화면의 현금 조정 의미를 대조하고 하나의 기준으로 맞춘다.

운영 DB 읽기 확인: `get_pos_daily_sales_summary(date)`에 `restaurant_bank_transfer`와 공통 `deposit_date = D+1`이 존재한다. 포토 원본에는 매출일, 마감에는 실사 현금·시재·환불·배달비 지급/회수 컬럼이 있다. 모바일 현장 화면을 직접 재현한 것은 아니며, 위 UI 문제는 현재 소스 확인 결과다.

## 3. 금액과 상태의 공통 계약

### 계좌이체

- 순수 이체와 현금+이체 혼합 결제 모두 `amount_portion`을 우선 사용한다. 주문 총액을 각 수단에 중복 합산하지 않는다.
- 현금, 카드, 전자지갑, 외상, 바우처와 계좌이체를 구분한다. 의미가 불명확한 QR을 계좌이체로 임의 분류하지 않는다.
- ‘POS에 계좌이체로 기록된 금액’과 ‘은행에서 확인한 실제 입금’을 구분한다. 은행 대조를 실행하지 않은 금액을 ‘은행 입금 확인 완료’로 표시하지 않는다.
- 모바일에서도 0원인 계좌이체 항목을 표시한다. 조회 실패/누락은 0원이 아닌 ‘확인 필요’다.

### 포토

- 현재 Super Admin의 Moers Excel 수동 등록 경로를 유지한다. 자동 수집·스케줄·복구 기능을 재도입하지 않는다.
- 동일 원천 거래 재등록은 한 번만 합산한다. 파일 업로드 횟수나 등록 응답 합계를 다시 더하지 않고 저장된 원천 거래를 집계한다.
- 자료가 완전하면 ‘등록 완료’, 일부 매장/자료가 빠지면 ‘등록 확인 필요’로 표시한다. 확인된 등록액은 별도로 보여주되 전체 확정액과 혼동하지 않는다.
- 성공적으로 등록한 0원과 미등록/불완전을 구분한다. 누락 매장 수와 확인 경로를 표시하며 포토 누락 때문에 분식클럽 금액을 숨기지 않는다.

### 분식클럽 마감 현금

- 입금 예정 확정액은 **마감 실사 현금 − 시재**다. 현재 계약의 `opening_cash_amount`를 시재 기준으로 사용하고, 시재 정책 자체를 임의 변경하지 않는다.
- 현금 매출은 비교용 별도 항목이다. 예상 현금은 기존 마감 업무 계약에 따라 `시재 + 현금 수금 − 현금 환불 − 현금 배달비 지급 + 현금 회수`를 대조한다. 기존 지급 필드와 새 지급 필드가 같은 돈을 나타내면 중복 차감하지 않는다.
- 환불·지급·회수는 실사 현금에 이미 반영돼 있으므로 확정 입금액에서 다시 빼거나 더하지 않는다. 과부족은 `실사 현금 − 예상 현금`으로 별도 표시한다.
- 수동 마감 전: ‘마감 전 · 예상액’, 확정 금액은 비어 있는 상태로 둔다. 자동 마감만 있는 경우에도 현금 실사가 확인되지 않았다면 확정하지 않는다.
- 수동 마감 후: ‘마감 확정’. 과부족이 있으면 ‘마감 확정 · 차이 확인 필요’를 함께 표시한다. 마감 완료와 차이 유무는 독립된 상태다.
- 실사 현금이 시재보다 적으면 부족액을 보존하고 확인 필요 상태를 표시한다. 부족액을 임의로 정상 0원 입금으로 바꾸지 않는다.
- 마감 이후 원장 변경이 발견돼도 보관한 실사 마감을 자동으로 다시 계산하지 않는다. 마감 스냅샷·최신 원장·차이를 구분한다.
- 여러 매장 중 일부만 마감했으면 마감 완료 매장의 금액과 미마감 매장 수를 함께 표시한다. 전체 확정액을 완성된 것처럼 표시하지 않는다.

공통 모델에는 계좌이체 금액, 포토 등록액/확정액/완전성, 분식클럽 현금 매출/마감 입금액/마감 상태, 입금 예정일, 과부족, 조회 시각을 각각 둔다. 하나의 `nextDeposit`·`depositConfirmed`로 세 정보를 표현하지 않는다.

## 4. 웹·모바일 화면 계획

### 매출신고 / 법인 매출 요약

- 날짜·법인 선택 바로 아래에 세 주요 카드를 둔다. 순서: **고객 계좌이체 → 포토 익일 입금 → 분식클럽 현금 익일 입금**.
- 각 카드에 제목, 전체 금액, 상태, 매출/마감일을 표시한다. 입금 대상 카드에는 예정일과 법인 계좌도 표시한다.
- 합계는 두 입금 대상의 완전성이 충족된 때 확정 표시한다. 한쪽 자료가 없으면 확인된 금액과 누락 상태를 구분하고, 다른 쪽 카드의 상태는 유지한다.
- 포토 확인 버튼은 기존 수동 등록 화면으로, 현금 확인 버튼은 해당 매장·마감일의 마감 상세로 연결한다. 고객 계좌이체는 해당 범위의 결제 내역으로 연결한다.
- 계좌 설정 버튼과 긴 계산서 작업 버튼은 주요 금액 뒤에 둔다. 현재 법인 계좌 관리 권한은 유지한다.

### 매장 보고서 / 일일 마감

- 보고서 상단에 현금·계좌이체·카드·기타 수단의 명확한 요약을 추가한다. 시간대 분석·예외 목록보다 먼저 볼 수 있게 한다.
- 분식클럽 마감 입력창에 ‘마감 후 [날짜] 법인통장 입금 예정액’ 미리보기를 추가한다. 저장 성공 후 확정 금액·예정일·수취 법인 계좌를 표시한다.
- 마감 이력 카드와 웹 표 모두 ‘입금 총액’을 ‘법인통장 입금 예정액’으로 구체화하고 예정일을 함께 표시한다.
- 주간/월간 보고서는 해당 기간의 결제수단 금액과 날짜별 입금 예정 내역을 구분한다. 여러 마감일을 한 번의 ‘내일 입금’으로 표현하지 않는다.
- 일반 매장 권한에는 접근 가능한 매장의 금액만 표시한다. 다른 법인/매장의 포토 자료를 추가로 노출하지 않는다. 고객 결제 화면에 내부 매출 요약을 노출하는 변경도 포함하지 않는다.

### 반응형 규칙

- 같은 Flutter 금액 모델과 카드 위젯을 웹·모바일에서 사용한다. 플랫폼별 계산식을 따로 만들지 않는다.
- 휴대폰은 카드 1열, 태블릿은 공간에 따라 2열, 넓은 웹은 3열이다. 실제 컨테이너 폭과 기존 `PosLayoutSpec`으로 결정한다. 큰 글씨에서는 1열로 전환한다.
- 주요 금액과 예정일은 가로 스크롤·접기·툴팁에 의존하지 않는다. 긴 법인명·계좌명은 줄바꿈하고 금액을 잘라 표시하지 않는다.
- 360/375/390/412px 휴대폰, 768/1024px 태블릿, 1440px 웹과 글자 배율 1.0/1.3/2.0을 확인한다. 한국어·베트남어·영어에서 같은 의미를 유지한다.

## 5. 데이터 조회·성능·호환성

- 매출신고의 첫 요약은 기존처럼 **RPC 1회**로 법인별 은행이체·포토·현금 마감 정보를 받는다. 매장/법인/카드별 추가 RPC를 만들지 않는다.
- 지급수단, 포토 원본, 마감, 포토 등록 완전성을 각 집합에서 먼저 집계한 다음 매장/법인별로 결합한다. 결제 행 × 포토 행 × 마감 행이 곱해지는 JOIN을 금지한다.
- 기존 요약 함수의 법인별 상관 서브쿼리와 revision/fingerprint 계산도 점검한다. 이 경로를 사용하는 변경에서는 법인 목록 전체의 일괄 집계로 묶으며, 한 RPC라는 이유만으로 서버 내부 N+1이 없다고 판단하지 않는다.
- 매장 보고서는 기존 서버 집계 응답의 은행이체 값을 재사용한다. 필요한 마감 정보는 기존 마감 조회 또는 선택한 매장 목록의 배치 요약으로 받는다. 매장별 개별 조회 루프를 추가하지 않는다.
- 조회 범위는 선택 베트남 영업일·선택 법인·허용 매장이다. 기간은 기존 보고서 허용 범위로 제한한다. 최대 500개 매장을 한 집합으로 처리하고 상세는 100행 keyset 페이지, 병렬 요청은 최대 2개다. 요약을 위해 영수증·품목 전체를 다운로드하지 않는다.
- 기존 `(restaurant_id, closing_date)`, 포토 매출일/매장/원천 거래, 결제 일시·매장·수단 인덱스를 실제 실행계획으로 확인한 뒤 필요한 것만 추가한다. 완료된 마이그레이션은 수정하지 않고 후속 마이그레이션을 만든다.
- 동일 조회의 진행 중 요청을 공유한다. 캐시 키에는 사용자·권한 범위·법인·매장·조회 날짜·포토/마감 변경 버전을 포함한다. 열린 운영 화면의 캐시 유효기간은 최대 30초로 하고, 수동 등록·마감 성공 시 해당 날짜/범위만 갱신한다. 범위 변경 후 늦게 도착한 응답은 폐기한다.
- 계산서 XLSX의 A:Q 형식, 기신고 보호, VAT, `process_payment`, Office의 물리 매장 읽기 계약은 유지한다. 입금 안내 요약 때문에 판매 원본이나 기발행 자료를 다시 쓰지 않는다.
- 성능 검증 규모: 기준 5개 매장/일일 결제 1,000건, 확대 50개/10,000건, 상한 500개/100,000건. 동시 사용자 1명·20명에서 호출 수, 실제 읽은 행, 응답 크기, p50/p95, 클라이언트 메모리를 측정한다.
- 검증 목표: 최초 요약 1회, 요약 응답 128KiB 이하, 상세 100행/256KiB 이하. 요약 p95는 기준 1초·상한 3초를 목표로 하되 실제 운영 환경에서 확인한다. 목표값이며 이번 계획에서 측정하거나 통과한 수치가 아니다.

## 6. 구현 위치와 순서

## 7. 인수 기준

1. 웹·모바일에서 고객 계좌이체 금액을 독립 항목으로 즉시 구분할 수 있다. 0원, 로딩, 오류 상태도 구분한다.
2. 포토와 분식클럽 현금의 익일 입금액·예정일·상태가 각각 보인다. 계좌이체는 입금 예정 합계에 더해지지 않는다.
3. 합성 예: 포토 10,000,000, 고객 계좌이체 3,000,000, 현금 수금 2,000,000, 시재 5,000,000, 현금 환불 100,000, 지급 150,000, 회수 50,000, 실사 현금 6,750,000이면 예상 현금 6,800,000, 과부족 −50,000, **분식클럽 입금액 1,750,000**, 익일 합계 **11,750,000**이다. 이체 3,000,000은 별도 표시한다.
4. 포토 미등록/일부 등록/정상 0원/재등록, 분식클럽 미마감/자동마감/수동마감/과부족/시재부족, 혼합 결제, 여러 법인·일부 매장 마감, 자정과 과거 날짜를 검증한다.
5. 포토 미등록이어도 분식클럽 확정액이 보인다. 마감 전 0원을 확정 입금액으로 표시하지 않는다. 환불·배달비·회수를 두 번 반영하지 않는다.
6. 마감 스냅샷과 뒤늦은 원장 수정의 차이가 표시되고 과거 마감이 자동으로 바뀌지 않는다. 문구 변경으로 은행 입금 완료 상태를 만들지 않는다.
7. 기존 `daily_sales_report_service_test`, `daily_sales_report_screen_test`, `daily_closing_record_test`, `daily_closing_responsive_test`, `reports_daily_closing_refresh_test`, 포토 등록·결제 계약 SQL/Flutter 시험에 의미 있는 시나리오를 추가한다. 실제 화면의 금액·날짜·가로 넘침까지 확인한다.
8. 운영 배포는 정확한 pushed SHA의 필수 GitHub Actions 성공과 정식 `scripts/deploy_pos_production.sh`를 따른다. 모바일 브라우저와 실제 사용 중인 설치 앱을 각각 확인한다. 웹 서버만 배포하고 설치된 앱도 변경됐다고 판단하지 않는다.

## 8. 이번 작업의 완료 범위

현재 코드·관련 운영 함수/컬럼을 읽고 위 계획을 작성했다. 이번 요청으로 앱 소스·운영 데이터·배포 설정을 변경하지 않았고, 구현 테스트·은행 대조·실제 입금을 실행하지 않았다. 계획 문서의 날짜·산식·경로와 기존 변경 보존을 확인한다.
