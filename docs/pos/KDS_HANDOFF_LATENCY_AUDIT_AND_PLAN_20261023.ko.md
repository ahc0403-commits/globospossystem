# 분식클럽·전가복 오더 전달 지연 조사와 개선 계획

작성: 2026-10-23, 베트남 시간(UTC+7). 범위는 현황 확인과 계획 수립이다. 앱·DB·운영 설정을 변경하거나 배포하지 않았다.

## 판단

가장 먼저 해결할 문제는 **분식클럽의 완료내역 조회가 작업 화면 갱신을 오래 붙잡는 구조**다. 트레이는 최근 24시간 완료내역 요청 1,754건이 모두 HTTP 500으로 실패했고, 중앙값 8.063초였다. 층도 같은 경로가 느리다.

전가복은 이미 revision/Broadcast 방식으로 운영 중이다. 층의 개별 주문 조회 중앙값은 0.126~0.173초지만, 변경 이벤트마다 개별 주문을 순차 조회하는 구조, 2초 음성 대기, 누락 복구 주기에는 개선 여지가 있다.

**실제 버튼 입력 → 상대 단말 카드 표시·첫 음성까지의 전체 시간은 아직 확정할 수 없다.** 수신 화면의 렌더링·음성 시작 확인 로그가 없기 때문이다. 아래 값은 실제 운영 API 시간이며, 코드에서 확인한 추가 대기와 구분한다.

## 1. 확인 방법과 운영 기준

- 로그 기간: **10월 22일 11:50 ~ 23일 11:50**, 베트남 시간, 24시간.
- 대상: BunsikClub Binh Thanh와 JeonGabok Binh Thanh. SAMPLE 매장은 수치에서 제외했다.
- Supabase 운영 로그의 `response.origin_time`을 ms로 집계했다. 중앙값·p95는 `quantileExact`이며 오류 응답도 포함한다. p95는 요청 95%가 해당 시간 이하였다는 뜻이다.
- 로그의 인증 사용자 식별자를 현재 활성 station 배정과 메모리에서 연결해 매장·담당 화면을 구분했다. 원본 사용자 ID·IP·토큰·주문 내용은 결과물에 저장하지 않았다.
- 운영 DB에서 설정·적용 migration·유효 함수 정의·인덱스를 읽었다. 기존 핵심 쿼리는 `EXPLAIN`, 개선 방향의 축소 쿼리는 제한된 읽기 전용 `EXPLAIN ANALYZE`로 확인했다.
- 운영 웹 alias: `READY`, SHA `98b6cf3bbe38c8734e81c3719222a02018fb4527`, 배포 시각 10월 23일 09:28. 로컬 HEAD `58e0fa8f`와 관련 파일을 비교했다. provider·실시간 동기화·알림 타이머는 동일하며, 배포본에는 층 준비 카드의 시각 강조가 추가돼 있다. 각 현장 단말의 캐시 갱신 여부는 확인하지 않았다.
- 원본 집계·계획·유효 SQL 근거: [evidence.json](../measurements/kds-handoff-20261023/evidence.json).

운영 계약은 분식클럽 **주방 → 트레이 → 층**, 전가복 **주방의 명시적 층 전달 → 해당 층**이다. 전가복 트레이를 복구하지 않는다. 전가복 고객 표시 1F/2F는 각각 저장 층 2F/3F다.

## 2. 실제 운영 시간

### 분식클럽: 화면의 조회 병목

| 담당 화면 | 현재 주문 목록 p50 / p95 | 완료내역 p50 / p95 | 완료내역 실패 / 요청 |
|---|---:|---:|---:|
| 트레이 | 0.257 / 0.498초 | **8.063 / 8.111초** | **1,754 / 1,754 (100%)** |
| 층 1F | 0.214 / 0.433초 | **8.058 / 8.109초** | **1,287 / 1,827 (70.4%)** |
| 층 2F | 0.141 / 0.311초 | **4.390 / 7.642초** | **31 / 1,486 (2.1%)** |

주방도 완료내역 1,888건 전부 실패했고 p50 8.062초였다. 같은 기간 프로젝트 PostgreSQL 로그에 `canceling statement due to statement timeout`이 4,950건 있다. 이 DB 로그 건수는 프로젝트 전체이며 개별 실패 요청과 일대일로 연결한 결과는 아니다.

목록 자체는 먼저 표시하도록 구현돼 있다. 따라서 위의 8초가 모든 카드의 표시 시간이라는 뜻은 아니다. 다만 완료내역을 기다리는 동안 `_refreshing=true`가 유지되어 다음 전체 갱신이 대기한다. 새 카드·새 항목·스냅샷 보강과 일부 확인창 닫기가 지연될 수 있다. 이미 알고 있는 항목의 수량은 Postgres 이벤트로 직접 반영되는 예외 경로가 있다.

### 전가복: 현재 실시간 경로

| 수신 층 | 변경 목록 p50 / p95 | 개별 주문 p50 / p95 | 개별 주문 표본 |
|---|---:|---:|---:|
| 고객 1F, 저장 2F | 0.029 / 0.079초 | **0.126 / 0.700초** | 359건 |
| 고객 2F, 저장 3F | 0.032 / 0.094초 | **0.173 / 0.710초** | 16건 |

두 층 모두 위 조회 오류는 0건이었다. 고객 2F는 표본이 작아 혼잡 시간 성능을 대표한다고 보기 어렵다. Broadcast 이동·브라우저 스케줄링·실제 렌더링은 이 값에 포함되지 않는다. 여러 요청의 p95를 더해 전체 p95로 계산해서는 안 된다.

### 보내는 쪽의 서버 처리

| 작업 | p50 / p95 | 표본 |
|---|---:|---:|
| 전가복 주방의 일괄 층 전달 | 0.214 / 0.487초 | 62건 |
| 분식클럽 트레이의 일괄 층 전달 | 0.422 / 0.422초 | 2건 |

트레이 표본 2건은 참고값이다. 분식클럽 트레이에서 더 자주 사용한 개별 station 진행 요청은 205건, p50 0.125초·p95 0.293초이며 6건 실패했다. 실패의 업무상 사유와 통신 오류는 추가 분류가 필요하다. 일괄 전달 수치만으로 모든 클릭을 대표하지 않는다.

### 코드에서 확인한 추가 대기

- 인계·층 직접 음료·추가 주문 음성은 **화면 상태 반영 후 2초**를 모아 알린다. 새 알림이 들어올 때 타이머를 취소하고 다시 시작하므로 연속 접수에서는 2초보다 길어질 수 있다. 준비 항목의 깜빡임과 화면 전체 알림·음성의 시점은 다르다.
- 기존 경로의 전체 재조회와 active 경로의 revision watchdog 모두 **25~35초 간격**이다. 이벤트를 놓치면 다음 확인까지 대기한다. 이는 매번 25초를 기다린다는 뜻이 아니며, 네트워크·조회 대기·단말 절전이 더해지면 복구가 35초를 넘을 수도 있다.
- 네트워크 왕복과 TTS 음성 대기열·오디오 권한도 전체 체감 시간에 영향을 주지만 이번 조회로는 측정하지 않았다.

## 3. 확인된 원인과 한계

### A. 분식클럽 완료내역 조회: 과거 전체 큐에 반복 집계

운영 설정은 분식클럽 `legacy`, 전가복 `active`다. 분식클럽은 갱신마다 설정 → 목록 → 완료내역·타이밍 → 운영 모드를 읽는다. 쓰기 RPC를 제외하고 정상 legacy 갱신 1회에 외부 RPC 5회다. 완료내역 오류는 optional 경로에서 null로 처리되지만, 이미 소비한 약 8초는 갱신 잠금을 계속 차지한다.

유효 `get_emergency_station_today_completed_base()`는 매장의 과거 큐 전체에서 각 주문의 당일 완료 이벤트를 상관 집계한다. 이벤트 쿼리에 `restaurant_id` 동등 조건이 없고 큐 생성일 필터도 없다. 당일 생성일 필터는 바깥 wrapper가 결과를 만든 뒤 적용한다.

조사 시 분식클럽 큐는 총 **4,463건**, 오늘 **3건**이었다. 기존 집계 핵심부의 EXPLAIN은 큐 약 4,562건을 예상하고, 각 큐에 이벤트 Aggregate/Index Scan을 배치했다. 이벤트 인덱스 조건에 날짜만 있고 매장 키 조건이 없다. 이는 계획상의 반복 구조이며, 전체 함수의 실제 반복 횟수를 측정한 것은 아니다.

개선 방향을 확인하기 위해 매장·당일·단계 이벤트를 먼저 한 번 집계한 축소 SELECT만 읽기로 실행했다. 기존 인덱스로 이벤트 50행을 검사해 10행을 집계하고 큐 3건을 반환했으며, execution 2.882ms·shared buffer hit 43·read 0이었다. **전체 RPC·동등 결과 검증·동시 부하·개선 배포의 성과 수치가 아니다.** 현재 데이터가 적은 단일 시점의 방향 확인이다.

또한 `emergency_add_order_batch_timings()`는 항목별 LATERAL 이벤트 집계를 유지한다. API 한 번으로 감쌌다는 이유로 내부 N+1이 없다고 판단할 수 없다.

### B. 전가복: 변경마다 단일 주문을 순차 조회

`KdsRealtimeSync.catchUp()`은 변경 목록을 받고 각 변경에 `await onChange()`를 실행한다. 일반 변경은 `get_kds_ticket_v2(queueId)` 한 번을 다시 호출한다.

동일 주문의 진행 중 요청 공유는 있지만, 앞선 호출이 끝난 다음 도착한 같은 주문 변경까지 합치지는 않는다. 변경 E개에 기본적으로 delta 1회 + 최대 E회 ticket 조회가 이어지는 N+1 경로다. 동시에 여러 음식을 넘기거나 재접속해 변경이 쌓이면 지연이 누적될 수 있다. 이번 로그만으로 현장 증상의 각 발생 건이 이 경로 때문이라고 확정하지 않는다.

### C. 공통: 지연을 더하는 알림·복구·재조회

- 음성의 2초 debounce와 제한 없는 재시작.
- 이벤트 유실 때 느린 25~35초 복구 주기.
- 일괄 완료 명령 뒤 active에서도 전체 `load()`를 기다리는 경로.
- active bootstrap도 완료내역·타이밍을 먼저 계산한다. 일부 주방 경로는 계산 후 결과를 버리므로 불필요한 비용이 남는다.
- 수신 시각·실제 표시 시각·음성 시작·사용 중인 앱 SHA가 없어 전체 시간과 원인을 확정하기 어렵다.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| P0-1 | 활성 주문 갱신과 완료내역·통계 갱신을 분리 | 완료내역을 8초 지연/실패시켜도 새 카드·인계 수량·다음 갱신이 진행 |
| P0-2 | 완료내역 SQL을 매장·당일 이벤트 선집계와 큐·품목 일괄 조회로 교체 | 정확한 결과·권한 보존, 실매장 크기에서 timeout 0, 이력 첫 페이지 p95 300ms 이하 목표 |
| P1-1 | revision별 변경 주문을 모아 일괄 ticket RPC로 수신 | 100개 변경·중복 포함에서 delta 1회 + ticket batch 1회, SQL 내부 단건 함수 반복 없음 |
| P1-2 | 짧은 즉시 알림과 음성 묶기를 분리 | 데이터 반영 뒤 짧은 알림 p95 100ms 이하, 음성은 첫 알림 기준 최대 500ms 묶기 |
| P1-3 | 누락·복귀 복구를 가벼운 revision 조회로 변경 | 정상 REST 연결의 전경 단말에서 유실 이벤트 6초 이내 복구 목표 |
| P2 | 분식클럽 shadow 검증 후 active 단계 전환 | 트레이·층별 수량/카드/층 격리 일치, 성능과 현장 확인 후 전환 |

### P0: 분식클럽의 8초 병목부터 제거

1. 활성 카드의 데이터 읽기·적용과 완료내역/통계의 요청 상태를 분리한다. 이력 실패로 현재 완료목록을 빈 목록으로 덮거나 새 알림 판단을 초기화하지 않는다. 추가 주문 재개·원복 알림에 필요한 기존 완료 주문 기준 상태를 보존한다.
2. SQL은 `restaurant_id + 당일 event 범위 + station stage`로 완료 후보를 먼저 묶고 필요한 큐·품목·action만 집합 조회한다. 최종 wrapper의 당일 생성일 규칙도 앞단에 반영한다.
3. item·combo·floor-direct 이벤트를 ID 집합별로 각각 선집계하고 합친다. 여러 일대다 테이블을 직접 JOIN해 행이 곱해지지 않게 한다.
4. 이력은 기본 50건·상한 100건, `completed_at, queue_id` 키셋 페이지를 사용한다. 숨겨진 완료 이력을 화면 갱신마다 전부 재조회하지 않는다. 기존 함수의 반환 계약은 호환 유지하고 새 페이지 RPC로 전환한다.
5. 매장·사용자·station·담당 영역·영업일·세션·설정 버전을 캐시 키에 포함한다. 화면 내 이력 캐시는 완료·원복 이벤트와 날짜/배정 변경으로 무효화하고, 이력 화면 재진입 시 30초가 지난 페이지를 재검증한다. 동일 조회 진행 중 요청은 공유한다. 활성 준비 상태는 오래된 이력 캐시로 판정하지 않는다.
6. 전체 완료 이력은 bootstrap 필수 경로에서 분리하고, 쓰기 성공 후 해당 주문만 갱신한다. 확인창을 닫는 데 전체 이력 조회를 기다리지 않는다. 서버 확인 전 상대 층 준비를 만들어서는 안 된다.
7. 기존 매장·날짜 인덱스를 먼저 활용한다. 추가 복합/부분 인덱스는 개선 SQL의 실행 계획·읽은 행·쓰기 비용을 비교한 뒤 결정한다.

### P1: 전가복과 공통 실시간 경로

1. 새 `get_kds_tickets_v3(uuid[])`는 최대 100개의 고유 queue ID를 받는다. 매장·session·station·floor/area 권한을 서버에서 다시 제한하고, 관계별 선집계로 카드·타이밍을 반환한다. 내부에서 `get_kds_ticket_v2`를 ID별로 반복 호출하지 않는다.
2. delta 페이지의 ticket 무효화를 queue별로 합친다. control·session 변경·남은 음식 포장 이벤트는 각각의 순서 의미를 유지한다. 삭제·조회 제외는 tombstone으로 반영한다. 일괄 적용 성공 뒤에만 cursor를 저장하고, 실패 시 revision을 건너뛰지 않는다.
3. 알림은 카드 적용 즉시 시각 강조·짧은 소리를 내고 음성은 첫 이벤트로부터 최대 500ms만 모은다. 뒤 이벤트가 대기 시간을 무한히 연장하지 않게 한다. 중복 revision·재접속·원복으로 같은 수량을 다시 알리지 않는다.
4. 전경에서 가벼운 config/revision 확인을 5초 ±0.5초로 한다. 단말 복귀·온라인 복구·재구독 시 즉시 catch-up한다. WebSocket 장애이면서 REST가 정상일 때만 2초 ±0.25초의 제한된 delta 복구를 사용한다. 전부 실패하면 3→6→12→30초 상한과 jitter로 backoff하고 복귀 시 초기화한다. 전체 snapshot을 짧은 주기로 반복하지 않는다.
5. 각 단말의 읽기 갱신 동시성 1, 쓰기는 기존 직렬화·request UUID 멱등성을 유지한다. 재시도는 일시 오류만 최대 3회/총 15초이며 동일 쓰기 ID를 유지한다. 이후에는 offline 대기와 실제 확인 상태를 구분한다. 서로 다른 재시도 계층이 같은 요청을 중복 실행하지 않게 한다.

요청량 목표: delta 100건/페이지, ticket 최대 100개/호출이므로 고유 주문 U개의 페이지는 **1 + ceil(U/100) RPC**다. 페이지는 순차 처리하고 최대 50페이지의 기존 안전 상한을 유지한다. 건강 확인은 D개 전경 단말에서 약 **D/5 RPC/초**다. 예를 들어 8개면 1.6회/초, 40개면 8회/초이며 실제 변경에 따른 delta·batch 호출은 별도다. 초기 카드와 backlog도 해당 영업일·담당 큐로 제한하고 응답량이 커지면 bounded page로 분할한다.

### P2: 분식클럽 실시간 전환

이력 문제를 고치기 전에 rollout만 active로 바꾸지 않는다. 새 bootstrap도 같은 완료내역 함수를 사용하기 때문이다.

분식클럽만 shadow로 정확도를 비교한 뒤 트레이와 층의 최신 수량·원복·추가 주문·담당 영역을 검증한다. 서버와 앱이 배치 읽기를 지원하는 것을 확인한 후 해당 매장을 active로 전환한다. 운영 주문 수량은 수정하지 않는다. 전가복 직접 전달·담당 층과 다른 매장 설정을 보존한다.

## 5. 목표와 검증

아래는 **개선 후 합격 목표**이며 이번에 달성한 수치가 아니다.

| 지표 | 목표 |
|---|---|
| 전경·정상 네트워크에서 버튼 → 대상 카드·깜빡임 | p50 0.5초 이하, p95 1.5초 이하 |
| 서버 commit → 수신 카드 표시 | p95 1초 이하 |
| 데이터 적용 → 짧은 알림 | p95 100ms 이하 |
| 음성 묶기 | 첫 수신부터 최대 500ms, 지속 접수에도 연장 금지 |
| WebSocket 유실, REST 정상 전경 단말 복구 | 6초 이내 |
| 완료내역 읽기 | 50건 페이지 p95 300ms 이하, timeout 0 |
| 정확성 | 누락·중복 수량·다른 층/매장 노출·원복 뒤 재알림 0 |

1. 먼저 전송 `request_id/event_id/revision`과 송신 단말의 버튼·응답 시간, 수신 단말의 Broadcast·delta·데이터 적용·첫 frame·오디오 시작을 연결해 계측한다. 단말/시계 차이를 기록하고 단순한 서로 다른 단말 시각 차이를 전체 시간으로 간주하지 않는다. 단말 내 시간은 monotonic clock, 단말 간은 서버 기준 및 보정 오차를 사용한다.
2. 격리 DB/스테이징에서 매장별 주방→트레이→층, 전가복 주방→담당 층을 각각 100회 이상 측정한다. 부분 수량·동시 10개·추가 주문·음료·콤보·남은 음식 포장·원복·중복 전송을 포함한다. 운영 고객 주문을 테스트용으로 만들지 않는다.
3. 분식클럽의 과거 큐 규모 4,463건을 반영하고 5,000/50,000건, 동시 단말 8/40개 조건을 검증한다. 실제 호출 수·스캔 행·응답 bytes·p50/p95/p99·클라이언트 peak memory·DB buffer/정렬 메모리를 함께 기록한다. SQL 호출 수만 줄었다고 완료하지 않는다.
4. 완료내역 8초 지연·HTTP 500, 중복/누락/역순 이벤트, catch-up 중 변경, floor 재배정, 앱 복귀, 오프라인 재전송, 세션 변경, 당일 경계, 오래된 앱을 회귀 검사한다.
5. 현장에서는 정상 영업의 실제 전달을 수동 관찰하고 화면 녹화/계측으로 카드·소리·물리 단말 절전을 확인한다. 실제 음성 가청 여부는 원격 SQL로 통과 처리하지 않는다.
6. 관련 Flutter·SQL 회귀 → `bash scripts/check_repo.sh` → 정확한 pushed SHA의 필수 GitHub Actions → `scripts/deploy_pos_production.sh` 순으로 릴리스한다. 배포와 현장 시간 측정은 각각 별도 증거로 남긴다.

현재 수행한 것은 운영 읽기 조사, 소스/배포 기준 비교, SQL 실행 계획과 축소 SELECT 확인, 이 계획 및 집계 파일 작성이다. 구현 변경이 없어 앱 빌드·Flutter 테스트·배포는 수행하지 않았다. 기존 구매/재고 작업 파일은 보존했다.
