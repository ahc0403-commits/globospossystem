## 3. 데이터 매핑 기준

### 3.1 영수증·품목의 식별자

- 영수증 키는 `(tax_entity_id, source_system, receipt_id)`로 잡는다. 식당은 원본 영수증/주문 ID, 포토는 등록된 `source_hash`를 사용한다.
- 표시용 `receipt_number`와 내부 ID를 함께 보존한다. 같은 고객·날짜·금액을 가진 별도 영수증을 합치지 않는다.
- 파일 순번 `invoice_sequence`는 해당 파일에서만 의미가 있다. 정렬은 판매시각, 안정적인 원본 ID, 필요 시 소스 유형을 포함해 일관되게 정한다. 발행 계산서 번호나 영구 영수증 ID로 사용하지 않는다.
- 원품목 ID는 `order_item_id`를 보존한다. 콤보의 세율 분할행은 기존 `order_item_id:vat_rate`를 유지하며 `source_order_item_id`와 분할 세율도 별도로 추적한다.
- 파일 생성 ID/파일 해시를 별도 명세에 보존해 서로 다른 파일의 같은 순번 `1`을 혼동하지 않게 한다. MISA 입력 A:Q에는 식별자 열을 추가하지 않는다.

### 3.2 2026-10-11 수동 매핑을 POS 초기 자료로 사용

수정본의 `Invoice Mapping`에는 `AKJ-MANUAL-20261011-v1` 기준 75개가 있다. **일반 메뉴 73개, `wet_tissue_charge` 1개, 포토 소스 계약 1개**다. DB 승인 ID는 모두 공란이며 수동 기준을 실제 DB 승인 프로필인 것처럼 취급하지 않는다.

사용자가 수동 매핑 기준 작성을 위임했던 범위를 반영해 이 자료를 초기 입력안으로 사용한다. 운영 반영 단계에서 실제 프로필을 생성하면 발급된 ID와 승인 이력을 연결한다. 기존 값을 임의 UUID로 채우는 방식은 사용하지 않는다.

| 대상 | 초기 명칭·단위 기준 | 관리 규칙 |
|---|---|---|
| 일반 메뉴 | 해당 메뉴 ID의 기존 `name_vi` 원문 / 메뉴 판매분 단위 | 같은 명칭이어도 서로 다른 메뉴 ID는 별도로 매핑 |
| 음식 | 수동 기준 `Phần` | POS 수량 1은 그 메뉴의 한 판매분. 메뉴에 2개 구성이 있어도 수량을 두 배로 바꾸지 않음 |
| 세트 | 수동 기준 `Bộ` | 세트 원품목과 세율 분할행의 관계 보존 |
| 음료 | 수동 기준 `Suất` | 원자료에 병·캔·컵 근거가 없으므로 1회 판매분으로 정의. 포장 단위가 확인되면 새 승인 버전으로 변경 |
| 원문 1개 핫도그 | `Cái` | 기존 메뉴의 1개 구성 기준 |
| 물티슈 | `Khăn ướt` / `Cái` | 품목 유형별 승인. 메뉴 ID 공란 유지, 유료 수량·매출 포함 |
| 포토 | `Dịch vụ chụp ảnh` / `Lần` | 기존 포토 서비스 계약 유지, 식당 메뉴 승인과 독립 |

수동 기준의 적용기간은 **2026-10-11 00:00 이상 ~ 2026-10-12 00:00 미만 HCM**이다. 이 기간을 자동으로 늘리거나 과거 발행 스냅샷을 덮어쓰지 않는다. 이후 영업일에 사용할 운영 프로필에는 새 승인 버전과 명시적인 적용시점을 기록한다. 사용자의 기존 위임을 반복 확인하는 별도 승인 절차를 만들 필요는 없으며, 실제 데이터의 적용 범위와 이력은 명확히 기록한다.

초기 자료를 읽을 때는 `Invoice Mapping`과 실제 메뉴 ID·매장·현재 승인 이력을 **일괄 조회**해 대조한다. 일괄 승인 RPC는 입력 100개 이하, 대상 중복·타 매장 ID·기간 겹침을 저장 전에 검사하고 한 배치 안에서는 트랜잭션으로 처리한다. 메뉴마다 원격 호출을 반복하지 않는다. 동일 입력을 다시 저장하면 같은 적용 범위에 중복 승인 버전을 만들지 않게 한다.

### 3.3 비메뉴 품목의 승인 구조

실제 SKU 연결이 없는 물티슈에는 별도 `invoice_item_type_profiles` 구조를 추가하는 방향으로 계획한다. 승인 범위는 최소한 **판매 법인·매장·소스·품목 유형**으로 제한한다. 한 매장의 유형 매핑이 다른 법인/매장에 자동 적용되지 않아야 한다.

필드: 승인 ID, 법인/매장 ID, 소스, `item_type`, 베트남어 계산서 명칭, 단위, 버전, 적용 시작/종료, 승인자/시각, 근거. RLS와 승인 RPC 권한은 기존 메뉴 승인 정책과 맞춘다. 같은 범위의 유효기간 중복을 DB에서 방지한다. 명칭·단위 승인과 판매 당시 세율·금액은 별도 데이터로 유지한다.

조회는 대상 페이지의 전체 품목에 대해 메뉴 승인과 비메뉴 승인을 각각 일괄 결합한다. 비메뉴 승인 유형과 승인 ID를 반환해 후속 코드가 빈 메뉴 ID를 오류로 일괄 판단하지 않게 한다. 물티슈를 0원 처리하거나 매출에서 제외하지 않는다.

| 결제 | 원본 `payment_methods`·구성별 금액과 승인 매핑 버전 보존. BANKTRANSFER→CK, CASH→TM, 혼합은 실제 구성. QR을 전자지갑으로 추정하지 않음 |
| 고객 | 일반 소비자는 원본에 없는 연락처·세금번호를 요구하지 않음. 제공된 이메일·전화는 문자열로 보존해 앞자리 0 유지. 사업자 정보는 기존 필수 기준 적용 |
| 시각·법인 | HCM 영업일 및 판매시각 당시 법인/매장 귀속을 보존 |

형식 수정 단계에서는 K:Q 계산 함수를 유지한다. 다음 데이터 계약 단계에서 원본 숫자 근거를 보강해 현재 `supply / quantity`로만 단가를 다시 만들며 잘못된 입력을 숨길 수 있는 경로를 검증한다. 금액을 고쳐 맞추는 보정은 추가하지 않는다.

## 4. 공통 XLSX 생성 계약

`Hóa đơn GTGT`, A:Q 17열, 8행 헤더, 9행 첫 데이터, 기존 6행 안내문과 7행 공란 위치를 유지한다.

| 열 | 영수증의 첫 품목 행 | 연속 품목 행 |
|---|---|---|
| A | `TextCellValue('1')` 같은 양의 정수 텍스트 | 같은 텍스트 순번 |
| B | HCM 영업일 `dd/MM/yyyy` | 실제 빈 셀 |
| C:I | 원본 고객 정보, 없는 선택값은 공란 | 실제 빈 셀 |
| J | 원본 결제 구성의 승인 표기 | 실제 빈 셀 |
| K:L | 해당 품목의 승인 명칭·단위 | 각 품목의 값 |
| M:Q | 원본 수량·계산서 단가·공급가액·세율·VAT, 숫자 셀 | 각 품목의 값 |

연속 행 B:J에는 `null`에 해당하는 빈 셀을 내보낸다. `''` 문자열, 0, 수식, 병합 셀로 대체하지 않는다. 일반정보는 영수증 객체에 그대로 남기고 셀 배치만 바꾼다. 빈 값의 의미를 원장 고객 정보 삭제로 해석하지 않는다.

예시:

| A (텍스트) | B 날짜 | J 결제 | K 품목 | M 수량 |
|---|---|---|---|---:|
| `1` | 11/10/2026 | CK | 첫 메뉴 | 2 |
| `1` | 공란 | 공란 | 둘째 메뉴 | 1 |
| `1` | 공란 | 공란 | 물티슈 | 2 |
| `2` | 11/10/2026 | TM | 다음 영수증 메뉴 | 1 |

입력 영수증 ID 중복, 동일 순번의 비연속 배치, 다른 영수증에 같은 순번 부여를 저장 전에 거절한다. 영수증별 원본 품목 순서를 보존하고 동일 세율이라는 이유로 여러 메뉴를 서비스 한 줄로 축약하지 않는다. 실제 콤보의 기존 8%/10% 배분행은 별도 품목 연결로 유지한다.

식당 단독, 식당+포토 통합, 기존 Photo MISA 출력이 모두 공통 생성기를 사용하도록 유지한다. **Moers → POS의 포토 6열 업로드 형식은 변경하지 않는다.** 포토의 정상 수동 등록을 식당 승인 누락으로 차단하지 않는다.

## 5. 원장 연결 명세와 오류 표시

기존 `POS Ledger` 14열은 유지한다. A열의 텍스트 순번과 Ledger의 순번은 정규화된 같은 양의 정수로 비교한다. 실제 엑셀 행 번호, 법인·영업일·소스, 영수증 ID/번호, 품목/메뉴 ID, 원본 버전·해시·결제 구성의 의미는 바꾸지 않는다.

새 파일 계약은 입력 시트 밖의 `Export Contract` 등 별도 명세에 기록한다. 제안 버전은 `pos-sales-xlsx-v3`이며 구현 단계에서 확정한다. 파일 형식 버전·원장 연결 버전·매핑 버전·스냅샷 버전을 서로 구분한다. 승인 근거는 별도 `Invoice Mapping`/품목 명세에 넣고 A:Q에 새 열을 추가하지 않는다.

검증 오류는 최소한 다음 필드로 반환한다: 영수증 ID/번호, 소스, 품목 ID·표시명, 오류 필드/코드, 판매시각, 관련 승인 버전, 해결 경로. 예를 들어 명칭 없음, 단위 없음, 적용기간 불일치, 물티슈 승인 없음, 숫자 누락, 금액 불일치를 서로 구분한다.

화면에는 오류 영수증 수와 오류 품목 수를 표시하고 영수증·품목을 확인할 수 있게 한다. 목록이 길면 해당 조회 범위에서 페이지로 표시한다. 파일 저장 호출은 전체 검증 성공 후에만 실행한다. 유효한 영수증만 조용히 제외해 부분 파일을 만들지 않는다. 사용자 메시지에 이메일·전화·세금번호 원문을 노출하지 않는다.

## 6. 미발행 재검증과 기처리 자료 보호

1. 일반 조회/과거 조회는 이미 확정된 스냅샷을 읽는다. 명시적인 미발행 재검증은 **판매 원본 + 해당 판매시각의 승인**에서 새 내용을 조립하는 별도 모드를 사용한다. 현재 저장된 버전 2 이상을 다시 원본처럼 재사용하지 않는다.
2. 재검증 대상은 선택 영업일·판매 법인·영수증 ID, 배치 100개 이하로 제한한다. 원본 결제·고객·품목을 배치로 조회한다. 다운로드 버튼 자체가 승인 변경이나 전체 재검증을 자동 수행하지 않게 한다.
3. 발행/전송 상태, 외부 식별자, 처리 중 claim, 발행 시도 이력이 있는 작업은 변경하지 않는다. SQL의 갱신 조건과 버전 보존 트리거 양쪽에서 막는다. 반복 요청으로 내용이 같으면 새 버전을 추가하지 않는다.
4. **수동 외부 신고가 완료됐어도 POS 작업 상태는 미발행으로 남을 수 있다.** 제공된 2026-10-11 완료 보고/영수증 연결 자료를 근거로 외부 처리 완료 이력을 POS에서 구분하는 설계를 포함한다. POS의 `pending` 표시만으로 그 569건을 다시 처리 가능한 것으로 판단하지 않는다.
5. 위 완료 이력은 외부 MISA 조회를 하지 않고, 사용자가 제공한 파일·보고 기록에 대한 출처와 확인 상태를 보존하는 방식으로 계획한다. 영수증별 외부 번호가 없으면 임의 번호를 만들지 않고 해당 범위를 보수적으로 재처리에서 보호한다. 증거 없이 POS의 개별 발행 상태를 성공으로 꾸며 쓰지 않는다.
6. 새 스냅샷은 이전 버전, 수정 이유, 승인 근거, 원본 해시와 연결한다. 기존 trigger/버전 테이블을 확장해 비메뉴 승인과 고객·결제 근거도 보존한다. 구간 겹침이나 동시 승인 변경이 있으면 다시 조회하도록 안내한다.

재검증 RPC는 갱신 건수 하나만 반환하는 현재 방식보다 대상/갱신/동일 내용/보호/오류 건수와 영수증별 이유를 구분해 반환하도록 보완한다. 전체 일자를 통째로 수정했다는 인상을 주지 않게 한다. 기발행 정정·취소·대체 계산서 기능은 이번 범위에 추가하지 않는다.

## 7. 집계와 반올림 표시

- `receipt_count`/`invoice_count`: 고유 영수증 수.
- `line_count`/`export_line_count`: 실제 출력 품목 행 수.
- 필요 시 `source_item_count`: 세율 분할 전 고유 원품목 수. 콤보 한 품목이 두 세율 행으로 나뉜 경우 두 번 판매한 것으로 합산하지 않는다.
- 화면에는 식당/포토 영수증 수, 총 영수증 수, 출력 품목 행 수, 오류 영수증/품목 수를 분리해 표시한다. 다운로드 결과 문구도 동일한 기준을 사용한다.
- 원장 합계는 판매 당시 소수 금액으로 유지한다. 별도로 **각 품목 공급가액과 VAT를 각각 정수 VND로 반올림한 예상액**과 그 차이를 계산한다. 전체 합계를 마지막에 한 번 반올림하지 않는다.
- 반올림은 양수 금액의 HALF_UP과 동일한 규칙을 사용하고 0.5 경계·수량 나눗셈 정밀도·많은 품목 누적을 시험한다. 통화 값을 화면에서 정수로 보여도 원본과 명세의 소수 값을 삭제하지 않는다.
- 기준 파일의 1.81 VND는 위 규칙으로 재현되는 차이다. 다른 파일의 차이도 같은 규칙으로 설명되었을 때만 반올림 차이로 분류한다. 큰 차이까지 임의 허용하는 상수를 두지 않는다.

## 9. 조회·성능 계획

조회 범위는 선택 HCM 영업일·판매 법인·소스이며, 영수증 페이지 100건을 유지한다. 현재 POS 서비스는 식당/포토 **최대 2개 원본 스트림**을 동시에 읽고 각 스트림의 페이지는 순차 진행한다. 전체 파일의 기본 원장 호출 수는 `요약 1 + ceil(식당 영수증/100) + ceil(포토 영수증/100)`이다. 기준 105/464건은 8회다. 이 수치는 코드에 따른 계산이며 이번 작업에서 측정한 운영 RPC 횟수는 아니다.

승인·품목·결제는 각 페이지에서 일괄 JOIN/사전 집계한다. 메뉴마다 승인 API를 다시 부르거나 영수증마다 DB/MISA 호출을 추가하지 않는다. 여러 일대다 JOIN이 결제액·품목 행을 곱하지 않는지 확인한다. 초기 매핑 일괄 승인과 미발행 재검증은 100개 이하 배치, 쓰기 동시성 1개로 제한한다.

서버의 `pos_daily_receipt_scope`/`pos_photo_receipt_rows`가 외부 LIMIT 전에 하루 범위를 다시 읽는지 실행계획으로 확인한다. 페이지 제한만으로 실제 DB 읽기가 100건이라고 단정하지 않는다. 필요한 경우 날짜·법인·커서를 실제 기반 조회에 밀어 넣고 관련 인덱스를 측정 후 보강한다. 클라이언트도 페이지 내부/페이지 사이 정렬·중복·커서 전진을 검사한다.

동일 조건의 진행 중 조회는 공유하고, 영업일·법인·세션/권한·소스가 바뀌면 재사용하지 않는다. 승인 변경 후에는 영향받은 범위만 무효화한다. 요약과 상세를 읽는 사이 원장/승인 버전이 변경되면 오래된 자료로 저장하지 않고 재조회 안내를 한다.

현재 생성기는 전체 엑셀을 메모리에 보유한다. 이번 배치 수정의 로컬 순회는 `O(품목 행 수)`, 메모리는 기존 원장·엑셀 크기에 비례한다. 569/1,034 규모와 10배 합성 자료로 생성 시간, 최종 파일 크기, 최대 메모리, RPC 응답 수·읽은 행·응답 바이트·페이지별 시간 및 SQL 실행계획을 기록한다. 스트리밍 전환이 필요하면 같은 17열·빈 셀·별도 명세 계약을 유지하는 후속 변경으로 진행한다.

## 10. 자동화에 인계할 POS 파일 계약

자동화 코드는 이번 POS 계획 작성에서 변경하지 않는다. 인계 내용은 다음으로 제한한다.

1. 새 파일 버전, A 텍스트, B:J 첫 행 전용, 17열/8행 헤더.
2. 연속 행의 공란은 같은 순번의 첫 행에서 고객·결제를 상속하는 정규화 규칙. XLSX 자체를 다시 채워 쓰지 않음. 처음 나온 순번의 필수 일반정보가 없거나 순번이 중간에 재등장하면 오류.
3. 영수증 수와 품목 행 수의 독립 집계 및 Ledger 실제 행 연결.
4. 메뉴/비메뉴/포토 승인 유형별 근거. 모든 품목에 메뉴 ID를 강제하지 않음.
5. 원장 소수 금액과 품목별 정수 반올림 예상액의 별도 전달.

현재 자동화 파서의 “모든 행 B/J 필수·일반정보 반복 일치” 조건과 새 공란 계약이 충돌한다는 점을 인계한다. POS 출력과 수신 버전의 호환 범위를 기록하되, **이 계획에 MISA 검사나 외부 수용 시험을 다시 추가하지 않는다.**

## 11. 완료 기준과 운영 반영

- 메뉴·물티슈·포토 승인 유형이 구분되고 판매시각에 맞는 프로필을 끝까지 추적할 수 있다.
- 공통 생성기로 로컬 기준 파일의 A 텍스트 1,034개·첫 행 569개·연속 B:J 공란 465개를 얻는다. K:Q와 첫 행 고객·결제 정보, 모든 Ledger 연결이 보존된다.
- 영수증 수·원품목 수·출력 행 수·오류 수·원장 금액·반올림 예상액이 각각 올바르게 표시된다.
- 누락/불일치는 파일 저장 전 구체적으로 알리며 부분 매출을 조용히 제외하지 않는다.
- 명시적 미발행 재검증은 새 원본으로 버전을 만들고 이전 기록과 기처리 범위를 보호한다.
- 관련 로컬 Dart/SQL/화면 시험과 분석이 통과하며, 조회/메모리 측정 결과와 미측정 한계를 남긴다.
- 파일 계약·초기 매핑·실제 DB 적용·POS 소스·운영 배포 상태를 구분해 기록한다. MISA 외부 검증은 완료 조건이 아니다.

구현 완료 후 운영 반영이 요청되면 `scripts/deploy_pos_production.sh`와 [정식 배포 절차](/Users/andreahn/globos_pos_system/docs/pos/POS_PRODUCTION_DEPLOYMENT_RUNBOOK.md)를 따른다. 정확한 pushed head SHA의 필수 GitHub Actions 결과를 확인한다. 운영에 이미 적용된 DB 구조와 초기 매핑을 먼저 확인하고 신규 승인/마이그레이션은 이력이 보존되도록 적용한다.

복구는 새 출력 기능과 해당 계약 버전의 사용을 중단하는 방식으로 계획한다. 원장·발행 스냅샷·매핑 승인 이력을 삭제하지 않는다. 기존 문제가 있는 형식을 자동 재활성화해 정상 파일처럼 제공하지 않는다. 결제 완료는 계산서 생성/검증 및 외부 서비스의 가용성에 의존하지 않게 유지한다.
