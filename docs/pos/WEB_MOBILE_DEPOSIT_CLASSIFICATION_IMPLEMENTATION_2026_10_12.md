# 웹·모바일 익일 입금 구분 구현 결과

2026-10-12 / Asia/Ho_Chi_Minh. 사용자 지시: **계획 구현, 배포 금지**. 로컬 소스와 후속 마이그레이션을 구현했으며 운영 DB 적용, 배포, 커밋, push, PR 생성은 하지 않았다.

## 표시 및 계산

| 항목 | 표시 기준 | 익일 입금 합계 |
|---|---|---|
| 고객 계좌이체 | BANKTRANSFER 결제 부분 금액. POS 수금 기록이라는 문구와 상세 내역 버튼 | 제외 |
| 포토 | 해당 매출일에 저장된 중복 제거 원본. 등록 완전성·확인된 금액·누락 매장을 별도 표시 | 등록이 완전하면 포함 |
| 분식클럽 현금 | 수동 마감 실사 현금 − 시재. 현금 매출과 예상액은 비교 정보 | 전체 수동 마감 후 포함 |

포토도 **D+1 입금 예정**이다. 과거 매출일은 해당 날짜의 다음 날을 표시한다. 부족액을 0원으로 덮지 않으며, 포토가 미등록이어도 확정된 분식클럽 현금을 표시한다. 미마감·자동마감·부분 마감은 전체 확정액이 비어 있는 상태로 남는다. 과부족 및 마감 뒤 원장 변경은 마감 완료 여부와 별개다.

예상 현금은 `시재 + 현금 수금 − 현금 환불 − 현금 지급 + 현금 회수`다. 실제 입금액에 환불·지급·회수를 다시 반영하지 않는다. 예시의 현금 실사 6,750,000 / 시재 5,000,000이면 입금액은 **1,750,000 VND**, 포토 10,000,000과 합계는 **11,750,000 VND**다. 고객 계좌이체 3,000,000은 별도다.

매출신고 화면에는 날짜·법인 선택 아래 세 금액 카드를 배치했다. 매장 보고서는 현금·계좌이체·카드·전자결제를 상단에서 분리한다. 마감 입력창, 모바일 마감 이력, 넓은 웹 마감 표 상단에는 입금 예정액·예정일·법인 계좌를 표시한다. 포토 등록 결과는 이번 파일의 등록 범위 금액과 법인 요약 확인 경로를 제공한다.

휴대폰 1열, 태블릿 2열, 넓은 화면 3열이며 큰 글씨에서는 1열로 전환한다. 주요 금액을 가로 스크롤 없이 표시한다. 한국어·베트남어·영어를 반영했다.

## 조회와 DB 변경

후속 SQL: `supabase/migrations/20261012210000_deposit_breakdown.sql` (**운영 미적용**).

- 기존 1인자 `get_pos_daily_sales_summary(date)`는 유지한다. 새 `(date, boolean)` 오버로드에서 `p_include_export_metadata=false`를 사용해 첫 요약과 30초 갱신을 RPC 1회로 처리한다. 모든 금융 값은 전체 메타데이터 조회와 동일함을 SQL로 비교했다.
- 내보내기 시에만 전체 원본 검사 메타데이터를 읽고, 페이지마다 같은 원본 revision과 매핑 revision을 확인한다. 두 종류의 원본 페이지 요청은 최대 2개를 병렬로 처리한다.
- 원본 fingerprint는 v3으로 전환한다. 품목·결제·계산서 작업·구매자·포토의 기존 필드 범위를 유지하며 큰 JSON 배열 대신 행별 digest를 일괄 집계한다. 요약과 페이지를 같은 트랜잭션에서 전환하고 판매 원본·기발행 자료를 다시 쓰지 않는다. 페이지는 `source_revision_version=3`을 명시한다.
- `get_daily_closing_deposit_days`는 기존 권한 검사와 이력을 유지하며, 선택한 과거 마감일을 정확히 조회한다. 미마감의 예상 현금은 중복 환불 증빙을 제거한 원장으로 계산한다. 수동 마감 스냅샷은 보존하고 뒤늦은 현금 원장 변경을 경고한다.
- preview와 신규 수동 마감의 예상 현금을 맞춘다. 기존 권한 검사·마감 잠금·입력 검증을 담당하는 before_reconciliation 함수는 유지한다. 과거 마감의 일괄 보정은 없다.
- 계좌이체 상세는 100행 keyset 페이지다. 동일 시각 205건을 100/100/5로 읽어 누락·중복·주문 총액 중복 합산이 없는지 검증했다. 매장 및 법인 권한을 검사하며 필요한 부분 인덱스를 추가했다.
- 요약 캐시 TTL은 30초, 최대 32개이며 동일 진행 요청을 공유한다. 포토 등록·마감 뒤 해당 날짜를 무효화한다. 숨겨지거나 백그라운드인 화면은 주기 조회를 중지하고 로그인 세션이 바뀐 응답은 폐기한다.

앱과 새 RPC가 함께 적용돼야 한다. 새 마이그레이션을 적용하지 않은 운영 환경에서 새 앱의 동작을 검증한 것은 아니다. 이번 작업에서는 운영 DB에 이를 적용하지 않았다.

## 검증 결과

최종 검증: **Flutter 전체 2,023건 통과 / 97건 환경 조건에 따라 skip**, `dart analyze --fatal-infos` 통과, `flutter build web --release --no-pub` 성공, `git diff --check` 통과. SQL 시험은 소유한 일회용 Docker DB만 사용했다. 새 마이그레이션을 두 번 적용해 재실행 가능성도 확인했다. 기존 계산서/VAT/기신고 보호/페이지 회귀와 신규 금액·권한·날짜 시나리오가 포함된다.

SQL의 기존 마감 before_reconciliation 및 이력 인터페이스는 테스트 fixture를 사용한다. 새 wrapper와 집계·페이지는 실제 신규 migration을 실행한다. 운영 원본 함수의 인터페이스·변경 anchor를 읽어 확인했으나, 실제 매장에서 현금 실사·은행 대조·입금을 실행한 검증은 아니다.

## 성능과 한계

로컬 일회용 DB, 합성 데이터, 법인 3개, 매장당 결제/품목 200건. PostgreSQL 세션 `work_mem=16MB`. 직접 SQL 실행의 서버 시간이며 Supabase 네트워크 왕복·실제 휴대폰 렌더 시간을 포함하지 않는다. 응답 크기는 UTF-8 JSON 텍스트다. 20명 동시 조회의 p50/p95는 20개 표본의 중앙값/95백분위로 계산했다.

초기 전체 원본 검사 방식은 500개 매장·10만 건의 단일 조회가 5.8~9.4초였다. v3 검사 자체는 약 2.8~4.3초였고 20명 동시 조회에서는 목표를 넘었다. 원본 검사를 내보내기 동작으로 분리한 첫 측정은 다음과 같다.

| 매장 / 결제 수 | 단일 서버 시간 | 동시 20명 p50 / p95 | 요약 크기 |
|---|---:|---:|---:|
| 5 / 1,000 | 19ms | 63 / 89ms | 4,204 bytes |
| 50 / 10,000 | 92ms | 300 / 371ms | 8,084 bytes |
| 500 / 100,000 | 742ms | 2,642 / 2,905ms | 47,199 bytes |

[첫 측정 원본](evidence/deposit_breakdown_20261012/performance_first_deferred.json). 추가 검사에서는 웹 빌드 등 로컬 CPU 부하가 겹친 상한 p95가 **6,403ms**였다. [빌드 중 측정 원본](evidence/deposit_breakdown_20261012/performance_during_web_build.json). 따라서 운영에서 3초를 보장한다고 주장하지 않는다. 실제 운영 환경의 성능 및 설치 앱 확인은 별도 배포 검증으로 남는다.

웹 빌드와 Flutter 시험이 끝난 뒤 **최종 소스**로 다시 측정했다. 기준/확대/상한의 20명 동시 p95는 각각 **85 / 371 / 2,581ms**, 상한의 단일 서버 시간은 **766ms**, 응답은 **47,201 bytes**였다. 이 로컬 조건에서는 계획의 3초 목표를 충족한다. [최종 측정](evidence/deposit_breakdown_20261012/performance_final.json), [SQL 및 성능 로그](evidence/deposit_breakdown_20261012/sql_and_performance.log).

21개의 요약 요청에서 원본 fingerprint 함수 호출은 0회이며 매장별/법인별 별도 RPC 루프를 만들지 않았다. 요약·원본 SQL reader의 실제 실행계획을 각각 측정해 관계 scan에서 검사한 행 합계는 510,723이었다. 반복 scan을 포함하며, 물리 디스크에서 읽은 고유 행 수와 같은 의미는 아니다. 해당 측정은 버퍼 hit였으며 일부 집계에서 임시 파일이 생겼다. [실행계획](evidence/deposit_breakdown_20261012/query_plans.json).

상한 응답은 128KiB 목표 이하다. 클라이언트 heap/실제 설치 앱 메모리는 측정하지 않았다. 웹 빌드는 기본 JavaScript 릴리스로 성공했다. 의존 패키지의 Wasm dry-run 경고와 기존 Cupertino icon font 경고가 출력됐으나 빌드 실패는 아니다.

전체 저장소의 모든 외부 통합을 검사하는 `scripts/check_repo.sh` 전체 실행은 하지 않았으며, 변경 관련 Flutter 전체 시험·분석·SQL 및 웹 빌드 결과를 사용한다.

## 변경 보존 및 후속 확인

작업 시작 시 관련 18개 파일을 별도 보관해 현재 변경과 비교했다. 저장소에는 기존 사용자 변경이 다수 있었으며 이를 reset/stash/pull로 정리하지 않았다. 기존 판매 원본·결제 처리·발행 XLSX writer·적용된 migration은 이번 구현에서 바꾸지 않았다. 이전 QR 보완도 보존했다. 기존 회귀 시험의 오래된 checksum/소스 이름과 성공 다운로드 fixture의 승인 정보를 현재 의도한 계약에 맞췄으며, 기존 런타임 검증을 약하게 만들지 않았다.

사용자가 배포를 금지했으므로 이번 완료 범위는 로컬 구현과 검증이다. 운영 반영 시 새 migration/API와 앱을 함께 검증해야 하며, 실제 설치 앱과 운영 응답 시간은 그때 별도로 확인한다. 이번에는 정식 배포 스크립트나 운영 migration 적용을 실행하지 않았다.
