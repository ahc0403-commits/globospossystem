# 주방·트레이·층별 주문 처리 상세 구현 계획

작성일: 2026-09-16 · 기준: 현재 작업 트리, HEAD `4dfa0d0d` 및 미커밋 변경 포함

상태: **계획 작성 완료. 애플리케이션 구현·테스트 실행·DB 적용·배포는 수행하지 않음.**

## 1. 구현 목표와 확정 사항

홀 주문의 업무 흐름을 **주문 접수 → 주방 조리 시작 → 트레이 조리 완료 → 층 고객 전달**로 맞춘다. 주문 카드의 위치, 메뉴 상태, 화면에서 사라지는 조건, 캐셔 취소를 같은 서버 상태에서 계산한다.

사용자 확인으로 다음 세 항목은 확정되었다.

1. **주방의 시작 체크가 완료된 수량만 트레이에서 조리 완료할 수 있다.** 시작 누락을 자동으로 보정하지 않는다.
2. **층 일괄 전달은 현재 준비된 미전달 수량만 처리한다.** 아직 조리 중인 음식은 남긴다. 모든 유효 메뉴가 전달되거나 캐셔에 의해 정식 취소되면 제공 업무가 완료된다.
3. **고객 화면 표시 기준 1F는 파랑, 2F는 빨강**이다. 주방·트레이 카드 테두리에 적용한다.

이번 구현의 기본 결정은 다음과 같다.

- 메뉴별 체크는 현재와 같이 수량 1개 단위다. 예: 3개 주문은 시작·완료·전달 각각 0/3에서 진행한다. 층에만 준비된 메뉴 일괄 전달 버튼을 추가한다.
- 주방·트레이는 주문 접수 FIFO를 유지한다. 시작 여부, 조리 완료 여부, 알림, 재접속 때문에 남아 있는 주문의 상대 순서가 바뀌지 않는다.
- 층은 미전달 준비 메뉴가 있는 주문을 먼저 표시하며, 이 그룹 안에서는 트레이의 **서버 확정 완료 순번 오름차순**을 따른다. 나중 완료된 주문이 먼저 완료된 주문을 추월하지 않는다.
- 음식이 부분 완료되면 해당 메뉴의 상태만 바뀐다. 카드 전체 제거는 담당 화면의 모든 유효 메뉴가 완료되었을 때만 한다.
- 완료는 삭제가 아니다. 활성 목록에서 빠지고 완료 이력과 감사 기록에 남는다.
- 일괄 전달 후 남은 조리 메뉴가 있으면 카드가 일반 FIFO로 돌아온다. 준비된 미전달 메뉴가 여전히 있으면 우선 그룹에 남는다.
- 한 테이블의 여러 주문은 기존 `queue_id/order_id` 단위를 유지한다. 테이블 번호만으로 카드를 합치지 않는다.
- 캐셔 취소에는 수량과 사유를 기록한다. 이미 전달한 수량은 이번 미전달 취소 기능으로 취소하지 않는다.

| 추가 주문 | 같은 주문 카드에 신규 배치 추가/재등장 | 동일 | 준비 메뉴가 없으면 원 주문 FIFO, 기존 준비분이 있으면 우선순위 유지 |

주방·트레이에서 floor-direct 음료는 기존처럼 처리 대상에서 제외한다. 음식은 모두 끝났지만 층 음료만 남은 주문 때문에 주방·트레이 카드가 남아 있어서는 안 된다.

### 주문 정렬 계약

서버는 불변 접수 키 `received_at`, `queue_no`, `queue_id`를 제공한다. `received_at`은 기존 `emergency_order_queue.created_at`을 기준으로 삼으며 주문 생성·추가 주문·재접속 때 덮어쓰지 않는다. 동일 시각은 `queue_no`, 마지막으로 `queue_id`로 정렬한다. 번호만으로 서로 다른 세션의 순서를 결정하지 않는다.

```text
주방 / 트레이: (received_at ASC, queue_no ASC, queue_id ASC)
층 준비 그룹: (oldest_pending_ready_sequence ASC, received_at ASC, queue_id ASC)
층 일반 그룹: (received_at ASC, queue_no ASC, queue_id ASC)
최종 층 목록: 준비 그룹 + 일반 그룹
```

`oldest_pending_ready_sequence`는 **현재 남아 있는 준비분**의 가장 이른 순번이다. 최초 완료 시각이나 마지막 수정 시각을 대신 사용하지 않는다.

| 예시 단계 | 층 화면 순서 | 이유 |
|---|---|---|
| A, B, C 순으로 주문 접수 | A → B → C | 접수 FIFO |
| C 조리 완료(순번 10) | C → A → B | 준비 그룹 우선 |
| B 조리 완료(순번 11) | C → B → A | 먼저 완료된 C 우선 |
| C의 준비분 전부 전달, C에 조리 중 메뉴 존재 | B → A → C | C는 일반 FIFO 복귀 |
| 별도 초기 상태에서 A 1개 완료(20), C 완료(21), A 추가 1개 완료(22) | A → C → B | A의 남은 최초 순번은 20, B는 준비 전 |
| A의 순번 20 수량 전달 | C → A → B | A의 남은 최초 순번은 22로 변경 |

다른 단말에서 물리적으로 누른 시간을 완벽하게 비교할 수는 없으므로, 여러 트레이 단말의 동시 클릭은 **서버에서 수락하여 확정한 순서**로 통일한다. 오프라인 클릭도 서버 재전송 성공 때 순번을 받는다.

주방·트레이 메뉴 행 역시 주문 배치 접수 시각 → 기존 품목 순서 → 콤보 구성 순서를 유지한다. 층은 카드만 위 정렬을 적용하고 메뉴 행 자체는 안정적인 배치 순서를 유지하며 점멸로 준비 상태를 알린다.

## 4. 상태·수량 모델

운영 단위는 실제 처리 가능한 단품 또는 콤보 구성품이다. 콤보 부모와 구성품을 중복 합산하지 않는다.

| 기호 | 의미 |
|---|---|
| Q | 현재 제공해야 하는 유효 수량. 금액 취소/미제공 종료를 반영한 서버 계산값 |
| S | 조리 시작한 유효 수량 |
| R | 트레이가 조리 완료한 유효 수량 |
| D | 고객에게 실제 전달한 수량 |
| P | 층에서 지금 전달 가능한 수량 `R - D` |

홀 주방 경유 음식의 기본 불변식은 **`0 ≤ D ≤ R ≤ S ≤ Q`**다. 취소로 Q를 줄일 때 취소 대상의 S/R과 준비 기록도 같은 트랜잭션에서 정리한다. D는 실제 전달 사실이므로 취소를 이유로 늘리거나 줄이지 않는다.

- 주방 시작 가능 수량: `Q - S`.
- 트레이 조리 완료 가능 수량: `S - R`.
- 층 메뉴 전달 가능 수량: `R - D`.
- 주방/트레이 카드 유지: 담당 주방 경유 메뉴 중 `Q - R > 0`이 하나라도 있음.
- 층 카드 유지: 담당 메뉴 중 `Q - D > 0`이 하나라도 있음.
- 층 우선순위/점멸: 주방 경유 메뉴 중 `P > 0`이 하나라도 있음.
- 액션 가능 수량 0과 주문 완료는 다른 상태다. `lastActionId`나 버튼 비활성만으로 완료를 판정하지 않는다.
- 전체 유효 수량이 0이 된 주문은 활성 보드에서 제거하되 이력에는 `전량 취소`로 남긴다. 고객에게 모두 전달한 것으로 기록하지 않는다.
- `needs_review` 등 수량 불일치가 있는 품목은 자동 완료시키지 않는다. 해당 카드는 확인 필요 상태로 유지하고, 유효 수량을 확정할 수 없는 진행 명령은 거절한다. 정상적인 캐셔 취소는 아래 동기화 계약으로 처리하여 불필요한 확인 필요 상태를 만들지 않는다.
- 준비 lot 잔량 합계는 해당 음식의 P와 같아야 한다. 필요한 표준/콤보 원장이 없거나 합계가 다르면 빈 메뉴/완료로 간주하지 않고 확인 필요로 표시한다. bootstrap으로 재확인한 뒤에도 다르면 명령을 중단하고 이력 기반 복구 대상으로 남긴다.

floor-direct 음료는 기존 직접 제공 계약을 유지한다. 트레이 준비 우선순위와 점멸 대상은 아니며, 별도 음료 영역에서 직접 전달할 수 있다. 층의 **준비된 음식 모두 전달**은 주방 경유 준비분만 처리한다. 음료까지 물리적으로 준비되었다고 추정해 함께 체크하지 않는다. 모든 메뉴의 최종 완료 판정에는 음료도 포함한다.

### 기존 수량 필드의 호환 처리

과거 `kitchen_done` 데이터를 ‘시작’이라고 재해석하지 않는다.

- 표준/콤보 구성품 원장에 `kitchen_started_quantity`와 시작 이벤트를 추가한다.
- 새 홀 흐름에서 주방은 S만 증가시킨다.
- 새 홀 흐름의 트레이 완료는 기존 `kitchen_done_quantity`, `tray_received_quantity`, `tray_dispatched_quantity`를 **하나의 트랜잭션에서 같은 완료 수량만큼** 증가시킨다. 이 세 필드는 완료/인계의 호환 투영이며 시작 버튼은 변경하지 않는다.
- 기존 소비자에게 부분 갱신이 보이지 않게 모든 수량·이벤트·준비 기록·ACK를 원자적으로 처리한다. 기존 주방 전용 RPC를 트레이 계정으로 연속 호출하는 구현은 사용하지 않는다.
- 읽기 응답에는 `started_quantity`, `ready_quantity`, `served_quantity`, `required_quantity`, `ready_unserved_quantity`, `workflow_version`을 명확히 노출한다.
- 정상 홀 v2에서는 호환 완료 카운터들이 R과 같아야 한다. 기존 v1/배달 데이터에는 기존 제약을 유지하며 v2 제약을 무조건 덮어씌우지 않는다.

## 5. DB와 RPC 설계

이 절의 새 이름은 **구현할 계약 제안**이며 이미 존재하는 API가 아니다. 적용된 migration을 수정하지 않고 최신 timestamp의 새 migration으로 추가한다.

### 추가 저장 데이터

1. 큐에 `workflow_version`, 명령 충돌 감지용 `progress_version`을 추가한다. 매장 설정에는 신규 주문의 기본 workflow version을 둔다. 기존 KDS 동기화 모드 `legacy/shadow/active`와 별개 설정이다.
2. 표준 음식/콤보 음식 원장에 `kitchen_started_quantity`를 추가한다. 시작 최초/최종 시간은 취소·원복을 반영한 이벤트로 계산하거나 일관된 투영으로 제공한다.
3. 층 준비 순번용 매장별 카운터를 둔다. 행 잠금으로 순번 발급을 직렬화하며 트랜잭션 종료까지 잠금을 유지한다. sequence의 빈 번호는 의미가 없고, 확정된 순번은 재사용하지 않는다.
4. `emergency_floor_ready_lots`를 추가한다. 필수 값은 매장/세션/큐, `source_kind + source_id`, 조리 완료 action ID, `ready_sequence`, 서버 완료 시각, 준비 수량, 전달 수량, 무효화 수량이다. 음식·콤보 구성품의 실제 원장 행에만 연결한다.
5. 준비 기록의 잔량은 `ready_quantity - served_quantity - voided_quantity ≥ 0`. `(ready_action_id, source_kind, source_id)`는 유일해야 한다. 명령 단위 순번 하나를 여러 구성품이 공유할 수 있다.
6. 기존 append-only fulfillment events/actions에 새 명령·원복·취소의 수량 배분을 기록한다. 준비 기록은 재구성 가능한 현재 투영이고, 실제 이력은 삭제하지 않는다. pending 조회 인덱스는 `(restaurant_id, queue_id, ready_sequence)`와 실제 line identity를 포함한다.
7. 기존 명령/이벤트 저장소에 멱등성 키, 정규화한 payload fingerprint, 확정 응답을 저장한다. 같은 ID+payload는 같은 결과, 같은 ID+다른 payload는 오류다.
8. 금액 유지 미제공 종료용 `excused_quantity`를 실제 표준/콤보/floor-direct 원장에 추가한다. 이 경우 `required_quantity = source_target_quantity - excused_quantity`로 계산한다. 금액 취소로 원본 billable quantity를 줄인 수량을 excused에도 중복 차감하지 않는다. CHECK 제약과 부모 집계는 실제 전달량이 유효 제공량을 넘지 않도록 한다.

준비 순번을 `kds_change_log.revision`이나 클라이언트 시각에서 가져오지 않는다. KDS v2가 꺼져 있거나 change log가 정리되어도 업무 순서가 남아 있어야 한다.

### 명령 계약

| 제안 RPC | 권한 | 검증과 동작 |
|---|---|---|
| `kds_start_cooking_v3` | 배정 주방 | 양수 수량, `S + n ≤ Q`, S 증가, 시작 이벤트 |
| `kds_mark_ready_v3` | 배정 트레이 | `R + n ≤ S`, 호환 완료 카운터 증가, 순번·준비 기록 생성 |
| `kds_serve_item_v3` | 배정 층 | 같은 층, 음식은 `n ≤ P`와 준비 lot FIFO 소비, floor-direct는 `n ≤ Q-D`로 직접 전달 |
| `kds_serve_ready_order_v3` | 배정 층 | 표시된 준비 수량 목록과 버전 검증 후 그 수량만 원자적 전달 |
| `kds_revert_progress_v3` | 해당 단계 계정 | downstream 진행을 침범하지 않는 수량만 원복 |
| `cashier_cancel_unserved_v1` | 캐셔/기존 관리 권한 | 최신 D 재검증, 사유 필수, 수량 취소와 금액 처리 구분 |

공통 입력은 request ID, queue/line ID, 수량 또는 일괄 대상 목록, workflow version, expected progress version이다. 매장·층·station은 로그인 배정과 서버 원장에서 결정하고 클라이언트 문자열을 권한 근거로 사용하지 않는다.

v2 큐의 floor-direct 개별 전달도 새 route-aware serve RPC를 사용해 버전/멱등성/ACK를 일치시킨다. 직접 음료에는 주방 시작 전제나 준비 lot을 만들지 않는다. 따라서 구 RPC 차단이 정상 음료 전달까지 막지 않는다. floor-direct 전달 원복도 같은 route-aware 계약에 포함한다.

ACK는 확정 버전과 변경된 티켓, 단계 수량, pending-ready 최소 순번, 완료 여부, 발생 이벤트를 포함한다. 새 RPC를 사용할 수 없는 v2 큐에서 구 RPC로 조용히 fallback하지 않는다.

새 테이블 직접 쓰기 권한을 authenticated/anon에 열지 않는다. RPC는 고정 search_path, 활성 사용자·매장 접근·station/floor 배정·유효 세션·workflow version 검증을 포함한다. 준비 lot의 조회에도 같은 매장/층 범위를 적용한다. 내부 helper는 공개 실행 권한을 회수한다.

일괄 전달은 버튼을 누른 시점 화면에 표시된 메뉴별 준비 수량을 입력으로 보낸다. 잠금 후 준비 목록/버전이 달라졌으면 `KDS_STALE_PROGRESS`와 최신 상태를 반환해 다시 확인하게 한다. 클릭 직후 새로 완성된 음식을 본인도 모르게 함께 전달 처리하지 않는다. 0개는 성공처럼 보이지 않게 처리한다. 콤보 구성품을 직접 순회하며 부모까지 중복 완료하지 않는다.

### 원복 규칙

- 시작 원복은 아직 완료되지 않은 `S-R` 범위만 허용한다.
- 트레이 완료 원복은 미전달 준비분만 가능하다. 지정된 준비 lot 잔량을 무효화하고 호환 완료 수량을 함께 감소시킨다. 시작 수량은 유지한다.
- 다시 조리 완료하면 새 순번을 발급한다. 취소된 과거 우선순위를 되살리지 않는다.
- 층 전달 원복은 실제 전달 action의 배분을 역으로 적용해 원래 lot에 돌려놓는다. 원래 준비 순번으로 점멸·우선순위가 복구된다.
- ‘체크 되돌리기’와 캐셔 ‘미전달 취소’를 문구·아이콘·API에서 구분한다.
- 취소·전달·후속 조리 때문에 원복이 불가능하면 전체 트랜잭션을 거절하고 최신 상태와 이유를 표시한다.

### 동시성과 잠금

명령·취소·결제 경로의 잠금 순서를 함께 감사한다. 기본 순서는 주문 → 주문 품목 ID 순 → 부모/구성품 원장 ID 순 → 준비 기록 순이며, 준비 순번 카운터와 KDS revision lock은 일관된 후반 순서로 잡는다. 이미 실행되는 trigger의 잠금까지 포함해 순환이 없는지 SQL 동시성 테스트로 증명한다. 새로운 RPC만 순서를 맞추고 기존 취소 RPC/trigger의 역순 잠금을 남겨두지 않는다.

모든 명령은 최신 유효 수량을 잠금 안에서 다시 읽는다. 동일 수량을 두 층 단말이 동시에 전달하면 한쪽만 성공하거나 갱신된 잔량 내에서만 성공한다. 취소가 먼저 성공하면 뒤늦은 전달은 거절되고, 전달이 먼저 성공하면 캐셔는 남은 미전달 수량만 취소할 수 있다.

## 6. Flutter 화면·정렬·점멸

### 공통 모델과 상태 계산

- `emergency_fulfillment_provider.dart`의 모델/파싱/단계 판정/optimistic 처리/티켓 병합을 새 계약에 맞춘다.
- 순수 함수 `sortStationOrders`, `stationVisibility`, `readyAttention`에 정렬과 노출 판정을 모아 bootstrap, legacy snapshot, active v2 ticket, 재접속, 명령 ACK 모두 사용한다.
- 진행 중 액션과 선택 주문은 배열 index가 아닌 queue/line ID로 추적한다. 카드가 재정렬되어도 다른 주문 버튼으로 바뀌지 않게 안정적인 key를 사용한다.
- 최근 완료·오늘 완료 조회와 개수도 같은 완료 판정을 사용한다. 일부 준비분만 전달했다고 최근 완료로 이동하지 않는다.

### 층별 테두리

- 주방·트레이 1F 테두리 `#1976D2`, 2F `#D32F2F`, 두께 2px를 기본안으로 한다. 층 배지/문자로도 식별한다.
- 동기화 대기·지연·완료 상태는 내부 배지와 아이콘으로 표시하며 테두리 층 색을 덮어쓰지 않는다.
- **이미 정규화된 queue.floor_label에 `displayFloorLabel()`을 다시 적용하지 않는다.** 서버 `emergency_floor_label()`은 특정 매장의 legacy raw 2F/3F를 KDS 1F/2F로 매핑한다. raw table label과 queue label의 의미가 다르다.
- 읽기 응답에 명시적인 `service_floor`와 표시값을 제공한다. 색상과 층 권한은 동일한 서버 층 식별자를 사용한다. 한국어/베트남어 문구 파싱이나 테이블 번호 앞자리만으로 클라이언트가 추측하지 않는다.
- 실행 전 preflight에서 테이블 raw 값 → 고객 표시 → queue floor → 계정 층 배정의 대응을 검증한다. 불일치가 있으면 묵시적으로 프린터/권한 라우팅을 바꾸지 말고 해당 매장의 매핑을 먼저 해결한다. 다른 매장까지 동일한 legacy 변환이 맞다고 가정하지 않는다.
- 배달/층 미지정/지원 외 층은 기존 구분 배지와 중립색을 사용한다.

### 층 메뉴의 1초 점멸

- 조건은 `station == floor && route == kitchen_tray_floor && ready_unserved_quantity > 0`이다.
- **1초에 한 주기**: 0~500ms 강조, 500~1000ms 기본. 글자를 완전히 숨기지 않고 메뉴 배경/준비 아이콘의 명도를 바꿔 읽을 수 있게 한다.
- 카드 메뉴 목록과 상세 메뉴 행에 동일 적용한다. 3개 중 2개 준비되어 1개 전달했다면 남은 준비 1개가 있는 동안 계속 점멸한다.
- 화면당 공유 AnimationController/시간 신호 하나를 사용한다. 메뉴마다 Timer나 DB polling을 만들지 않는다. 1초 경과시계와 점멸 애니메이션을 구분하고, 점멸은 네트워크 요청을 발생시키지 않는다.
- 정상 전달 ACK 또는 캐셔 취소 ACK로 P가 0이 되면 즉시 멈춘다. 응답 대기/오프라인 중에는 전달을 확정한 것처럼 점멸을 없애지 않고 ‘동기화 대기’를 표시한다.
- 새로고침/재접속 시 서버 P 값으로 점멸을 재개한다. 상세를 열거나 음성을 끄는 행동은 점멸 종료 조건이 아니다.
- 애니메이션 감소 설정에서는 고정 강조·준비 배지를 사용한다. 숨은 화면에서는 ticker를 멈추고 복귀할 때 최신 서버 상태로 복구한다.

### 버튼·페이지·문구

| 위치 | 한국어 | 베트남어 | 영어 |
|---|---|---|---|
| 주방 메뉴 | 조리 시작 | Bắt đầu nấu | Start cooking |
| 트레이 메뉴 | 조리 완료 | Nấu xong | Cooking complete |
| 층 메뉴 | 고객 전달 | Đã phục vụ | Serve to customer |
| 층 상세 일괄 | 준비된 음식 모두 전달 · N개 | Phục vụ tất cả món đã sẵn sàng · N | Serve all ready food · N |
| 역방향 진행 | 체크 되돌리기 | Hoàn tác | Undo progress |

기존 paperless 메뉴명 베트남어 표시 계약은 유지하고 시스템 라벨은 기존 KO/VI/EN 방식에 맞춘다. 접근성 label/tooltip도 단계별로 바꾼다.

- 기존 Phone 4칸/Tablet 8칸을 유지한다. 우선순위 주문을 추가 복제하지 않는다.
- 층 보드에서 새로운 준비분이 확정되면 첫 페이지를 보여준다. 상세 열람 중에는 강제 이탈하지 않고 준비 건수 알림만 표시한다. 상세에서 돌아오면 첫 페이지의 최신 순서를 보여준다.
- 전달 버튼 조작 중에는 대상 ID를 고정해 카드 이동으로 오클릭이 나지 않게 한다. 읽기 갱신만으로 페이지/상세가 임의 전환되지 않게 준비 이벤트인지 구분한다.
- 대량 메뉴로 카드에서 생략된 준비 음식이 있어도 ‘준비 N개’ 배지는 항상 보인다. 상세에는 전체 메뉴가 나온다.
- 주방 시작 알림에 ‘음식 완성’ 음성을 재사용하지 않는다. 층의 준비 알림은 트레이 완료에서만 발생하며 기존 음성/푸시 중복 제거와 coalescing을 유지한다. 점멸 주기마다 소리를 재생하지 않는다.

## 7. 캐셔 미전달 취소와 금액 처리

기존 캐셔 UI는 진행 정보를 읽지만 취소 가능 판단에 실제 전달 수량을 사용하지 않는다. 서버와 UI를 함께 수정한다.

1. 캐셔에 주문/시작/준비/전달/미전달 수량과 취소 가능 수량을 보여준다. `0 < 취소 수량 ≤ 현재 미전달 수량`, 취소 사유를 필수로 받는다.
2. 수량을 줄일 때 미시작 → 조리 중 미완료 → 준비되었지만 미전달 순으로 소비한다. 준비분을 취소해야 한다면 최신 ready lot부터 무효화해 오래 기다린 유효 음식의 순서를 유지한다. 적용 내역을 이력에 남긴다.
3. 취소 확정은 세 화면에 전파한다. 취소된 메뉴의 점멸은 끝나고, 다른 미전달 준비분이 있으면 그것을 기준으로 순서를 다시 계산한다.
4. 실제 전달 D를 취소로 조작하지 않는다. 취소된 음식은 `취소`, 전달된 음식은 `전달 완료`로 구분한다.

금액 처리 기본 정책은 다음과 같이 고정한다. 준비 중단과 환불을 한 상태로 숨기지 않는다.

| 대상 | 제공 업무 | 금액 처리 |
|---|---|---|
| 결제 없는 단품의 미전달 일부 | 해당 수량 취소 | 기존 품목 ID의 유효 quantity를 줄이고 기존 취소 원장에 취소 수량/금액 기록 |
| 결제 없는 단품 전체 미전달 | 전체 취소 | 기존 전체 품목 취소 경로를 강화하여 사용 |
| 모든 구성품이 아직 미전달인 콤보 전체 | 모든 구성품 취소 | 부모 콤보 전체 취소 가능 |
| 일부 구성품이 이미 전달된 콤보 | 선택한 남은 구성품만 미제공 종료 | 부모 금액 유지, 할인/환불은 기존 승인 경로로 별도 처리 |
| 이미 결제 이력이 있는 주문 | 미전달 수량을 미제공 종료 가능 | 기존 결제는 유지, 금액 변경은 기존 adjustment/refund 경로 |

부분 단품 취소를 표현하려고 가짜 취소 형제 주문행을 생성하지 않는다. 기존 취소 원장에 `cancellation_kind`, 원본 item ID, request ID, 사유, 취소 전후 수량·금액·단계 snapshot을 확장한다. 수량이 0이면 현재 품목의 상태를 cancelled로 전환하며, 유효 주문행의 0 수량을 억지로 허용하지 않는다.

부분 금액 취소는 서버 가격·VAT·서비스품목 규칙으로 계산한다. 원본 unit price/세율 snapshot을 보존하고 남은 `paying_amount_inc_tax` 등 파생 금액을 현재 결제 계산 규칙대로 재계산한다. 할인은 기존 `void_active_order_discount_for_item_change` 계약과 재계산 정책을 따른다. 콤보 구성 메뉴의 임의 가격 배분은 만들지 않는다.

기존 source sync는 `ordered_quantity = GREATEST(source_quantity, 각 진행 수량)`과 `needs_review`를 사용하므로 같이 변경해야 한다. 승인된 취소는 먼저 취소 배분에 따라 S/R·준비 lot을 정리한 뒤 원본 수량을 변경하고, 새 required quantity를 명시적으로 투영한다. 이후 품목 UPDATE/추가 주문/메뉴 이름 갱신이 취소 수량을 재생성해서는 안 된다. 새 시작 수량도 일반 수량 감소의 일관성 검사에 포함한다. 콤보 부모는 구성품의 S/R/D/excused 결과를 다시 집계하며 이미 제공한 구성품을 지우지 않는다.

부분 취소 원장의 `item_snapshot.quantity`와 금액은 원래 전체 행이 아니라 **취소한 부분**을 나타낸다. 취소 전/후 전체 snapshot은 별도 metadata에 저장한다. 취소 부분과 남은 부분의 세금/금액은 기존 반올림 규칙하에서 취소 전 기준 금액과 일치해야 한다.

금액을 유지하는 미제공 종료는 기존 fulfillment event/action에 별도 취소 종류와 사유를 남기고 Q를 감소시키는 별도 excused quantity를 투영한다. 0원 매출 취소로 위장하지 않는다. 화면에 ‘미제공 종료 · 금액 유지’를 명시하며 완료 이력도 ‘전달/미제공 종료’를 구분한다.

기존 취소 복원도 대응한다. 부분 취소는 취소 원장 ID를 선택해 정확한 수량만 복원하고, 매출 취소 reversal은 append-only로 기록한다. 복원된 음식은 미시작/미준비 작업으로 돌아가 새 시작·완료 체크를 거친다. 기존 유효 메뉴의 D/R/우선순위는 그대로 유지한다. 완료·정산·결제 때문에 복원이 불가능한 경우 기존 제약을 유지한다.

BM 취소 이력(`20260915120000_bm_service_cancellation_history.sql`)은 현재 품목 status만으로 부분 취소를 `changed`로 오인하지 않게 원장의 종류·reversal을 기준으로 판단한다. 취소 합계와 live sales/export에서 같은 금액이 두 번 차감되지 않는지 검증한다.

신규 미전달 취소 RPC는 캐셔와 기존 관리 권한에만 허용한다. 기존 일반 주문 편집 권한을 프로젝트 전체에서 불필요하게 바꾸지 않되, 구 `cancel_order`/`cancel_order_item` 호출로 새 v2 큐의 전달 수량 보호를 우회할 수 없도록 동일 서버 검증을 적용한다.

**층 제공 완료는 결제 완료가 아니다.** 전달 버튼은 payments 생성, `orders.status='completed'` 강제 지정, 테이블 해제, MISA 호출을 하지 않는다. 기존 `recalc_order_status`와 결제 anchor를 통해 현재 계약에 맞게 파생 상태만 갱신한다. 미전달 경고는 기존처럼 결제를 임의 차단하지 않는다.

## 8. 실시간·오프라인·기존 기능 연결

- 새 시작·조리 완료·전달·취소를 legacy snapshot과 active v2 bootstrap/ticket/delta 양쪽에 포함한다. 정상 active v2를 1초 전체 polling으로 퇴행시키지 않는다.
- tray ready는 **kitchen + tray + 해당 floor**에 전달한다. cancellation/restore는 관련 모든 station과 캐셔 요약에 반영한다. 고객 QR 진행/fully-served 계산도 같은 유효 수량과 콤보/floor-direct를 사용한다.
- 신규 큐뿐 아니라 기존 큐의 **추가 주문 line order_received**도 해당 주문이 표시되는 kitchen + tray + 담당 floor를 갱신한다. 현재 kitchen 중심 target을 그대로 두지 않는다. floor-direct 전용/배달 분기는 실제 표시 대상과 동일하게 제한하고, 신규·추가 주문 음성과 조리 완료 음성을 구분한다.
- 호환용 kitchen_done/received/dispatched 이벤트가 여러 건 생기더라도 새 준비 action의 논리 알림은 한 번이다. 동일 action ID로 dedupe하고 최종 대상 station 집합이 확정된 후 publish한다. 원장 trigger의 중간 이벤트 때문에 주방 시작을 완성으로 알리거나 층 음성이 여러 번 울리지 않게 기존 push/voice 발행 경로도 함께 연결한다.
- 서버 이벤트와 ACK가 역순으로 도착해도 `progress_version`이 오래된 응답을 새 상태 위에 덮어쓰지 않는다. ready sequence는 정렬용, progress/realtime revision은 동기화용으로 구분한다.
- outbox는 새 command kind, workflow version, 고정 request ID, 대상 수량을 저장한다. 타임아웃 재전송에서도 같은 ID를 사용한다. 권한 오류·수량 충돌·stale version은 무한 재시도하지 않고 최신 티켓과 사용자 조치로 전환한다.
- offline pending은 화면에서 식별 가능하게 표시한다. 아직 서버에 없는 시작 체크를 근거로 다른 트레이 단말이 완료할 수 없다. 아직 확정되지 않은 전달로 완료 목록에 미리 이동하지 않는다.
- 연결 복구는 확정 ACK/delta로 순서를 복구하고, 로그 공백이면 bootstrap한다. 중복 알림·중복 lot·중복 취소 원장을 만들지 않는다.
- 타이머는 접수 경과, 시작 시각, 트레이 완료 시각, 고객 전달 시각을 구분한다. `kitchen_first_done_at`을 시작 시간으로 이름만 바꾸지 않는다. 시작 이전의 대기 시간도 손실 없이 표시한다.
- 운영 분석에서 v2 조리시간은 시작→트레이 완료, 대기시간은 접수→시작, 제공대기는 트레이 완료→전달로 구분한다. 과거 v1 이력과 혼합 평균을 만들지 말고 버전별 의미를 명시한다. 기존 ‘트레이 처리시간’이 0으로 바뀌어 성능 향상처럼 보이지 않게 리포트 계약/문구를 함께 보정한다.
- 매장 영업일, 추가 주문 배치 시간, 완료 이력, paperless/print draining, 포장 잔여음식, 프린터, QR 추가 주문, 결제·할인·VAT·영수증·MISA 비동기 흐름은 회귀 대상으로 유지한다.

### 배달 주문 범위

이번 홀 3단계 변경은 `sales_channel != delivery && route == kitchen_tray_floor`에 적용한다. 기존 direct delivery는 floor로 보내지 않고 기사 인계로 끝나는 별도 계약을 유지한다. 공통 주방·트레이 보드의 배달 카드는 채널 배지를 보이며 기존 단계/문구를 채널별로 유지한다. 홀 조리 완료 때문에 배달 ticket이 `dispatched`가 되어서는 안 된다.

배달까지 주방 시작/조리 완료/기사 인계를 세 단계로 바꾸는 것은 이번 요구에 없는 별도 제품 변경이다. 공통 색상·FIFO 계산 수정이 배달 카드의 기존 권한/상태를 바꾸지 않는 테스트는 이번 범위에 포함한다.

| C07 | 잘못된 매장·층·station, 구 RPC 우회 | RLS/RPC 모두 거절, 다른 매장 데이터 노출 없음 |
| N01 | 중복·역순·유실 delta, 오래된 ACK | 최신 버전을 유지하며 준비 순서/점멸 수렴 |
| N02 | offline outbox·reload·foreground 복귀 | 확정 전 pending 유지, 재전송 한 번 처리, 순번 안정 |
| N03 | legacy/shadow/active sync | 업무 결과 동일, active에 상시 전체 polling 추가 없음 |
| R01 | floor-direct/콤보/배달/포장 | 기존 채널별 제공/인계 규칙 보존 |
| R02 | 결제·할인·VAT·서비스·영수증·MISA | 기존 결제 결과/원자성/비동기 경계 보존 |
| R03 | 취소/BM/live-sales/export/복원 | 원장 합계와 남은 결제금액 일치, 이중 차감 없음 |
| R04 | 완료 이력·영업일·운영시간 분석 | 부분 진행을 완료로 오인하지 않음, v1/v2 시간 의미 구분 |

Flutter 점멸 검증에는 명시적인 `pump(Duration(...))`를 사용한다. 무한 애니메이션에 `pumpAndSettle()`을 사용하지 않는다. SQL 동시성은 실제 별도 연결/트랜잭션으로 실행하고 순차 테스트로 대체하지 않는다.

최종 검증은 변경 Dart format, 대상 테스트, `flutter analyze`, 전체 `flutter test`, Web build, 새 SQL 검증, `bash scripts/check_repo.sh`, `git diff --check`를 포함한다. 같은 전체 검증을 이유 없이 반복하지 말고 결과와 SHA를 기록한다. 기존 실패와 이번 변경의 실패를 구분한다.

## 11. 운영 적용과 롤백

1. **준비:** 운영 적용 migration 목록, 실제 RPC 정의, 층 매핑, 진행 중 큐/준비 수량, 단말 버전, outbox 미전송 상태를 preflight로 확인한다. 현재 문서 작성 시 운영 DB를 조회하지 않았다.
2. **호환 DB 배포:** 새 구조/API를 추가하되 기존 주문은 `workflow_version=1`로 보존한다. 과거 조리 완료 이벤트를 시작 이벤트로 backfill하지 않는다. 새 시작 시각을 추정해 통계를 만들지 않는다.
3. **앱 배포:** 새 클라이언트는 v1 읽기/진행과 v2 읽기/진행을 분리한다. v1 진행 카드에는 이전 단계 의미를 사용하고 새 의미로 잘못 체크하지 않는다. 기능 버전과 최소 클라이언트 버전 handshake를 포함한다.
4. **매장 전환:** 첫 도입은 대상 매장의 진행 중 v1 큐와 outbox를 정리한 시점에 실행한다. 신규 큐만 v2로 생성한다. 구 브라우저가 v2 큐를 구 RPC로 수정하려 하면 `KDS_CLIENT_UPGRADE_REQUIRED`로 거절한다.
5. **과거 주문:** v1 완료 이력은 원래 의미를 보존한다. 과거 작업을 원복해 다시 활성화하면 해당 큐 버전으로 끝까지 처리하며 새 카드와 혼동되지 않게 표시한다. 금융 취소 복원은 현재 유효한 주문/결제 제약을 검사한다.
6. **실운영 검증:** 주방 1대, 트레이 1대, 1F/2F 층 단말, 캐셔에서 주문·부분 시작·부분 완료·전달·부분 취소·재접속을 함께 검증한다. 시험 주문은 실제 매출과 구분되는 허용된 검증 절차를 사용한다.
7. **관측:** 명령 실패, start prerequisite 거절, stale conflict, 동기화 지연, pending lot 합계 불일치, 완료 후 잔존 카드, outbox 누적을 확인한다. 정상 연결 검증 환경에서 ACK 후 대상 화면 반영 2초 이내를 목표로 측정하고 실제 결과를 기록한다.
8. **롤백:** 새 v2 유입을 끄되 진행 중 v2 큐는 호환 앱/API로 마무리한다. v2 잔량/명령이 있는 동안 이전 앱으로 강제 되돌리거나 새 테이블/이력을 삭제하지 않는다. additive 데이터를 남기는 기능 비활성화/수정 배포를 우선하며, SQL rollback은 안전 전제조건 불충족 시 중단한다.

운영 배포 경로는 `scripts/deploy_pos_production.sh`만 사용한다. 새 migration과 이름이 맞는 preflight/verify/rollback을 제공하고 clean release checkout을 준비한다. 사용자 소유 미커밋 파일을 지우거나 일괄 stash하지 않는다.

현재 필수 GitHub Actions 체크 이름은 **`Photo Objet contract`**이며 실제로 `scripts/check_repo.sh`를 실행한다. 로컬 테스트와 독립 Judge는 사전 증거이고, **정확한 pushed head SHA의 필수 체크가 성공하기 전에는 release gate PASS로 기록하지 않는다.** 실제 배포는 최신 origin/main 일치 등 배포 스크립트의 게이트를 통과해야 한다.

구현 보고서는 `소스 구현 / migration 적용 / 앱 배포 / 다단말 운영 검증` 네 상태를 분리한다. 계획을 작성했거나 테스트 파일을 만들었다는 이유로 뒤 단계의 완료를 주장하지 않는다.

## 12. 한 번의 구현으로 완료하기 위한 종료 기준

- 시작/완료/전달의 의미가 DB, RPC, Flutter, 알림, 고객 진행, 완료 이력, 운영 분석에서 일치한다.
- 주방·트레이 FIFO와 층 ready 순서가 부분 수량·추가 주문·원복·취소·재접속에도 유지된다.
- 메뉴별 1초 점멸이 실제 준비 잔량에만 연결되고 확인된 전달/취소 후 종료된다.
- 준비 수량 일괄 전달과 캐셔 미전달 취소가 아직 조리 중인 주문이나 이미 전달한 수량을 잘못 완료/취소하지 않는다.
- 콤보·직접 음료·배달·금액/결제 경계가 명시된 정책대로 보존된다.
- 실행 SQL 동시성 테스트와 Flutter 행동 테스트가 CI에 포함되고, 소스 문자열 검증만으로 완료를 판정하지 않는다.
- 독립 리뷰 보고서는 `CRITICAL / HIGH / MEDIUM / LOW / CONFIRMED` 분류, 근거, Priority Fix List를 포함한다. CRITICAL/HIGH 미해결 상태로 릴리스하지 않는다.
- 위 항목을 모두 같은 구현 범위로 끝낸다. 색상/문구만 변경하고 서버 상태·정렬·취소·검증을 후속 작업으로 남기지 않는다.
