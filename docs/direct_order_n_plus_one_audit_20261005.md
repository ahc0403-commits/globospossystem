## 주방 수정

`supabase/migrations/20261005080000_direct_order_fallback_set_based_reads.sql`은 기존 v3 함수만 교체한다. 원래 v1 함수와 단일 주문 context 함수는 유지한다.

- 매장 권한 검사 1회 후 베트남 당일·상태·정렬·최대 200건을 먼저 확정한다.
- 선택한 페이지의 항목을 GROUP BY로 집계하고 요청 테이블에서 포장 정보를 JOIN한다.
- 주방 `delivery`는 사용하는 `{diner_count, method, version}`만 제공한다. 업체·견적·환불 정보는 단일 주문 상세에서 계속 읽는다. 주방 Flutter는 이 축소된 projection을 사용하는 raw map 경로다.
- 기존 티켓 필드, 승인 당시 메뉴 이름, 메모, 수량, 항목 정렬, 빈 항목 배열, 기존 NULL 인원을 보존한다.
- NULL limit도 거절하여 최대 페이지 제한을 우회하지 못하게 한다.

## 실측과 회귀 검증

- 수정 쿼리의 정확한 본문을 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 실행: 페이지 200건/1회, 항목 그룹 199개/집계 1회, 상관 SubPlan 0개. 한 티켓의 빈 항목도 보존한다.

## 남은 개선 순서

1. 직원/고객 목록: 페이지의 request ID를 먼저 확정한 뒤 항목·메시지·리뷰·최신 견적·미환불 정보를 일괄 집계/JOIN한다. 기존 JSON 계약, 진행 중 이전 날짜 주문, 미환불 완료 주문 노출을 응답 parity로 검증한다.
2. 고객 알림: 버전이 있는 목록 projection에 견적 ID/버전·사진 재요청 ID 등 알림에 필요한 값만 제공하여 순회 중 상세 호출을 없앤다. 선택 주문 상세 조회는 유지한다. 동시 변경 M건에도 API 호출 수가 늘지 않는 widget/호출 수 검증이 필요하다.
