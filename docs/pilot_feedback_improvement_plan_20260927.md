# 파일럿 피드백 개선 계획 — 2026-09-27

## 1. 결론과 조사 범위

먼저 전표·현금실사 제출과 POS 입고 → Office 회계 연결을 복구하고, 제출본 잠금과 테스트 데이터 격리를 완료한다. 이후 상세보기·검색·새로고침·Excel/PDF를 보완한다.

사용자 피드백 1~4와 첨부 화면 8장을 POS/Office 현재 소스에 대조했다. 이번 작업은 개선 계획 수립이며, 업무 기능 수정·운영 DB 조회/변경·배포는 수행하지 않았다. 첨부 화면의 문구는 관찰 자료로 취급했다.

- POS 기준: `cc4de81a` + 조사 시작 시 존재한 사용자 작업 파일. 기존 변경은 보존했다.
- Office 기준: `07b2b2a`, 조사 시작 시 Git 작업 트리 clean.
- **소스 구현, DB 마이그레이션 적용, 배포 버전, 실제 운영 검증은 별개다.** 아래 원인 판정은 화면 및 로컬 소스 수준이다.
- 기존 문서보다 최신 마이그레이션 순서와 호출 코드를 우선했다. 일부 구매 V2 문서는 운영 미배포를 명시하므로 V1/V2 모두 재현 범위에 포함한다.

### F01 — 제출 무반응과 부분 성공 복구

1. ‘서명된 전표/실사표를 첨부하세요’처럼 원인을 입력 영역 바로 아래에 표시한다. 첨부 형식·용량·선택 파일·업로드 진행 상태도 보여준다.
2. 입력 누락, 파일 선택 실패, RPC 권한/검증 오류, 파일 업로드 실패를 구분한다. 서버 저장 전에 입력값을 잃지 않게 한다.
3. 현재는 업무 레코드 생성 후 파일 업로드·서명 기록을 순서대로 호출한다. 레코드 생성만 성공한 경우도 구분하여 같은 ID에서 증빙 연결을 재개하고, 전체 완료 전 성공 안내를 하지 않는다.
4. 입력 내용이 같은 재시도에는 같은 작업 식별자를 유지한다. 내용 변경 후 새 제출과 실패 재개를 구분한다.
5. 베트남어 ‘제출’ 버튼이 완료형처럼 보이는 번역과 ‘안전 현금 물리적 계수’ 등 어색한 실사 문구를 교정한다. ko/en/vi를 함께 수정한다.

서명 증빙 요건을 없애는 방식으로 해결하지 않는다. 첨부한 정상 케이스도 실패하는지는 staging에서 RPC 응답까지 재현한다.

### F02·F03 — 전달 단계를 구분해서 복구

현재 구현의 주요 흐름:

```text
직원 발주 작성 → Store Manager 승인 → Brand Manager 승인/발주
  → 직원 입고 내역 제출 (receipt.status=draft, submitted_at 설정)
  → 별도 POS inventory_accounting 계정의 최종 검증
  → receipt.confirmed + 재고 반영 + PO partially_received/received
  → Office 입고 조회 (pos-bridge로 POS 원본 읽기)
  → Office 회계 원천/AP 초안 인계 (자동 동기화 또는 허용된 수동 인계)
  → 후속 대조·회계 승인/전기
```

구매 V2에는 공급업체 확인과 품목별 검수가 추가된다. Office 로그인과 POS 로그인은 독립적이며, Office finance 조회 권한을 POS 입고 확정 권한과 혼동하지 않는다.

Office 입고 화면의 원본 조회와 Office 회계 레코드 생성은 다른 경로다. 원본 화면은 bridge 조회로 갱신되고, 회계 자동 인계는 소스상 5분 주기다. **5분 주기 정의가 있다고 실제 운영에서 성공 중이라는 뜻은 아니다.**

| 진단 순서 | 확인할 사실 | 후속 조치 |
|---|---|---|
| 1 | POS PO의 실제 restaurant_id, 주문번호, workflow_version, 승인자, 배포 SHA | Sample·본점 혼동 및 구버전 흐름 분리 |
| 2 | receipt ID, draft/confirmed, submitted_at, received_by, verified_by/at, 제출 응답 | 제출 실패와 회계 검증 대기를 구분 |
| 3 | Office 동일 PO 조회, 허용 store/brand 매핑, 취소·기간·상태 필터 | 조회 권한/필터 문제 복구 |
| 4 | 확정 입고와 라인 합계, 수락·거절 수량, 단위 환산, 공급가·세액 | 불완전한 확정 금액은 예외로 표시하고 임의 0원 대체 금지 |
| 5 | 자동 인계 migration/Edge 버전, cron 활성 여부, 설정 존재 여부, 최근 실행 결과 | 실패 이유 표시, 누락 확정본만 중복 없이 재처리 |
| 6 | Office 회계 원천·AP 초안 생성 여부와 후속 대조 상태 | 조회 성공과 회계 업무 완료를 구별 |

UI에는 ‘입고 예정 / 직원 제출 완료·회계 검증 대기 / 부분 확정 / 입고 확정 / Office 인계 대기 / 인계 완료 / 인계 실패’를 실제 데이터에 따라 표시한다. `draft + submitted_at`을 단순 ‘미입고’처럼 숨기지 않는다. PO 상세에는 다음 담당자와 막힌 사유를 표시한다.

회계 접근은 다음을 함께 검증한다.

- 최신 v2 사용자의 finance 조회 권한, grant 활성기간과 매장 범위.
- legacy 사용자의 역할 순서 기반 메뉴 필터가 finance 권한 사용자를 숨기는지.
- 입고 조회 이후 3자 대조 경로가 현재 purchase/inventory 조회만 허용하는 경계. 필요한 회계 조회 범위를 합의해 일관되게 연결하되 승인·수정 권한을 일괄 부여하지 않는다.
- ‘전체 매장’ 및 법인 선택 UI와 bridge의 실제 권한 범위를 일치시키거나 명확히 안내한다.

추가 소스 불일치도 포함한다. 재고 발주 내역의 기존 ‘남은 수량 입고 확정’ 버튼은 `confirm_inventory_purchase_receipt`를 호출하지만, 최신 해당 SQL 정의는 독립 검증 흐름을 요구하며 항상 거절한다. 이 진입점은 기존 승인/입고 화면으로 연결하고 폐기된 단일 확정 RPC를 다시 활성화하지 않는다.

### F04 — 메인 계정 테스트와 기존 데이터 처리

**현재 상태에서는 메인 계정의 기존 주문으로 승인·입고·재고 조정 테스트를 계속하지 않는 것이 맞다.** 조회만으로 상태를 조사하고, 변경 테스트는 별도 staging에서 실행별로 소유한 데이터로 수행한다. SAMPLE이라는 로그인명/매장명만으로 격리를 보장하지 않는다.

1. 위 주문번호와 테스트 시각을 기준으로 원본 PO·입고·재고 트랜잭션·Office 원천·AP 초안을 읽기 전용으로 대조한다.
2. 정상 운영 내역과 테스트 내역, 미확정본과 확정본을 구분한다. 불일치가 있으면 데이터별 영향표를 만든다.
3. 수정이 필요하면 원본을 보존한 승인된 취소·반품·역분개/조정 절차로 처리한다. 기존 주문 삭제나 재고 수량 직접 덮어쓰기는 복구 계획에 넣지 않는다.
4. staging의 POS와 Office 연결, 계정 권한, 매장/브랜드/법인 매핑, 재고 및 AP 대상이 모두 테스트 범위인지 검증한 뒤 역할별 E2E를 시작한다.

### F05 — 제출본과 최종 확정본 보호

권장 정책은 **승인 절차와 수정 이력을 함께 적용**하는 것이다.

| 단계 | 직원 수정 | 처리 원칙 |
|---|---|---|
| 입력 중 | 허용 | 수량·단가·첨부 임시 입력 |
| 직원 제출 완료 | 잠금 | 제출 내용과 버전 보존; 검증 담당자에게 전달 |
| 검증 중 | 원본 덮어쓰기 금지 | 검증 수량/금액을 원 제출값과 비교; 변경 이유와 검증자 기록 |
| 반려 | 반려된 다음 버전만 허용 | 반려 사유 확인 후 재제출; 이전 제출본 유지 |
| 최종 확정 | 직접 수정 금지 | 별도 정정 요청 → 독립 승인 → 조정 기록 반영 |
| 부분 입고 뒤 추가 납품 | 새 입고 건 허용 | 이전 확정 건 잠금을 유지하며 미입고 잔량에 별도 receipt 생성 |

최소 변경 우선안은 기존 `draft/confirmed` 계약을 보존하면서 `submitted_at`과 제출 버전으로 잠금/대기 상태를 구분하는 방식이다. 반려·재제출·검증 경로를 함께 설계하고 모든 쓰기 RPC와 직접 테이블 접근에서 서버 검증을 적용한다. 새 status 값을 화면에만 추가하면 현재 검증 RPC·bridge와 충돌하므로 금지한다.

감사 이력에는 PO/입고 ID, 버전, 수정 전후 수량·단가·금액·첨부 참조, 요청자·승인자·실행자, 시각, 사유, 재고/회계 조정 ID를 보존한다. 현재 제출 시도 테이블의 actor/hash 기록만으로 사용자가 요구한 전후 비교를 충족했다고 보지 않는다.

수량 감소/반품은 이미 존재하는 반환 원장과 재고 조정 경로를 우선 활용한다. 확정 금액 정정은 Office에 영향을 전달하되 기존 승인·전기 결과를 조용히 덮어쓰지 않는다.

### F06·F07·F08 — 상세·검색·새로고침

- 상세: 현재 테이블 + 전체 액션 목록 아래에 붙는 상세를 클릭 즉시 보이는 패널로 옮긴다. 좁은 화면은 시트를 사용한다. 선택 주문번호, 품목·수량·단가·금액, 승인·검수·확정 이력, 첨부, 다음 업무를 표시한다. 늦게 도착한 이전 요청이 새 선택을 덮지 않아야 한다.
- 검색: SM/BM 주문·승인·입고 목록에 통합 검색을 제공한다. 서버에서 원재료명, 주문번호, 공급업체명으로 검색하며 기존 역할·매장 제한을 유지한다. 부분 일치, 입력 지연 처리, 검색 초기화, 상태/기간 필터와 조합, 페이지 전체 검색을 검증한다. 베트남어 악센트 유무 검색은 사용자 기대를 반영해 같은 결과가 나오도록 설계한다.
- 새로고침: POS/Office 화면, 사용자 역할, callback, loading/busy 상태, 마지막 성공 시각을 목록화해 재현한다. 정상 상태의 버튼은 사용 가능해야 하고 실행 중에는 진행 표시를 제공한다. timeout/오류 후 `finally`로 복원하며 입력값·필터·선택을 보존한다. 최신 조회 실패를 빈 데이터나 성공 갱신으로 표현하지 않는다.

‘새로고침이 대부분 비활성’은 현재 증거로 단일 공통 결함을 확정할 수 없으므로 버튼을 일괄 강제 활성화하는 수정은 하지 않는다.

### F09 — 내보내기 범위와 기존 사용 경로

현재 확인된 경로:

- POS 발주 내역: 각 주문 행의 **출력/PDF**.
- POS 발주·입고 상세: 승인된 발주서의 **PDF 저장 / 이미지 저장**.
- Office 보고서: 매출·근태·품질 보고서에 **CSV 내보내기**. Excel에서 열 수 있지만 입고/AP용 XLSX 내보내기는 아니다.
- Office 입고 관리 및 은행·현금 화면: 요청한 XLSX/PDF 내보내기 버튼 연결이 없다.

1차 제공 범위는 입고 목록/품목 상세, 공급업체별 대조에 필요한 입고·인계 상태, 현금전표 및 현금실사다. 각 화면 우측에 ‘내보내기 → Excel(.xlsx) / PDF’를 제공한다. 공급업체 채무 잔액을 포함할 경우 승인된 Office AP 원장을 원천으로 사용하고 발주 총액을 미지급금으로 대체하지 않는다.

내보내기는 현재 검색·필터에 해당하는 전체 결과와 동일한 조회 권한을 적용한다. PO/입고번호, 매장, 공급업체, 상태, 주문·실입고·수락·거절 수량, 단위, 단가, 공급가·세액·합계, 제출/확정 시각을 포함한다. 현금 문서는 해당 업무 필드와 상태·서명 증빙 유무를 사용한다.

Office의 기존 `ExportSnapshotRepository`와 `ExportSnapshotSerializer`를 재사용한다. 다만 새 업무 종류의 서버 허용 목록·행 조회·권한 계약을 추가해야 하며 직렬화 함수만 붙여 완료했다고 보지 않는다. 개인정보/서명 파일의 공개 URL을 내보내지 않는다. 파일에는 조회 범위, 생성 시각, 생성자, 통화, 건수/합계를 표시한다.

Office 원본 조회는 갱신 완료 시 POS 최신 확정 데이터와 일치해야 한다. 자동 회계 인계는 소스의 5분 주기를 기준으로 staging에서 **두 주기 이내 정상 처리 또는 명시적 실패 상태**를 목표로 검증한다. 후속 회계 승인/전기는 자동 인계 성공과 구분한다.

최종 release PASS는 로컬 테스트만으로 선언하지 않는다. 변경된 저장소별 CI가 정확한 pushed HEAD SHA에서 통과하고, 적용 migration·배포 SHA·staging 결과·운영 읽기 확인이 연결되어야 한다. POS는 지정 배포 스크립트, Office는 고정 프로젝트/깨끗한 정확한 origin/main/마이그레이션 이력 확인 및 프로젝트 지침의 운영 확인 절차를 따른다.
