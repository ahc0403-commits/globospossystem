**고정 QR 주문: 고객 목록 리셋 및 추가·신규 주문 분기 개선계획**

작성·개정일: 2026-09-09 · 개정 3 · 상태: 로컬 구현·집중 검증 완료, 운영 DB 적용·배포 전

고정 QR과 현재 주문 방식을 유지한다. **고객 화면은 모든 음식의 층 전달 완료 후 추가주문 없이 10분이 지나면 새 주문 입력 상태로 리셋하고, 실제 접수는 서버의 결제 상태로 기존 주문 추가 또는 신규 주문 생성을 결정한다.** 피크 시간의 다음 손님을 위해 전액 결제가 먼저 완료되면 10분을 기다리지 않고 리셋하는 것을 적용 기준으로 삼는다.

기존 계획의 방문별 확인코드, 직원 착석 승인, 방문·기기 인증 체계, 재접속 시 강제 인증 제안은 이번 개정에서 제외한다. 착석할 때마다 QR을 재발급하거나 교체하지 않는다. 문서 경로는 기존 링크를 유지하기 위해 그대로 사용한다.

이번 작업에서 서버 표시 상태, 10분 리셋, 부분 결제 주문 추가, 주문 문맥 검사와 고객 화면 초기화를 로컬 소스에 구현했다. 운영 DB 적용과 웹 배포는 수행하지 않았으며, 실제 iOS Safari·Android Chrome·매장 QR 인앱 브라우저 검증은 출시 전 단계에 남아 있다.

**1. 적용 정책**

| 조건 | 고객 화면 | 실제 주문 처리 |
| --- | --- | --- |
| 음식 전달 진행 중 | 접수·진행 내역 유지 | 결제 미완료이면 기존 주문에 추가 |
| 모든 음식 전달 완료, 추가주문 없이 10분 미만 | 기존 내역 유지 | 결제 미완료이면 기존 주문에 추가 |
| 모든 음식 전달 완료, 추가주문 없이 10분 이상 | 이전 접수 목록을 비우고 주문 입력 화면으로 전환 | 결제 미완료이면 같은 주문 ID에 추가 |
| 전액 결제 완료 | 10분 경과 여부와 관계없이 이전 목록·성공 표시·장바구니 리셋 | 다음 접수는 새 주문 ID로 생성 |
| 결제 완료 직후 다음 손님이 QR 접속 | 이전 결제 주문을 표시하지 않고 주문 가능 | 새 주문 생성, 고정 대기시간 없음 |
| 화면 리셋 후 새 손님의 진행 주문이 이미 생긴 경우 | 서버의 최신 주문 구분을 확인 | 오래된 제출 요청을 새 손님 주문에 자동 합치지 않음 |

10분 경과는 **화면을 새 주문 입력 상태로 만드는 기준**이다. 미결제 주문을 완료 처리하거나 삭제하거나 새 계산서로 분리하는 기준으로 사용하지 않는다. 실제 DB 신규 주문은 다음 주문 제출 시 생성하며, 타이머만으로 빈 주문을 만들지 않는다.

결제 완료는 결제 시도나 결제 기록 한 건의 존재가 아니라, 서버에서 전액 결제를 확정하고 주문을 완료한 상태다. 부분 결제도 “결제 미완료”에 포함한다. 결제 처리 트랜잭션이 진행 중인 짧은 구간은 동시 수정을 막고, 결과가 확정된 후 최신 상태로 재판정한다.

**2. 10분의 시작점과 재시작 규칙**

10분은 휴대폰에서 마지막 터치한 시각이나 주문 버튼을 누른 시각만으로 계산하지 않는다. 서버가 현재 주문의 취소되지 않은 음식·음료·콤보 구성품이 모두 손님에게 전달됐다고 확정한 시각을 사용한다.

- 마지막 남은 음식이 층에서 전달 완료되면 `all_served_at`을 기록하고 `reset_due_at = all_served_at + 10분`을 설정한다.
- 그 사이 QR 또는 직원 POS를 통해 추가주문이 정상 접수되면 기존 타이머를 취소한다. 추가한 음식까지 모두 전달된 시점부터 새로 10분을 센다.
- 추가주문 요청 실패, 메뉴 열람, 장바구니 편집, 자동 새로고침은 서버의 추가주문 접수로 보지 않는다.
- 전달 완료를 되돌리거나 수량이 늘어 아직 전달하지 않은 음식이 생기면 타이머를 취소한다.
- 취소·수량 변경으로 전체 전달 완료 조건이 새로 성립하면 그 변경이 확정된 시각부터 센다. 과거 전달 이벤트를 단순히 최댓값으로 계산해 즉시 만료시키지 않는다.
- 전체 주문 취소는 별도 종료 사유로 리셋한다. 음식이 0개라는 이유만으로 전달 완료 타이머를 시작하지 않는다.
- 서버 시각 기준으로 정확히 10분 이상이면 리셋 대상이다. 휴대폰 시계가 다르거나 페이지가 잠들어 있어도 결과가 같아야 한다.
- 이미 처리한 주문 구성에 대한 10분 리셋은 한 번만 적용한다. 이후 추가주문이 생기고 그 음식까지 모두 전달되면 다음 리셋 주기를 시작한다.

예를 들어 12:00 전체 전달 완료 → 12:08 추가주문 → 12:12 추가 음식 전달 완료라면 리셋 시각은 12:22다. 12:10에 리셋하지 않는다.

**3. 피크 시간 처리 예시**

| 시각 | 상황 | 결과 |
| --- | --- | --- |
| 12:00 | A 손님 음식 전체 전달 완료 | 12:10 리셋 예정 |
| 12:06 | A 손님 전액 결제 | 즉시 A 주문 목록 리셋, 기존 주문 완료 |
| 12:07 | B 손님 착석 후 같은 QR로 주문 | B 신규 주문 생성, 12:10까지 기다리지 않음 |
| 12:10 | A 주문에 걸려 있던 타이머 만료 | B 주문·화면에 영향 없음 |

미결제 예시는 12:00 전체 전달 완료 → 12:10 고객 목록 리셋 → 12:15 추가주문이다. 이 경우 기존 주문 ID와 누적금액을 유지하며 추가 항목만 붙인다. POS에는 최초 주문과 추가주문이 함께 남는다.

**5. 서버 변경 계획**

기존 `orders`와 주문 항목을 기준으로 구현한다. 새 방문 인증 시스템을 만들지 않는다. 최소한의 주문별 QR 표시 상태를 추가하고, 기존 전달·주문·결제 이벤트에 연결한다.

| 서버가 관리하거나 응답할 정보 | 목적 |
| --- | --- |
| `order_id` 및 주문 변경 버전 | 이전 주문과 새 주문, 추가주문 전후를 구별 |
| `all_served_at`, `reset_due_at` | 마지막 전체 전달 완료와 10분 리셋 시각 |
| 리셋을 적용한 주문 변경 버전 | 같은 주문 구성에 대한 중복 리셋 방지 |
| `display_version`, 리셋 사유 | 휴대폰들이 같은 목록 초기화 상태를 적용 |
| 목록 표시 기준점 | 리셋 전 항목이 다음 조회에서 다시 나타나지 않게 구분 |
| 결제 완료 여부와 현재 주문 구분 | 다음 제출을 추가·신규 주문으로 판정 |

필드 명칭은 제안이다. 구현은 주문별 보조 상태 한 곳에 필요한 값만 저장하고, 기존 항목·이벤트에서 안정적으로 얻을 수 있는 값은 중복 저장하지 않는다. 표시 기준점은 단순 휴대폰 시각 대신 서버의 주문 변경 순서를 사용한다. 기존 항목의 수량 증가도 새 추가분으로 인식하도록 범위를 정한다.

서버 조회는 전체 미결제 원장과 고객 기본 목록을 구분한다. 10분 리셋 이후에는 기존 접수 항목을 기본 목록에 다시 채우지 않는다. 이후 추가된 항목은 새 표시 주기에 표시한다. 미결제 누적금액 및 전체 원장은 계속 유지하고, 필요한 경우 같은 주문의 전체내역을 별도 보기로 제공한다. 화면 목록 합계와 전체 미결제 금액이 다르면 이름을 명확히 구분한다.

리셋 판정은 조회·제출 시에도 적용해 예약 작업의 실행 지연에 의존하지 않는다. 만료 시점에 페이지가 닫혀 있었어도 재접속하면 같은 리셋 상태를 받는다. 추가주문이 10분 이후 처음 들어왔다면, 해당 변경을 적용하기 전에 이전 상태의 리셋을 확정해 새 항목까지 숨기지 않도록 한다.

현재 `qr_get_active_order`는 `STABLE` 함수였으므로 리셋 상태를 원자적으로 반영할 수 있는 함수 계약으로 변경했다. 고객 주문은 `expected_order_id`를 받는 새 오버로드만 공개하고, 문맥 값이 없는 과거 오버로드는 `service_role` 전용으로 제한해 고객이 주문 문맥 검사를 우회하지 못하게 했다.

**6. 전달 완료 판정**

Paperless는 일반 음식, 층에서 직접 주는 음료, 콤보 구성품의 현재 전달 수량을 모두 검사한다. 실제 전달 대상의 수량과 기록이 모두 존재하고, 취소·미확인 상태를 제외한 필요한 각 항목이 충족돼야 한다. 일부 항목의 기록이 누락됐는데 기록이 있는 항목만으로 “모두 완료”라고 판정하지 않는다.

기존 운영 분석 함수는 활용 가능한 데이터의 근거다. 보고서용 전체 기간 집계를 고객의 15초 조회마다 실행하지 않고, 해당 주문에 한정된 판정과 상태 변경 기록을 사용한다. 콤보 부모와 구성품을 이중 계산하지 않으며, 과거 Paperless 세션의 완료 상태를 새 추가주문의 완료 상태로 가져오지 않는다.

일반 인쇄 모드에서는 현장의 전달 완료 기록 경로를 확인한다. 주방의 `served` 상태가 실제 층 전달 확인을 의미하는지도 검증한다. 근거가 없는 경우, 층 직원이 전달 완료를 기록할 수 있는 최소 동작을 연결해야 한다. 인쇄 성공 시각이나 주문 접수 시각으로 10분을 임의 추정하지 않는다. 전달 근거가 없는 기존 주문은 10분 자동 리셋 대상에서 제외하되 전액 결제 시 리셋은 적용한다.

남은 음식 포장 요청은 음식 추가주문으로 보지 않아 10분 타이머를 연장하지 않는다. 미결제 주문의 유효한 포장 요청은 화면 리셋만으로 취소하지 않는다.

**7. 부분 결제와 동시 요청**

사용자 기준의 “결제 미완료”에는 부분 결제가 포함되므로 기존 추가주문 차단 정책 변경이 필요하다. 단순히 오류 조건 한 줄을 없애는 것으로 완료하지 않는다.

- 이미 수납한 금액과 결제 기록을 보존한다.
- 추가 음식의 금액·세금·할인 적용과 새 잔액을 현행 결제 계약에 맞게 재계산한다.
- 수납된 결제 자체를 수정하거나 이전 결제분을 중복 수납하지 않는다.
- 캐셔가 열어둔 결제 화면에도 변경된 잔액을 반영하고, 오래된 금액으로 완납 확정하지 않도록 한다.
- 주문 완료가 확정되기 전에는 같은 주문에 추가하고, 완료된 주문을 다시 열어 추가하지 않는다.
- 합산 결제 실패 시 주문 완료와 표시 리셋도 함께 롤백한다. 이미 완료된 결제의 영수증·매출 자료는 보존한다.

주문 선택, 추가·신규 분기, 항목 저장, 표시 버전 갱신은 한 DB 트랜잭션에서 처리한다. 결제·추가주문·테이블 이동의 잠금 순서를 맞추고, 잠금 대기 후 최신 상태를 다시 확인한다. 현재 QR의 테이블→주문 잠금과 결제의 주문 우선 잠금이 충돌할 수 있으므로 관련 경로를 함께 검토한다.

화면이 알고 있는 `expected_order_id` 또는 서버 발급 주문 문맥 버전을 제출에 포함한다. A 주문에 작성된 요청이 처리될 때 이미 B 주문으로 바뀌었다면 자동으로 B에 추가하지 않고 화면을 리셋·재확인한다. 이 확인은 별도 인증코드 입력이 아니다. 서버 상태를 다시 받은 다음 고객이 새로 제출한 요청에만 최신 추가·신규 분기를 적용한다.

동일 요청의 재시도는 기존 중복 제출 키를 유지해 주문과 인쇄를 한 번만 생성한다. 결제 직후 도착한 과거 접수 응답은 이미 완료된 결과임을 표시 상태에 반영하고, 예전 성공 목록을 다시 살리거나 새 주문을 자동 생성하지 않는다.

**8. 휴대폰 화면 변경**

고객 화면은 “접수·진행 중”, “새 주문 입력”, “주문 정보 재확인 중”을 구별한다. 주문 분류는 서버가 결정하며 UI 문구 때문에 실제로 미결제 주문을 새 계산서로 분리하지 않는다.

- 10분 리셋: 이전 접수 결과·기본 주문 목록을 비우고 메뉴를 표시한다. 기존 미결제 주문 연결은 유지한다.
- 10분이 되는 순간 고객이 추가 메뉴를 작성 중이면 그 장바구니를 삭제하거나 확인창을 강제로 닫지 않는다. 이전 접수 목록만 정리하고 제출 시 서버가 다시 판정한다.
- 결제 완료 또는 주문 ID 변경: 이전 주문 목록·성공 표시·장바구니·콤보 선택·제출 문맥을 함께 정리한다. 다음 주문으로 예전 장바구니를 넘기지 않는다.
- 제출 결과가 아직 불명확한 요청은 타이머만으로 잊지 않는다. 중복 제출 키로 결과를 확인한 뒤 최신 리셋 상태를 반영한다.
- `active=false`를 관찰하지 못했더라도 주문 ID 또는 표시 버전이 바뀌면 이전 상태를 정리한다.
- 늦게 도착한 이전 조회 응답은 주문 ID·표시 버전·요청 순서 검사로 무시한다.
- 메뉴 조회 실패와 주문 상태 조회 실패를 분리해, 메뉴 통신 오류 때문에 확인된 결제 리셋이 취소되지 않게 한다.
- 새로고침·재접속은 허용한다. 서버에서 리셋 상태를 다시 받아 이전 목록을 브라우저 저장값으로 복원하지 않는다.
- 탭 복귀 시 서버 재검증 전에는 이전 주문의 제출을 허용하지 않는다. 네트워크 오류가 결제 미완료라는 의미로 해석되지 않게 한다.

온라인 전경 화면은 서버가 내려준 리셋 예정 시각에 재검증하고, 결제·테이블 변경 신호가 오면 바로 갱신한다. 기존 15초 조회는 이벤트 누락의 보조 경로로 사용한다. 서버에서 결제 완료가 확정된 뒤 새 QR 접속은 첫 응답부터 이전 내역을 받지 않아야 한다. 연결이 끊긴 휴대폰 화면은 즉시 원격 삭제할 수 없으므로 복귀 시 재검증한다.

현재 1~3단계는 로컬 구현과 집중 테스트를 완료했다. 임시 PostgreSQL DB에서 전달 완료 후 10분 리셋, 리셋 후 신규 항목만 표시, 추가주문에 따른 타이머 재시작, 완료 주문 즉시 종료 표시, 오래된 주문 문맥 거절과 결제·QR 동시 요청의 잠금 순서를 확인했다. Flutter 모델·서비스·화면 회귀 테스트와 정적 분석도 통과했다. 운영 데이터 마이그레이션, 실제 기기 확인과 한 매장 파일럿은 4~5단계로 남아 있다.

기존 QR 이미지·토큰을 그대로 유지한다. 별도 착석 확인코드나 직원 승인 절차를 추가하지 않는다. 마이그레이션은 새 파일로 추가하고 기존 사용자 수정·미추적 파일을 보존한다. 레거시 주문의 전체 전달 시각을 임의로 만들어 과거 시각으로 리셋하지 않는다.

결제 관련 변경은 현재 함수와 후속 래퍼·패치의 유효 정의를 기준으로 진행한다. 과거 결제 함수를 복사하여 최신 할인·VAT 처리를 덮어쓰지 않는다. MISA 전자세금계산서 처리와 기존 일 마감 규칙은 그대로 유지한다.

관련 검증과 `bash scripts/check_repo.sh`를 실행하고, [기존 배포 스크립트](/Users/andreahn/globos_pos_system/scripts/deploy_pos_production.sh)를 사용한다. 로컬 검증, DB 적용, 웹 배포, 운영 확인을 각각 기록한다. 문제가 생기면 리셋 기능을 중지하되 POS 주문·결제 원장은 복원/삭제 대상으로 삼지 않는다.

**11. 이번 정책의 효과와 한계**

완료 기준은 고객 목록의 적절한 초기화, 미결제 추가주문 보존, 전액 결제 후 신규 주문 분리, 피크 시간의 이전·다음 주문 표시 혼합 방지다.

고정 QR 주소만으로 누구나 다시 접속할 수 있는 조건에서는, 이 10분 규칙이 매장 밖의 악의적인 주문을 완전히 차단하지는 못한다. 주문 문맥 검사는 오래된 요청의 잘못된 합침을 막지만 현장 고객 인증은 아니다. 이번 계획에서는 별도 확인코드 도입 없이 사용자가 지정한 리셋·결제 분기 정책을 구현하며, 원래의 원격 악용 문제까지 해결됐다고 보고하지 않는다.
