# 외부 주문 상태·결제 안내·결제 화면·이미지 재인증 개선 계획

작성일: 2026-09-10
추가 반영: 주문별 상태 표시, 복수 주문 조회·접수, Grab 배송 확인 후 Cashier 수동 주문 완료.
대상: Direct Order 고객 웹 화면 및 Cashier 외부 주문 화면
상태: 2026-09-10 소스 구현 및 로컬 검증 완료. 운영 DB 적용과 Edge/Web 배포, 실제 기기 운영 확인은 아직 수행하지 않았다.

구현 결과: 고객 주문 이력과 주문별 상태, 5단계 완료 표시, VAT·결제 안내, 금액 도착 소리·진동, 결제 이미지 재전송, Cashier의 Grab 확인 후 수동 완료를 추가했다. V1 공개 API는 유지하고 새 고객 기능은 V2 API로 연결했다.

## 1. 개선 방향

고객이 결제 금액 도착을 알아차리고, VAT가 포함된 정확한 송금액을 확인한 뒤, **결제하기 → QR·은행 정보 확인 → 송금 → 이미지 제출 → Cashier 확인** 순서로 진행하도록 구성한다. 잘못된 이미지는 Cashier가 사유와 함께 재전송을 요청하고 고객이 같은 주문에서 다시 제출한다.

‘결제하기’는 기존 계좌이체 안내 화면에 진입하는 버튼으로 정의한다. 실제 입금 확인과 Cashier 승인으로 결제가 완료되는 현재 작업본의 계약을 따른다. 이미지 제출·재제출과 실제 입금 확인은 별도의 사실로 표시한다.

**최종 주문 완료는 Cashier가 Grab에서 고객에게 배송이 완료된 것을 확인하고 ‘주문 완료’를 누른 시점**으로 정의한다. 고객과 Cashier는 주문번호별로 독립된 진행 상태를 확인하며, 완료된 주문에는 ‘주문이 완료되었습니다’를 명확히 표시한다. 진행 중인 주문이 있어도 추가 주문을 접수하고 각각 추적할 수 있도록 설계한다.

## 2. 현재 소스에서 확인한 사항

| 항목 | 현재 구현 | 개선 필요 사항 |
|---|---|---|
| 고객 갱신 | `_startStatusPolling`이 2초마다 상태를 조회 | 새 견적·재전송 요청 감지, 소리·진동·지속 안내 추가 |
| VAT | DB 견적에 메뉴·서비스비·배송비별 세전 금액과 VAT 저장. `final_total`에 이미 포함 | 공개 상태 응답·Flutter 모델·고객 및 Cashier 금액 표시에 VAT 전달 |
| 결제 화면 | 견적 카드에서 QR·예금주·계좌번호·이미지 업로드를 바로 표시 | 결제하기 버튼과 결제 안내 화면으로 정리, 은행명·복사 기능 추가 |
| 은행 정보 | `DirectOrderBank`에 `label`, `accountNumber`, `accountHolder`, `bin` 존재 | 기존 데이터를 사용해 은행명·계좌번호·예금주 표시 |
| 이미지 재전송 | 고객 버튼은 `quoted + active`에서만 표시. 첫 제출 후 `awaiting_payment_review + locked`로 전환되어 버튼이 사라짐 | 재전송 요청 상태를 고객에게 전달하고 업로드 버튼 재활성화 |
| 서버 업로드 | 기존 commit RPC는 `quoted`, `awaiting_payment_review` 모두 허용하며 새 경로의 이미지를 추가 가능 | Cashier 재요청 사유·회차·최신 이미지 식별·경합 제어 추가 |
| 만료 | proof commit은 잠긴 견적에도 `expires_at > now()`를 요구. 후속 migration의 승인은 잠긴 견적의 기존 TTL 만료를 허용 | 첫 제출과 요청받은 재제출의 만료 규칙을 구분 |
| 승인 | 최근 작업본은 매장·금액이 일치하는 검증된 SePay 입금과 Cashier 승인을 요구 | 재인증 기능에서도 이 조건 유지 |
| API 호환성 | 고객 모델이 알 수 없는 응답 필드를 거부 | 기존 응답에 필드를 즉시 추가하지 않고 버전별 응답 계약 제공 |
| 최종 상태 | 고객 진행 단계에서 `dispatched`와 `completed`가 같은 마지막 단계. 완료 감지 시 active request를 지우고 메뉴로 이동 | 배송 중과 최종 완료를 분리하고 완료 카드·상세·완료 시각 유지 |
| 완료 버튼 | 주방 화면에서 `dispatched → completed` 가능. 공통 RPC가 kitchen·cashier·관리자 역할을 허용 | Cashier 주문 상세에 완료 버튼 추가, 최종 완료 권한과 확인 기록 보강 |
| 복수 주문 | 고객 저장소는 매장별 주문 ID 한 개. DB unique index와 submit RPC가 세션당 승인 전 주문 한 건으로 제한 | 주문 목록·선택 상태·주문별 재시도를 분리하고 동시 접수 제한 변경 |
| Cashier 목록 | 요청 상태 중심이며 최신 list RPC는 해당 날짜 접수분만 조회 | 조리·배송·완료 상태를 함께 표시하고 날짜를 넘긴 미완료 주문도 추적 |

현재 저장소에는 관련 기능을 포함한 사용자 수정·미추적 파일이 다수 존재한다. 후속 구현은 그 변경을 기반으로 최소 범위에서 진행한다. 위 내용은 소스 근거이며 운영 반영 여부를 증명하지 않는다.

## 3. 주문 상태 표시와 Cashier 최종 완료

### 고객·Cashier 공통 상태

주문번호를 기준으로 주문 상태와 결제 상태를 함께 표시한다. ‘결제 확인 완료’와 ‘주문 완료’는 서로 다른 단계이며, 조리·배달은 기존 fulfillment 상태를 기준으로 표시한다.

| 서버 근거 | 고객 표시 | Cashier 표시·행동 |
|---|---|---|
| `awaiting_quote` | 결제 금액 확인 중 | 금액 안내 대기 |
| `quoted` | 결제 대기 | 고객 결제 대기 |
| `awaiting_payment_review` | 입금 확인 중 / 이미지 재전송 요청 | 입금 검토 / 이미지 재제출 대기 |
| `approved` + `pending` | 결제 확인 완료 · 조리 대기 | 조리 대기 |
| `preparing` | 조리 중 | 조리 중 |
| `ready` | 조리 완료 · 기사 픽업 대기 | 픽업 대기 |
| `dispatched` | 배달 중 | 배달 중 · Grab 배송 확인 |
| Cashier가 확정한 `completed` | **주문이 완료되었습니다** | **주문 완료** · 처리자·완료 시각 |
| 거절·취소·만료 | 해당 상태와 사유 | 정상 완료와 구분된 종료 상태 |

고객 진행 단계에는 ‘배달 중’ 다음에 독립된 ‘주문 완료’ 단계를 둔다. `approved`는 결제·주문 승인 상태로 유지하고, 기존 `direct_delivery_fulfillment_tickets.status=completed`를 최종 이행 완료의 기준으로 사용한다. 요청 상태 enum에 중복된 완료 상태를 새로 만들지 않는다. KO/VI/EN 문구와 상태 판단은 고객·Cashier에서 일관되게 적용한다.

### Cashier의 Grab 배송 확인 → 주문 완료

1. Cashier가 주문번호별 상세에서 ‘Grab 배송 확인’을 눌러 해당 주문의 Grab 추적 화면을 연다.
2. 고객에게 배송이 완료된 것을 확인한 후, 해당 주문의 **‘주문 완료’** 버튼을 누른다. 확인 화면에는 주문번호·주문 요약과 ‘Grab에서 고객에게 배달 완료된 것을 확인했습니다’를 표시한다.
3. 서버가 해당 매장 접근 권한, Cashier 또는 기존 운영 관리자 역할, 주문·티켓 연결, 현재 `dispatched` 상태와 기대 버전을 검증한 뒤 `completed`로 전환한다.
4. 완료 시각·처리자·전후 상태를 감사 이력에 남긴다. 고객 화면에는 다음 정상 상태 조회에서 ‘주문이 완료되었습니다’와 주문번호·완료 시각을 표시한다. Cashier 목록에서도 해당 주문만 완료로 이동한다.

- 결제 승인, Grab 링크 전송·열람, 기사 인계, 시간 경과만으로 최종 완료시키지 않는다. Grab 화면의 배송 완료 여부는 Cashier가 직접 확인하며 자동 판정 연동을 추가하지 않는다.
- 주방의 조리 시작·조리 완료 권한은 유지하되, 최종 `completed` 변경 버튼은 Cashier 업무로 이동한다. 공통 transition RPC에서도 kitchen 역할의 최종 완료를 차단해 이전 주방 클라이언트의 직접 호출로 우회되지 않게 한다.
- 기존 transition의 행 잠금·버전 검증을 재사용한다. 중복 클릭·응답 유실·두 Cashier 동시 완료는 한 번만 반영한다. 재조회 결과 이미 완료되었다면 기존 완료 결과를 표시하고 처리자·시각을 덮어쓰지 않는다.
- 완료 처리 오류·오프라인 시 성공 표시를 먼저 하지 않는다. 주문을 배달 중 상태로 유지하고 재조회·재시도를 제공한다. 다른 주문으로 전환한 뒤 도착한 응답은 원래 주문에만 반영한다.
- 이 동작은 배송 완료 확정이다. 기존 결제·재고·매출·주방 티켓·Bill·MISA 작업을 다시 만들지 않는다. `completed`의 일반적인 역방향 전환은 제공하지 않는다.

### 고객의 여러 주문 표시·접수

고객 화면에 **‘내 주문’** 진입점과 진행 중·완료·기타 종료 목록을 제공한다. 각 카드에는 주문번호, 접수 시각, 품목 요약, 최종 금액 또는 금액 확인 중, 주문 상태, 결제·재전송 상태를 표시한다. 카드를 누르면 그 주문의 결제 안내·이미지·채팅·Grab 추적 상세를 연다.

예: 같은 고객의 `주문 A — 배달 중`, `주문 B — 결제 대기`, `주문 C — 주문 완료`를 동시에 표시한다. 금액 안내·이미지 재요청 알림에도 주문번호를 넣고, 알림을 누르면 해당 주문으로 이동한다.

- 진행 중에도 ‘추가 주문하기’를 제공한다. 새로운 장바구니·제출 식별자로 접수하며 기존 주문을 지우거나 다시 제출하지 않는다. 매장 CLOSED·접수 마감은 새 주문에 기존대로 적용하고 기존 주문 추적은 유지한다.
- 고객의 단일 active request 저장을 ‘주문별 상태 + 현재 선택한 주문 ID + 작성 중 장바구니/제출 재시도 정보’로 분리한다. 기존 저장된 주문 ID는 새 목록에서 복구한다. 새 주문 작성·주문 전환·완료 처리 때문에 다른 주문의 이미지·채팅·재시도 키를 초기화하지 않는다.
- 인증된 고객 세션에 속한 주문 목록을 반환하는 공개 API/RPC를 추가한다. 기존 `session_id`와 비밀값 검증을 사용하고 페이지네이션·보관 기간을 적용한다. 로컬 저장은 선택 상태와 복구 보조 용도로 사용하며 상태와 소유권 판단은 서버에서 한다.
- 1차 고객 식별 범위는 같은 매장의 동일 브라우저 유효 세션이다. 이름·전화번호 일치만으로 서로 다른 세션 주문을 합치지 않는다. 다른 기기·새 브라우저·세션 만료 후 주문 복구는 별도 소유권 인증이 필요한 확장 범위로 명시한다.
- 동시 접수를 위해 `direct_order_requests_one_open_per_session` unique index와 submit RPC의 `DIRECT_ORDER_OPEN_REQUEST_EXISTS` 조건을 함께 변경한다. 기존 세션 인증·요청 빈도 제한·`client_request_id` 멱등성은 유지한다. 새 주문은 새 키, 동일 제출 재시도는 같은 키를 사용한다.
- 단일 `pendingSubmit`도 주문 작성 건별로 분리해 두 탭·빠른 연속 접수·실패 후 재시도에서 서로 다른 주문을 같은 요청으로 취급하거나 중복 생성하지 않게 한다.
- 목록은 진행 중 주문 요약을 한 번에 갱신하고 선택한 주문의 상세만 추가 조회한다. 주문 수만큼 기존 2초 polling을 복제해 요청 제한을 초과하지 않게 한다. 모든 응답·알림을 주문 ID와 상태 버전으로 반영한다.
- 완료 주문은 목록·상세에 완료 문구와 완료 시각을 유지한다. 기존 `_finishCompletedOrder`의 주문 제거·전체 장바구니 초기화·강제 메뉴 전환을 해당 주문 카드의 완료 갱신으로 대체한다. 고객이 보고 있는 완료 상세와 작성 중인 다른 주문을 보존하며 ‘추가 주문하기’와 ‘내 주문 보기’를 제공한다.

### Cashier의 주문별 관리

- 기존 주문별 목록을 확장해 ‘금액 안내 대기 / 결제 확인 / 조리 중 / 픽업 대기 / 배달 중 / 주문 완료’로 필터링한다. 동일 고객 주문도 주문번호별 독립 행으로 유지한다.
- 요청 상태와 fulfillment 상태를 함께 반환하도록 staff list/detail을 보완한다. 주문 완료 여부를 `request.state=approved`만으로 판단하지 않는다.
- 진행 중 목록은 날짜가 바뀌어도 미완료 주문을 유지한다. 완료 목록은 업무 날짜·기간 필터와 페이지네이션을 적용한다. 기존 일마감·주문 접수 마감 시각 자체를 변경하지 않는다.
- `completed_at`은 고객에게, 완료 처리자·상태 버전은 권한 있는 Cashier에게 필요한 범위로 제공한다. 기존 API 응답 계약의 하위 호환 방식도 동일하게 적용한다.

## 4. 고객 결제 금액 알림

### 사용자 경험

1. 주문 요청 단계에 ‘결제 안내 알림’ 설정을 제공한다. 주문 요청 클릭처럼 고객의 직접 조작 시 오디오를 준비하고, 소리 켜기·끄기를 제공한다. 알림 사용 여부가 주문 진행을 막지 않는다.
2. 첫 견적 도착 시 짧은 알림음 1회와 지원 기기의 짧은 진동을 실행한다. 화면에는 ‘결제 금액이 도착했습니다’와 총액, ‘결제하기’를 표시한다.
3. Cashier가 견적을 다시 보내면 ‘결제 금액이 변경되었습니다’로 안내한다. 이미지 재전송 요청에는 요청 사유와 ‘이미지 다시 보내기’를 표시한다.
4. 안내는 고객이 확인하거나 관련 상태가 해소될 때까지 남긴다. 색상·소리에만 의존하지 않고 텍스트와 접근성 알림을 함께 제공한다. 입력 중인 채팅이나 업로드를 강제로 닫지 않는다.

### 처리 규칙

- 견적 이벤트 키는 `request_id + quote.id/version`, 재요청 키는 `request_id + review_request_id`로 구분한다. 일반 polling이나 채팅 도착으로 결제 알림을 반복하지 않는다.
- 마지막 처리 이벤트를 주문별로 저장해 새로고침 시 반복음을 막는다. 확인하지 않은 현재 안내는 다시 표시한다. 복귀 시 오래된 이벤트를 연속 재생하지 않고 최신 유효 상태를 알린다.
- 전면 온라인 상태에서 다음 정상 polling 응답 직후 안내한다. 2초 주기는 보통의 조회 간격이며 네트워크 지연까지 포함한 도착 보장은 아니다.
- 브라우저 전면 복귀·네트워크 복구 시 즉시 재조회한다. 늦게 도착한 이전 주문 응답이나 낮은 견적 버전이 최신 화면·알림을 덮어쓰지 못하게 한다.
- 기존 Direct Order 오디오 구현을 재사용하되 고객의 알림 설정과 이벤트 관리는 고객 화면 범위에 둔다.

브라우저는 소리 자동 재생을 제한하므로 직접 조작 시 오디오 준비 및 실패 처리가 필요하다. 진동 API는 일부 브라우저·기기에서 지원되지 않고 사용자 조작이 필요하므로 실행 가능 여부를 검사한다. 미지원 또는 차단 시에도 화면 안내는 항상 동작한다. 근거: [MDN 자동 재생 정책](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), [MDN 진동 API](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate).

1차 완료 범위는 열린 주문 화면의 알림과 복귀 시 상태 복구다. 화면 잠금·브라우저 종료 중 알림이 필요하면 2차 Web Push 범위로 진행한다. 이때 구독·권한·서버 발송·재시도·만료 구독 정리가 필요하며, iOS/iPadOS는 홈 화면 웹 앱과 사용자의 알림 허용 조건을 반영해야 한다. 근거: [WebKit Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

## 5. VAT 표시

### 기본 표시안

기존 VAT 포함 항목 금액을 유지하고, 최종 금액 아래에 **‘포함된 VAT’**를 별도로 표시한다. 금액 상세를 펼치면 메뉴·서비스비·매장 수취 배송비의 VAT를 각각 볼 수 있게 한다. 고객 화면과 Cashier 화면이 동일한 견적을 사용한다.

설명용 예시이며 실제 주문 금액은 서버 견적을 사용한다.

| 항목 | 금액 |
|---|---:|
| 메뉴 금액 · VAT 포함 | 216,000 VND |
| 서비스비 · VAT 포함 | 10,800 VND |
| 매장 수취 배송비 · VAT 포함 | 30,000 VND |
| **최종 결제 금액** | **256,800 VND** |
| 위 금액에 포함된 VAT | 16,800 VND |

- `vat_total = menu_vat + service_charge_vat + delivery_fee_vat`를 견적 스냅샷에서 읽어 서버 응답으로 전달한다. 이미 VAT가 포함된 `final_total`에 다시 더하지 않는다.
- 세전·VAT 상세는 기존 `*_pretax`, `*_vat` 값을 사용한다. 고객 화면에서 세율을 적용해 역산하거나 현재 매장 설정으로 과거 견적을 재계산하지 않는다.
- 여러 세율이 섞인 주문은 ‘VAT 합계’로 표기한다. 전체 주문을 하나의 세율로 표시하지 않는다. 기존 inclusive/exclusive 계산 정책과 견적 확정 금액을 유지한다.
- `delivery_payment_mode=customer_direct`이면 ‘배송비는 기사에게 별도 결제’로 표시하고 매장 송금액에 넣지 않는다. 고객 API에도 주문별 배송비 지급 방식을 전달한다.
- VND 표시는 기존 formatter와 서버 금액 정밀도를 점검한다. 세전·VAT·최종 금액·QR 금액 사이에 반올림 차이가 생기면 구현 단계에서 공통 표시 규칙을 확정하고 검증한다. 이번 표시 변경으로 원장 금액을 임의 보정하지 않는다.

## 6. ‘결제하기’ 화면

견적 카드에는 금액 내역과 큰 ‘결제하기’ 버튼을 둔다. 클릭하면 모바일은 시트 또는 전용 화면, 컴퓨터는 충분한 폭의 다이얼로그로 결제 안내를 연다.

표시 순서:

1. 주문번호와 최종 송금액, 포함된 VAT.
2. 해당 금액·계좌·주문 참조코드가 담긴 기존 VietQR.
3. 은행명, 계좌번호와 ‘복사’, 예금주.
4. 송금 내용인 주문 참조코드와 ‘복사’.
5. ‘송금 후 결제 이미지를 첨부해 주세요’ 안내와 이미지 선택·미리보기·제출.

계좌번호는 문자열로 다루어 앞자리 0과 긴 번호를 보존한다. 복사 성공 시 짧은 확인을 표시하고, 복사 실패 시 선택 가능한 원문을 유지한다. 같은 휴대폰에서 주문과 송금을 진행하는 고객도 계좌 복사로 은행 앱을 이용할 수 있어야 한다.

결제 안내를 열 때 최신 상태를 조회하고 서버가 반환한 동일 견적·은행 정보로 QR과 텍스트를 구성한다. 은행명은 기존 `bank.label`을 우선 사용하며 비어 있으면 설정 보완 대상으로 처리하고 이름을 추측하지 않는다. 필수 계좌 정보가 유효하지 않으면 송금 안내 오류를 표시한다.

견적 교체·만료·주문 종료를 감지하면 이전 QR과 제출 동작을 무효화하고 현재 상태를 안내한다. 업로드 요청·commit에는 고객이 확인한 견적 ID/버전을 연결하여 다른 견적에 이미지가 잘못 귀속되지 않게 한다. 이 단계의 버튼 클릭 자체는 입금 또는 결제 완료로 기록하지 않는다.

이미지 제출 이후에는 ‘입금 확인 중’과 제출 정보를 보여준다. Cashier가 재전송을 요청하면 ‘이미지 다시 보내기’가 표시되며 **‘이미지를 다시 보내 주세요. 다시 송금하지 마세요’**를 명시한다.

## 7. Cashier 이미지 재인증 요청

### 업무 흐름

1. 승인 전 주문의 이미지 검토 영역에 ‘결제 이미지 재전송 요청’ 버튼을 추가한다.
2. 사유를 선택한다: 이미지가 흐림 / 거래 내용 확인 불가 / 다른 거래 이미지 / 금액 확인 필요 / 기타. 기타 선택 시 설명을 입력한다. 미리보기에서 고객에게 전달될 문구를 확인하고 요청한다.
3. 고객 화면에 사유·요청 시간과 재전송 버튼을 표시하고 결제 안내와 같은 알림 방식으로 알린다.
4. 고객이 새 이미지를 미리보기 후 제출하면 Cashier에 최신 이미지가 도착한다. 이전 이미지와 재요청 이력도 확인할 수 있게 한다.
5. 필요하면 Cashier가 새 회차의 재전송 요청을 할 수 있다. 같은 회차의 중복 요청은 한 건으로 처리한다.

### 상태와 승인 규칙

주문은 `awaiting_payment_review`, 견적은 `locked`를 유지한다. 이미지 관련 상태는 별도로 관리한다.

| 이미지 상태 | 허용 동작 | 다음 상태 |
|---|---|---|
| 최초 제출 후 검토 중 | Cashier가 사유와 함께 재전송 요청 | 재전송 대기 |
| 재전송 대기 | 고객이 현재 요청에 새 이미지 제출 | 재제출 이미지 검토 중 |
| 재제출 이미지 검토 중 | 검토 후 승인 또는 새 재전송 요청 | 승인 또는 다음 회차 재전송 대기 |

- 권고 운영 규칙: Cashier가 명시적으로 재전송을 요청한 동안은 승인 버튼과 서버 승인 경로를 보류한다. 새 이미지가 접수되면 기존 실제 입금 검증 조건으로 승인을 진행한다. 재요청이 없으면 기존 이미지 없는 검증 입금 승인 경로도 유지한다.
- 이미지 재요청은 기존 검증 입금을 취소하거나 새로운 송금을 요구하는 동작이 아니다. 기존 결제·입금 매칭을 유지한다.
- 이미 승인·거절·취소된 주문에는 재요청·재제출을 허용하지 않는다. 금액 변경이 필요한 문제는 이미지 교체로 해결하지 않는다.
- 승인 보류 조건은 모든 외부 주문 승인 진입점과 공통 승인 함수에 적용해 우회를 막는다. 입금이 검증되지 않은 주문은 이미지가 있어도 승인할 수 없다.

### 서버와 이력

- `direct_order_proof_review_requests` 같은 작은 재요청 이력 테이블을 추가한다. 주문·매장·견적·대상 이미지·요청자·사유 코드/메모·요청 시각·완료 이미지/시각을 보존한다. 주문당 열린 재요청은 최대 1개다.
- 새 Cashier RPC는 매장 접근 권한과 역할, 검토 상태, 대상 견적·이미지를 검증한다. 주문 잠금과 기대 회차/ID 검증으로 두 Cashier의 중복 요청·동시 승인을 직렬화한다.
- 공개 상태 API는 고객에게 필요한 재요청 ID·사유·시각·제출 가능 여부만 제공한다. 직원 내부 식별자나 Storage 경로는 공개하지 않는다. 버튼 표시 조건과 서버 검증 조건을 일치시킨다.
- 기존 `direct-order-proofs` 저장소와 이미지 검증을 재사용한다. 새 이미지는 새 경로에 추가하고 기존 이미지를 덮어쓰거나 삭제하지 않는다. 현재 최신 이미지와 과거 이미지를 명확히 구별한다.
- signed upload URL 발급 시와 commit 시 모두 세션·주문·견적·현재 재요청·상태를 검증한다. 기존 MIME·파일 크기·실제 이미지 검증과 비공개 접근 규칙을 유지한다.
- 최초 제출은 유효한 active 견적을 요구한다. 요청받은 재제출은 해당 locked 견적에 연결된 열린 재요청이 있으면 최초 견적의 browsing TTL이 지나도 허용하도록 보완한다. 세션 유효성·주문 종료·기존 보관 기간 제한은 계속 적용한다.
- 업로드 실패 시 재요청은 대기 상태로 남는다. commit 응답 유실 후 같은 이미지·요청으로 재시도하면 같은 결과를 반환한다. 이전 요청의 늦은 업로드가 새로운 회차를 완료하지 못하게 한다.
- 승인·거절과 업로드가 경합하면 먼저 확정된 상태를 따르고 이미지나 결제 이력을 섞지 않는다. 완료되지 않은 파일은 기존 orphan 정리 경로를 사용한다.
- 사유 코드는 KO/VI/EN으로 번역하고 고객·Cashier 각자의 화면 언어로 표시한다. 자유 입력 메모는 기존 번역 정책에 맞추어 처리한다.

## 10. 배포와 운영 확인

현재 엄격한 디코더 때문에 서버가 기존 응답에 VAT·재요청 필드를 일괄 추가하면 열려 있는 고객 탭이 실패할 수 있다. **기존 요청은 기존 응답 유지, 새 클라이언트만 명시적으로 새 계약 요청** 방식을 우선한다. 예를 들어 Edge 요청의 계약 버전으로 기존 projection과 확장 projection을 분리한다. 새 클라이언트가 구 서버를 만나면 기능 준비 중 상태 또는 기존 흐름을 제공하며 없는 VAT를 0으로 표시하지 않는다.

하위 호환 서버를 먼저 준비하고 새 고객·Cashier를 배포한 뒤 기능을 활성화한다. 진행 중 주문과 구 클라이언트의 재제출 불가 상황은 새로고침/업데이트 안내로 복구하며, 구 API가 재요청 승인 보류를 우회하지 못하도록 서버 조건은 공통 적용한다.

수동 완료 권한 변경은 새 Cashier 완료 화면을 사용할 수 있는지 확인한 뒤 활성화해 주방에서도 Cashier에서도 완료할 수 없는 배포 공백을 막는다. 이미 여러 미결제 주문이 만들어진 뒤에는 기존 ‘세션당 한 건’ unique index를 무조건 재생성할 수 없으므로, 복수 주문 중단 시 신규 접수를 제어하고 기존 주문을 보존하는 복구 절차를 마련한다.

릴리스 시 `CLAUDE.md`의 정확히 push된 head SHA에 대한 필수 GitHub Actions 성공과 `scripts/deploy_pos_production.sh` 절차를 따른다. 소스 구현, migration 적용, Edge/Web/native 배포, 실제 운영 검증을 각각 기록한다. 파일럿에서는 두 Cashier·고객 휴대폰으로 복수 주문의 금액 안내·재제출·입금 승인·Grab 배송 확인·Cashier 수동 완료·주문별 완료 표시까지 확인한다. MISA 및 출력 실패가 결제를 중복 처리하지 않는 기존 계약도 유지한다.
