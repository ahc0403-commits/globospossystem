# 신규 주문 시스템 파일럿 개선 계획

작성: 2026-09-08 · 기준: `origin/main` 67c08526에서 분리한 배포 작업본

이 문서는 사용자 파일럿 보고와 현재 소스·SQL·기존 설계를 대조한 개선 계획과 구현 결과다. 운영 DB, 배포 버전, 실제 입금, 실물 프린터는 이번 작업에서 확인하지 않았다. 소스 구현 / migration 적용 / 배포 / 매장 검증을 별도로 판정한다.

## 구현 상태 · 2026-09-08

현재 작업본에는 다음 항목이 **소스 구현 및 로컬 검증 완료** 상태로 반영됐다.

- Cashier 승인 조건을 같은 매장·최종 금액의 실제 SePay 입금 연결로 강제했다. 입금증 이미지는 보조 자료이며, 동일 공급자 거래는 한 주문에만 연결된다.
- 배송비 지급 방식을 주문별로 `customer_direct`와 `store_prepaid`로 저장한다. 신규 주문 기본값은 고객이 기사에게 직접 지급하는 방식이며 매장 결제·Bill·현금 지출에서 배송비를 제외한다.
- 주문 선택 시 배송비·메모·Grab 링크·실제 기사비 입력을 모두 해당 주문 값으로 다시 구성하고, VND 입력을 `30.000` 형식으로 통일했다.
- 결제 승인 시 고객 Bill 최초 job을 멱등하게 생성하고 Cashier에서 상태 확인, 실패 재시도, 완료 후 명시적 재출력을 제공한다. 출력 장애는 결제를 롤백하지 않는다.
- 고객 화면은 배달 완료 상태를 받으면 이전 주문 상태·장바구니·메모를 정리하고 Reload 없이 메뉴로 자동 복귀한다.
- 기존 OPEN/CLOSED 접수 제어를 유지하고, 배차 시 `ready → dispatched` 전이를 복구했다.

신규 migration은 disposable PostgreSQL에서 적용하고 결제·배송비·Bill·상태·권한 계약을 실행했다. 직접 주문 Flutter 테스트 48개, Edge 테스트 22개, 기존 SQL 회귀 7종, 동일 작업 경합 50회와 종료 상태 경합 3회를 통과했으며 `dart analyze`와 Web release build도 성공했다. `scripts/check_repo.sh`는 전체 Flutter 테스트 단계에서 이번 작업 전에 변경되어 있던 `payment_total_calculator.dart`와 생성 localization 파일의 frozen hash 불일치 2건으로 중단됐다. 해당 기대값을 임의로 갱신하지 않았고, 이번 기능의 SQL 오류 레지스트리 누락은 수정 후 별도 테스트로 통과시켰다. 운영 migration 적용, 앱 배포, 실계좌 입금, 실물 프린터 확인은 아직 수행하지 않았다.

## 범위와 권고

보고서의 배송비·기사 호출·고객 주문 링크를 근거로, 우선 `/order/:storeSlug`의 직접 배달 주문(Direct Order)을 대상으로 해석한다. POS 일반 포장, 홀 QR 주문, Deliberry는 별도 흐름이다. 고객이 직접 수령하는 포장 주문도 동일하게 중지해야 한다면 적용 채널을 추가로 확정해야 한다.

**실매장 확대 전 필수 조건은 실제 입금에 근거한 주문별 승인, 주문별 금액 보존, 완료 후 연속 주문, 실물 Bill 출력이다.** 신규 주문 알림은 정상 기능으로 유지한다. 배송비 운영 방식은 합계·입금 매칭·Bill·일마감에 영향을 주므로 구현 전에 먼저 고정한다.

## 현재 소스에서 확인한 사항

| 영역 | 확인한 사실 | 해석과 남은 확인 |
|---|---|---|
| 입금 승인 | `direct_order_approve_payment`는 입력 금액과 잠긴 견적, 입금증 첨부를 검사한다. 실제 은행 거래 연결을 필수 조건으로 검사하지 않는다. | 사용자가 보고한 결제 위험을 서버에서 차단하는 추가 구현이 필요하다. |
| 입금 후보 | SePay 거래 원장·알림·후보 연결 기능은 있다. 후보는 같은 매장·같은 금액·최근 2일 기준이며, 후보 테이블의 unique는 `(request_id, sepay_transaction_id)`다. | 후보와 주문 확정 증빙을 구별해야 한다. 같은 금액의 다른 주문과 동일 거래의 중복 소비를 막는 조건이 필요하다. |
| 배송비 저장 | `direct_order_quotes`가 요청·견적 버전별 배송비를 저장하고, `direct_order_financials`가 승인 시 주문·결제별 값을 저장한다. 견적 변경 SQL은 해당 요청으로 제한된다. | 소스상 주문별 저장 구조는 이미 있다. 운영 DB 전체가 덮어써졌다고 아직 단정할 수 없다. |
| 배송비 입력 | 캐셔 화면에 `_feeController`가 하나 있고 주문 선택 시 초기화·견적값 재주입이 없다. `_seedDispatchInputs`도 배차 값이 없을 때 이전 실제 배송비·URL을 지우지 않는다. | 다른 주문의 입력값이 남을 수 있는 명확한 코드 위험이다. 실제 저장 오류 범위는 재현으로 구분한다. |
| 금액 파싱 | 출력에는 `NumberFormat('#,###', 'vi_VN')`를 사용하지만 입력 formatter가 없고, 저장 시 쉼표만 제거한다. | `30.000`을 입력하면 `30`으로 파싱할 수 있으므로 표시와 파싱을 함께 수정한다. |
| 고객 화면 | 2초 상태 조회 및 종료 상태의 `새 주문` 버튼이 이미 있다. 완료 시 polling만 중단하고 active request를 자동 해제하지 않는다. | 자동 전환 요구는 충족하지 않는다. 파일럿의 수동 Reload 필요 현상은 배포 버전·완료 상태 전파도 함께 확인해야 한다. |
| Bill | 직접 주문 화면에는 기사 전달용 출력·재출력 버튼과 전용 RPC가 있다. 출력 상태 조회 오류는 빈 상태로 처리한다. | 기사 전달용 영수증이 고객 Bill을 대신한다고 가정하면 안 된다. 누락된 출력 요청, 오류가 가려지는 UI, 단말·프린터를 각각 확인한다. |
| 일시중지 | 현재 작업본에 cashier OPEN/CLOSED, 매장별 최소 권한 RPC, 고객 CLOSED 화면과 테스트가 추가되어 있다. | 신규로 다시 설계하기보다 기존 변경의 배포·검증을 완료한다. 기존 문서는 실매장·배포 미완료로 기록한다. |
| 실제 배송비 | 9월 7일 작업본 migration은 기사 호출 시 실제 배송비를 필수 입력받고 매장 현금 지출로 일마감에서 차감한다. | 고객이 기사에게 직접 지급하는 운영 방식과 충돌하므로 UI 문구만 바꿔서는 안 된다. |
| payOS | 별도 자동화 작업은 어댑터·MOCK 준비 단계다. 해당 V1 계획은 Direct Delivery를 후속 범위로 둔다. | 일반 POS payOS 작업이 이번 직접 주문 결제까지 해결한다고 볼 수 없다. |

## 실행 작업

### T0. 재현 기준과 운영 방식 확정

담당: 개발 + 매장 운영. 나머지 금액·결제 작업의 선행 조건.

- 파일럿 매장, 고객 링크, 캐셔 OS·앱 빌드/SHA, Edge 버전, 적용 migration 목록, 프린터 모델·연결 방식을 기록한다. 개인정보·인증정보는 진단 문서에서 제외한다.
- 배송비가 달랐던 A/B 주문의 요청 ID, 견적 버전, 결제·Bill 금액과 입력/저장 전후를 확보한다. 읽기 조회로 `quotes → financials → order_items/payments → dispatches → print payload`를 대조한다.
- “주문 완료”를 요청 제출, 입금 승인, 조리 완료, 배달 완료로 구분한다. 현재 financial `orders.status=completed`는 결제 승인 시 만들어지므로 배달 완료를 의미하지 않는다.
- Bill은 우선 **고객 결제 영수증**으로 정의하고 기사 전달용 문서와 출력 목적을 구분한다. 자동 출력은 기본 1회, 이후 출력은 명시적 재출력으로 계획한다.
- 실계좌·은행·입금 공급자의 연결 가능 여부를 확인해 SePay 또는 payOS 중 이번 파일럿의 한 경로를 선택한다. 코드 보유량만으로 운영 준비 완료를 판단하지 않는다.

산출물: 재현 기록, 금액 변경 전후 비교, 채널·완료 시점·입금 경로 결정표.

### T1. 주문별 배송비 보존 및 VND 입력 수정

담당: Flutter + DB. T0 재현을 기준으로 진행.

1. 주문 변경 시 배송비·견적 메모·실제 기사비·추적 URL을 해당 주문의 값으로 다시 구성한다. 값이 없는 필드는 비우고 완료 주문은 저장된 값을 읽기 전용으로 보여준다. 주기적 조회는 현재 주문에서 편집 중인 입력을 임의로 덮어쓰지 않는다.
2. 비동기 조회·저장·승인창에는 요청 ID와 견적 버전을 고정한다. A 작업 응답이 늦게 와도 B 화면을 덮어쓰거나 B로 저장되지 않게 한다. 상태 조회 실패 시 이전 주문 값으로 작업하지 못하게 한다.
3. 요청·매장 범위, 견적 버전, 잠금 상태를 서버에서도 재검증한다. 확정된 견적·결제 금액은 일반 수정으로 변경하지 않고 필요한 정정은 별도 근거와 이력을 남긴다.
4. VND 정수 입력을 공통 처리한다. 표시 `30.000`, 내부 숫자 `30000`, 서버 전달값 `30000`을 분리한다. 숫자·정상 천 단위 형식 붙여넣기를 지원하고 음수·소수·모호한 구분자·초과 금액은 안내와 함께 거절한다. 빈 값과 0도 구분한다.
5. 운영 DB 변경이 확인되면 영향 주문을 먼저 추출하고 원견적·결제·출력 증빙과 대조한 복구안을 만든다. 추정값 일괄 덮어쓰기나 과거 주문에 새 배송 정책 일괄 적용을 하지 않는다.

완료: A=30.000, B=45.000, C=0을 생성하고 A↔B↔C 전환·재접속·견적 수정·두 캐셔 동시 조작 후 각 주문의 저장값과 Bill이 일치한다. B 수정 전후 A의 승인 금액과 일마감 기초 데이터가 동일해야 한다.

### T2. 배송비 결제 방식과 정산 일치

담당: 운영 + Flutter + DB. T0에서 방식 확정, T1과 같은 금액 계약에 반영.

| 방식 | 고객의 매장 결제액 | 배송비 기록 | 매장 현금 지출 |
|---|---|---|---|
| 기본: 고객이 배송업체에 직접 지급 | 음식 및 기존 적용 세금·서비스료 | `고객 직접 지급`으로 명시. 예상 배송비가 있어도 매장 수취 합계에서 제외 | 발생하지 않음 |
| 예외: 고객 요청으로 매장 대납 | 음식 결제와 구분한 실제 배송비 청구/수취 | 기사 호출 시 실제 금액, 확인 시점, 고객 동의, 수취·지급 상태 | 실제 지급한 금액과 수단만 기록 |

- 주문별 배송비 지급 주체/방식, 매장이 고객에게 받은 배송비, 실제 기사비, 지급 시점·수단을 구분한다. 기존 확정 견적·financial snapshot은 보존한다.
- 매장이 기사 비용을 내지 않은 고객 직접 지급 주문은 `cash_paid_at`과 현금 차감 대상이 되지 않아야 한다. 추적 링크 전달만으로 현금 지출을 확정하지 않는다.
- 선택한 배달 서비스에서 수취인 직접 지급이 실제 가능한지 확인한다. 가능하지 않은 호출 방식은 기본 경로로 노출하지 않는다.
- 대납 시 최초 예상액으로 확정 청구하지 않는다. 호출 시 실제 금액을 확인하고 고객에게 안내한 후 수취·지급을 기록한다. 음식 결제가 이미 끝났다면 기존 음식 결제와 Bill을 다시 쓰지 않고 추가 청구/수취 기록으로 연결한다.
- 음식·배달비·총 매장 수취액을 고객 화면, 캐셔, QR, Bill, 보고서에서 동일하게 계산한다. 세금·서비스료 산식은 기존 계약을 유지하고 배송비의 회계 분류는 담당자에게 확인한다.
- 대납 기록과 추가 수취 검증을 해당 릴리스에서 완성하지 못하면 V1은 고객 직접 지급만 제공한다. 미구현 대납을 기존 배송비 입력으로 우회하지 않는다.

완료: 두 방식 각각에서 주문 합계, 확인할 입금액, Bill, 실제 현금 잔액과 일마감이 일치한다. 과거 거래는 이전 계약을 유지한다.

### T3. 실제 입금 검증과 주문별 승인 강제

담당: DB/Edge + Flutter, 계좌 설정은 매장 운영. T2의 매장 수취액 정의가 선행된다.

**입금 수신 → 해당 주문과 대조 → 캐셔 승인 → 기존 결제 처리**를 분리한다. 초기에는 검증된 입금 이후 캐셔가 최종 승인하는 방식으로 운영하며 무인 자동 승인은 필수 범위로 두지 않는다.

1. 기존 SePay 수집·알림 경로가 실계좌와 맞는지 먼저 확인한다. 실제 webhook 인증 설정과 검증 코드를 대조한다. SePay 공식 문서는 HMAC-SHA256 서명 및 timestamp/raw body 검증을 제공한다. [SePay 인증 규격](https://developer.sepay.vn/en/sepay-webhooks/xac-thuc).
2. payOS를 선택하면 기존 준비 작업을 재사용하되 직접 주문 요청과 견적에 연결하는 범위를 추가한다. **Direct Order의 실제 `orders` 행은 승인 시 생성된다.** 따라서 승인 전 입금 식별자는 `request_id + quote_id/version`에 연결하고 승인 후 `order_id/payment_id`로 이어져야 한다. 일반 POS의 기존 order ID 기반 결제만 연결해서는 부족하다. payOS 서명은 해당 공급자의 별도 규격을 사용한다. [payOS 서명 검증](https://payos.vn/docs/tich-hop-webhook/kiem-tra-du-lieu-voi-signature/).
3. 서버가 발급한 주문별 결제 식별자와 QR/송금 메모, 매장 수취계좌, 입금 방향, 기대 금액·통화, 견적 버전, 거래 시점을 대조한다. 같은 금액만으로 확정하지 않는다. API에 통화 필드가 없다면 검증된 계좌·연결 계약에서 VND를 고정한다.
4. 기존 `sepay_transactions.resolution_status=matched`는 계좌와 매장의 매핑 성공이며 주문 매칭 성공으로 해석하지 않는다. 후보 연결과 별도로 확정 증빙을 기록하고, 하나의 공급자 거래가 다른 주문에 재사용되지 않도록 DB unique 제약과 원자적 소비를 적용한다. 복수 공급자가 같은 입금을 수신할 가능성이 있으면 동일 주문/계좌의 처리 경로를 하나로 제한한다.
5. 입금 증빙 확정과 결제 승인을 같은 서버 트랜잭션에서 재검증한다. 기존 `process_payment` 및 직접 주문의 financial/ticket 생성 흐름을 재사용하고, 거래·요청 잠금과 멱등성으로 결제·주방 티켓을 한 번만 만든다. 최신 유효 `process_payment`는 8월 promotion wrapper까지 포함해 migration 순서로 확인한다.
6. 캐셔는 `입금 대기 / 입금 확인 / 금액·주문 확인 필요 / 결제 완료`를 구분한다. 예: `입금 확인: 150.000 VND · 주문 D12345678`. 상세에 거래 시각·참조번호를 보여준다. 고객 이미지와 수동 입력 금액만으로는 승인할 수 없고, UI 버튼뿐 아니라 RPC 직접 호출도 막는다.
7. 현재 입금증 업로드가 견적을 잠그고 검토 상태로 이동시키는 계약도 수정한다. 결제 시작 시 견적·입금 식별자를 잠그고, 검증된 입금만으로 이미지 없이 검토·승인이 가능하게 한다. 입금증은 보조 자료로 남긴다.
8. 중복 알림, 잘못된 계좌, 부족/초과 입금, 주문코드 누락, 취소/만료 후 입금, 이전 견적 입금은 별도 확인 대상으로 보존한다. webhook 지연·누락은 서버 거래 조회/대조로 복구하고, 단말 재접속 시 미처리 입금을 다시 보여준다.
9. 테스트 거래가 운영 결제로 승인되지 않도록 환경과 데이터 경계를 검증한다. 연동 장애 때 이미지 기반 승인으로 자동 전환하지 않는다. 매장 운영은 입금 검증이 복구될 때까지 승인·상품 전달을 보류한다.

완료: 정상 입금, 같은 금액의 두 주문, webhook 반복 10회, 두 캐셔 동시 승인, 위조/잘못된 인증, 과부족 입금, 다른 매장 거래, 지연 입금, 단말 종료·복귀를 검증한다. 실제 은행 거래가 없는 결제 승인과 한 거래의 두 주문 소비는 모두 0건이어야 한다. 결제 완료는 MISA나 프린터 가용성과 독립적으로 유지한다.

### T4. 고객 완료 화면 자동 전환과 연속 주문

담당: Flutter, 상태 API 문제 재현 시 Edge/DB.

- 기본 기준은 `fulfillment.status=completed`다. 입금 승인만으로 아직 진행 중인 배달 추적을 없애지 않는다. 보고서의 완료가 “접수 완료 직후”를 의미한다면 진행 주문 보존과 추가 주문 진입 범위를 별도 확정한다.
- 서버 완료를 받으면 active request와 장바구니·품목 메모·주문 메모·채팅 입력 등 이전 주문 작성 상태를 정리하고 메뉴로 자동 전환한다. 주문번호·완료 안내·기존 주문을 다시 볼 수 있는 최소 요약은 유지한다.
- 수동 Reload, 강제 페이지 재시작, 임의 타이머 경과를 완료 판정으로 사용하지 않는다. 기존 2초 상태 조회를 활용하고 전면 복귀·재접속 시 즉시 재조회한다.
- 완료 시 polling 중지뿐 아니라 상태 revision도 갱신한다. 지연된 이전 요청 응답이 새 주문 상태를 덮어쓰거나 새 polling을 중단하지 못하게 한다.
- 고객이 저장에 동의한 주소만 재사용한다. 단순 네트워크 조회 실패는 기존 주문의 삭제 근거가 되지 않아야 한다. `_load`의 모든 status 오류 시 active request 삭제 처리도 원인별로 좁힌다.
- 새 메뉴 진입 전 접수 가능 상태를 재확인한다. 매장이 CLOSED이면 완료 안내와 CLOSED 화면을 보여주고 신규 주문 접수는 차단한다.

완료: 전면 온라인 상태에서 서버 완료 후 한 번의 정상 polling 응답으로 자동 갱신되고, Reload 없이 두 번째 주문이 새 request/멱등키로 생성된다. 느린 이전 응답, 모바일 백그라운드 복귀, 종료 상태 복원, CLOSED 상태에도 주문이 섞이지 않는다. 거절·취소·만료는 사유를 보여주고 새 주문 진입을 제공한다.

### T5. 고객 Bill 출력 정상화

담당: Flutter/DB + 매장 단말·프린터 담당. T2/T3 금액·승인 계약을 따른다.

1. 실패 주문을 기준으로 `승인된 financial → 고객 Bill enqueue → print_jobs → 매장 receipt destination → 실행 중 print agent → USB/TCP 프린터` 순서로 확인한다. 기사 전달용 `delivery_driver_receipt`도 별도로 점검한다.
2. 결제 승인 후 고객 Bill의 최초 출력 요청을 1회 생성하고, 완료 주문 상세에서도 출력 상태·재시도·재출력을 제공한다. 요청 실패가 감춰지지 않도록 결제 완료/출력 미요청 상태를 구별하고 복구 시 누락된 최초 job을 생성한다.
3. 조리 완료나 배달 완료 시 같은 Bill을 반복 자동 출력하지 않는다. 이후 필요 출력은 재출력으로 기록한다. 사용자에게는 주문번호, 매장 수취액, 고객 직접 지급 배송비 안내가 구분되어 보여야 한다.
4. RPC 부재/상태 조회 실패, destination 미설정, agent 미실행, 연결 오류를 구분한다. 오류를 빈 상태나 출력 성공으로 표시하지 않는다.
5. 재시도는 실패한 job을 재사용하고 명시적 재출력만 새 이력을 만든다. 출력 직후 응답 유실처럼 실제 종이 출력 여부가 불확실하면 단말 확인을 거쳐 재출력한다. job 완료 기록만으로 종이 출력 성공을 단정하지 않는다.
6. 종이 부족·전원 차단·네트워크 단절에도 결제를 취소하거나 재결제하지 않는다. 기존 결제/영수증 원장과 비동기 MISA 처리를 유지한다.

완료: 실물 프린터에서 결제 직후 최초 Bill, 배달 완료 후 재출력, 장애 복구 출력을 확인한다. 금액·주문번호·베트남어·천 단위 표시를 대조하고 재출력 때문에 결제·재고·매출이 중복되지 않아야 한다.

### T6. 기존 주문 접수 일시중지 기능 검증

담당: Flutter/DB + 매장 운영. 현재 변경을 재사용한다.

- `.design/2026-09-cashier-delivery-open-close/`의 작업본과 migration 적용·배포 상태를 먼저 확인한다.
- Cashier 메인의 OPEN/CLOSED를 사용하고 신규 submit은 서버에서 막는다. 이미 열린 고객 탭에서 보내는 요청도 차단해야 한다.
- 닫기 전 접수된 주문의 견적·입금 검토·채팅·조리·배송은 유지한다. 타 매장/권한 없는 단말은 상태를 변경할 수 없어야 한다.
- 현재 설계는 수동 재개이며 자동 해제 시간을 포함하지 않는다. 기간 지정 자동 재개는 추가 요구 시 별도 구현한다.

완료: 두 캐셔와 고객 링크로 OPEN→CLOSED→OPEN을 확인하고 진행 주문 보호, 오프라인·다중 단말 상태 수렴, 한국어/베트남어/영어 화면을 검증한다.

## 실행 순서와 매장 적용 판정

| 단계 | 작업 | 다음 단계 진입 조건 |
|---|---|---|
| 1. 기준 확보 | T0, 실제 거래 연결 준비, 프린터 진단 | 보고 현상 재현 또는 미재현 조건 기록, 배송비·완료 의미 확정 |
| 2. 금액 안정화 | T1 + T2, 기존 일시중지 검증 T6 | 주문별 금액 보존, 매장 수취/현금 지출 계산 일치 |
| 3. 결제와 고객 흐름 | T3 + T4, T5 출력 연동 | 입금 없는 승인 차단, Reload 없는 재주문, 출력 복구 |
| 4. 통합 검증 | 아래 운영 시나리오 및 기존 회귀 검사 | 실패·경합·재시도에서도 돈과 주문이 보존됨 |
| 5. 제한 파일럿 | 테스트 환경 통과 후 승인된 한 매장·계좌·단말에서 실입금/출력 확인 | 실제 증거와 담당자 확인 후 확대 |

금액 정책과 서버 계약이 합의되면 UI 수정·프린터 진단·은행 계정 준비는 독립 진행할 수 있다. 은행 가입·실계좌 연결·기기 준비는 외부 의존성이므로 현재 정보만으로 확정 완료일을 약속하지 않는다. T0 결과로 개발 공수와 운영 준비 일정을 분리 산정한다.

필수 통합 시나리오:

1. **정상 경로**: 고객 주문 → 확정 금액 안내 → 실제 입금 수신·주문 매칭 → 캐셔 승인 → 주방 처리 → Bill → 배달 완료 → 자동 메뉴 전환 → 두 번째 주문.
2. **데이터 보호**: A/B 다른 배송비, 동일 금액 두 결제, 견적 재발행, 두 캐셔 교차 작업. 과거 견적·결제·Bill·일마감은 변경되지 않는다.
3. **실패 복구**: 입금증만 업로드, 위조/중복 webhook, 누락 입금 알림, 네트워크 끊김, 인쇄 실패, POS 재시작. 미확인 결제·중복 결제·주문 소실이 없다.
4. **운영 정책**: 고객 직접 지급/매장 대납의 합계·지급 수단·일마감, CLOSED 전후 신규/진행 주문, 영업 마감 경계의 지연 입금을 확인한다.

기술 검증은 기존 직접 주문 Flutter/Edge/SQL 테스트를 확장해 실제 동작·상태 전이·DB 불변성을 검증한다. 문자열 존재 테스트만으로 완료 처리하지 않는다. `flutter analyze`, 관련 Flutter/SQL/Edge 테스트와 `bash scripts/check_repo.sh`를 실행한다. 기존 작업 문서에 기록된 frozen-hash 실패는 이번에 재실행한 결과가 아니므로, 실제 실행 시 현재 원인과 범위를 다시 확인하고 기대값만 바꿔 통과시키지 않는다.

릴리스는 사용자 변경을 보존한 검증 가능한 변경 묶음으로 만들고, **정확히 push된 head SHA의 필수 GitHub Actions 성공** 후 `scripts/deploy_pos_production.sh`를 따른다. source·migration·Edge/Web/native 배포·운영 검증을 각각 기록한다. 은행 실거래 테스트는 선택 공급자의 테스트 환경 및 기존 runtime gate를 먼저 충족한 뒤 별도 운영 절차로 수행한다.

운영 중 재발 시 신규 직접 주문 접수를 닫고 기존 주문·입금·출력 기록을 보존한다. 미입금 승인, 잘못된 주문 매칭, 과거 금액 변경, 필수 Bill 출력 실패, Reload 없는 재주문 실패 중 하나라도 남으면 일반 운영 확대를 보류한다. 금액·결제 변경을 되돌릴 때도 확정 거래 원장은 삭제하지 않는다.
