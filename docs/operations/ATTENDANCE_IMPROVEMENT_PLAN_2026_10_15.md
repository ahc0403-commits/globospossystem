# 근태 기능 개선 계획 재수립 — 2026-10-15

상태: 코드 수정 및 DB·웹 배포 완료(2026-10-15). DB 복구 검증 10:05, 웹 배포 검증 10:34 베트남 시간. [실행·검증 기록](ATTENDANCE_RECOVERY_IMPLEMENTATION_2026_10_15.md)을 참조한다. 포토 6개 매장별 복구 후 신규 업무 입력은 아직 미관측이다.
이 문서는 앞선 권한 확대 제안을 대체한다.

## 목표와 범위

기존 근태 권한을 가진 포토 매장 운영 계정과 분식클럽 캐셔 등에서 사진 촬영·업로드·출퇴근 저장을 정상화한다. 실패했을 때는 실패 단계를 알리고 안전하게 다시 시도할 수 있도록 개선한다.

키친(`bt_kit`), 트레이(`bt_tray`), 층별(`bt_1f`, `bt_2f`)에는 원래 근태 권한이 없다. 이 상태는 정상 계약이다. 역할 허용 목록, 계정 역할, 화면 진입·내비게이션 권한을 확대하지 않는다. 기존 관리자 역할과 매장별 접근 경계도 그대로 유지한다.

급여 계산·근무시간 계산·직원 등록·발주 승인 업무·결제 기능은 개선 범위에 추가하지 않는다. 근태 장애의 직접 원인인 공용 Storage 정책의 잘못된 함수 참조만 필요한 범위에서 수정한다.

## 확인된 근거

- 운영 근태 사진 업로드에서 HTTP 400 / `AccessDenied`와 `permission denied for function procurement_pre_inbox_can_create_order`가 확인됐다.
- `20261014080000_procurement_approval_inbox` 적용 기록은 기존 발주 판정 함수의 이름 변경과 `authenticated` 실행 권한 회수를 포함한다.
- 공용 `storage.objects`의 `inventory_receipt_statement_objects_write` 정책이 이름 변경된 기존 함수 객체를 계속 참조한다. 새 `can_create_inventory_purchase_order(uuid)` 래퍼는 실행 가능하다.
- INSERT를 실행하지 않는 운영 `EXPLAIN` 검사에서도 동일 오류가 재현됐다.
- 클라이언트는 사진 업로드가 성공해야 근태 저장 RPC를 호출한다. `StorageException`은 현재 오류 분류에서 일반 저장 실패로 처리될 수 있다.
- 저장 실패 시 화면이 입력 대기 상태로 돌아가므로 재촬영을 요구하는 흐름이 된다.
- 운영 DB의 역할 허용 목록에는 `kitchen`, `emergency_station`이 없다. 사용자 정정에 따라 그대로 보존한다.

조사 시점 근거는 [장애 조사 보고서](ATTENDANCE_INCIDENT_2026_10_15.md)에 있으며, 구현 시작 시 운영 정의와 최신 배포 소스를 다시 대조한다.

## 1단계: 공통 사진 저장 장애 우선 복구

변경 대상은 새 단일 마이그레이션과 동명 preflight/verify 검사다.

1. 기존 변경이 많은 현재 작업 폴더를 보존하고 최신 운영 릴리스와 연결되는 깨끗한 작업 공간에서 진행한다. 오래된 로컬 소스만 기준으로 배포하지 않는다.
2. 현재 운영 정책과 함수 서명·실행 권한·객체 의존성을 먼저 확인한다. 조사 이후 정의가 바뀌었으면 변경 차이를 재평가한다.
3. `inventory_receipt_statement_objects_write`를 원자적으로 재생성해 현재 공개 래퍼 `can_create_inventory_purchase_order(uuid)`를 참조하게 한다. 기존 버킷 조건, 매장 조건, `can_verify_inventory_receipt` 조건과 정책 적용 역할을 보존한다.
4. 이름 변경된 내부 함수의 직접 실행 권한은 복구하지 않는다. 새 발주 승인 조건을 우회하는 경로를 만들지 않는다.
5. 정책의 의존성이 새 래퍼로 연결됐고 모든 직접 참조 함수에 필요한 실행 권한이 있는지 검증한다.

완료 기준:

- 허용된 계정의 자기 매장 근태 사진 업로드와 근태 저장이 성공한다.
- 일반 허용 계정의 다른 매장 업로드와 비로그인 업로드는 계속 거부된다.
- 사진 필수 조건, 중복 출퇴근 차단, 기존 근태 역할 허용 목록이 유지된다.
- 발주 증빙 파일 정책의 정상 허용·거부 조건도 유지된다.

이 단계는 공용 저장소 정책의 연결을 바로잡는 DB 복구다. 앱 개선 완료를 기다리지 않고 독립적인 DB-only 릴리스로 먼저 배포할 수 있다. 프로젝트 공식 배포 스크립트와 해당 모드의 필수 검증은 그대로 적용한다.

## 2단계: 근태 오류 안내와 재시도 개선

대상 파일:

- `lib/core/services/attendance_service.dart`
- `lib/features/attendance/attendance_kiosk_provider.dart`
- `lib/features/attendance/attendance_kiosk_screen.dart`
- 필요한 근태 문구에 한해 `lib/l10n/app_ko.arb`, `app_vi.arb`, `app_en.arb`

구현 항목:

1. 사진 처리·업로드·서명 URL 생성과 근태 RPC 저장의 실패를 단계별로 구분한다. Storage 오류를 단순 직원번호 오류나 일반 저장 실패로 숨기지 않는다.
2. 사용자에게는 사진 저장 실패, 네트워크 연결 문제, 근태 기록 저장 실패에 맞는 짧은 안내를 제공한다. 내부 함수 이름·SQL·토큰·사진 URL을 화면에 노출하지 않는다. 기존 직원번호·중복 출퇴근·접근 거부 안내는 보존한다.
3. 제출 중 추가 제출을 차단한다. 실패하면 직원번호와 촬영 사진을 유지해 명시적으로 다시 시도하거나 다시 촬영할 수 있게 한다.
4. 업로드 및 URL 생성이 완료된 사진은 같은 제출의 재시도에서 재사용한다. 매장·직원번호·출퇴근 구분이 달라지거나 화면을 초기화하면 재사용 상태를 비운다.
5. 사진 저장 실패 시 근태 RPC를 호출하지 않는다. 사진 없이 저장하는 우회 경로는 만들지 않는다.
6. RPC 응답 유실 등 저장 여부가 불명확한 경우 자동으로 재전송하지 않는다. 저장 상태 확인 또는 기존 중복 방지 응답을 통해 결과를 확인한 뒤 재시도하도록 처리한다. 무제한 재시도·반복 업로드는 추가하지 않는다.

범위 제한: 역할·라우팅·내비게이션 권한 코드와 발주 업무 로직은 이 단계에서 수정하지 않는다.

## 3단계: 회귀 검증

실제 영향을 검증하는 SQL/서비스/화면 테스트를 추가하거나 보강한다.

| 검증 대상 | 기대 결과 |
| --- | --- |
| 포토 운영·캐셔 등 기존 허용 역할 | 자기 매장 사진 포함 출퇴근 저장 성공 |
| 키친·트레이·층별 계정 | 기존 근태 RPC 거부 유지, 화면 권한 계약 변경 없음 |
| 타 매장·비로그인 요청 | 기존 범위 밖 요청 거부 |
| Storage 권한·네트워크·URL 생성 실패 | 실패 단계에 맞는 안내, 사진 없는 저장 없음 |
| 사진 업로드 완료 후 RPC 실패 | 사진·입력 유지, 재시도 시 완료된 사진 재사용 |
| 중복 클릭·동시 요청·응답 유실 | 중복 저장 또는 성공 오표시 방지 |
| 기존 출퇴근 규칙 | 출근 전 퇴근 거부, 연속 같은 유형 거부, 분할 근무·익일 퇴근 보존 |
| 공용 Storage 정책 | 새 래퍼 의존성과 함수 권한 확인, 발주 증빙 정책 회귀 없음 |

SQL 기능 테스트는 테스트 환경 또는 롤백 가능한 격리 fixture에서 실행한다. 운영 실제 직원의 출퇴근 기록을 테스트 목적으로 만들지 않는다. 운영 계획 검사와 실제 업로드·저장 성공 검증을 별도 증거로 기록한다.

데이터 접근·성능 기준:

- 정상 제출은 기존처럼 사진 1회 업로드, 서명 URL 생성 1회, 근태 저장 RPC 1회가 기준이다. 직원 목록 전체 재조회나 직원별 추가 쿼리를 도입하지 않는다.
- 제출 상태 확인이 필요한 경우에만 해당 매장·직원의 최신 근태를 제한 조회한다. 폴링 또는 전체 근태 재조회로 대체하지 않는다.
- 테스트에서 정상·재시도 경로의 실제 요청 수와 단계별 지연을 측정한다. 완료된 사진 재사용 시 업로드 요청이 추가되지 않는지 확인한다.

## 4단계: 배포와 운영 확인

1. 1단계 DB 복구를 우선한다. `scripts/deploy_pos_production.sh --db-only`와 규정된 단일 마이그레이션·preflight·verify 검사를 사용한다.
2. 수정 커밋을 최신 main에 반영하고 깨끗한 작업 공간, freshly fetched `origin/main`과 일치하는 HEAD, 정확히 해당 SHA의 필수 GitHub Actions 성공을 확인한다. 게이트를 우회하지 않는다.
3. 2단계 앱 개선은 관련 테스트·정적 분석·빌드·화면 검증 후 같은 공식 배포 경로로 후속 배포한다. `dart analyze --fatal-infos`와 변경에 필요한 Flutter/SQL 테스트를 실행한다.
4. 운영에서는 기존 허용 계정의 실제 정상 업무 입력을 기준으로 사진 업로드 성공·근태 저장 성공·조회 반영을 확인하고 신규 권한 오류가 없는지 확인한다. 7개 매장 모두 로그와 저장 상태를 점검하되, 실제 입력이 발생하지 않은 매장은 미검증으로 표시한다.
5. 이전 조사 보고서의 0건·오류 수는 조사 당시 수치다. 배포 전후 시각과 관측 구간을 기록해 새 결과와 구분한다.
6. 장애 기간의 누락 근태는 실제 출퇴근 시각을 확인한 뒤 기존 관리자 수동 절차로 처리할 별도 운영 항목으로 남긴다. 실패 업로드 시각으로 근태를 자동 생성하지 않는다.

복구 완료 판단은 운영 사진 저장과 근태 저장의 성공 증거에 근거한다. 로컬 테스트 통과, 배포 성공, 운영 입력 성공을 각각 구분해 보고한다.
