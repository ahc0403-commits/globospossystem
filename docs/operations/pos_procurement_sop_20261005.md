# POS·Office 구매 운영 SOP — 2026-10-05

이 문서는 구현된 소스의 운영 절차다. 생산 DB migration·배포·매장 정책 활성화는 수행하지 않았다. 실제 역할·매장 ID·회계 기준을 확정하고 릴리스 검증 후 적용한다. [구현 결과와 제한](/Users/andreahn/globos_pos_system/docs/implementation/pos_procurement_process_implementation_20261005.md)을 함께 확인한다.

빈탄점은 공용 역할 ID를 사용하고 부재 대리자는 두지 않는다. 최초 PR `bt_pr1`, SM `bunsik_sm1`, BM `bunsik_bm1`, Office 구매 `bunsik_purchase1`, 입고 검증 `bt_verify1`로 계정 단계를 분리한다. 기존 `bt_order`와 법인 `account`는 유지한다. 신규 세 ID는 아직 생성하지 않았다. 감사 기록은 계정 기준이며 서로 다른 공용 ID를 쓰는 개인의 동일 여부를 보장하지 않는다. 직원 대납·상환에는 실제 지급 대상 직원을 연결한다.

## 1. 매장 요청자·주방

구매요청·발주 화면에서 PR을 생성한다. 원재료/도구/문구/기타와 일반/Shopee 채널, 희망 입고일, 사유를 선택한다. 품목 규격·요청 단위·환산·현재고·예상 공급가격을 확인하고 수량을 입력한다. 가격이 없으면 견적을 요청한다. 예상가격을 실제 확정가격으로 해석하지 않는다. 필요한 품목이 보이지 않으면 품목 검색 또는 다음 품목 페이지를 사용한다.

작성 후 제출한다. 작성일은 유지되고 제출일이 별도로 기록된다. 반려 사유를 확인해 수정·재제출한다. PR PDF는 내부 요청·승인 자료로 사용한다. 공급업체에는 구매팀이 생성한 업체용 PO를 전달한다.

납품 시 확정 PO·남은 수량과 비교해 실제 수령량·합격량·거절량을 기록한다. 규격·품질·포장·유통기한·온도 등 해당 검수 항목과 입고증·사진을 남긴다. 10개 중 6개, 이후 4개가 오면 입고 회차를 각각 제출한다. 이미 확정된 입고를 직접 수정하지 않는다. 네트워크 실패 시 저장된 명령을 재시도하며 같은 건을 새로 만들지 않는다.

## 2. Store Manager — Adjust

요청 사유·수량·재고를 확인한다. 조정할 때 변경 수량과 사유를 남긴 뒤 매장 승인한다. 문제가 있으면 사유를 적어 반려한다. 새 정책 PR은 매장 승인 후 브랜드 검토로 넘어간다. 빈탄점은 별도 대리 계정을 두지 않고 해당 역할의 공용 ID를 사용한다. 관리자 권한으로 승인 단계를 생략하지 않는다.

## 3. Brand Manager — Agree

브랜드 범위의 요청과 매장 조정·예상 조건을 검토하고 동의 또는 반려한다. 매장 승인과 동일한 principal은 브랜드 승인을 할 수 없다. 견적 선정 후 가격·VAT·수량 조건이 달라져 다시 브랜드 검토로 돌아오면 새 조건을 재검토한다. 과거 정책 건에 없던 브랜드 승인 기록을 만들어 넣지 않는다.

## 4. 구매팀 — Approval·PO·업체 확인

유효기간·납기·결제 조건·단위·수량·단가·VAT와 견적 증빙을 등록하고 공급업체를 선정한다. 구매 승인과 필요 시 상위 승인을 진행한다. 승인된 PR 수량을 업체별로 배분해 PO를 발행한다. 중복 할당이나 승인 후 조건 변경은 서버에서 거부된다.

업체용 PO PDF를 생성한다. 이 문서는 규격·수량·단위·납품 정보·비고만 전달하며 가격·VAT·총액·은행정보를 포함하지 않는다. 내부 가격 포함 PO는 별도 출력한다. 발송 증빙을 남긴 뒤 업체의 조건 확인·납품일 회신을 등록한다. 현재 revision의 업체용 PDF가 없으면 발송 상태로 진행할 수 없다. 출력 언어가 달라도 파일이 별도 보존된다.

조건 변경은 기존 문서를 편집하지 않고 취소/변경 PR과 연결한다. 추가 납품·교환 이슈를 종결할 때 PO/입고증 번호로 후속 확정 입고를 검색·선택하고 처리 사유·증빙을 남긴다. 입고 예정이나 업체 메시지만으로 완료 처리하지 않는다. Credit은 Office에서 해당 PO의 기존 Invoice와 연결된 게시 완료 공급업체 조정 분개번호를 확인한다.

## 5. 입고 검증자·회계

수령자가 제출한 입고량·검수·실제 증빙을 확인해 확정한다. 재고 품목의 합격량만 한 번 반영된다. 비재고/자산은 수령 증거만 남기며 원재료 재고를 만들지 않는다. 반품은 실제 반품 증빙과 원래 입고 라인을 연결한다.

Office Invoice 대조 화면에서 POS 원본을 갱신하고 내부 PO 가격·VAT·순합격량과 Invoice 라인을 대조한다. 원본 없음/동기화 실패/가격·수량 차이/중복 청구/반품 후 변경은 보류한다. 게시·AP·지급의 기존 회계 승인과 실행 절차를 따른다. POS에 표시되는 Invoice/채무/보류/지급 건수는 조회용이다. 오래되었거나 원본 버전이 달라진 상태는 Office에서 갱신·재대조한다.

비재고 Invoice 라인은 실제 활성 비용계정을 선택한다. 자산은 먼저 기존 고정자산/CCDC 화면에서 실제 등록·원가·취득 clearing credit 계정·책임자·위치를 설정한다. Invoice 대조에서 해당 등록과 같은 clearing 계정을 선택한다. 일치하지 않거나 이미 자본화한 등록은 사용할 수 없다. 혼합 PO도 라인별로 비용/clearing을 구분한다. 계정/자산이 200개 검색 결과에 없으면 검색어로 다시 조회한다.

Invoice의 기존 검토·승인·AP 생성·게시를 진행한다. 이때 자산 취득원가는 clearing에 인식된다. 이후 기존 자산/CCDC의 독립된 승인·활성화에서 실제 자산 또는 선급 계정에 자본화한다. Invoice 인식과 자산 자본화를 같은 계정에 두 번 기록하지 않는다. Invoice 진행 중 연결된 등록의 원가·매장·취득 credit 계정을 바꾸지 않는다. 원가가 다르면 등록과 증빙을 정정한 뒤 다시 대조한다.

## 6. Shopee 선결제·환불·직원 대납

승인된 Shopee PO에서 플랫폼 주문번호·금액·결제 참조·증빙을 등록한다. 회사 선결제와 직원 대납을 구분하고 직원은 실제 Office HR 검색 결과에서 선택한다. 직원 Auth 계정 ID를 HR 직원 ID 대신 입력하지 않는다. 환불·보전은 원 선결제 기록을 선택해 주체와 직원을 이어받는다. 다른 직원의 기록이나 남은 금액을 넘긴 정산은 서버가 거부한다. 취소된 PO도 실제 환불을 기록할 수 있다.

이 기록은 실제 출금을 실행하지 않는다. 회계 담당자는 기존 은행·현금/선급금·총계정원장 메뉴에서 증빙과 독립 승인·실행·게시를 먼저 완료한다. 회사 선결제는 실제 현금 대변/선급자산 차변으로, 환불은 실제 현금 차변/해당 선급자산 대변으로 처리한다. 실제 회사 계정과 처리 기준을 사용한다.

Invoice 전 회사 선결제 또는 취소 환불은 구매 화면의 원장 연결에서 실제 게시 전표를 검색·선택한다. 환불은 원 자금 전표도 선택한다. 금액과 PO의 결제 참조/Document Vault 증빙이 일치해야 한다. 새 AP·비용·재고를 만들기 위한 기능이 아니다. 자금이 이미 Invoice 충당에 사용되었다면 기존 충당을 정정하는 회계 절차를 먼저 따른다.

선결제 AP는 Office에서 보류된다. 업체에 같은 금액을 다시 지급하지 않는다. Invoice 게시 후 대조 화면의 선결제/직원 정산 연결에서 실제 게시된 충당 전표를 선택한다. 회사는 AP 차변/동일 선급자산 대변 및 실제 원 출금 전표를 연결한다. 전표는 원 Invoice의 조정 관계 또는 실제 선급 정산의 Invoice 영수증 관계를 가져야 한다.

직원은 AP 차변/해당 직원 채무 대변으로 전환한 실제 게시 전표를 연결한다. 보전할 때 기존 지급 기능에서 같은 직원 채무 차변/현금 대변으로 지급하고 게시한 뒤 원 대납의 보전 증빙에 연결한다. 직원 보전을 공급업체 AP 지급으로 다시 입력하지 않는다. 회사로 수취한 환불과 직원에게 직접 반환된 환불을 구분하고 실제 수취 방향에 맞는 원장을 사용한다.

서버가 게시·증빙·직원·계정·매장·금액·잔액·원 Invoice를 검증한다. 충당/자금 전표 역분개 후 AP 잔액을 다시 확인한다. 보류 해제는 기존 회계 통제로 진행하고 단순 증빙 숫자나 사유 삭제로 처리하지 않는다. 통신 결과가 불명확하면 같은 전표·금액으로 재확인하며 다른 금액으로 다시 등록하지 않는다.

## 7. 관리·중단·시범 운영

관리자는 실제 매장 ID, 공급업체, 품목 처리 유형·단위·환산, 요청자·세 승인 역할·수령/검증·회계 및 대리자, 기존 진행 건을 확인한다. 실제 Office HR 직원과 POS/Office principal을 시스템별로 명시 연결한다. 같은 사람이 두 시스템을 사용하는 경우 두 principal에 같은 HR person ID를 등록한다. 유효기간과 부재 대리 사유를 기록한다. 담당자 roster는 기존 Auth 권한을 부여하거나 만료시키지 않으므로 기존 권한·위임 관리도 함께 확인한다. CHEONGA/JEONGABOK 이름을 임의 통합하지 않는다. 기존 정책 건은 기존 정책·해시로 계속 처리한다. 신규 3단계 정책은 시범 매장별로 명시적으로 활성화한다.

문제가 생기면 신규 PR 생성만 일시 중단한다. 진행 중 PR/PO·입고·반품·회계 처리는 계속 가능하다. 이미 반영한 재고·지급을 삭제하거나 과거 문서를 덮어쓰지 않는다. PDF 실패는 동일 revision에서 재생성하고, cross-database 동기화 실패는 저장된 같은 명령 키로 재시도한다.

시범 사례는 정상 구매, 반려 후 수정, 6+4 부분입고, 거절/반품, 가격 차이, 타 매장 권한 거부, 원본 동기화 실패, 통신 재시도다. 실제 사용자 계정과 마감 대조 결과를 남긴다. 승인 대기시간·입고 확정 지연·대조 보류·납기/품질·중복 여부를 첫 2주 동안 관찰해 책임자와 대응 시간을 확정한다. 교육·실제 시범 운영은 아직 수행하지 않았다.

## 8. 운영 지표·교육 기록

구매 작업함의 운영 지표를 열어 최근 90일 PR/PO·승인 단계별 대기·열린 승인 대기의 p95 경과시간·무가격 PO 출력·회계 보류를 확인한다. 입고 검증 대기와 미결 이슈는 현재 전체 미완료 건이다. p95는 완료된 처리시간이나 확정 SLA가 아니다. 관찰 시각과 범위를 함께 기록한다. 기존 보충 제안은 사람이 검토한 후 PR을 만들며 자동 발주로 처리하지 않는다.

관리자에게 표시되는 누락 역할을 채우고 실제 계정 권한과 대조한다. 배포 전후 [운영 전환표](/Users/andreahn/globos_pos_system/docs/operations/pos_procurement_rollout_20261005.md)와 [UAT 기록표](/Users/andreahn/globos_pos_system/docs/operations/pos_procurement_uat_20261005.csv)를 사용한다. 로컬 자동 테스트 결과를 실제 교육/UAT 결과 칸에 복사하지 않는다.
